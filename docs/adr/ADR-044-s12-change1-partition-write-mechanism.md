# ADR-044: S12 Change 1 -- механизм записи раздела для OTA

## Статус

Принято, 2026-09-12.

## Контекст

S12's Definition of Ready (`docs/os/sprints/S12-ota-release-gate.md`)
поставил Change 1 первым и единственной задачей: до любого кода про
подпись/manifest/download установить, как SaaiOS вообще может
физически записать раздел на этом устройстве. DoR's Current state
утверждал: "в SaaiOS нет ни одного пути писать раздел изнутри себя" --
на основании отсутствия `/dev/block/by-name` и `grep` по ключевым
словам `ota/OTA/A-B/bootctl/slot` без учёта конкретных имён функций.
**Это утверждение оказалось существенно неполным и исправляется этим
ADR** (см. Находка 3 и Rollback/Ссылки) -- честная самокоррекция,
предусмотренная `DEVELOPMENT_PROCESS.md`'s принципом "не предполагать,
проверять".

Инвестигация этого ADR -- целиком read-only на реальном устройстве:
ни один раздел не записан, только чтение `/sys/class/block/*/uevent`
и просмотр исходников.

## Находки

**1. Ядро уже парсит GPT и отдаёт имена разделов через sysfs.**
`/sys/block/<disk>/<partition>/uevent` содержит `PARTNAME=`/`MAJOR=`/
`MINOR=` для каждого из 55 реальных разделов на `sda`/`sdb`/`sdc`/
`sdd` (полная карта -- в Evidence). Писать собственный байтовый
GPT-парсер не нужно вообще -- нужного факта уже готовы ядром.

**2. `/dev`-узлы не создаются автоматически.** На реальном устройстве
`ls /dev/sda*` показал только `/dev/sda8` (уже созданный
`native-init.c` для `/metadata`) -- devtmpfs не авто-заполняет `/dev`
для каждого раздела; узлы создаются по требованию через `mknod`.

**3. Исправление DoR: `create_partition_node()` уже существует,
уже используется в продакшене.** `os/targets/panther/src/
native-init.c:339` -- полностью рабочая функция: сканирует `/sys/
class/block/*/uevent`, ищет `PARTNAME=<имя>`, извлекает MAJOR/MINOR,
делает `unlink()`+`mknod()` целевого device-пути. **Уже вызывается на
каждой загрузке для двух реальных разделов**: `persist` (read-only
mount для haptic-калибровки, `apply_haptic_factory_calibration`,
:411) и `devinfo` (read-write, см. Находку 4). Это прямо противоречит
DoR's формулировке "ни в одном файле репозитория нет кода, парсящего
GPT или пишущего в произвольный раздел" -- код есть, работает, уже
физически проверен всей историей проекта.

**4. `mark_current_slot_successful()` уже реально пишет в раздел на
каждой загрузке.** `native-init.c:478` -- вызывается из `:1582`, сразу
после `log_message("native userspace ready")`. Резолвит `devinfo`
(`sdd1`) через `create_partition_node()`, открывает `/dev/
saaios-devinfo` с `O_RDWR | O_DSYNC`, читает 128-байтную структуру
(`current_slot_index()` определяет slot 0/1 из `androidboot.
slot_suffix` в `/proc/bootconfig`), проверяет magic `0x49564544`
("DEVI") и версию (>=3.3), вычисляет флаговый байт по смещению `48 +
slot*4 + 1`, ставит бит `0x02`, делает `pwrite()` ровно этого одного
байта и `fsync()`. Это единственное во всём `native-init.c` место,
пишущее в реальный GPT-раздел (проверено -- `grep` на `pwrite(`/
`O_RDWR`/`O_WRONLY` во всём файле не нашёл других таких мест).
**Это самый сильный из возможных прецедентов "физически проверено
безопасным"** -- код работает без единого известного сбоя каждую
загрузку с момента появления в проекте.

**5. Реальный, ранее не замеченный тайминг-пробел (не устраняется
этим ADR, флаг для Change 5).** `mark_current_slot_successful()`
вызывается сразу после того, как USB/сеть/console/runtime всего лишь
**запущены** -- задолго до того, как здоровье UI-слота
(`saai-shell`/`saai-displayd`) хоть как-то подтверждено, и намного
раньше, чем мог бы проявиться тот класс отложенного отказа, что S11/
ADR-043 физически нашёл (OOM-кластер `saai-displayd`, исчерпание
PID1's `UI_RESTART_BUDGET` с падением в `drm-splash`-fallback). Если
этот бит в `devinfo` -- то, что реальный bootloader (ABL) читает для
собственного tries-remaining/successful A/B-учёта (правдоподобно,
учитывая точный, версионированный, уже реверс-инжинированный формат,
но не доказано в этой сессии), то сегодняшний вызов уже глушит любой
аппаратный автооткат именно для того класса отказов, который S11
нашёл. Проверяется ли этот бит бутлоадером вообще -- открытый,
физически проверяемый вопрос для Change 5, не решается здесь.

**6. Полная проверенная карта разделов (55 разделов, 4 диска)** --
см. Evidence.

**7. Загрузочно-критичные/запрещённые разделы теперь точно
поименованы.** Цепочка бутлоадера (`bl1/pbl/bl2/dram_train/abl/bl31/
tzsw/gsa/ldfw/dpm`, по `_a`/`_b` на `sdb`/`sdc`); `vbmeta*_a/b`,
`devinfo`, `pinfo`, `blenv`, `mfg_data` на `sdd`; `persist`, `frp`,
`efs`, `efs_backup`, `modem*`, `misc` на `sda` -- все существуют как
отдельные, индивидуально адресуемые разделы из той же самой карты, что
называет `init_boot_a` (`sda11`)/`vendor_boot_a` (`sda12`). Значит
allow-list по `PARTNAME` -- это реальная, проверяемая граница
безопасности, а не гипотетическая.

## Решение

Механизм записи раздела для OTA строится поверх уже существующей,
уже проверенной `create_partition_node()` -- без нового GPT/
partition-резолвера, он не нужен. Запись ограничена жёстким,
захардкоженным allow-list имён разделов -- сегодня ровно `{init_boot_a,
vendor_boot_a}`, совпадает с уже принятым в S12's DoR скоупом Change 4
(единственный доступный SaaiOS-слот A). Любое другое имя раздела --
включая всю цепочку бутлоадера, `vbmeta*`, `devinfo`, `persist`, `frp`,
`efs*`, `modem*`, `misc`, `dtbo*`, `pvmfw*` -- жёстко отклоняется на
уровне allow-list, независимо от того, что указывает manifest.

Отклонённая альтернатива: исключительно fastboot-driven обновления
(вариант "б" из DoR) -- отклонён, потому что требовал бы хоста/
companion-машины для каждого реального обновления, а предполагаемо
"новый, рискованный" нативный путь оказался уже работающим,
проверенным кодом, а не новой поверхностью риска.

## Последствия

- **DoR исправлен тем же коммитом, что этот ADR**: `docs/os/sprints/
  S12-ota-release-gate.md`'s Current state переформулирован --
  `create_partition_node()`/`mark_current_slot_successful()`
  задокументированы как уже существующий прецедент, не как пробел.
- Change 4 (запись обновления) теперь конкретен: переиспользовать
  `create_partition_node()` для `init_boot_a`/`vendor_boot_a`, писать
  staged+проверенные байты, `fsync`, перечитать и сверить хеш -- новый
  механизм резолва не нужен.
- Change 5 (health confirmation) наследует реальный, физически
  предсуществующий открытый вопрос: не глушит ли текущий тайминг
  `mark_current_slot_successful()` аппаратный автооткат уже сегодня?
  Требует отдельной физической проверки перед финализацией Change 5 --
  флагируется, не решается здесь.
- Allow-list -- единственный контроль безопасности всего write-пути
  этого спринта; добавление любого нового целевого раздела требует
  осознанного, review-пройденного изменения кода, никогда не
  выводится из manifest во время выполнения.

  `vendor_kernel_boot_b`(23) `dtbo_b`(24) `vbmeta_b`(25)
  `vbmeta_system_b`(26) `vbmeta_vendor_b`(27) `pvmfw_b`(28)
  `modem_b`(29) `super`(30) `userdata`(31).
- `sdb` (бутлоадер, slot A): `bl1_a`(1) `pbl_a`(2) `bl2_a`(3)
  `dram_train_a`(4) `abl_a`(5) `bl31_a`(6) `tzsw_a`(7) `gsa_a`(8)

на реальном запущенном устройстве, не из документации/предположений.
