# ADR-029: Intent-текст вводится через bespoke touch-hit-test клавиатуру в saai-shell, не через generic Wayland text-input

## Статус

Принято, 2026-09-11.

## Контекст

S09's Definition of Ready назвала физически нерешённый вопрос: как
вообще вводится текст на этом устройстве. `saai-shell` не имеет ни
одного экрана ввода текста (`KeyboardInteractivity::None`,
"touchscreen-only" по собственному комментарию `main.rs`). Общий
Wayland `input-method-v2`/OSK-путь для сторонних клиентов уже физически
доказан нерабочим на этом железе (ADR-022 -- `libxkbcommon` крашится
при попытке скомпилировать любой keymap, 7 независимых вариантов).
Change 1 требовал физического, не теоретического ответа до любого
другого кода S09.

## Находка

`saai-shell` уже рисует собственный UI напрямую в `wl_shm`-буфер через
`fontdue` (чистый Rust-растеризатор шрифтов, без FreeType/fontconfig) и
уже имеет готовую декларативную layout/hit-test систему
(`saai-ui-core`'s `Node`/`layout()`/`hit_test()` -- та же система, что
уже рисует и хит-тестит tab-бар и consent-экран). Это первое лицо
(compositor's собственный клиент), не сторонний Wayland-клиент через
generic-протокол -- вообще не обязано проходить через
`zwp_input_method_manager_v2`/`libxkbcommon` для получения текста,
поскольку сама решает, что каждое нажатие означает.

Throwaway-спайк (temporary patch к `saai-shell`, НЕ закоммичен,
`git checkout` отменил после теста): добавлена минимальная клавиатура
из 6 клавиш (`H`, `I`, `!`, `DEL`, `CLR`, `OK`) той же системой
`Node::leaf(...).with_action(...)` + `layout()` + `hit_test()`, что уже
используют `tab_at()`/`consent_action_at()` -- ни единого обращения к
`libxkbcommon`, `zwp_text_input_manager_v3` или
`zwp_input_method_manager_v2`. Активна с запуска (без триггера, для
throwaway-теста), обрабатывается в `TouchHandler::down()`/`up()` до
существующей lock/tab-логики.

Физически на устройстве: throwaway `panther-hardware saai-displayd`
(чистый, хэш совпадает с боевым `541a5eeb...`) в изолированном
`unshare -m` namespace, модифицированный `saai-shell` bind-mount'ится
поверх `/saaios/saai-shell` только внутри этого namespace (реальный
боевой `saai-shell`, pid 613, не затронут). Синтетическая evdev-
инъекция через `uinput` (тот же метод, что ADR-028) отправила
последовательность из 4 тапов по реальным экранным координатам
клавиш. Итоговый лог (`saai-shell`'s собственный `println!`, тот же
процесс, что уже используется для diagnostics по всему проекту):

```
saai-shell: keyboard-test buffer now: "H"
saai-shell: keyboard-test buffer now: "HI"
saai-shell: keyboard-test buffer now: "HI!"
saai-shell: keyboard-test RESULT: "HI!"
```

Каждый тап корректно попал в свою клавишу и собрал ожидаемую строку
`"HI!"`, подтверждённую нажатием `OK`. Session lock (активная с
запуска, как обычно) не помешала -- touch маршрутизируется displayd на
`lock_surface`, пока `locked=true`, но клиентский код проверяет
`keyboard_test_active` независимо от того, на какую именно свою
поверхность пришло событие, так что это не помешало тесту (сама lock/
unlock-логика для этого спайка была сознательно обойдена, не
проверялась заново -- она уже физически доказана в S04/ADR-015).

Диагностический патч отменён (`git checkout --`), пересобран и
физически сверен: хэш реверченного `saai-shell` (`34653527...`)
байт-в-байт совпадает с хэшем боевого работающего процесса (pid 613).

## Решение

Ввод текста для Intent в S09 реализуется как bespoke touch-hit-test
экранная клавиатура внутри `saai-shell`, той же системой
`Node`/`layout`/`hit_test`, что уже рисует весь остальной UI --
никакого нового Wayland-протокола, никакого `libxkbcommon`, никакого
`zwp_input_method_manager_v2`. Голосовой ввод (Кандидат B из S09's
Definition of Ready) не рассматривается дальше -- физический путь A
уже доказан рабочим при на порядок меньших трудозатратах.

Реальная раскладка (полный алфавит, не 6 клавиш спайка) -- отдельная,
не архитектурная, задача дизайна/вёрстки для основной части Change 1
или Change 2, не требует нового ADR.

## Последствия

- S09's Change 1 наполовину закрыт -- остаётся решить (тем же Change
  1, отдельно) вопрос Intent/Task/Action's модели данных
  (native entity store vs Platform Track).
- Полная раскладка потребует больше 6 клавиш и, вероятно, отдельного
  полноэкранного режима -- переиспользует `Frame`-паттерн
  (`Frame::Consent`/`Frame::Root`/новый `Frame::IntentInput`), уже
  установленный этим спайком как рабочий шаблон.
- Throwaway-патч не закоммичен -- метод воспроизводим по коду в этом
  ADR, не требует постоянного присутствия в репозитории.
