# ADR-006: Системный интеллект, а не встроенный чат

## Статус

Принято, 2026-09-05.

## Контекст

Первый экран помощника позволил отправить текст локальной модели и вызвать
несколько диагностических tools. Физический тест показал архитектурный дефект:
модель могла ответить, что SaaiOS не установлена на телефоне, хотя запрос
создан внутри работающей SaaiOS. Runtime не передавал удостоверенную
идентичность устройства, а UI представлял ИИ как отдельный чат.

Языковая модель не может быть источником истины о системе. Она может
интерпретировать наблюдения и предлагать план, но идентичность, возможности,
состояние, разрешения и результат действия должны приходить от локальных
сервисов SaaiOS.

## Решение

Системный интеллект является постоянным слоем ОС, а не приложением Assistant.
Любой вход — касание, намерение, событие батареи, аппаратная ошибка или текст —
проходит один и тот же цикл:

```text
Observe -> Interpret -> Plan -> Authorize -> Act -> Verify -> Record
```

- **Observe:** локальные адаптеры создают датированные наблюдения с источником;
- **Interpret:** правила и модель объясняют состояние, не меняя его;
- **Plan:** создаётся явный список ограниченных `Action`;
- **Authorize:** policy engine принимает `Allow / Deny / AskUser`;
- **Act:** только зарегистрированный tool или device adapter выполняет шаг;
- **Verify:** новое наблюдение подтверждает или опровергает результат;
- **Record:** событие и причинная цепочка сохраняются в audit/event store.

Runtime всегда получает локальный `DeviceContext` до обращения к модели. В нём
есть только ограниченные не-секретные факты с происхождением: продукт,
deployment, класс устройства, target, hardware model, архитектура, kernel и
boot slot. Доступный набор tools передаётся отдельно и является фактическим
набором действий. Отсутствующее значение остаётся `unknown`; модель не должна
его угадывать.

Первый вертикальный срез:

- Pixel PID 1 объявляет `native_device / phone / panther` в окружении runtime;
- `system-tools` наблюдает kernel/device-tree/boot slot и предоставляет
  read-only `system.identity`;
- `ai-runtime` добавляет локальный контекст в каждый системный prompt;
- runtime status возвращает тот же снимок для UI и диагностики;
- экран называется `DEVICE`, принимает `SET AN INTENT`, показывает
  `DEVICE ACTIONS` и `SYSTEM RESULT`.

Это ещё не полная автономность. Пока нет отдельного `saai-deviced`, каталога
всех capability, универсальной проверки результата и workflow state machine,
система честно показывает только реализованные tools.

## Инварианты

- модель не создаёт факты о железе или выполненном действии;
- пользовательский текст, tool output и memory не могут изменить системную
  идентичность;
- действие не исполняется напрямую из текста модели;
- опасное действие проходит policy до исполнения;
- успех действия подтверждается новым наблюдением, а не формулировкой модели;
- manual control остаётся доступным без модели;
- удалённому provider передаётся минимальный контекст без hostname, серийных
  номеров, адресов, credentials и пользовательского содержимого устройства.

## Последствия

- SaaiOS отвечает от лица работающей системы только на основании локальных
  фактов;
- UI может показывать состояние и действия без диалоговой метафоры;
- один и тот же контур подходит ручным командам, автоматизации и ИИ;
- потребуется отдельный device-state service, schema наблюдений и механизмы
  freshness/verification;
- текущий чат остаётся возможным способом ввода, но не архитектурным центром.

## Отклонённые альтернативы

### Усилить только system prompt

Текст снижает вероятность неправильного ответа, но без локального источника
фактов остаётся внушением. Prompt используется только вместе с наблюдаемым
`DeviceContext` и tools.

### Сделать ИИ привилегированным PID 1

Это смешало бы вероятностное планирование с полномочиями ядра системы и
сделало бы ошибку модели системной ошибкой. PID 1 и policy остаются
детерминированными.
