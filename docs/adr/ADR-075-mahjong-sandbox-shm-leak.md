# ADR-075: почему Маджонг падал под песочницей (S28) -- утечка shm-буферов в 16МБ `/tmp`

## Статус

Принято, 2026-09-14.

## Контекст

S28 в бэклоге: `org.saaios.mahjong` (ADR-072) при обычном запуске
через "Сейчас" (реальный путь `saai-appd` -> `sandbox::apply()`,
ADR-020) открывался нормально, доска отрисовывалась -- но падал
сразу же на первом тапе по плитке. Тот же самый бинарь, запущенный
вручную с серийной консоли с полным окружением (`XDG_RUNTIME_DIR`,
`WAYLAND_DISPLAY`, `SAAIOS_APP_ID` заданы вручную, БЕЗ `unshare`/
`seccomp`), работал безупречно -- тапы по плиткам матчились, игра
доигрывалась до конца.

`saai-appd` глушит stdout/stderr любого запущенного приложения
полностью (`services/saai-appd/src/supervisor.rs`, `Stdio::null()`
на обоих) -- значит, любая причина падения sandboxed-процесса
изначально невидима никак, кроме как через сам факт "процесс исчез".
Расследование по порядку исключило:

- отсутствие `/tmp` внутри песочницы -- он есть, доступен на запись,
  просто `noexec` (`mask_tmpfs(Path::new("/tmp"), "mode=1777,
  size=16m", true)`, `sandbox.rs:133`) -- `noexec` не должен мешать
  `tempfile`/`mmap` без `PROT_EXEC`;
- seccomp-денylist -- он именно денylist (`SeccompAction::Allow` по
  умолчанию, `EPERM` только на явно перечисленные вызовы:
  `ptrace`, `kill`, `mount`, `bpf` и т.п.), и на `aarch64`
  (реальная архитектура Pixel 7) `ARCH_DENIED_SYSCALLS` вообще
  пустой список -- ничего из пути `tempfile::tempfile()`/`mmap`/
  `openat` там не значится.

## Диагностика

Раз оба обычных канала (stdout приложения, лог `saai-appd`) молчат,
пришлось добавить временную диагностику и катить её на устройство
через `file-recv`/SSH (ADR-073/074) без единой пересборки образа --
именно то, для чего эти каналы и строились:

1. Временный `std::panic::set_hook` в самом `saai-mahjong`,
   пишущий панику в `$SAAIOS_DATA_DIR/crash.log` (единственный путь,
   куда приложению точно можно писать что в песочнице, что вне её).
   Результат: файл так и не появился ни разу -- значит, это не
   Rust-паника вообще.
2. Временное логирование в `saai-appd` самом: `ExitStatusExt::
   signal()` вместо `ExitStatus::code()` (который для убитого
   сигналом процесса всегда `None`) при каждом `AppEventKind::
   Crashed`, дописывается в `/data/saaios/var/appd-crashes.log`.
   Результат, воспроизведено вживую: `signal=Some(11)` -- настоящий
   SIGSEGV, четыре раза подряд (столько раз `SupervisorPolicy`
   перезапускает приложение до `crash_limit`).

С сигналом на руках причина нашлась при чтении `redraw()`
(`services/saai-mahjong/src/main.rs`): при каждой перерисовке (в том
числе на каждый тап) создавался СОВЕРШЕННО НОВЫЙ `tempfile::
tempfile()` + `wl_shm_pool` + `wl_buffer`, а предыдущие никогда не
уничтожались (ни `wl_buffer::destroy`, ни `wl_shm_pool::destroy` не
вызывались). Один кадр 1080x2400 XRGB8888 -- это `1080*4*2400`
= 10 368 000 байт, то есть ~9.9МБ. Компоситор (`saai-displayd`)
держит у себя dup'нутый fd каждого созданного пула, так что
страницы tmpfs первого кадра остаются занятыми даже после того, как
сам `saai-mahjong` закрыл свой файловый дескриптор. Вне песочницы
это было незаметно -- у хостового `/tmp` нет искусственного лимита.
А `/tmp` внутри песочницы -- `size=16m` (ADR-020, для КАЖДОГО
приложения одинаково). Первый кадр (после `configure`, до всякого
тапа) укладывался -- 9.9МБ из 16МБ. Второй кадр (первый тап,
`needs_redraw = true` -> `redraw()`) должен был занять ещё ~9.9МБ
поверх уже занятых -- это уже ~19.8МБ, `write_all` при попытке
записать полный кадр в новый tmpfs-файл упирался в переполненный
лимит квоты на уровне ядра при работе с отображённой в
`wl_shm_pool` памятью -- и вместо аккуратной ошибки Rust получался
SIGSEGV на уровне доступа к странице.

`saai-demo-surface` использует буквально тот же самый паттерн
("новый tempfile на каждую перерисовку", собственный комментарий
`saai-mahjong` прямо на это ссылался как на образец) -- но ни разу
не наткнулся на баг, потому что это статичная демка, которая рисует
ровно один кадр и никогда не перерисовывается повторно. Баг был
скрыт архитектурно с самого ADR-072/S08, просто не было ни одного
приложения, которое реально перерисовывалось бы больше одного раза
под песочницей -- `saai-mahjong` стало первым.

## Решение

`redraw()` теперь держит ОДИН файл/пул/буфер в `AppState`
(`shm_file`, `shm_pool`, `buffer`, `buffer_width`/`buffer_height`) и
пересоздаёт их только при реальном изменении размера поверхности
(смена `configured_width`/`configured_height` через `xdg_toplevel`'s
`Configure`) -- на каждый обычный тап просто перезаписывает те же
самые страницы (`Seek::seek` в начало + `write_all`) и переиспользует
уже созданный `wl_buffer` без нового `create_pool`/`create_buffer`.
При реальном ресайзе старые `buffer`/`pool` явно уничтожаются
(`.destroy()`) перед созданием новых -- в любой момент времени в
16МБ `/tmp` живёт не более одного кадра.

Временная диагностика убрана после подтверждения (панический хук в
`saai-mahjong` ни разу не пригодился и был просто мёртвым кодом), а
сигнальное логирование в `saai-appd` (`log_crash_diagnostic` в
`supervisor.rs`) оставлено насовсем -- `saai-appd` по-прежнему
глушит stdout/stderr любого приложения, и это единственный
оставшийся способ узнать хотя бы сигнал следующего подобного краша,
не гадая заново.

## Test

Host: `cargo build`/`cargo clippy -p saai-mahjong --all-targets`
чисты.

Device: воспроизведено вживую до фикса (SIGSEGV, `signal=Some(11)`
в `appd-crashes.log`, 4 раза подряд до `crash_limit`), бинарь
пересобран и заменён на устройстве через `file-recv`/SSH БЕЗ
пересборки образа/`fastboot flash` (ADR-073/074 впервые
использованы по назначению для итерации, а не только для их
собственной проверки). После фикса: игра открывается, несколько
тапов подряд по разным плиткам -- стабильно, без падений.

## Последствия

- Открытый пункт, найден попутно: `sandbox::apply()` маскирует
  `/saaios` целиком для любого стороннего приложения -- а там же
  лежат системные шрифты (`/saaios/fonts/*.ttf`, тот же путь, что
  ADR-070 исправил для `saai-shell`). Подтверждено вживую: доска
  Маджонга под песочницей рисуется вообще без текста (только
  цветные прямоугольники) -- `Fonts::load()` тихо проваливается
  через `.ok()`, код это переживает, но результат выглядит
  недоделанным. Касается ЛЮБОГО стороннего Wayland-приложения, не
  только Маджонга -- ни одно из них не сможет показать текст, пока
  `/saaios/fonts` не станет читаемым внутри песочницы (по аналогии
  с точечным "пробиванием" `wayland_socket`/`portal_socket` сквозь
  маску `/run`). См. `docs/os/ideas.md` -- не исправлено этим ADR,
  отдельная задача.
- `saai-demo-surface` несёт тот же самый "новый tempfile на каждую
  перерисовку" паттерн в комментариях как образец для подражания --
  сам по себе безобиден (демка не перерисовывается), но комментарий
  в `saai-mahjong`, который на него ссылался, теперь не соответствует
  актуальному коду; никакой другой код на этот паттерн не ссылается.
