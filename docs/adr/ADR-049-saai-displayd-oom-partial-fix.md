# ADR-049: saai-displayd OOM -- найден и частично устранён реальный механизм

## Статус

Принято, 2026-09-12.

## Контекст

S11/ADR-043 нашёл реальные OOM-килы `saai-displayd` (dmesg, 4+ раза за
~11.8 минут, рост до 1-2.5 ГБ RSS) во время плотного тестирования
Change 2's suspend-циклов, но три методичные попытки воспроизвести
причину -- все чисто механические `echo mem`-циклы без реальной
UI-активности -- дали плоскую память. Расследование было остановлено
по решению с пользователем: цена дальнейших нажатий кнопки питания
перестала быть оправданной без более точного диагностического подхода.

Этот раунд возобновляет расследование по roadmap-пункту "Начни с
OOM-бага saai-displayd", с новым инструментом: синтетический touch
через `uinput` вместо ручных нажатий кнопки питания -- убирает
физическую усталость как ограничитель и позволяет воспроизводить
именно то, чего не хватало прошлым попыткам -- реальную UI-активность
(касания, переключение вкладок), а не просто suspend/resume.

## Метод

- **Синтетический touch без участия человека.** `/dev/uinput`
  (`mknod c 10 223`, зарегистрирован ядром как misc-устройство,
  просто не имел файла) + уже существующий `os/targets/panther/
  tools/uinput-touch.c` (протокол-B synthetic touchscreen, ADR-028's
  метод). `saai-displayd` читает touch с фиксированного пути
  `/dev/input/touchscreen`, не сканирует `/dev/input/event*`
  динамически -- пришлось временно перенаправить этот путь (обычно
  символическая ссылка на реальный `fts_ts`) на синтетическое
  устройство (`event4`, найдено по `PARTNAME`-подобному скану
  `/sys/class/input/*/device/name`) и перезапустить `saai-displayd`,
  чтобы он открыл новый источник. Восстановлено на реальный touch
  (`event2`) после расследования.
- **Точечное логирование вместо угадывания.** Временно (не
  закоммичено) добавлены: счётчик реальных commit'ов + чтение
  `VmRSS` из `/proc/self/status` в `saai-displayd`'s `commit()`;
  уникальный diag-тег перед КАЖДОЙ из 9 точек вызова `draw()` в
  `saai-shell` -- чтобы не гадать, какая именно ветка вызывает лишний
  рендер, а увидеть это напрямую в логе.

## Находки

**1. `hardware.rs`/`DumbMapping` -- не источник.** Прочитан исходник
крейта `drm` (0.14.1): `Drop for DumbMapping` корректно вызывает
`rustix::mm::munmap` с тем же указателем и длиной, что и `mmap` --
`.expect("Unmap failed")` означал бы падение процесса при реальном
сбое unmap, чего не происходит. Реальной утечки mmap нет.

**2. `saai-shell` не зацикливается.** Все 9 мест вызова `draw()`
помечены уникальными diag-тегами и физически прогнаны дважды под
нагрузкой реального касания-burst'а (40+ касаний за 12-20 секунд,
переключение всех 4 вкладок по кругу). **Ни один тег не сработал** в
момент, когда `saai-displayd`'s лог показывал серию из нескольких
подряд идущих commit'ов с идентичным SHA256 для одной и той же
поверхности -- то есть ни одна ветка кода `saai-shell`, вызывающая
`draw()`, не отвечает за эти повторы. Все проверенные ветки (`poll_
appd`/`poll_entityd`/`check_idle_timeout`/переключение вкладок/
`apply_appd_message`/`apply_entityd_message`) корректно сравнивают
новое состояние со старым перед вызовом `draw()`.

**3. Реальный механизм: Wayland физически доставляет несколько сырых
commit'ов подряд с одинаковым содержимым, и `saai-displayd`'s
`commit()`-хендлер делал дорогую работу (`bytes.to_vec()` ~10МБ +
SHA256 + `HashMap::insert`) безусловно на каждом из них**, даже когда
результат не отличался от уже закешированного кадра для этой
поверхности. `request_recomposite()`'s `flip_pending`-гейтинг уже
схлопывал ИЗБЫТОЧНУЮ ПЕРЕРИСОВКУ (реальный `blit`/`present` был только
один), но не избыточное кеширование, стоящее перед ним.

**4. Физически воспроизведено и измерено.** Burst из 40-85 синтетических
касаний за 12-25 секунд (темп значительно выше обычного человеческого,
но не нереалистичный при плотном тестировании -- именно такая нагрузка
была в исходном инциденте ADR-043) до фикса давал RSS 184 -> 346 -> 670
МБ и продолжал расти без предела. Побочная находка: во время сборки/
тестирования USB-соединение с устройством пропадало на несколько минут
без видимой причины -- при возврате `/proc/uptime` показал
непрерывную работу (устройство не падало и не перезагружалось), core-
сервисы не пострадали -- транспортный USB-глюк на стороне хоста, не
связан с самим расследованием.

## Решение

`SurfaceFrame` получил поле `digest: [u8; 32]` (SHA-256 уже
вычислялся на каждый commit, просто не сохранялся). Перед дорогим
`bytes.to_vec()` новый digest сравнивается с уже закешированным для
этой поверхности; при совпадении -- копирование и `HashMap::insert`
пропускаются целиком (`is_new_content()`, юнит-протестирована: первый
commit без кеша, совпадающий digest, несовпадающий digest).
`request_recomposite()`/`flip_pending`-логика не тронута -- изменение
затрагивает только кеширование, не перерисовку.

## Test

Host: `cargo test -p saai-displayd` (без `panther-hardware`) -- все
существующие тесты зелёные, без регрессий. `cargo test -p
saai-displayd --features panther-hardware --bin saai-displayd` --
5/5, включая 3 новых теста для `is_new_content()`. (Интеграционные
`tests/*.rs` не запускаются вместе с `panther-hardware`
осознанно -- эта фича заставляет `main()` пытаться открыть настоящий
DRM, которого на R620 нет; это предсуществующее ограничение сборки, не
новая проблема.) `clippy` чист на обеих комбинациях фичи. Кросс-
компиляция `aarch64-unknown-linux-musl`/`pixel7` чиста, финальный hash
`a5ab2613e41478e7bf2721ff83ba20bb08c015cad02a783f279f6aa2b5c7253e`.

Device (runtime-подмена `/saaios/saai-displayd`, `cp && mv` + `chmod`,
ADR-042's паттерн -- не переживает настоящую перезагрузку, это
верификация логики, не постоянная установка): тот же burst-тест (40
касаний, 0.3-0.5с между) после фикса -- `skipped_duplicates` рос
устойчиво (14, 19, 23...67 к концу самого агрессивного раунда из 85
касаний), RSS выходила на плато вместо непрерывного роста (82 -> 184
МБ и держалась там несколько проверок подряд под продолжающейся
нагрузкой). При достаточно долгом и агрессивном burst'е (85 касаний
за ~20с) RSS всё же доросла до 670 МБ, но **79% всех commit'ов (67 из
85) были дубликатами и успешно пропущены** -- рост дали только
оставшиеся ~18 генуинно различающихся кадров.

## Последствия

- **Честно: это существенное снижение, не полное устранение.** Фикс
  убирает затраты на все ПОВТОРНЫЕ commit'ы с неизменным содержимым
  (в этом тесте -- около 4/5 всей нагрузки), но не меняет того, что
  каждый генуинно НОВЫЙ кадр всё ещё аллоцирует свежий `Vec<u8>`
  (~10МБ). Достаточно быстрая серия РЕАЛЬНО различающихся кадров всё
  ещё может разогнать аллокатор (та же гипотеза фрагментации musl
  malloc, не опровергнутая и не подтверждённая напрямую в этом
  раунде).
- **Рекомендация для будущей работы (не входит в этот фикс)**:
  заменить `pixels: Vec<u8>` на переиспользуемый буфер на поверхность
  (resize/clear+extend вместо новой аллокации на каждый генуинно новый
  кадр) -- убрало бы оставшиеся ~10МБ аллокации/копирования там, где
  content действительно меняется, а не только там, где он совпадает.
- Метод (синтетический `uinput`-touch + перенаправление `/dev/input/
  touchscreen` + point-in-code diag-теги) -- реиспользуемый для
  будущих UI-нагрузочных расследований без физической усталости
  человека-тестировщика.
- `is_new_content()` и `SurfaceFrame::digest` -- постоянный код,
  закоммичен; вся diag-инструментация (`diag_commit_count`,
  `diag_skipped_duplicate_commits`, `diag_rss_kb()`, точечные теги
  в `saai-shell`) -- временная, удалена перед коммитом, `saai-shell`
  не менялся вовсе (все правки там были диагностическими).
