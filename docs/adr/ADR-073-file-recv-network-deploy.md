# ADR-073: file-recv -- первый канал доставки файлов на устройство без полной перепрошивки

## Статус

Принято, 2026-09-14.

## Контекст

Вся эта сессия (S14-S25, ADR-072's Маджонг) доставляла на устройство
ровно одним способом: вшить файл в 8МБ `init_boot`-ramdisk через
`build-native-c-image.sh` и `fastboot flash init_boot_a`. Для одной
игры это чуть не упёрлось в предел размера раздела (ADR-072). SSH и
adb к устройству недоступны (порт 22 отклонён, `adb devices` пуст) --
подтверждено многократно за сессию.

Пользователь дал WiFi-данные реальной сети (SSID `Wallbox`) и явный
карт-бланш на инфраструктуру: "качай, гружи на телефон, сделай
постоянное хранилище, создай нормальное подключение через wifi".
Реального пространства для новых разделов не требовалось --
`/data`/`/metadata` уже персистентны и подтверждены переживающими
reflash (настройки `saai-shell`, ключи Bluetooth и т.п. уже там).
Подключение к WiFi выполнено напрямую через `wpa_cli` с serial-
консоли (не через UI `saai-shell` -- у пароля сети есть заглавные
буквы и цифры, а клавиатура шелла только строчная латиница,
ADR-065), сохранено в `/metadata/saaios/wifi.conf` (реальный
персистентный `f2fs`-раздел `/dev/sda8`, не ramdisk) --
переживёт перезагрузку.

## Решение

`file-recv` (`os/targets/panther/src/file-recv.c`) -- постоянно
слушающий TCP-приёмник файлов, запускается `native-init.c` при
каждой загрузке (тот же паттерн supervision/restart, что и
`saai-appd`). Текстовый заголовок, бинарное тело -- `PUT
<relative-path> <byte-count>\n`, затем ровно `byte-count` сырых
байт -- специально не бинарный length-prefix, чтобы клиентом мог
быть голый bash (`/dev/tcp`) без дополнительных инструментов.
Единственное правило безопасности: путь должен быть относительным,
без `..` -- каждая запись гарантированно остаётся внутри `/data/
saaios/incoming/` (реальный персистентный раздел). Никакой
аутентификации сверх "достижим по этой LAN" -- та же модель доверия,
что уже у сокетов `wpa_supplicant`/`saai-appd` на этом устройстве
(если что-то уже может достучаться до них, оно уже имеет
сопоставимый доступ); это bootstrap-инструмент для
single-developer устройства, не production-сервис.

Потребовалась ровно одна, предположительно последняя в обозримом
будущем, полная пересборка + `fastboot flash` для доставки самого
`file-recv` -- дальше любой файл (новый `saai-shell`, новое
приложение, что угодно) можно передать напрямую по WiFi, без
reflash вообще.

## Test

Кросс-компиляция чиста (`zig cc`, тот же паттерн, что и
`wifi-scan.c`/`bt-scan.c`), итоговый образ -- ровно 8388608 байт (в
пределах лимита раздела). Функциональная проверка -- следующий шаг
после этого ADR: реальная передача файла по WiFi после прошивки.

## Последствия

- `file-recv` слушает на ВСЕХ интерфейсах (`INADDR_ANY`) без
  аутентификации -- приемлемо для устройства разработчика в
  доверенной домашней сети, неприемлемо как есть для чего-либо
  выходящего за эти рамки. Явный, осознанный компромисс, не
  недосмотр.
- Открытый пункт: не реализован метод СКАЧАТЬ файл с устройства
  (только загрузить) -- при необходимости логи/данные всё ещё нужно
  тянуть через serial console вручную (как в разборе проблемы с
  зарядкой в этой же сессии).
- WiFi-сеть (`Wallbox`) сохранена в `/metadata/saaios/wifi.conf` в
  открытом виде -- тот же честный компромисс, что уже принят для
  PIN-кода (ADR-068) и паролей Wi-Fi через `saai-shell` (ADR-065).
