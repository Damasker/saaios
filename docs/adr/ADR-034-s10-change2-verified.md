# ADR-034: S10 Change 2 -- planner bridge physically verified end to end, zero saai-shell changes

## Статус

Принято, 2026-09-11.

## Контекст

ADR-033 (Change 1) решило: `saai-taskd` вызывает уже работающий на
устройстве `saaios-runtime` вместо изобретения нового ИИ-стека, и
`WorkflowStatus` определяется наличием `pending` в ответе. Change 2 --
минимальный вертикальный срез, реализующий это решение в коде, вместо
старого `echo`-плейсхолдера (S09/ADR-031), и физически подтверждающий
его на реальном устройстве, включая оба узла существующего экрана
подтверждения (ADR-032) -- без единого изменения в `saai-shell`.

## Реализация

**`saai-taskd/src/runtime_bridge.rs`** (новый модуль): минимальный
TCP-клиент протокола `saaios-runtime`, без зависимости от `protocol`/
`ai-runtime`/`model-provider` (ADR-030's принцип) -- только JSON-форма
проверена и повторена. `diagnose()`/`confirm()`, 4 wire-теста
(fake-сервер тем же паттерном, что `client.rs`'s собственные тесты).

**`model.rs`**: `RUNTIME_ACTION_KIND` заменяет `ECHO_ACTION_KIND`
(последний и его тесты удалены -- placeholder Change 2 из S09 был
явно временным, не постоянной функцией). Новые переходы:
`Pending->Failed` (мост недоступен ещё до начала выполнения),
`WaitingConfirmation->Failed` (подтверждённое действие не удалось
выполнить -- см. Находки ниже). Task теперь стартует `Pending` для
planner-пути (не `Running` сразу), поскольку до ответа
`saaios-runtime` неизвестно, обычный это ответ или требующий
подтверждения.

**`lib.rs`**: `process_planner_intent()` -- Pending Task, вызов
`runtime_bridge::diagnose()`; при ошибке моста -- `fail_task()`
(Failed, БЕЗ падения демона); при `pending` в ответе --
`WaitingConfirmation` Task/Action (то же самое, что ADR-032's опасный
путь, другой `kind`); без `pending` -- Running->Done с ответом модели
как Result. `execute_confirmed_action()` теперь диспетчеризует по
`kind` Action'а: `delete_entity` (без изменений) или
`saaios_runtime_tool` (новое -- `runtime_bridge::confirm(confirmed:
true)`). `try_cancel_pending_action()` для `saaios_runtime_tool`
дополнительно уведомляет `saaios-runtime` (`confirmed: false`),
best-effort.

## Находки (обе -- реальные баги, найденные и исправленные до коммита)

**Собственная тестовая оснастка**: `SerialPort.Write(string)`/`Read`
в PowerShell-скрипте использовали кодировку по умолчанию (ASCII) --
кириллический текст интента ушёл на устройство как `???????`.
Исправлено (`$port.Encoding = UTF8`, ручной byte-buffer при чтении).
Это баг тестовой инфраструктуры этой сессии, не проекта.

**Реальный баг в `saai-taskd`, найден физически**: `saai-entity-store`
требует непустой, ≤160 символов, без control-символов заголовок
(`validate_human_text`). Заголовок `saaios.result`, построенный
напрямую из ответа модели (`&summary`), не имел такой гарантии --
многострочный или длинный ответ (реально получен от `qwen2.5:3b-
instruct`: два абзаца, суммарно больше 160 символов) заставил
`saai-entityd` отклонить `CreateEntity`, что не было обработано и
уронило демон (`Ok`/`?`-цепочка распространила ошибку до `run()`).
Исправлено: `model::safe_title()` -- убирает control-символы,
обрезает по символам (не байтам) до `MAX_ENTITY_TITLE_CHARS`,
подставляет fallback при пустой строке. Применено ко всем местам,
где заголовок строится из intent-текста или ответа модели (Task,
Action, оба места создания Result). 5 host-тестов, включая
UTF-8-safe обрезку многобайтовых символов.

## Физическая проверка

Тот же реальный Pixel 7 (COM13-serial + USB-NCM на этом Windows-хосте).

**Побочная находка перед основным тестом**: `saai-taskd`, работая НА
устройстве, не мог подключиться ни к `172.31.7.1:38127` (свой же
USB-NCM адрес), ни к `127.0.0.1:38127` -- таймаут, не отказ.
`ip link show lo` показал `<LOOPBACK>` БЕЗ `UP`/`LOWER_UP` и без
`inet 127.0.0.1` вообще -- `native-init.c` никогда не поднимает
loopback-интерфейс. Это объясняет таймаут: даже self-directed трафик
на "чужой" IP (172.31.7.1) внутренне маршрутизируется ядром через
`lo`. Поднят вручную (`ip link set lo up` + `ip addr add
127.0.0.1/8 dev lo`) для этого теста -- подтверждено сразу после:
`127.0.0.1:38127` дал мгновенный "connection refused" (корректно --
там никто не слушает), `172.31.7.1:38127` -- успех. **Не исправлено
в `native-init.c`** -- отдельная, не входящая в этот ADR задача (см.
Последствия).

**Неопасный путь**: свободный текст ("Сколько свободно места на
диске?") -> `saai-taskd` вызвал `saaios-runtime` -> модель сама
вызвала `system.disk`, ответила (два абзаца, по-русски, с
переносами строк) -> `Task` стал `Done`, `Result` создан с корректно
усечённым заголовком (проверено: ровно 160 символов, без переносов),
полный текст сохранён в `properties.summary`. Демон не упал.

**Опасный путь, подтверждение**: текст ("Останови процесс с pid
999999, пожалуйста") -> модель предложила `process.kill_request` ->
`pending` -> `Task`/`Action` `waiting_confirmation`. Реальный тап на
уже существующем экране `Frame::TaskConfirm` (ADR-032, **без единого
изменения кода `saai-shell`**) -> `saai-taskd` вызвал
`runtime_bridge::confirm(confirmed: true)` -> `saaios-runtime`
попытался выполнить (безвредно провалилось: pid не существует) ->
`Task` `Done` с честным "Не выполнено: process.kill_request
(execution failed: pid 999999 not found)".

**Опасный путь, отклонение**: второй такой же запрос -> `pending` ->
реальный тап "Отклонить" -> `Task`/`Action` `cancelled`, ничего не
выполнено.

**Побочная находка, критичная, зафиксирована честно**: для первой
попытки подтверждения UI не реагировал на тапы физически подтверждения
корректно -- экран подтверждения не появлялся вообще (тапы уходили в
таб-бар). Расследование показало: восстановленный "истинный оригинал"
`saai-shell` (`87dbe83f...`, найденный как реальное содержимое
`init_boot`-образа в ADR-032's cold-reboot тесте) **не содержит
код экрана подтверждения** -- вероятно, зашитый образ старше S09's
Change 2/3 целиком. Все успешные тесты ADR-032 использовали
ВРЕМЕННО подменённый бинарник, не сам `87dbe83f`; после теста
`87dbe83f` был "восстановлен" как верный, но это никогда не
проверялось как содержащий Change 2/3. Для ЭТОГО теста подставлен
уже известный по ADR-032 рабочий бинарник (хэш `9d4df0ee...`,
подтверждено через `/proc/PID/exe`) -- после подстановки экран
подтверждения появился и сработал корректно. **Реальный, зашитый
`init_boot`-образ устройства сегодня не содержит on-screen клавиатуру
и экран подтверждения** -- см. Последствия.

**Откат тестовой оснастки, полностью выполнен**: `uinput`-устройство
уничтожено, `/dev/input/touchscreen` восстановлен на `event2`,
`/saaios/saai-shell` восстановлен к `87dbe83f` (сверен байт-в-байт),
`saai-taskd` остановлен, 15 тестовых сущностей удалены из `work` с
явным подтверждением пользователя. `lo` оставлен поднятым (корректное,
а не тестовое состояние).

## Решение

S10 Change 2 закрыт: свободный `Intent` реально превращается в
предложенный, а не жёстко закодированный `Action` через уже
работающий `saaios-runtime`, без дублирования его риск-политики, с
нулевыми изменениями в `saai-shell`'s UI-коде -- подтверждая
центральный тезис ADR-033.

## Последствия

- **Найден и явно назван, но не исправлен здесь, серьёзный
  операционный пробел**: (1) `native-init.c` никогда не поднимает
  `lo` -- любой будущий native-компонент, которому понадобится
  loopback (не только этот мост), столкнётся с тем же таймаутом;
  (2) зашитый `init_boot`-образ устройства (`87dbe83f`) устарел
  относительно репозитория минимум на весь объём S09's Change 2/3 --
  реальное устройство после настоящей холодной перезагрузки
  ЛИШАЕТСЯ on-screen клавиатуры и экрана подтверждения опасного
  действия, пока кто-то не подставит новый бинарник вручную. Оба --
  явные кандидаты для отдельной, безотлагательной задачи (пересборка
  и перепрошивка `init_boot`, плюс `ip link set lo up` в
  `native-init.c`), не входящей в S10.
- `--runtime-addr` обязателен (не имеет default) в `saai-taskd`'s
  CLI -- физически подтверждённый на этом устройстве адрес
  (`172.31.7.1:38127`) не переносим на другое железо/сессию по
  умолчанию.
- Расписания/триггеры и memory-с-пространством по-прежнему не
  решены -- явно вне Change 1/2, как и было зафиксировано в
  Definition of Ready.
