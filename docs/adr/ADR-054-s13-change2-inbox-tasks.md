# ADR-054: S13 Change 2 -- "Входящие" из реальных задач, честный остаток на taskd

## Статус

Принято (с честной оговоркой), 2026-09-13.

## Контекст

"Входящие" не имела ни одной записи в `root.sui` -- `content_cards`
для неё всегда были пусты, и `render::draw_root` рисовал серые
placeholder-строки вместо честного пустого состояния. Отдельно от
этого, обнаружено (в процессе проектирования этого Change) что
экран подтверждения опасной задачи (`Frame::TaskConfirm`) до сих пор
глобально перехватывал ВЕСЬ ввод, как только появлялась хоть одна
задача со статусом `waiting_confirmation`, независимо от того, какая
вкладка была активна -- то есть "Входящие" физически не могла
показать непустой список: модалка вклинивалась раньше. По решению
пользователя это поведение изменено: подтверждение задачи теперь
открывается только тапом по конкретной строке в "Входящих".

## Решение

- `inbox_pending_tasks()`/`inbox_row_rect()`/`inbox_task_at()` --
  "Входящие"'s собственный, вычисляемый в рантайме эквивалент
  `ROOT_CONTENT_ACTIONS`/`content_action_rect`/`content_action_at`
  (которые не подходят: их набор фиксирован на этапе сборки из
  `root.sui`, а список задач -- рантайм-данные переменной длины).
  Раскладка строк -- та же геометрия 190px/220px, что уже использует
  "Пространства".
- Новое поле `confirming_task_id: Option<Uuid>` (требует
  `uuid.workspace = true`, добавлено в `Cargo.toml` -- уже было
  workspace-зависимостью для `saai-entity-store` и других крейтов)
  заменяет старую `pending_task_confirmation()` (искала "первую
  подходящую" без выбора пользователя) на `confirming_task()` (ищет
  конкретный id). `Some` только после тапа по строке в "Входящих",
  `None` снова после принятия/отклонения -- без старого
  авто-перехода к следующей задаче.
- Пустой список показывает честный текст ("Нет задач, ожидающих
  подтверждения"), не placeholder-блоки -- прямое требование
  Acceptance criteria из DoR.

## Test

Host: `cargo test -p saai-shell` -- 22/22 зелёные (новая uuid-
зависимость не потребовала новых тестов -- вся новая логика --
тонкая обвязка вокруг уже протестированного `confirm_pending_task`).
`cargo clippy -p saai-shell` чист. Кросс-компиляция чиста, hash
`97220c436b7d44adf83e6d40fc9162f409c3aab4efd61f6171cd0f0ec3f13459`.

Device (`cp && mv` + `chmod`, ADR-042):

- Пустое состояние физически подтверждено: "Входящие" показывает
  честный текст на реальном устройстве.
- Реальное намерение отправлено через существующий экран ввода
  ("Сейчас" → "Новое намерение") -- физически подтверждено, что оно
  НЕ создаёт ложную запись во "Входящих" (свободный текст никогда не
  становится `waiting_confirmation`-задачей, по дизайну ADR-032 --
  `saai-taskd::model::dangerous_action_of` явно исключает
  произвольный текст, только структурированный `delete_entity`-intent
  считается опасным).

**Честный остаток, не устранён.** Чтобы физически проверить сам тап
по строке (открытие модалки, принять/отклонить), нужен настоящий
`waiting_confirmation`-task -- для этого вручную собран и отправлен
через `entityd.sock` (busybox `nc` не умеет AF_UNIX -- собран
одноразовый throwaway-инструмент `sockline`, вне workspace, не
закоммичен) корректно оформленный `delete_entity`-intent. Сам
`saai-entityd` принял его (`ok: true`, событие `entity_created`
подтверждено) -- но **`saai-taskd` не запущен на этом устройстве
вообще** (`ps -ef` не находит процесс, `/saaios/saai-taskd` не
существует как файл). Это не баг Change 2 -- это отдельная,
предсуществующая инфраструктурная дыра: путь intent → task на этом
конкретном тестовом образе никогда не был развёрнут до конца. Тап-по-
строке остаётся код-ревьюнутым (прямая параметризация уже физически
проверенного `confirm_pending_task` конкретным id вместо "первого
найденного"), но не end-to-end физически подтверждённым. Открыто для
будущей работы, если/когда `saai-taskd` будет развёрнут на этом
устройстве.

## Threat / privacy impact

Никаких новых данных или каналов -- `confirming_task_id` держит
только уже существующий `Uuid` из уже трекаемых `selected_entities`.

## Rollback

Предыдущий физически подтверждённый `saai-shell` (`cp && mv`, тот же
паттерн, что и остальной проект).
