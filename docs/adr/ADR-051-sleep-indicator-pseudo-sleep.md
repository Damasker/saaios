# ADR-051: индикация сна экрана -- surface-фикс, отказ от реального suspend

## Статус

Принято, 2026-09-12.

## Контекст

ADR-041 (S11 Change 2) реализовал `check_deep_idle`: по истечении
`deep_idle_timeout` поверх обычной блокировки экрана она вызывала
`echo mem > /sys/power/state`, полагаясь на спайк ADR-040. Физическая
проверка (нажатие в реальном цикле простоя) показала: **экран не
гас вообще**. Первая гипотеза и попытка исправления рисовала чёрный
кадр в toplevel-поверхность (`self.window`, через новый вариант
`Frame::Sleeping` в `draw()`) -- физически подтверждено пользователем
как **не давшее эффекта** ("Нажал, но экран НЕ гас").

Корневая причина: `saai-shell` держит ДВЕ независимых поверхности --
персистентный toplevel (`draw()`) и отдельную ext-session-lock-v1
lock-поверхность (`self.lock_surfaces`/`lock_pool`/`lock_buffer`,
заполняется один раз захардкоженным цветом в `configure()` и больше
не перерисовывается). `saai-displayd::recomposite()` показывает LOCK
surface, когда `self.locked == true` -- ровно то состояние, в котором
`check_deep_idle()` вообще может сработать (guard `if !self.locked`).
Фикс, целившийся в toplevel, был структурно недостижим в этом
сценарии.

Второй раунд физической проверки (после исправления surface-таргета)
выявил ОТДЕЛЬНУЮ проблему: `echo mem > /sys/power/state` стабильно
падал с `EBUSY`. `/sys/kernel/debug/wakeup_sources` показал
`dwc3-otg` с ненулевым `active_since` и `max_time` порядка 9620с --
контроллер USB OTG держит wakeup lock, пока USB-линк сконфигурирован
(в нашем случае -- ровно то же самое serial-консоль + USB-NCM
соединение, которым мы наблюдаем за устройством). Это
аппаратно-платформенное поведение, не баг в `saai-shell`/`saai-
displayd`: настоящий suspend физически не проверить, не отключив
кабель -- а тогда пропадает и консоль для наблюдения за результатом.

По совместному решению с пользователем: отказаться от попытки
настоящего system suspend в этом коде и реализовать более простой,
надёжно проверяемый псевдо-сон -- визуальное гашение экрана до
следующего касания, без затрагивания состояния ядра.

## Решение

1. **Surface-фикс.** Заполнение lock-поверхности вынесено из
   `SessionLockSurfaceHandler::configure()` в переиспользуемый метод
   `present_lock_surface(&mut self, color: [u8; 4])` (новые поля
   `lock_width`/`lock_height` запоминают размер вне колбэка
   `configure`). `configure()` по-прежнему вызывает его с
   `LOCK_SCREEN_COLOR` при первом конфигурировании.
2. **Псевдо-сон вместо реального suspend.** `check_deep_idle` больше
   не трогает `/sys/power/state` и не переключает `wlan0`. По
   истечении `deep_idle_timeout` (при `self.locked`) один раз
   вызывает `present_lock_surface(SLEEP_INDICATOR_COLOR)` (чёрный) и
   выставляет новый флаг `self.sleeping = true`, после чего сразу
   возвращается -- экран остаётся чёрным сколь угодно долго, а не
   мигает и тут же откатывается назад, как было в версии с реальным
   suspend (там `EBUSY` возвращался мгновенно, поэтому `check_deep_
   idle` тут же перерисовывала красный экран обратно).
3. **Пробуждение по касанию.** `TouchHandler::down` в самом начале
   проверяет `self.sleeping`: если `true`, первое касание только
   гасит флаг и перерисовывает `LOCK_SCREEN_COLOR` (будит экран),
   явно сбрасывая `unlock_pending`/`tab_touch_pending` и выходя без
   дальнейшей обработки -- разблокировка требует отдельного второго
   тапа по уже проснувшемуся красному экрану, тем же принципом
   "нажатие кнопки, затем свайп", что и на обычном телефоне.

## Test

Host: `cargo test -p saai-shell` -- существующие тесты зелёные
(логика `is_new_content`-подобных unit-тестов в этом файле не
затронута). Кросс-компиляция (`ZIG=... build-saai-shell.sh`, профиль
`pixel7`) чиста для боевого (300с) и тестового (`SAAIOS_DEEP_IDLE_
SECS`-эквивалент, локально 15с через временную подмену константы,
восстановлена перед коммитом) вариантов.

Device (тот же runtime-подмену `cp && mv` + `chmod`, ADR-042; hash
рабочего 15с-теста `f22aafbab43927667e69a63f3af962b179ff7e3040e82c6cc4d8b5d7ef4e76f4`,
подтверждён через `sha256sum /proc/<pid>/exe`):

- Естественный цикл простоя (без касаний, ~60с до блокировки + 15с
  тестовый deep-idle) физически пронаблюдан: лог показал `saai-shell:
  deep idle timeout, screen off`, новый commit/blit с изменившимся
  digest, **без** последующего отката к красному экрану (в отличие от
  версии с реальным suspend, где `suspend request failed: Resource
  busy` -> немедленный откат повторялись в логе десятками циклов).
- Пользователь подтвердил визуально: экран действительно чёрный.
- Один тап: экран проснулся, показал красный lock-экран, **не**
  разблокировался -- ровно ожидаемое поведение.

Настоящий system suspend (`mem`) в этом ADR не проверялся и не
является больше целью данного пути кода -- см. "Честный остаток"
ниже.

## Честный остаток

- Реальный переход в `mem`-suspend по-прежнему невозможно
  верифицировать при подключённом по USB устройстве (`dwc3-otg`
  держит wakeup lock всё время, пока линк сконфигурирован) -- это
  ограничение методики тестирования через serial-консоль/USB-NCM, не
  недоработка кода. Возможность (не реализованная) для будущей
  работы: физический тест с отключённым кабелем и последующим
  подключением для считывания лога, если экономия энергии реального
  suspend когда-либо станет приоритетом.
- Псевдо-сон не выключает подсветку/панель на аппаратном уровне --
  только рисует чёрный кадр поверх lock-поверхности. Реальной
  экономии энергии по сравнению с горящим красным lock-экраном может
  не быть или быть небольшой (зависит от того, экономит ли панель
  энергию на полностью чёрном кадре) -- не измерялось.

## Последствия

- UX-пробел ADR-041/042 ("экран не гаснет при простое") закрыт
  функционально: экран действительно визуально темнеет и остаётся
  тёмным до касания, что физически подтверждено.
- Реальный system suspend больше не является частью `check_deep_idle`
  -- если аппаратное энергосбережение снова станет целью, потребуется
  отдельная работа (вероятно, за пределами `saai-shell`, ближе к
  platform/init-уровню, где можно управлять USB gadget независимо от
  консоли наблюдения).
- `std::process::Command`-вызовы `wlan0 down`/`up` вокруг suspend
  удалены вместе с самим suspend -- одной причиной меньше для отказа
  Wi-Fi при простое.
