# ADR-024: GPU-рендеринг на panther -- реальный kbase поднимает MCU-прошивку; настоящий Mali UMD создаёт VkDevice на этом железе

## Next session entry point: fence completion producer отсутствует (2026-09-16, продолжение)

На этом этапе инструментально подтверждено и закрыто (не пересматривать без новых фактов):

* poll/read notification chain kernel -> `mali-event-hand`: полностью рабочая.
  `ppoll()` — не вечная блокировка, а цикл с конечным timeout; `fd=3`
  (`/dev/mali0`) реально становится readable (`revents=POLLIN`) примерно
  через 100мс после `vkQueueSubmit()`; `read(fd=3)` реально читает 64 байта
  настоящего `struct base_csf_notification` — all-zero, что для реального
  открытого `kbase_read()` (CSF-путь) является корректно сформированным
  generic `BASE_CSF_NOTIFICATION_EVENT` (type=0), а не признаком поломки.
* CSF event-память (`0x5fffff1000`, `0x5ffff79000`, встреченные в ring
  buffer как операнды `EVADD`): реально замаплены. `sysprobe`-трасса
  `ioctl`+`mmap` показала `ioctl(fd=3, request=0xc040803b)` —
  `_IOWR(0x80, 59, 64 bytes)`, то есть **это `KBASE_IOCTL_MEM_ALLOC_EX`
  (не обычный `KBASE_IOCTL_MEM_ALLOC`, у которого nr=5)** -- раньше по памяти
  без проверки предполагался номер 5 — прямо перед каждым `mmap(fd=3, offset=0x41000)`,
  который возвращает **ровно** `0x5fffff1000`/`0x5ffff79000`. CPU VA ==
  GPU VA, `munmap` за весь прогон не встречается ни разу. Гипотеза
  "SAME_VA cookie-mmap для `BASE_MEM_CSF_EVENT` не происходит/сломан в
  нашем bionic-island окружении" — **опровергнута прямым фактом**, не
  предположением.
* Ранняя находка "мали-event-hand после `read()` уходит в тугой spin-loop
  `libc.so+0x62300` <-> `libGLES_mali.so+0x1374f94`" — **отброшена**.
  Статический дизассемблер этих двух адресов (после проверки, что
  `p_vaddr == p_offset` для всех `LOAD`-сегментов обеих библиотек, т.е.
  file offset действительно можно использовать как ELF vaddr для
  `objdump --start-address`) показал, что это ветка
  `scudo_mallopt(M_LOG_STATS=-205, ...)` — диагностический дамп аллокатора
  (`getStats`/`outputRaw`/`printFragmentationInfo`), никак не связанная с
  ожиданием fence. Параллельный быстрый (без single-step) прогон той же
  программы показал, что `mali-event-hand` вообще не делает ни одного
  syscall между `read(fd=3)=64` и следующим `ppoll()` — старая
  single-step трасса либо перепутала поток (баг атрибуции в
  `sysprobe`), либо сам single-step исказил scheduling. **Не доверять
  этой трассе впредь.**
* Настоящий `vkGetFenceStatus` найден не предположением, а через
  `dladdr()` прямо в самом `vk_exec01` (указатель, возвращённый
  `vkGetInstanceProcAddr`, у закрытого Mali UMD не экспортируется по
  имени — только Android-specific extension-функции видны в `--dyn-syms`).
  Статический дизассемблер (`libGLES_mali.so` file offset `0x915da0`)
  показал: `vkGetFenceStatus(device, fence)` берёт `x0 = fence + 0x250` и
  вызывает `sub_1b38520(x0)`; эта функция проверяет `[x0+128]`
  (attached sync-fd) — если это не `-1`, реально делает `ppoll()` на этом
  fd; если `-1` (наш случай, всегда), просто читает закэшированный
  `byte[x0+1]` ("signaled"-флаг) без единого syscall. Это объясняет,
  почему `vkGetFenceStatus()` не производит ни одного `ioctl`/`poll` в
  нашей трассе — это ожидаемое поведение при отсутствующем sync-fd, а не
  баг сам по себе.
* Прямое, без `ptrace`, чтение `*(fence_handle+0x250+{0,1,128})` из
  самого `vk_exec01` каждые 500мс на протяжении всего 5-секундного окна
  ожидания показало: `byte[0]=0`, `byte[1]=0` (signaled cache),
  `fd_field=-1` — **неизменны с момента `vkCreateFence()` и до самого
  конца прогона**, включая всё время после `vkQueueSubmit()`. Это уже не
  "не поймано в трассе syscall'ов" (как в старой, неверной
  интерпретации single-step находки), а прямое доказательство: **тот,
  кто должен записать `byte[1]=1` (сам "producer" completion-состояния),
  не вызывается вообще ни разу** за весь прогон.

### UMD-FENCE-01: следующая цель

Найти setter `byte[fence_obj+0x250+1]=1` внутри `libGLES_mali.so`
(искать `strb w?, [x?, #1]` в связке с тем же объектом — рядом уже
найдены соседние helper'ы на `0x1b384c0`-`0x1b384d8`, работающие с
байтами `[0]`/`[1]` и полем `+128` того же объекта) и определить:

1. При каком событии/условии этот setter должен вызываться (по коду —
   не предположением).
2. Вызывается ли он вообще где-либо в загруженном `libGLES_mali.so` для
   этого пути submit, или недостижим (dead code в нашей конфигурации).
3. Если достижим — какой шаг/поток должен был его вызвать, и какое
   条件 (feature flag, property, callback registration) в нашем
   bionic-island окружении может блокировать этот путь.

Инструмент: `sysprobe` (ptrace, уже доказанно безопасен) + статический
дизассемблер `libGLES_mali.so` (`aarch64-linux-gnu-objdump`,
`aarch64-linux-gnu-readelf`, оба на R620). Kretprobe на новых
kernel-функциях для этого шага не требуется — разрыв уже локализован в
closed-source userspace UMD, не в ядре.

### UMD-FENCE-01: setter найден -- gated на event-код 10, который, похоже, никогда не производится

Найден вероятный setter: file offset `0x1b38314` в `libGLES_mali.so`:

```asm
1b38308: ldrb  w8, [x20, #218]
1b3830c: cmp   w8, #0xa            ; 10
1b38310: b.ne  1b38348             ; иначе -- пропустить сигнализацию
1b38314: ldr   x8, [x19, #16]
1b38318: ldrb  w9, [x8, #1]
1b3831c: orr   w9, w9, #0x1        ; signaled |= 1
1b38320: strb  w9, [x8, #1]
```

`x20` -- указатель на входящее сообщение/дескриптор (поля со смещениями
36/24/218/64/88/100 -- похоже на декодированную KCPU-команду или
sync-событие), `x19->[16]` -- указатель на fence-подобный объект, чей
`byte[1]` мы уже отследили как никогда не меняющийся в реальном
прогоне. Рядом (`0x1b38420`) -- парный object-init/reset, зануляющий
тот же `byte[1]` и выставляющий `fd_field(+128)=-1` -- совпадает
побитово с начальным состоянием, которое мы наблюдали через прямое
чтение памяти.

Т.е. сигнализация fence в этом UMD гейтится конкретным кодом события
(`==10`) во входящем KCPU/sync-сообщении -- не происходит
автоматически по факту завершения ring buffer. Это напрямую
согласуется с более ранней находкой этой же сессии (ftrace:
`mali_KCPU_FENCE_SIGNAL`/`mali_KCPU_CQS_SET` не срабатывают ни разу за
весь прогон, см. выше) -- наиболее вероятное объяснение теперь:
**UMD в фазе 1 submission никогда не ставит в KCPU-очередь настоящую
`CQS_SET`-команду**, которая единственная могла бы породить входящее
сообщение с кодом 10 и дойти до этого setter'а. Ring buffer целиком
состоит из `EVADD`-бухгалтерии (см. выше) -- ни одной job-launch или
явной `CQS_SET` KCPU-команды в нём нет.

Следующий шаг: найти, кто/что решает, добавлять ли реальную
`CQS_SET`/job-launch команду в фазу 1 (вероятно, feature-flag/
capability-check по GPU properties или architecture ID где-то в
`libGLES_mali.so`/`vulkan.mali.so` init-пути) -- не kernel-side и не
notification-delivery баг, а решение, принимаемое проприетарным UMD на
основе того, что он думает о железе/окружении. Кандидаты для проверки:
структуры, которые наш kbase отдаёт через `vkGetPhysicalDeviceProperties`-
путь, и реальный `arch_major_rev`/`product_id`/feature bitmask, сверить
с тем, что ожидает закрытый UMD (сравнение с тем, что видит stock
Android на этом же железе, недоступно без второго устройства).

### UMD-KCPU-01: kernel полностью исключён -- CQS_SET никогда не enqueue'ится

По предложению пользователя: прежде чем спрашивать "почему kernel не
ставит CQS_SET", проверено, отправляет ли сам UMD команду `CQS_SET`
через `KBASE_IOCTL_KCPU_QUEUE_ENQUEUE` вообще -- без единого нового
kernel probe, чисто через `sysprobe` (декодирование ioctl-аргументов
по реальным UAPI-структурам из `mali_base_csf_kernel.h`/
`mali_kbase_csf_ioctl.h`):

```
KBASE_IOCTL_KCPU_QUEUE_CREATE  = _IOR(0x80,45,8)  = 0x8008802d
KBASE_IOCTL_KCPU_QUEUE_DELETE  = _IOW(0x80,46,8)  = 0x4008802e
KBASE_IOCTL_KCPU_QUEUE_ENQUEUE = _IOW(0x80,47,16) = 0x4010802f
```

Результат полного прогона `vk_exec01` под новым `sysprobe` (декодирует
`kbase_ioctl_kcpu_queue_enqueue` + массив `struct base_kcpu_command` по
адресу из userspace до передачи ядру):

* `KBASE_IOCTL_KCPU_QUEUE_CREATE` -- вызван **3 раза** (UMD реально
  создаёт 3 KCPU-очереди для этого submit);
* `KBASE_IOCTL_KCPU_QUEUE_ENQUEUE` -- **вызван 0 раз**;
* `KBASE_IOCTL_KCPU_QUEUE_DELETE` -- вызван 0 раз (не успевает до
  `sleep(10)`/выхода).

То есть **в KCPU-очереди не enqueue'ится вообще ни одна команда** --
ни `CQS_SET`, ни `CQS_WAIT`, ничего. `kbase_csf_kcpu_queue_enqueue()`
(ядро) физически не может быть источником проблемы: ему просто нечего
обрабатывать, потому что до него дело не доходит. Это то же самое
заключение, что и раньше (ring buffer содержит только `EVADD`
event-бухгалтерию, ftrace не видит `mali_KCPU_CQS_SET`), но теперь
подтверждено на **один уровень выше**, напрямую на границе ioctl, а не
косвенно через firmware trace.

**Разрыв на 100% локализован внутри closed-source `libGLES_mali.so`/
`vulkan.mali.so`, до какого-либо системного вызова.** Следующий шаг
(`UMD-KCPU-02`): статически найти в этих библиотеках место, где
собирается вызов `ioctl(fd, KBASE_IOCTL_KCPU_QUEUE_ENQUEUE, ...)` --
по x-ref на константу `0x4010802f` (обычно `mov`/`movk` пара или litpool
`adrp+ldr`) -- и понять, какое условие решает, вызывать ли его вообще
для этого submission path (скорее всего capability/feature-флаг,
читаемый из GPU properties, которые наш kbase возвращает через
`KBASE_IOCTL_GET_GPUPROPS`/`KBASE_IOCTL_VERSION_CHECK` -- оба реально
вызываются в этом прогоне, видны в трассе).

### UMD-KCPU-02: найдена точка решения "enqueue FENCE_SIGNAL или нет"

Статически найдены три тонкие функции-обёртки вокруг ioctl в
`libGLES_mali.so` (соседний кластер, единственные во всей библиотеке
вызовы `KBASE_IOCTL_KCPU_QUEUE_{CREATE,DELETE,ENQUEUE}`):

* `0x1c46600` -- `QUEUE_CREATE(fd) -> id`
* `0x1c46690` -- `QUEUE_DELETE(fd, id)`
* `0x1c46710` -- `QUEUE_ENQUEUE(fd, id, cmds_addr, nr_commands)`

Всего в библиотеке 9 x-ref на `0x1c46710`, каждый -- в отдельной
маленькой функции, строящей РОВНО одну `struct base_kcpu_command` с
жёстко зашитым `type` (например `0x1c4d000` пишет `type=0`
(`FENCE_SIGNAL`) в `[sp]`, `0x1c4d090` -- `type=1` (`FENCE_WAIT`)).

Вызывающий код для `FENCE_SIGNAL`-обёртки (`0x1c4d000`) найден в
районе `0x1b3bc90`-`0x1b3bcc0` (тот же файл/регион, что и
`vkGetFenceStatus`/CQS-setter из UMD-FENCE-01 -- судя по всему, единый
translation unit, отвечающий за submission + fence lifecycle):

```asm
1b3bc90: mov  x0, x21
1b3bc94: bl   1b392f0          ; acquire-slot(x21) -> x0 (NULL если недоступно)
1b3bc98: str  x0, [sp, #56]
1b3bc9c: cbz  x0, 1b3bd38      ; НЕТ слота -> пропустить весь FENCE_SIGNAL блок
1b3bca0: ldrb w8, [x20, #12]
1b3bca8: tbz  w8, #0, 1b3be18  ; бит0 [x20+12] не установлен -> тоже пропустить
...
1b3bcc0: bl   1c4d000          ; enqueue FENCE_SIGNAL -- достигается только если оба условия выше пройдены
```

`0x1b392f0` -- похоже на "acquire slot из пула" (читает счётчик
`[x0+208]`, вызывает проверочную `0x1c47810(...)`, при успехе
инкрементирует счётчик и возвращает указатель на слот массива, при
неудаче -- `NULL`).

В нашем прогоне (`UMD-KCPU-01`: 0 вызовов `QUEUE_ENQUEUE` вообще) одно
из двух условий (или оба) не выполняется. Следующий шаг
(`UMD-KCPU-03`): дизассемблировать `0x1c47810` (что именно она
проверяет) и найти семантику бита `[x20+12] bit0` (какое поле объекта
`x20` он отражает -- вероятно "queue group has KCPU support
enabled"/"fence export requested" флаг, выставляемый где-то раньше на
основе GPU properties или флагов создания устройства/очереди).

### UMD-KCPU-03: живой software breakpoint через ptrace -- гипотеза UMD-KCPU-02 опровергнута, разрыв ещё выше по стеку

По плану пользователя: прежде чем гадать дальше статически, реализован
настоящий live-эксперимент -- программный breakpoint (`BRK`,
инструкция `0xD4200000`) через чистый `ptrace` (`PTRACE_PEEKTEXT`/
`POKETEXT`/`SINGLESTEP`, без единого kernel probe) прямо в `sysprobe`,
ставящийся динамически после того, как `libGLES_mali.so` реально
замаплена (через уже существующий `load_maps()`).

**Эксперимент 1**: breakpoint на `0x1b3bca0` (точка сразу после
`bl 0x1b392f0` -- предполагаемый `acquire_slot()` -- из UMD-KCPU-02).
За весь прогон (`vkQueueSubmit` + 5с ожидание fence + 10с sleep)
**ни разу не сработал**.

**Эксперимент 2**: breakpoint на входе в сам `0x1b392f0`
(`acquire_slot`). Тоже **ни разу не сработал**. Значит вызов
`bl 0x1b392f0` по адресу `0x1b3bc94` физически не исполняется в этом
прогоне -- ветка кода, которую UMD-KCPU-02 определил статически, в
реальности **не задействована** для простого одно-буферного
`vkCmdFillBuffer`-submission (вероятно, это путь для
multi-buffer/multi-queue-family batched submissions).

**Эксперимент 3**: breakpoint на входе в сам builder `FENCE_SIGNAL`
(`0x1c4d000`, тот, что заполняет `type=0` и вызывает ioctl-обёртку
`ENQUEUE`) -- единственная функция во всей библиотеке, которая может
реально произвести `KBASE_IOCTL_KCPU_QUEUE_ENQUEUE(FENCE_SIGNAL)`, и у
неё все 9 x-ref со всей библиотеки. **Тоже ни разу не сработал.**
Согласуется с UMD-KCPU-01 (0 реальных ioctl `ENQUEUE`), но означает,
что разрыв находится **выше по стеку вызовов**, чем весь
исследованный в UMD-KCPU-02 кластер -- ни один из известных builder'ов
командного типа вообще не достигается, то есть решение "не сигналить
через KCPU" принимается значительно раньше, скорее всего сразу в
начале реализации `vkQueueSubmit` (единый ранний branch/return, а не
per-command-type проверка).

**Методологический вывод**: статический разбор соседнего кода (xref,
"похоже на функцию X") показывает ВОЗМОЖНЫЙ путь, а не обязательно
РЕАЛЬНО исполняемый -- это подтверждено инструментально, а не
предположением, и является прямым развитием того же принципа, что и
`liblp`/property-area уроки ранее в сессии. Гипотеза UMD-KCPU-02 (про
конкретный callsite `0x1b3bc94`) официально отозвана.

Также по ходу эксперимента обнаружена и исправлена ловушка
инструмента: `x0`/аргументы-указатели на объекты внутри UMD -- tagged
pointers (верхний байт вроде `0xb4`, классическая Android
handle-tagging схема) -- `PTRACE_PEEKDATA`/`PEEKTEXT` не игнорирует
верхний байт (в отличие от обычных `LDR`/`STR` самого процесса под TBI),
поэтому чтение по таким адресам нужно всегда делать через
`addr & 0x00ffffffffffffff` перед вызовом `read_mem()` -- иначе
получите ложный `read_mem FAILED` там, где память реально
замаплена и доступна (та же природа ошибки, что и в более ранней,
так и не до конца объяснённой находке про `ptrace PEEKDATA FAIL` на
`0x5fffff1000`/`0x5ffff79000` в UMD-FENCE-01 -- вероятно, тот случай
тоже tagged-pointer, а не реальная проблема маппинга; стоит
перепроверить при случае).

Следующий шаг (`UMD-KCPU-04`): найти реальный адрес `vkQueueSubmit`
самого UMD (тем же способом, что и `vkGetFenceStatus` в UMD-FENCE-01 --
через `dladdr()` в самом `vk_exec01`, не предположением), и либо
дизассемблировать его напрямую с самого начала, либо ставить
breakpoint'ы на цепочку реальных `bl`-вызовов внутри него по очереди,
пока не найдётся точка, где UMD решает не готовить `FENCE_SIGNAL`
вообще.

### UMD-KCPU-04: реальный call-trace vkQueueSubmit -- KCPU enqueue не задействован нигде, разрыв концептуальный, не локальный

Найден настоящий `vkQueueSubmit` через `dladdr()` в `vk_exec01`
(`libGLES_mali.so` file offset `0x933120`, не предположением). Вместо
дальнейшего статического гадания реализован **живой call-trace**:
breakpoint на входе функции, затем внутренний (не сетевой,
печатающий только на `BL`/`BLR`) `PTRACE_SINGLESTEP`-цикл до
возврата, декодирующий цель каждого `BL`/`BLR` прямо по машинному
слову инструкции.

Собрано **1267 реальных вызовов** (~40000 инструкций) одного
`vkQueueSubmit()` -- функция не успела вернуться за это окно (внутри
явно есть петля, `933880: b 933180`, обрабатывающая, видимо, несколько
проходов/queue). Среди ВСЕХ 52 уникальных целей вызовов **не
встретилось ни одного** из уже известных KCPU-related адресов:
`0x1c46600`/`0x1c46690`/`0x1c46710` (ioctl-обёртки CREATE/DELETE/
ENQUEUE), `0x1c4d000`/`0x1c4d090` (builder'ы FENCE_SIGNAL/FENCE_WAIT),
`0x1b392f0` (`acquire_slot`). Это третий, полностью независимый метод
(после точечных breakpoint'ов в UMD-KCPU-03), подтверждающий тот же
результат.

По пути в самом начале `vkQueueSubmit` найдена ещё одна развилка:

```asm
933180: ldr  x8, [x0, #272]
93318c: ldr  x0, [x8, #4416]
93319c: cbnz x0, 93378c        ; альтернативный путь, если это поле != 0
```

`0x93378c` ведёт в отдельную ветку с вызовом `1b5e340(...)` и в итоге
зацикливается обратно на `933180` (`933880: b 933180`) -- похоже на
обработку batched/multi-pass submission, а не на fence-specific логику
как таковую; не исследовано глубже (не похоже на прямой кандидат).

### Промежуточный итог всего цикла UMD-KCPU-*

Тремя независимыми методами (статический xref-разбор, точечные live
breakpoint'ы через чистый `ptrace`, и теперь полный call-trace живого
`vkQueueSubmit`) многократно подтверждено: **закрытый Mali UMD в этой
конфигурации никогда не пытается enqueue'ить `BASE_KCPU_COMMAND_TYPE_
FENCE_SIGNAL`** для простого одно-буферного `vkCmdFillBuffer`-submit
-- ни разу, ни с одного из известных путей. Это уже не "не нашли
нужный branch", а воспроизводимый, многократно перепроверенный факт.

Встаёт более фундаментальный вопрос, который стоит явно
переформулировать на следующую сессию: **возможно, исходная посылка
неверна** -- что fence должен сигнализироваться именно через KCPU
`FENCE_SIGNAL`. Реальный Mali UMD может использовать для этого
конкретного, простого случая (без внешнего sync-fd export, без
timeline-семафоров) совершенно другой, более прямой механизм
(например, прямую проверку `CS_EXTRACT`/ring-buffer-состояния из
`vkGetFenceStatus`, минуя KCPU полностью) -- но мы уже знаем из
UMD-FENCE-01, что `vkGetFenceStatus` в нашем случае идёт по ветке
"нет attached sync-fd" и просто читает закэшированный байт, который
никто не пишет. Значит единственный оставшийся кандидат-producer
байта `[fence+0x251]` -- какой-то путь, который мы ещё не нашли, и
он не обязательно связан с KCPU вообще.

Следующий шаг на будущее: не продолжать исчерпывающую ручную
трассировку `vkQueueSubmit` (диминishing returns, функция огромная и
содержит несколько проходов/циклов) -- вместо этого стоит
STATICALLY найти ВСЕ x-ref на сам адрес `fence_handle+0x250+1`-паттерн
(т.е. все места, где вообще пишут байт по смещению `+1` от объекта
такого шейпа, независимо от KCPU), либо поставить live breakpoint не
на "предполагаемый setter", а на сам байт памяти через hardware
watchpoint (`ptrace(PTRACE_POKEUSER)` на debug-регистры ARM64,
`DBGWVR`/`DBGWCR`, либо `perf_event_open(HW_BREAKPOINT_W)`) -- это
поймает ЛЮБОЙ писатель этого конкретного байта, откуда бы он ни
пришёл, без необходимости гадать через какую функцию.

### Полезная деталь для сборки: правильный link recipe для `vk_exec01`/`vk_probe`

Простой `aarch64-linux-gnu-gcc -O0 -o vk_exec01 vk_exec01.c -ldl` линкует
против **glibc** (`interp=/lib/ld-linux-aarch64.so.1`, `NEEDED
libc.so.6`) — такой бинарник не запускается под настоящим bionic
`linker64` устройства ("library libc.so.6 not found"). Рабочий рецепт
(воспроизводит `vk_probe`, `interp=/system/bin/linker64`, `NEEDED
libc.so`/`libdl.so`):

```sh
CRTDIR=/home/mike/android-sdk/ndk/magisk/toolchains/llvm/prebuilt/linux-x86_64/sysroot/usr/lib/aarch64-linux-android/30
STAGING=/home/mike/panthor-backport/vk-libs-staging
aarch64-linux-gnu-gcc -nostdlib -fPIC -pie \
  -Wl,--dynamic-linker=/system/bin/linker64 \
  -Wl,-rpath-link="$STAGING" \
  "$CRTDIR/crtbegin_dynamic.o" vk_exec01.c "$CRTDIR/crtend_android.o" \
  -I "$STAGING/include" -L "$STAGING" -lc -lm -ldl \
  -o vk_exec01
```

`-nostdlib` + настоящие NDK crt-объекты (`crtbegin_dynamic.o`/
`crtend_android.o`, взяты только ради корректного `_start`/`.init_array`
под bionic) + линковка против **настоящих extracted** `libc.so`/
`libm.so`/`libdl.so` в `vk-libs-staging/` (не NDK-заглушек, не glibc).

Важно: не ставить `kretprobe` на `kbase_csf_kcpu_queue_process()` или
другие горячие KCPU scheduler paths. Такой probe уже вызывал softlockup
и реальную перезагрузку устройства; этот путь исключён из дальнейшей
инструментализации.

тогда истолковали как "MCU не квитирует CS-уровень". **Это оказалось
артефактом слишком короткого окна наблюдения**, не реальным
поведением -- см. следующее обновление.

Обновлено в четвёртый раз, 2026-09-16 (полный синтез, тот же день,
существенно позже): официальный (штатный, `CONFIG_DEBUG_FS`,
`kctx_dentry`) debugfs-файл `csf_sync`/`groups`/`kcpu_queues` под
`/sys/kernel/debug/mali0/ctx/<pid>/`, прочитанный через несколько
РЕАЛЬНЫХ секунд после submit (не 10 мс), показывает: `cs_extract`
реально догоняет `cs_insert` (оба `0x100`), KCPU-очередь -- `Pending
Commands: 0`, `Blocked: 0`, `Enqueue err: 0`. И GPU ring, и KCPU
полностью и безошибочно завершают обработку. Ранний вывод про
"MCU не квитирует" был вызван тем, что наш собственный kretprobe
проверял регистры только 10мс после kick -- реальное завершение
(включая связанные с energy-management таймерами задержки, видимые
в firmware trace как `TIMER ELAPSED`) занимает больше времени.
Полный, побайтовый декод самого ring buffer (та же debugfs, плюс
независимая, точная документация CSF ISA) показал: в этом
конкретном, минимальном `vkCmdFillBuffer` command stream **нет ни
одной job-launch инструкции** (`RUN_COMPUTE`/`RUN_FRAGMENT` и т.п.)
-- только `ENDPT` (маска endpoint'ов), 5×`EVADD` (инкремент
event-счётчиков) и один `WAIT` на тот же scoreboard-слот. Единственное
подтверждённое, ещё не закрытое звено на конец сессии -- userspace
notification: внутренний поток настоящего Mali UMD (`mali-event-hand`)
навсегда блокируется в `poll()` на файловых дескрипторах ядра
(`/dev/mali0` eventfd + `malitl` anon_inode), из-за чего ни сам факт
завершения GPU/KCPU работы, ни `VkFence` не долетают обратно до
приложения, и (предположительно) финальная запись в буфер, которую
UMD мог бы выполнять асинхронно после этого уведомления, тоже не
происходит. Подробности -- раздел "Real submit: полный синтез" ниже.

рассчитывать.

## Находка

Устройство (Pixel 7 / Tensor G2) физически подтверждено содержащим
рабочий Mali GPU:

- `/sys/firmware/devicetree/base/mali@28000000/` -- реальный DT-узел с
  полными DVFS/power-таблицами (`gpu_dvfs_table_v1/v2`,
  `gpu_dvfs_governor`, `slc-acpm/gpu_g0_p8` и т.п.) -- GPU физически
  описан прошивкой устройства.
- Текущее ядро (`uname -a`): `6.1.157-android14-11-gbd23337e42e7-
  ab14791245` -- это настоящий Google Android Common Kernel (GKI)
  ветки android14-6.1, собранный тем же billing-процессом, что и
  штатный Pixel 7 (`clang 17.0.2, +pgo +bolt +lto`), не кастомное с
  нуля ядро -- уже подтверждено 118 реальными vendor-модулями (`wifi
  bcmdhd4389`, `pcie_exynos_gs`, `cs40l26` audio и т.д.), загруженными
  на боевом устройстве.
- `zcat /proc/config.gz | grep CONFIG_DRM_PANFROST` -> `is not set`.
  Открытый Mesa-совместимый DRM-драйвер (panfrost -- для более старых
  Bifrost/Midgard GPU) явно выключен в сборке этого ядра. `/dev/dri/
  card0` существует, но это `exynos-drm` -- дисплейный (KMS/scanout)
  драйвер, уже используемый `saai-displayd` (S02/S03) для
  framebuffer -- не 3D/render-нода. Ни `/dev/mali*`, ни `/dev/kgsl*` не
  существует; ни один GPU-модуль (`mali`/`panfrost`/`panthor`) не
  загружен (`lsmod` -- 118 модулей, ни один не совпадает).

Проверены оба возможных пути вперёд:

**1. Проприетарный стек ARM/Google (тот, что стоит в штатном
Android).** Локальные factory-образы (`os/targets/panther/artifacts/
factory/images/`, уже часть toolchain'а сборки) смонтированы read-only
на R620 (не на телефоне -- никакого риска для боевого устройства):
`vendor_dlkm.img` содержит `lib/modules/mali_kbase.ko`,
`mali_pixel.ko` (тот самый узел `mali@28000000`, судя по названию --
Pixel-специфичное расширение над ARM's kbase), `mali_kutf*.ko` --
собраны под ТОЧНО этот же kernel ABI (тот же factory-релиз, что и
загруженное ядро). `vendor.img` содержит полный userspace: `lib64/egl/
libGLES_mali.so`, `lib64/hw/vulkan.mali.so`, `lib64/hw/gralloc.
default.so`, `firmware/mali_csffw-r54p{0,1,2,3}.bin` -- то есть
технически ядро-часть стека физически присутствует и ABI-совместима.
Однако: `strings libGLES_mali.so | grep -i wayland/gbm` -- **пусто**.
Блоб не содержит ни единого упоминания Wayland или GBM платформы --
собран исключительно под Android's EGL_PLATFORM_ANDROID
(ANativeWindow/gralloc HAL/SurfaceFlinger). Чтобы использовать его
вообще, потребовалось бы реализовать существенный слой совместимости
с Android HAL (gralloc mapper, hwbinder-заглушки, ANativeWindow) --
то, что проекты вроде Waydroid делают, запуская ПОЛНЫЙ Android-контейнер
со своим Binder/HAL стеком, а не добавляя одну библиотеку. Несоразмерно
любому spike, и прямо противоречит уже устоявшемуся в проекте
предпочтению минимальных, полностью открытых, аудируемых компонентов
(Alpine пакеты вместо проприетарных блобов везде, где до сих пор был
такой выбор).

**2. Открытый Mesa-стек (panfrost/panthor).** Правильный драйвер для
Mali-G710 (Valhall, второе поколение, CSF/command-stream-frontend) --
`panthor`, вошедший в mainline Linux ядро начиная примерно с 6.10.
Работающее на устройстве ядро -- 6.1.157, GKI-залоченное (Google
фиксирует KMI/ABI для GKI-сборок специально для того, чтобы vendor-
модули оставались совместимыми без пересборки ядра) -- т.е. backport
`panthor` (или даже более старого `panfrost`, который для Valhall/CSF
GPU в принципе не подходит -- рассчитан на предыдущее поколение) через
~9 минорных версий ядра, включая существенно изменившуюся за это время
DRM scheduler/dma-fence инфраструктуру -- многонедельная задача с
неопределённым результатом, не spike-масштаба работа.

Отдельно, независимо от выбора драйвера: Alpine предоставляет
`mesa-dri-gallium` (24.0.9-r1, единая `libgallium_dri.so`, 27 MiB,
включает `llvmpipe` -- чистый CPU-рендеринг без GPU вообще, плюс
зависимость `llvm17-libs`, 136 MiB) -- установлен в тестовый sysroot на
R620 и физически проверен headless через `qemu-aarch64-static` против
уже работающего `saai-displayd`: `libEGL warning: egl: failed to
create dri2 screen` -- EGL's DRI2/Wayland-путь требует
`zwp_linux_dmabuf_v1` от компоситора для обмена буферами, которого
`saai-displayd` не реализует (см. Current state в S08-toolkit-
compatibility.md -- уже задокументированный пробел). То есть даже
чистое CPU-рендеринг (`llvmpipe`) без единого проприетарного байта не
может дойти до экрана через GTK4's EGL-путь без отдельной, довольно
существенной протокольной работы над `saai-displayd` (тот же класс
задачи, что `wl_data_device_manager`/`text-input-v3`, Change 2/3, но
для `linux-dmabuf`).

**Неожиданная находка.** До установки `mesa-dri-gallium` тот же
headless `gtk4-demo` через `qemu-aarch64-static` против того же
`saai-displayd` (Change 4) **успешно** рендерил и коммитил кадр --
`saai-displayd`'s лог подтверждает `commit on surface ..., frame
sha256=926ea70d...` -- то есть плейн Cairo/`wl_shm`-путь (SHM, без
EGL/DRI/GBM/dmabuf вообще) у GTK4 УЖЕ работал в headless-окружении без
единого GPU-компонента. После установки `mesa-dri-gallium` тот же
запуск (без каких-либо других изменений) стал завершаться штатно
(`exit 0`), но **без** коммита кадра -- клиент подключается
(`client connected`, `new xdg_toplevel`, `commit ... (no buffer)`), но
не доходит до финального `commit` с буфером и тихо завершается. Само
присутствие пакета `mesa-dri-gallium` в путях поиска меняет то, какой
рендерер GTK4/GDK выбирает первым, и, судя по всему, делает это в
сторону худшего результата для headless/qemu-случая, а не лучшего.
Причина не расследована дальше (не входит в объём этого spike) --
зафиксировано как предупреждение для Change 7: **не паковать
`mesa-dri-gallium` бездумно "на всякий случай"**, это не бесплатное
добавление.

Раздельно от вопроса GPU: реальный крэш на телефоне (Change 6,
`Unable to create Cairo image surface: invalid value ... for the size
of the input`) **не воспроизводится** в headless/qemu окружении с тем
же `gtk4-demo` и тем же `saai-displayd` (тот же кадр успешно
коммитится). Значит это не общий баг Cairo/Wayland-пути в GTK4 как
таковой, а что-то специфичное для физического запуска через
`saai-appd`'s sandbox (либо отличие в собранном для телефона пакете --
Change 6-тестовый пакет включал только `bin/`+`lib/`, без большей части
`usr/share`/локалей/`etc`, что мог использовать сам GDK при вычислении
размера поверхности,-- либо отличие реального `saai-displayd` на
панели устройства от headless-сборки). Требует отдельного
расследования в рамках Change 7, не блокируется этим ADR.

## Решение

Change 7 нацеливается ТОЛЬКО на software-рендеринг через существующий
`wl_shm`/Cairo-путь GTK4/Qt -- уже подтверждено физически рабочим в
headless-окружении (Change 4, до появления `mesa-dri-gallium` в
sysroot'е). Ни проприетарный Mali-блоб, ни `mesa-dri-gallium`/llvmpipe,
ни backport `panthor` не входят в объём Change 7 -- каждый из них либо
несоразмерно велик (Android HAL shim, backport ядра), либо требует
предварительной протокольной работы над `saai-displayd`
(`zwp_linux_dmabuf_v1`) и при этом не гарантированно лучше уже рабочего
пути (см. находку про регресс с `mesa-dri-gallium`). GPU-ускорение
остаётся открытым, не решённым вопросом -- не закрыто, просто явно вне
объёма текущего спринта; реализуемо в будущем только через открытый
`linux-dmabuf` + либо дождавшись/бэкпортировав `panthor`, либо
переоценив это решение при появлении новой информации (например, более
новое ядро в будущем OTA/сборке).

## Последствия

- Change 7 работает над тем же классом бага, что и упал на телефоне в
  Change 6 (`invalid value ... for the size of the input`), но теперь
  известно, что это НЕ GPU-driver вопрос -- сужает расследование до
  различий между headless/qemu и реальным физическим запуском через
  `saai-appd`'s sandbox, либо до состава самого тестового пакета.
- `saai-displayd` не получает `zwp_linux_dmabuf_v1` в этом спринте --
  явная, не молчаливая граница scope, как и в Change 4 с settings-
  порталом.
- Любое будущее решение упаковать `mesa-dri-gallium` (даже просто ради
  `llvmpipe`) требует отдельной физической проверки на регресс,
  аналогичной той, что обнаружена здесь -- не считать "software GL
  driver есть в пакете" синонимом "рендеринг работает или работает
  лучше".
- Проприетарный Mali/Android-HAL путь остаётся закрытым по архитектурным
  причинам (не лицензионным -- хотя это тоже отдельный, не
  рассмотренный здесь вопрос при использовании factory-блобов),
  задокументирован как сознательно не выбранный, не как "не
  рассматривался".

полная попытка, вплоть до физической загрузки собранных модулей на
реальном устройстве. Итог: три из четырёх собранных модулей грузятся
и работают на реальном ядре без единой ошибки; четвёртый (`panthor.
ko` сам) физически пробует железо и корректно, безопасно отваливается
на первом же шаге -- с точным, не гипотетическим диагнозом, почему.

### Подпись модулей и lockdown -- не стена

`CONFIG_MODULE_SIG_FORCE` не установлен, `CONFIG_SECURITY_LOCKDOWN_LSM`
не установлен -- неподписанные (tainted) модули физически можно
загружать. Это не тот же класс блокировки, что GSA у голоса (ADR-092).

### Точное дерево ядра -- нашлось, но без официального манифеста

`kernel/common` (`android.googlesource.com`) на ветке `android14-6.1-
lts`, коммит `1fd39c9383c2` ("Merge 6.1.157 into android14-6.1-lts"),
даёт SUBLEVEL, побайтово совпадающий с `uname -r` устройства. Но
официального `repo`-манифеста для точной комбинации "Pixel 7 (pantah)
+ ядро 6.1 + брендинг android14" не существует публично -- у pantah
в манифестах 6.1 начинается только с android15. Взято ближайшее
воспроизводимое: общий ACK-коммит с точным номером патч-версии.

### Тулчейн: KCFI-хеши эмпирически подтверждены идентичными

`CONFIG_CFI_CLANG=y`, `CONFIG_CFI_PERMISSIVE` не установлен -- жёсткий
KCFI, неверный компилятор рискует паникой ядра при `insmod`, не просто
ошибкой сборки. Точный внутренний Android-clang (`r487747c`) не нашёлся
публично (вычищен из видимой истории `prebuilts/clang/host/linux-x86`).
Вместо archaeology -- физическая проверка: собран тестовый `.c` с двумя
реальными сигнатурами функций ядра (`generic_file_llseek`,
`simple_attr_read`) через ванильный upstream LLVM 17.0.2 (официальный
релиз с github.com/llvm/llvm-project) с `-fsanitize=kcfi`, и
дизассемблирован результат. Оба embedded type-hash слова оказались
**побитово идентичны** реальным `__kcfi_typeid_*` из настоящего
заводского `.ko` (`0xe61887de`, `0xe866e2f4` -- проверено дважды,
разными сигнатурами). Причина: KCFI-хеш -- чистая функция от
Itanium-mangled сигнатуры типа, вычисляется в стабильной части
Clang'а, не в PGO/BOLT/mlgo-патчах Android-форка. Так что ванильный
LLVM 17.0.2 безопасен для этой конкретной задачи.

### `struct module`'s layout реально зависит от `.config`

Первая попытка `insmod` дала `disagrees about version of symbol
module_layout` даже при точном совпадении `vermagic`-строки (через
`.scmversion`). Причина найдена чтением `include/linux/module.h`:
`CONFIG_DEBUG_INFO_BTF_MODULES` добавляет в `struct module` поля
`btf_data`/`btf_data_size` -- реальное расширение размера структуры.
На устройстве этот конфиг включён (там есть `pahole`); в первой
локальной сборке -- нет (`pahole` не был установлен на R620). Установка
`dwarves`, включение `CONFIG_DEBUG_INFO_BTF_MODULES=y`, полная
пересборка -- разногласие исчезло. Отдельная ловушка по пути: попытка
одновременно синхронизировать `CONFIG_TRIM_UNUSED_KSYMS=y` с пустым
whitelist обрушила `Module.symvers` с 15735 до 1357 записей (пустой
whitelist -- значит "обрезать всё") -- пришлось откатить именно эту
часть, `TRIM_UNUSED_KSYMS` не влияет на `struct module`, значит
безопасно оставить выключенным локально.

### Реальный экспорт символов уже устройства ⊊ то, что есть в исходниках

`CONFIG_TRIM_UNUSED_KSYMS=y` на РЕАЛЬНОМ устройстве (в отличие от
локальной сборки) означает: символ может существовать в коде ядра
(и даже быть `EXPORT_SYMBOL`) и всё равно быть недоступен модулям,
если его нет в кураторском `android/abi_gki_aarch64_pixel` (и
остальных vendor-списках, они уже лежат прямо в дереве исходников).
Проверка ВСЕХ внешних символов всех 4 модулей против объединённого
списка из всех `abi_gki_aarch64_*`-файлов поймала это до, а не во
время `insmod`-цикла -- но `kvrealloc` (сигнатура сменилась ещё и
между версиями ядра, отдельная находка) проскочила при первой
проверке и подтвердилась только реальным `insmod`: `Unknown symbol
kvrealloc`. Итоговый список того, что есть в коде mainline, но не
экспортируется на этом реальном устройстве: `kvrealloc`, `cancel_work`
(есть `cancel_work_sync`), `__drmm_mutex_release` (обвязка
`drmm_mutex_init`), `kmem_cache_alloc_bulk`/`kmem_cache_free_bulk`
(есть поштучные `kmem_cache_alloc`/`_free`). Всё заменено локальными
реализациями через уже доступные примитивы -- не изменения ABI, чисто
обходные пути на уровне вызывающего кода.

### `struct drm_gem_object`'s ABI: BTF -- решающий инструмент

`drm_gpuvm` в mainline ожидает поле `gpuva` прямо в `struct
drm_gem_object`. Проверка через `/sys/kernel/btf/vmlinux` (реально
присутствует на устройстве) и `bpftool btf dump` подтвердила: у
реального ядра этого поля нет. Добавление его в локальную копию
заголовка означало бы рассинхронизацию layout с уже скомпилированным
`vmlinux` -- вместо этого `drm_gpuvm.c`'s 10 точек использования
переведены на отдельную side-table (hashtable по указателю на объект),
общая структура не тронута. Тот же BTF-инструмент -- рекомендуемый
способ проверять подобные вопросы впредь, не гадать.

### Итог: 3 из 4 модулей работают, четвёртый корректно и безопасно отказывает

Собранный бандл (`drm_exec.ko`, `drm_gpuvm.ko`, `gpu-sched.ko` --
принесённый из mainline v6.12 целиком, поскольку `CONFIG_DRM_SCHED` в
реальном ядре вообще не собран, значит риска для существующих
драйверов нет -- и `panthor.ko`, ~13000 строк) физически загружен на
устройство в порядке возрастания риска. `insmod` каждого из первых
трёх дал `exit 0`, ни одной ошибки в `dmesg`, устройство оставалось
полностью отзывчивым. `panthor.ko` тоже загрузился (`exit 0`) -- но
чтобы проверить реальный probe, потребовалось добавить `arm,malit6xx`
(реальный `compatible` GPU-узла устройства, не совпадающий со
штатными `rockchip,rk3588-mali`/`arm,mali-valhall-csf` в mainline) в
`dt_match[]`, локальный, не upstream патч. После этого probe
корректно и безопасно провалился на самом первом шаге:
`devm_clk_get(dev, NULL)` вернул `-ENOENT`, реальный GPU MMIO ни разу
не читался -- потому что devicetree-узел не содержит свойства
`clocks` вообще (только Samsung-проприетарные `gpu0_cmu_cal_id`/
`gpu1_cmu_cal_id`, схема управления частотой/питанием CMU/CAL, не
generic Linux clock framework). Это НЕ провал бэкпорта -- это точный,
физически подтверждённый диагноз следующего реального шага.

## Решение (обновлено)

Открытый `panthor` физически МОЖЕТ быть собран и загружен на этом
устройстве без единой правки в общих подсистемах ядра (`drm_gem.h`,
`drm_sched`, GEM/dma-resv API) -- весь риск был локализован в наших
собственных 4 модулях через side-table и точечные compat-обвязки.
Реальный bring-up GPU (а не просто успешный `insmod`) требует
отдельной, отдельно оцениваемой задачи: переписать
`panthor_device_init()`'s управление частотой/питанием под Samsung's
CMU/CAL API вместо `devm_clk_get`, что само по себе:
(а) не задокументировано публично для Tensor G2/gs201,
(б) требует реверс-инжиниринга либо proprietary kbase's использования
    той же devicetree-схемы,
(в) отдельный, не малый объём работы, сравнимый по духу с этим самым
    бэкпортом, но не бэкпорт кода, а bring-up конкретного SoC.
Рабочее дерево (точный коммит ядра, тулчейн, собранные `.ko`)
сохранено на диске R620 (`/home/mike/panthor-backport/`, ~16 ГБ, вне
git) для продолжения без повторной многочасовой подготовки.

## Финальное уточнение: почему CAL/ACPM-путь закрыт, не просто отложен (2026-09-16)

Продолжая от найденного диагноза (нужен clock/power backend под
Samsung CMU/CAL вместо `devm_clk_get`) -- проверено, дошло ли это до
реального тупика или просто до следующей задачи по объёму сравнимой
с уже сделанной. Ответ: структурный тупик, не вопрос объёма работы.

`clk_exynos_gs.ko` (уже загружен на устройстве) реально экспортирует
`cal_vclk_enable`/`cal_vclk_dfs_set_rate`/`cal_vclk_disable` и
регистрируется как настоящий Linux common-clock-framework provider
(`samsung_clk_of_add_provider`) -- это НЕ полностью непубличная схема,
как казалось изначально. Но: (а) реальный GPU devicetree-узел не
содержит свойства `clocks`, только Samsung-специфичные
`gpu0_cmu_cal_id`/`gpu1_cmu_cal_id` (сырые значения `0x0B040006`/
`0x0B040005`), то есть достучаться до этого клока через штатный
`devm_clk_get()`/devicetree-phandle в принципе нельзя без live
DT-overlay; (б) прямой вызов `cal_vclk_enable()` по этим ID
дизассемблирован (`llvm-objdump` по `clk_exynos_gs.ko`) -- функция
принимает `struct vclk *`, с байтом-тегом типа на смещении `0x1c` и
spinlock-защищённым состоянием на `0x18`/`0x20`, но **ни одна
экспортированная функция не резолвит CAL ID в `struct vclk *`** --
эта таблица приватна внутри модуля. Единственный обходной путь --
`kallsyms_lookup_name()` для поиска этой внутренней таблицы вслепую по
дампу памяти -- но эта функция намеренно не экспортируется ядру с
Linux 5.7+ (подтверждено: отсутствует в `Module.symvers` этого
дерева), именно чтобы внешние модули не могли делать то, что здесь
потребовалось бы. Дальше -- это уже kprobe-обход намеренно
поставленного барьера защиты ядра, тот же класс границы, что GSA
firmware authentication у голоса (ADR-092) -- решено не переходить,
не потому что не получилось бы технически, а потому что это уже не
легитимная инженерная задача, а обход защиты.

### Итоговый статус GPU-направления (устарел -- см. исправление ниже)

- Открытый `panthor`-стек (drm_gpuvm/drm_exec/drm_sched/panthor)
  реально собирается и грузится на этом устройстве -- подтверждено
  физически, не в теории.
- Реальный GPU bring-up (не просто успешный `insmod`) требует clock/

- Это тот же класс закрытия, что проприетарный Mali/Android HAL путь
  выше в этом же ADR -- сознательно не продолженный, а не "не
  рассмотренный".
- Рабочее дерево (`/home/mike/panthor-backport/`) остаётся полезным
  артефактом (панthor реально грузится, полезно для будущих экспериментов
  не требующих реального управления частотой/питанием), но дальнейшее

## Исправление: вывод про архитектурный тупик был неверным (2026-09-16, часы спустя)

Предыдущий раздел ошибался не в методе (дизассемблирование, поиск
`kallsyms_lookup_name` в `Module.symvers` -- всё это было правильно
сделано), а в исходных данных: поиск публичного манифеста для
device-specific части ядра gs201 в прошлый раз ограничился
официальным `android.googlesource.com/kernel/manifest` (там его для
этой комбинации действительно нет). Не был проверен **публичный
GitHub-зеркал реального device-specific дерева** --
`kerneltoast/android_kernel_google_gs201` -- который содержит
`google-modules/soc/gs/drivers/soc/google/cal-if/` с полным исходником
CAL/CMUCAL, включая `cmucal_get_node(unsigned int id)`
(`EXPORT_SYMBOL_GPL`, подтверждено и в исходнике, и живым `nm` на
реальном `.ko` устройства -- `T`, не `t`) -- легальную, публичную,
GPL-лицензированную функцию резолвинга CAL ID в указатель на
CAL-структуру. Никакого обхода защиты ядра не требуется вообще --
предыдущий вывод был построен на неполном поиске, не на реальном
architectural closure.

Расшифровка ID по найденному `cmucal.h`: `gpu0/1_cmu_cal_id`
(`0x0B040006`/`0x0B040005`) -- тип `ACPM_VCLK_TYPE` (`0x0B040000`),
т.е. управление реально идёт через ACPM-мейлбокс, не голый регистр.
Но у GPU оказался и отдельный, куда более простой стандартный
Linux-клок: `GATE_GPU` (числовой ID `350` = `CLK_G3D_BASE(350)+0`,
публично задокументирован в `google-modules/soc/gs/include/
dt-bindings/clock/gs201.h`), зарегистрированный настоящим
common-clock-framework провайдером (`drivers/clk/gs/clk-gs201.c`,
`compatible = "samsung,gs201-clock"`) -- этот узел РЕАЛЬНО существует
в devicetree устройства (`clock-controller@1e080000`, `#clock-cells =
<1>`), просто без связи с GPU-узлом через `clocks=`. Написан
`panthor_compat_get_gpu_clk()` -- вручную собирает `of_phandle_args`
против этого узла с ID `350` и резолвит через штатный, экспортированный
`of_clk_get_from_provider()` (не CAL API напрямую, не хаки).

### Физический результат после этого исправления

С этим одним фиксом (плюс обход `devfreq`/regulator'а -- аналогичная
история: `operating-points-v2`/`regulator-name` тоже нет в devicetree,
DVFS у Samsung через свои `gpu_dvfs_table_v1/v2`; `panthor_devfreq_
init()` просто возвращает 0 сразу после аллокации, все вызывающие
места уже сами проверяют `pdevfreq->devfreq == NULL`) -- **probe
дошёл до реального MMIO-чтения настоящего железа**:

```
panthor 28000000.mali: [drm] mali-unknown id 0xa862 major 0x0 minor 0x0 status 0x4
panthor 28000000.mali: [drm] Features: L2:0x8130306 Tiler:0x809 Mem:0x301 MMU:0x2830 AS:0xff
panthor 28000000.mali: [drm] shader_present=0x1110055 l2_present=0x1 tiler_present=0x1
```

Это настоящая, физическая конфигурация Mali-G710 в Tensor G2, прочитанная
напрямую по MMIO -- не теория, не эмуляция. "mali-unknown" -- просто
этот product ID ещё не в таблице моделей mainline panthor, косметика,
не блокер. Дальше упёрлись в рассинхрон имён IRQ (devicetree --
`GPU`/`JOB`/`MMU` заглавными, panthor -- строчными; три
однострочных фикса), и в итоге -- в настоящую, другого типа стену:
`request_firmware()` для `arm/mali/arch10.8/mali_csffw.bin` возвращает
`-2` (файла физически нет -- у устройства только проприетарная
kbase-прошивка, другой формат/протокол). Это не рассинхрон
именования, это другой бинарный протокол -- честно открытый вопрос,
не проверенный дальше в рамках этой сессии.

Устройство оставалось полностью стабильным на каждом шаге, включая
финальный отказ по прошивке -- чистый, штатный `probe failed with
error -2`, без единого сбоя.

сторонние зеркала реального дерева). Стоит держать в голове для
будущих похожих ситуаций: "не нашёл в одном официальном источнике" --
не то же самое, что "не существует публично".

## Дальше: реальная прошивка есть в формате panthor, но MCU не загружается (2026-09-16, продолжение)

По просьбе "сделать всё возможное" для графики -- пошли дальше
диагноза "нет файла прошивки" и попробовали реально её получить.

### Формат прошивки СОВПАДАЕТ -- проверено побайтово

`panthor_fw.c`'s заголовок ожидает magic `0xc3f13a6e`. Реальные
проприетарные файлы устройства (`/vendor/firmware/mali_csffw-r54p{0,1,
2,3}.bin`, `mali_csffw-legacy-r56p0.bin` -- все по ~280 КБ, не
десятки МБ) начинаются именно с этих байт (`6e 3a f1 c3`), с
`major=0` (проходит panthor'а собственную проверку
`CSF_FW_BINARY_HEADER_MAJOR_MAX=0`). ARM использует один и тот же
контейнерный формат прошивки CSF и для kbase, и для panthor -- не
два разных протокола, как предполагалось раньше.

Скопировали `mali_csffw-r54p3.bin` под ожидаемым panthor именем в
`/vendor/firmware/arm/mali/arch10.8/mali_csffw.bin` (через
`/data/saaios/firmware/...` + symlink, тот же паттерн, что уже
использован для AoC в ADR-092). Результат -- **прошивка прошла
валидацию заголовка и загрузилась**, и GPU **реально начал
исполнение**: `Unhandled Page fault in AS0 at VA 0x0` пришёл от
собственного MMU GPU (`PERM_FAULT_3`, `WRITE`) -- то есть загруженный
код физически выполнялся на командном процессоре Mali G710, не
просто лежал в памяти. `r54p0`/`legacy-r56p0` дают другую картину
(без page fault, просто таймаут) -- разные ревизии ведут себя
по-разному, но ни одна не завершает загрузку MCU
(`Failed to boot MCU (status=fatal)`, `probe failed with error -110`).

### Систематически исключены четыре гипотезы (не догадками, физическим и исходным сравнением)

Дополнительно нашли реальный, открытый (GPL) исходник kbase именно
для этого чипа -- `google-modules/gpu/borr_mali_kbase/` в том же
`kerneltoast/android_kernel_google_gs201` зеркале ("borr" -- кодовое
имя варианта Mali в Tensor G2). Сравнили пошагово с `panthor_fw.c`/
`panthor_mmu.c`:

1. **Таблица записей прошивки** -- распарсили реальный файл байт в
   байт (Python-скрипт по алгоритму `panthor_fw_load`): единственные
   ОБЯЗАТЕЛЬНЫЕ записи -- 8 штук типа 0 (IFACE), которые panthor
   полностью реализует. Все типы, которые panthor не знает (5,6,7,8,9,
   включая `PAGE_FAULT_CNT`), помечены `optional=true` в самом файле --
   их пропуск panthor'ом корректен, не баг.
2. **Layout структуры IFACE-записи** -- `flags`/`va.start`/`va.end`/
   `data.start`/`data.end`, по 4 байта каждое -- побайтово идентичен
   `parse_memory_setup_entry()` в kbase.
3. **Порядок инициализации clock/L2** -- `clk_prepare_enable()` вызывается
   до `panthor_gpu_init()`, что уже подтверждено рабочим (реальные
   регистры GPU_ID/Features читаются успешно) -- совпадает с
   kbase'вским `kbase_pm_wait_for_l2_powered()` перед загрузкой прошивки.
4. **DMA-когерентность MMU** (`pgtbl_cfg.coherent_walk`) -- ни
   `dma-coherent`, ни `system-coherency` в devicetree нет; и panthor
   (`device_get_dma_attr`), и kbase (`of_dma_is_coherent` +
   `system-coherency` override) сошлись бы на "не когерентно" одинаково.
5. **DT-based firmware quirks** (`quirks-ext`/`quirks_ext`, отдельный
   механизм в kbase для передачи прошивке аппаратных workaround'ов) --
   свойства нет в реальном devicetree, значит и это не применимо здесь.

Ни одна из этих пяти проверок не выявила расхождения -- значит
реальная причина лежит глубже: в самой конструкции MMU-таблиц
страниц (`io_pgtable`/ARM LPAE формат) или в порядке/содержимом
регистровых операций AS0, которые kbase выполняет, а panthor'у
неизвестны (в исходнике `panthor_mmu.c`/kbase'вском MMU backend'е,
~2700+ строк с каждой стороны) -- либо в недокументированном
Tensor-специфичном аппаратном нюансе, которого нет даже в этом
открытом зеркале kbase. Дальнейшее продвижение без трассировки
регистров в реальном времени (недоступно на этой ОС) means genuinely
open-ended reverse engineering, не directed debugging.

### Итог по-настоящему

- Формат прошивки CSF -- ОБЩИЙ между kbase и panthor, подтверждено
  физически. Это открытие само по себе ценно для любой будущей
  попытки.
- GPU реально выполняет загруженный код (MMU page fault -- прямое тому
  доказательство), т.е. probe дошёл до самого сердца аппаратного
  bring-up, а не остановился на периферийных проверках.
- Оставшийся разрыв точно локализован (AS0/MMU page table setup для
  прошивки, либо недокументированный аппаратный нюанс), но не решён --
  честно открытый вопрос, не тупик и не "не пытались".
- Устройство оставалось полностью стабильным на каждом шаге всей этой
  сессии (13.5+ часов uptime без единого сбоя к моменту завершения).

## MCU boot -- поведение недетерминировано между попытками (2026-09-16, ещё позже)

По наводке "может, экран должен быть включён" -- проверили гипотезу
про состояние дисплея (`self_refresh_active`, наша же находка из
ADR-093/HIA-15) как возможный фактор. Прямого подтверждения не
нашли, но по пути обнаружили нечто более фундаментальное: **результат
`panthor_fw_start()`'s попытки загрузки MCU меняется от попытки к
попытке на одном и том же файле прошивки, без видимых изменений
кода**:

1. Первая попытка (после серии предыдущих `insmod`/`rmmod` в течение
   долгого uptime): `WRITE` `PERM_FAULT_3` по `VA=0x0`.
2. Вторая (сразу следом, экран активен по утверждению): `READ`
   `TRANSLATION_FAULT_3` по `VA=0x02040000` -- другой адрес, другой
   тип ошибки.
3. Третья: вообще без fault, просто `status=fatal` по таймауту.
4. После **настоящей полной перезагрузки устройства** (`reboot -f` --
   первая же `reboot` без `-f` оказалась no-op на этой ОС, ничего не
   перезагрузила, хотя команда и не выдала ошибки -- сама по себе
   находка, требующая отдельного разбора в другой раз) и с активным,
   разблокированным экраном: **`status=enabled`** -- MCU реально
   продвинулся дальше по своей внутренней state machine
   (DISABLED→ENABLED→...), не свалился в FATAL, просто не успел
   просигналить о полной загрузке за 1 секунду. Единственный раз
   за всю сессию, когда `status` был НЕ `fatal`.
5. Увеличили таймаут `wait_event_timeout` в `panthor_fw_start()` с
   1000мс до 5000мс, тут же повторили (тот же чистый boot, экран
   всё ещё активен) -- **вернулось к `status=fatal`**.

Это означает: поведение реально недетерминировано между попытками,
не фиксированный логический баг (который давал бы одинаковый исход
каждый раз на одном и том же коде/файле). Гипотеза про экран не
подтвердилась однозначно -- `self_refresh_active=1` наблюдался почти
при всех попытках независимо от исхода, включая единственную "лучшую"
(`status=enabled`). Более вероятные объяснения: race condition в
последовательности инициализации самого panthor (что-то, что иногда
успевает завершиться до триггера `MCU_CONTROL_AUTO`, а иногда нет),
либо пограничная по времени аппаратная совместимость (MCU этого
конкретного SoC достоверно медленнее reference-платформ, для которых
таймауты panthor'а изначально калибровались). Раскрутить точную
причину race'а потребовало бы множества контролируемых повторов с
измерением таймингов или живой трассировки регистров -- ни то, ни
другое не сделано в рамках этой сессии.

Устройство осталось полностью стабильным через все эти попытки,
включая настоящую перезагрузку -- ни одного зависания или паники ни
разу.

## Уточнение: отказ MCU надёжно воспроизводится, варьируется только симптом (2026-09-16, финал)

Проверили ещё две конкретные вещи по итогам находок выше.

**Собственный UI-стек не влияет.** Остановили `saai-shell`/
`saai-displayd` (через штатный механизм этого же проекта -- 6 быстрых
`kill` за 60 секунд исчерпывают `UI_RESTART_BUDGET`, `native-init.c`
сам переключается на лёгкий `drm-splash`, не пришлось ничего ломать
вручную) и повторили тест в почти пустой системе -- результат тот же
`status=fatal`. WiFi (`wlan0`) сознательно не трогали -- это
единственный канал удалённого доступа к устройству в этой сессии,
его отключение оборвало бы саму возможность продолжать тестировать.

**Три попытки подряд сразу после настоящей перезагрузки -- все три
`fatal`, синхронно, без единого fault.** С увеличенным до 5с
таймаутом все три попытки дошли до `Failed to boot MCU (status=fatal)`
ровно через ~5.03-5.05 секунд после старта прошивки, без единого
`Page fault` в логе ни разу. Это меняет интерпретацию более ранней
серии из четырёх разных исходов: отказ MCU, похоже, **надёжный и
детерминированный** (всегда в итоге fatal), а варьируется только
ТОЧНЫЙ побочный симптом по пути (иногда GPU успевает засветить page
fault до того, как MCU окончательно перейдёт в fatal, иногда нет --
гонка в том, когда именно прерывание фиксируется/логируется, не в
том, удастся ли загрузка). Наблюдавшийся один раз `status=enabled`
(вместо `fatal`) при коротком 1-секундном таймауте, по всей видимости,
был просто снимком MCU в процессе перехода в fatal, а не настоящим
частичным успехом.

Итог: гипотеза про состояние экрана/self-refresh не подтвердилась --
результат одинаков что с активным экраном, что с остановленным нашим
UI, что сразу после чистой перезагрузки. Настоящая причина остаётся
там же, где и была локализована раньше (MMU/AS0 page table setup
или недокументированный аппаратный нюанс), но теперь известно
жёстче: это стабильный, воспроизводимый отказ, не редкая гонка,
которую можно было бы поймать удачным стечением условий среды.

## Настоящая регистровая трассировка -- проблема внутри самой прошивки MCU (2026-09-16, ещё позже)

По запросу создать трассировку -- на этой ОС нет внешних инструментов
(JTAG, логический анализатор), но есть `ftrace`, и есть полный
собственный исходник бэкпорта. Инструментировали сами макросы
`gpu_write`/`gpu_read` (`panthor_regs.h`) вызовом `trace_printk()` --
каждое обращение к регистру GPU теперь пишется в кольцевой буфер
ftrace с именем вызывающей функции, адресом и значением. Пересобрали,
включили `tracing_on`, прогнали попытку `insmod`, выключили трассировку
сразу после отказа, скачали `/sys/kernel/debug/tracing/trace` целиком
(91 запись, вся попытка от начала до конца). Сохранено в
`panthor-external/mcu-boot-regtrace.txt`.

Трасса читается однозначно:

1. `panthor_gpu_init_info` -- 23 чтения (GPU_ID, Features, shader/l2/
   tiler_present и т.д.) -- то же самое, что мы уже видели в `dmesg`,
   теперь с точными адресами регистров.
2. IRQ unmask (`panthor_gpu_irq_resume`/`panthor_mmu_irq_resume`/
   `panthor_job_irq_resume`) -- штатно.
3. `panthor_gpu_block_power_on`: `W 0x1a0=0x1` -- включение силового
   домена шейдеров/тайлера.
4. `lock_region`/`write_cmd` -- flush-перед-настройкой AS0, штатная
   TLB-инвалидация.
5. `panthor_mmu_as_enable`: `TRANSTAB=0xa0320000`, `MEMATTR=
   0x9c4c9f4c/0x9f9f9f9f`, `TRANSCFG=0x420001c6` -- реальная
   конфигурация MMU AS0 для прошивки. Флаги в исходнике (`AS_TRANSCFG_
   PTW_MEMATTR_WB`, `AS_TRANSCFG_PTW_RA`, `AS_TRANSCFG_ADRMODE_
   AARCH64_4K`) побитово совпадают по смыслу с тем, что kbase
   выставляет (`AS_TRANSCFG_PTW_MEMATTR_WRITE_BACK` и аналоги) --
   сверено по исходнику `mali_kbase_mmu_hw_direct.c`, не по угадыванию.
6. `panthor_fw_start`: `W 0x700=0x2` (`MCU_CONTROL_AUTO`) -- триггер
   запуска.
7. **Дальше -- 5.12 секунды (наш увеличенный таймаут) АБСОЛЮТНОЙ
   тишины на шине регистров.** Ни одного `gpu_write`/`gpu_read` со
   стороны драйвера -- он корректно ждёт прерывания
   (`wait_event_timeout`), не поллит.
8. После истечения таймаута: `panthor_fw_start: R 0x100c=0x0`
   (`JOB_INT_STAT` -- прерывания не было вообще, ни разу за все 5
   секунд) и `R 0x704=0x3` (`MCU_STATUS` = FATAL).

Это не подтверждает и не опровергает конкретную гипотезу про
MEMATTR/TRANSCFG -- значения выглядят структурно правильными
(нужные флаги на месте) -- но даёт куда более точную локализацию:
**после того, как MCU_CONTROL был записан, MCU не подаёт вообще
никаких признаков жизни через прерывания в течение всего окна
ожидания, и заканчивает во внутреннем состоянии FATAL сам, без
дополнительных действий со стороны драйвера.** Значит проблема
находится либо (а) в самих байтах конфигурации AS0 (MEMATTR/TRANSCFG),
для окончательной проверки которых нужно посчитать, что именно
вычислил бы kbase для тех же входных `va_bits`/`pa_bits`/coherent на
этом железе, и сравнить бит в бит -- не сделано (риск арифметической
ошибки при ручном подсчёте без возможности перепроверить на живом
kbase), либо (б) в самой прошивке/GPU при попытке выполнить свой
собственный код запуска, что уже за пределами того, что видно на
уровне регистров хоста.

Трассировочная инфраструктура (инструментированные `gpu_write`/
`gpu_read`) остаётся в `panthor-external/panthor/panthor_regs.h` --
готова для повторного использования при следующей попытке.


## Проверенная и отклонённая гипотеза: два power domain "top"/"cores" (2026-09-16, ещё позже)

Пользователь прислал развёрнутый технический разбор (со ссылками на
android.googlesource.com) с предложением перейти на проприетарный
`mali_kbase.ko`. Пока не переключались на эту стратегию, но по ходу
чтения открытого исходника реального kbase для этого чипа
(`google-modules/gpu/borr_mali_kbase/platform/pixel/pixel_gpu_power.c`)
нашлась конкретная, ранее упущенная зацепка для ТЕКУЩЕЙ проблемы
(MCU molчит и уходит в fatal): у реального devicetree-узла GPU есть
`power-domain-names = "top", "cores"` -- то есть ДВА именованных
power domain, а `panthor_device.c` в апстриме вообще никогда не
вызывает никакой функции привязки power domain (при этом
`<linux/pm_domain.h>` включён, но не используется) -- Linux
автоматически привязывает только ОДИН домен для platform-устройства.
Гипотеза: "top" (шина регистров) привязан неявно -- этим объясняется,
почему чтение GPU_ID/Features и запись MCU_CONTROL работают -- а
"cores" (вероятно, сами шейдеры/MCU) никогда не включается, что
идеально объясняет "AS0 настроен, запись прошла, дальше тишина".

Реализация заняла две итерации:

1. Первая попытка (`dev_pm_domain_attach_list()`, есть в исходнике
   этого ядра) собралась чисто, но на реальном устройстве `insmod`
   упал: `Unknown symbol dev_pm_domain_attach_list (err -2)` -- функция
   не экспортирована на этом устройстве (`CONFIG_TRIM_UNUSED_KSYMS`,
   тот же класс проблемы, что раньше с `kvrealloc` и другими).
2. Нашли правильную, разрешённую функцию -- `dev_pm_domain_attach_by_name()`,
   подтверждена и в `android/abi_gki_aarch64_pixel` (строка 514), и
   через `grep -w ... /proc/kallsyms` на самом устройстве (`T`).
   Точный эталон -- в том же реальном исходнике kbase,
   `gpu_pm_init()`: цикл `dev_pm_domain_attach_by_name(kbdev->dev,
   {"top","cores"}[i])` + `device_link_add(..., DL_FLAG_STATELESS)`.
   Переписали `panthor_compat_attach_power_domains()` по этому образцу
   -- пересобралось, `insmod` прошёл без ошибок про unknown symbol.

Проверка через `/sys/kernel/debug/pm_genpd/pm_genpd_summary`
подтвердила: оба домена реально привязались как потребители
`28000000.mali` (`pd-g3d`="top", `pd-embedded_g3d`="cores" -- те же
имена, что были в присланном пользователем разборе), но оба
показывали статус `off`/`suspended`. `dev_pm_domain_attach_by_name()`
только создаёт связь, а не включает домен -- нужен явный
`pm_runtime_get_sync()` на КАЖДОМ возвращённом виртуальном устройстве
домена (не на самом GPU-устройстве). Добавили `pm_runtime_enable()` +
`pm_runtime_get_sync()` в цикл привязки.

После этого `pm_genpd_summary` показал оба домена `on`/`active` --
подтверждено на полностью чистой перезагрузке (без остаточного
состояния от предыдущих `insmod`/`rmmod`, которые не отвязывают
domain -- второй `insmod` в той же сессии без ребута закономерно
поймал `-EEXIST` на повторной привязке, это отдельно диагностировано
и не спутано с реальным результатом).

**Итог решающего чистого прогона: домены реально включены (`on`/
`active` в `pm_genpd_summary`), прошивка на месте, и MCU всё равно
уходит в `fatal` ровно через 5.04с (наш увеличенный таймаут) -- то же
самое поведение, что и без привязки доменов вообще.** Гипотеза о
недостающих power domain была весьма обоснованной (подтверждена
структурой реального devicetree и точным эталонным кодом из открытого
kbase), но экспериментально отклонена: включение обоих доменов не
меняет исход. Код привязки оставлен в дереве (физически корректен и,
возможно, всё равно нужен для дальнейшей работы -- отключение GPU не
может быть лишним), но проблему не решает.

(Мелкая, не мешающая работе заметка: `pm_runtime_enable()` на
возвращённом domain-устройстве выдаёт `Unbalanced pm_runtime_enable!`
-- похоже, `dev_pm_domain_attach_by_name()` уже включает runtime PM
сам; не мешает работе, не исследовано глубже, т.к. не влияет на
решающий результат.)

Это заметно сужает круг оставшихся объяснений: дело не в питании (оба
домена доказано включены), не в прошивке (формат и байты
проверены побайтово), не в порядке настройки AS0/MCU_CONTROL
(совпадает по структуре с kbase). Остаётся либо (а) тонкая ошибка в
конкретных битах MEMATTR/TRANSCFG, которую пока нельзя перепроверить
без живого kbase-запуска рядом, либо (b) что-то ещё в реальной,
проприетарной последовательности запуска (например ACPM/CAL-уровневая
инициализация тактовой частоты и/или AGT-таймера, которую делает
Samsung/Google платформенный код kbase и которую наш бэкпорт в
принципе не воспроизводит, т.к. она не идёт через стандартный clk
framework), либо (c) сама MCU-прошивка ожидает что-то специфичное для
`kbase`, чего `panthor`, будучи независимой реализацией CSF-протокола,
не делает и структурно не может знать без документации.

## Диагностика реальным kbase вместо гадания в panthor (2026-09-16, ещё позже)

Пользователь прислал развёрнутый разбор с предложением перейти на
проприетарный `mali_kbase.ko`/`mali_pixel.ko`. Вместо использования
непроверенных прекомпилированных `.ko` под конкретную сборку
(`CP2A.260705.006`), нашли, что в уже используемом зеркале
(`kerneltoast/android_kernel_google_gs201`) лежит РЕАЛЬНЫЙ, ОТКРЫТЫЙ
(GPL) исходник `mali_kbase` и `mali_pixel` для этого же чипа --
собрали их из исходников тем же тулчейном (clang-17.0.2), что и
panthor, вместо гадания дальше над битами TRANSCFG в собственном
бэкпорте. Цель: диагностика, а не смена архитектуры -- понять, где
именно проблема (в нашем бэкпорте panthor или глубже в железе/прошивке).

Сборка оказалась заметно сложнее panthor (полноценный Android-специфичный
многомодульный build (kbase зависит от `mali_pixel` через
`Module.symvers`, оба -- от `google-modules/soc/gs/Makefile.include`),
рассчитанный на реальную оркестровку Bazel/`build_utils.sh`, которой у
нас нет). Прошли через десяток мелких, реальных несоответствий в этом
конкретном срезе исходников (не выдумки, а факты, каждое проверено):

- `Makefile.include` подключается через `$(KDIR)/../private/...` --
  сделали симлинки (`kernel-src/common/google-modules` и
  `kernel-src/private` на корень зеркала), чтобы это резолвилось без
  правки самого кода.
- Часть `-I`/`ccflags-y`, которые в реальной сборке добавляются глобально
  оркестровкой сборки (а не самими Kbuild-файлами), пришлось добавить
  вручную в `mali_pixel/Kbuild` и `borr_mali_kbase/Kbuild`
  (`soc/gs/include`, `power/mitigation`).
- `KBUILD_EXTRA_SYMBOLS` в обоих Makefile ссылается на несуществующие
  `$(OUT_DIR)/../private/...` пути -- переопределили на реальный путь
  к уже собранному `mali_pixel/Module.symvers` (для `soc/gs` и
  `power/mitigation` просто нет -- эти модули не собираем).
- `__ANDROID_COMMON_KERNEL__` не определён в нашей сборке -- часть
  compat-кода в `version_compat_defs.h` (`vm_flags_set`/`clear`)
  завязана именно на этот макрос, а не только на версию ядра --
  добавили `-D__ANDROID_COMMON_KERNEL__`.
- Несколько мест с несогласованностью между `.c` и `.h` в этом
  конкретном срезе исходника (не выдумка -- каждое подтверждено):
  `MIN`/`MAX` переопределены без `#ifndef` (в этом ядре
  `linux/minmax.h` уже их даёт); `check_padding_KBASE_IOCTL_CINSTR_GWT_DUMP`
  использует JM-only union без `#if !MALI_USE_CSF`;
  `kbase_backend_get_cycle_cnt()` читает `kbdev->last_cycle_count`,
  которого нет в структуре при `MALI_USE_CSF`; `kbase_hwaccess_pm_powerup()`
  использует необъявленную `irq_flags`; `mali_kbase_pm_driver.c` вызывает
  `trace_mali_pm_mcu_state()`/`trace_mali_pm_l2_state()` без
  `#include <mali_linux_trace.h>`; `BASEP_MEM_FIRST_FREE_FLAG` для CSF
  (бит 61) не согласован с `BASEP_MEM_FLAGS_NR_BITS=4` из uapi-заголовка
  (должен быть бит 59, как у JM) -- поправили под этот инвариант.
- `CONFIG_GOOGLE_BCL` жёстко прописан как всегда включённый в самом
  Kbuild (не наша настройка) -- вызывает `google_retrieve_bcl_handle()`/
  `google_init_gpu_ratio()` из `google-modules/power/mitigation`,
  которую не собираем. Добавили локальный stub-файл
  (`pixel_gpu_bcl_stub.c`) в сборку kbase.
- `CONFIG_MALI_PIXEL_GPU_SLC=y` тянет `pt_client_register()` (Samsung
  SLC/партиции кэша) -- падает с `-ENOSYS`, что раньше валило весь
  probe `physical-memory-group-manager` целиком; сделали ошибку не
  фатальной (SLC -- оптимизация кэша, не нужна для диагностики).

Итог сборки: **`mali_kbase.ko` и `mali_pixel.ko` полностью собрались
и слинковались из настоящего, официального, открытого исходника этого
чипа.** Первая попытка `insmod` тихо зависла в вечном
`-EPROBE_DEFER` -- драйвер не логирует ничего для отложенного probe,
а сам `kbase_platform_device_probe()` в первой же строке делает
`if (!google_retrieve_bcl_handle()) return -EPROBE_DEFER;` -- наша
заглушка возвращала `NULL`. Проверили все места использования этого
указателя во всём дереве -- нигде не разыменовывается, только
передаётся дальше в такие же заглушки -- поэтому заменили заглушку на
возврат валидного ненулевого фиктивного указателя. Это разблокировало
probe.

**Реальный kbase дошёл заметно дальше, чем можно было ожидать, и упал
на содержательной, понятной причине:**

```
mali 28000000.mali: Kernel DDK version r51p0-00eac0
mali 28000000.mali: using synchronous suspend for TOP domain
mali 28000000.mali: Failed to find GPU power domain 'pd-embedded_g3d'
mali 28000000.mali: PM init failed error = -19
```

Это НЕ тот же механизм привязки power domain, который проверяли и
отклонили в прошлом разделе (`dev_pm_domain_attach_by_name()` для
`"top"`/`"cores"` через стандартный Linux genpd, который в реальном
kbase тоже присутствует и, судя по логам, успешно отработал). Ошибка
-- из СОВЕРШЕННО ОТДЕЛЬНОГО, Samsung-специфичного пути в том же
`platform/pixel/pixel_gpu_power.c`: `pc->pm.domain =
exynos_pd_lookup_name(g3d_power_domain_name)`, где `g3d_power_domain_name`
берётся из devicetree-свойства `g3d_genpd_name`, а
`exynos_pd_lookup_name()` -- функция из ОТДЕЛЬНОГО модуля
`google-modules/soc/gs/drivers/soc/google/exynos-pd.c`, компилируемого
только при `CONFIG_EXYNOS_PMU_IF`. У нас этот конфиг не включён (и сам
модуль не собран) -- поэтому вызов буквально не компилируется
(`#if IS_ENABLED(...)`), `pc->pm.domain` остаётся `NULL`, и код
корректно репортит "не найден" -- не потому что домена нет физически
(он есть, подтверждено ранее через `pm_genpd_summary`), а потому что мы
не собрали Samsung-специфичный уровень поиска домена по имени поверх
стандартного genpd.

Исходник `exynos-pd.c` у нас есть (тот же паблик-зеркало), но это
отдельная, объёмная SoC-подсистема (`google-modules/soc/gs/drivers/soc/google/`:
`cal-if`, `exynos-pmu-if`, `exynos-pd`, вероятно `exynos-pm` и другие,
судя по `Kbuild` с `obj-$(CONFIG_...)` на добрый десяток модулей) --
по объёму сравнимая с уже проделанной работой по kbase, а не
"ещё один маленький stub". Решили сделать паузу на этом чекпоинте,
а не продолжать нарастающий ком зависимостей без подтверждения, что
это стоит продолжать.

**Ключевой вывод: и открытый бэкпорт panthor, и настоящий, официальный,
открытый kbase от Google для этого же железа независимо друг от друга
упираются в тему power domain "top"/"cores" -- но на РАЗНЫХ уровнях**
(panthor -- полностью решил вопрос привязки через стандартный Linux
genpd, но MCU всё равно не подаёт признаков жизни; kbase -- падает
раньше, на Samsung-специфичном слое поиска домена по имени, ещё до
попытки включить что-либо). Это не противоречие, а два независимых,
взаимно подтверждающих друг друга наблюдения о том, что штатная
Google-конфигурация питания GPU на этом SoC устроена сложнее, чем
голый Linux genpd -- нужен ещё и Samsung-специфичный уровень
(`exynos-pd`/`cal-if`/ACPM), который ни panthor, ни наша текущая
сборка kbase не реализуют.

## Догнали exynos_pd_lookup_name до конкретной, локализованной точки отказа (2026-09-16, ещё позже)

Пользователь подтвердил: собрать недостающий Samsung-уровень. Прежде
чем собирать `google-modules/soc/gs/drivers/soc/google/` целиком
(десятки поддиректорий -- phy, pinctrl, PCIe, iommu, ufs, thermal и
т.д., по объёму сравнимо с whole-device kernel), проверили реальное
устройство напрямую: **`exynos_pd.ko` и `exynos_pmu_if.ko` уже
загружены штатной прошивкой Android** (`lsmod` подтверждает,
`exynos_pd_lookup_name`/`exynos_pmu_read` -- оба `T` в
`/proc/kallsyms`). Собирать эти модули самим не нужно вообще -- нужно
было только заставить kbase их РЕАЛЬНО ВЫЗЫВАТЬ (флаг
`CONFIG_EXYNOS_PMU_IF` не был включён при компиляции, поэтому весь
`#if IS_ENABLED(...)` блок с вызовом просто не компилировался).

Добавили `-DCONFIG_EXYNOS_PMU_IF=1 -DCONFIG_SOC_GS201=1` (второй
понадобился для `#error "Unknown CONFIG_SOC"` в
`exynos-pmu-if.h`). На этапе линковки modpost предсказуемо не нашёл
`exynos_pmu_read` в наших локальных `Module.symvers` (она не наша,
а из уже загруженного модуля) -- понизили это через
`KBUILD_MODPOST_WARN=1` до предупреждения: настоящее разрешение
символа происходит в момент `insmod` на устройстве против уже
загруженных модулей, а не на этапе сборки.

Пересобранный `mali_kbase.ko` теперь ДЕЙСТВИТЕЛЬНО вызывает
`exynos_pd_lookup_name("pd-embedded_g3d")` (значение взято из
DT-свойства `g3d_genpd_name`, подтверждено напрямую через
`/sys/.../of_node/g3d_genpd_name`). Результат тот же: `NULL`,
`PM init failed error = -19`.

Разобрали механизм `exynos_pd_lookup_name()` по исходнику (тот же
паблик-зеркало): она перебирает **только** devicetree-узлы с
`compatible = "samsung,exynos-pd"`, для каждого доступного
(`of_device_is_available`) берёт связанный `platform_device`, читает
`pd = platform_get_drvdata(pdev)` и сравнивает `pd->name` со строкой
через `strcmp`. Проверили на реальном устройстве все предусловия этого
цикла для обоих доменов:

- `compatible` обоих узлов (`18061e00.pd-g3d`, `18062000.pd-embedded_g3d`)
  -- ровно `"samsung,exynos-pd"` (совпадает).
- `status` обоих узлов -- `okay` (доступны).
- Оба узла реально привязаны к драйверу `exynos-pd`
  (`/sys/.../driver -> .../drivers/exynos-pd`), то есть `platform_get_drvdata()`
  должен вернуть валидный указатель, а не `NULL` (иначе `pd->name`
  тут же дал бы NULL-разыменование и панику ядра, чего не произошло).

Итог: по всем внешне проверяемым признакам (compatible, status,
привязка драйвера, реальное имя genpd-домена по `pm_genpd_summary`)
лукап должен был сработать -- но не сработал. Единственное оставшееся
объяснение -- внутреннее поле `pd->name`, которое **реальный,
проприетарный** `exynos_pd.ko` на этом устройстве (не наша публичная
копия исходника, а фактическая vendor-сборка) заполняет при своём
собственном probe из какого-то отличающегося источника (не совпадает
с тем, что мы предполагаем по аналогии с открытым исходником этой же
функции). Проверить это дальше можно только заглянув внутрь уже
загруженного бинарника (например, kprobe на `exynos_pd_lookup_name`,
чтобы залогировать реальные значения `pd->name` при переборе) --
принципиально другой уровень вмешательства (отладочная интроспекция
уже работающего, реального, проприетарного модуля производителя, а
не наш собственный код), который не совершали без отдельного решения.

**Общий итог по обеим независимым попыткам (panthor и настоящий
kbase)**: оба -- разными путями, на разных уровнях абстракции --
упираются в тему конфигурации power domain "top"/"cores" для этого
чипа. Panthor полностью решил задачу привязки через стандартный Linux
genpd, но MCU всё равно не подаёт признаков жизни. Настоящий kbase
использует ДОПОЛНИТЕЛЬНЫЙ, Samsung-специфичный слой поверх genpd
(`exynos_pd_lookup_name` по имени), который тоже не срабатывает, но
уже на этапе PM-инициализации, раньше, чем MCU вообще пытается что-то
делать -- и в этом случае причина куда точнее локализована (конкретная
функция, конкретное сравнение строк), просто дальнейшая диагностика
требует отладки уже загруженного проприетарного бинарника, а не
исходного кода.

## Прямая проверка вместо гадания: pd->name полностью совпадает, реальный exynos_pd.ko всё равно возвращает NULL (2026-09-16, ещё позже)

Пользователь подтвердил: вместо инвазивного kprobe на живую функцию
написали маленький read-only диагностический модуль
(`gpu-probe-tools/pd-diag/pd_diag.c`), который делает ровно то же
самое, что `exynos_pd_lookup_name()` по открытому исходнику -- обходит
`for_each_compatible_node(..., "samsung,exynos-pd")`, резолвит
`platform_device`, читает `platform_get_drvdata()` -- и логирует
реальное значение `pd->name`, а не гадает. Поле `name` -- второй член
`struct exynos_pm_domain`, сразу после `struct generic_pm_domain
genpd`, до всех Kconfig-зависимых полей дальше по структуре, так что
его смещение не зависит от неизвестных нам настроек сборки vendor-модуля
-- только от `generic_pm_domain`, чей layout уже многократно
подтверждён (та же сборка ядра, что и везде в этой сессии). Это чистая
интроспекция через публичные API ядра (`for_each_compatible_node`,
`of_find_device_by_node`, `platform_get_drvdata`) поверх уже
загруженного, уже экспортирующего свои символы модуля -- без хуков и
без изменения работающего кода.

Результат для всех 20 доменов `samsung,exynos-pd` в реальном
devicetree, включая нужный:

```
node=/pd-embedded_g3d@18062000 available=1
  pd=000000000a945fb5 pd->name=pd-embedded_g3d
```

**`pd->name` побайтово совпадает со строкой, которую ищет kbase.**
Домен зарегистрирован, доступен, привязан к драйверу, имя точно
совпадает -- `strcmp()` в `exynos_pd_lookup_name()` по открытому
исходнику обязан был вернуть совпадение. Тем не менее реальный,
уже загруженный (проприетарный vendor-билд) `exynos_pd.ko` на этом
самом устройстве, при вызове из kbase несколькими секундами ранее,
возвращает `NULL`.

**Вывод: реальная, работающая на этом устройстве прошивка
`exynos_pd.ko` внутри устроена иначе, чем открытый исходник этой же
функции в публичном зеркале** (кроме `pt_client_register`/SLC и
`google_retrieve_bcl_handle`/BCL, которые мы уже намеренно не собирали
и просто заглушили, здесь ситуация другая: модуль РЕАЛЬНО загружен,
экспортирует нужный символ, но ведёт себя не так, как показывает
открытый код с тем же именем функции). Дальнейшая локализация точной
причины потребовала бы разбора самого бинарника `exynos_pd.ko`
(дизассемблирование) или live-инструментации уже работающей функции
(kprobe/kretprobe) -- решили не продолжать в эту сторону без отдельного
осознанного решения, поскольку это переходит в разбор чужого
скомпилированного бинарника, а не работу с исходным кодом.

**Итог всей диагностики (panthor + реальный kbase + прямая проверка
exynos-pd) сходится в одной точке**: настоящая проблема физически
находится в связке "как этот конкретный vendor-билд Samsung/Google
на самом деле включает питание GPU-доменов на этом чипе" -- то есть
именно там, где ни открытый исходник panthor, ни открытый исходник
kbase, ни открытый исходник exynos-pd (все три -- независимо и
по-разному) не совпадают с тем, что реально происходит в
проприетарной прошивке этого конкретного устройства. Это не пробел в
нашей реализации -- это предел того, что можно установить из открытого
кода и штатных интерфейсов ядра без разбора самого бинарника.

## Прорыв: kprobe вскрыл настоящую причину -- не расхождение с бинарником, а наша ошибка конфигурации сборки; kbase probe теперь полностью успешен (2026-09-16, ещё позже)

Пользователь предложил live-инструментацию вместо дизассемблирования --
поставили `kretprobe` (`gpu-probe-tools/pd-diag/pd_probe.c`) на реальный
`exynos_pd_lookup_name()`, логирующий вход/выход/call stack, без
изменения работающего кода. Загрузили `mali_kbase.ko` с этим kprobe
армированным заранее -- **пробник не сработал вообще**, при том что тот
же самый лог отказа появился. Это означало, что реальная,
экспортированная функция НЕ ВЫЗЫВАЕТСЯ ВООБЩЕ -- не "вызывается и
возвращает NULL", а буквально не вызывается.

Проверили дизассемблированный `.o`: вызов `exynos_pd_lookup_name`
отсутствовал как relocation вообще, хотя предыдущая проверка (pd-diag)
и сам факт "Failed to find GPU power domain" в логе создавали
впечатление, что вызов происходит. Добавили канареечные `pr_info()`
прямо в тело `#if IS_ENABLED(CONFIG_EXYNOS_PMU_IF)` блока -- обе
строки скомпилировались и вызвались (ветка реально берётся), но сам
вызов `exynos_pd_lookup_name` сразу после них всё равно не
генерировался.

Причина нашлась в заголовке `soc/google/exynos-pd.h`:

```c
#if IS_ENABLED(CONFIG_EXYNOS_PD)
struct exynos_pm_domain *exynos_pd_lookup_name(const char *domain_name);
#else
static inline
struct exynos_pm_domain *exynos_pd_lookup_name(const char *domain_name)
{
	return NULL;
}
#endif
```

**Реальная функция гейтится `CONFIG_EXYNOS_PD` -- другим конфигом, не
`CONFIG_EXYNOS_PMU_IF`**, который гейтит только вызов В
`pixel_gpu_power.c`. Мы задавали только `CONFIG_EXYNOS_PMU_IF`, поэтому
компилятор ВСТРАИВАЛ (инлайнил) заглушку "всегда `NULL`" вместо
настоящего extern-вызова -- отсюда и константный, предсказуемый
`pc->pm.domain == NULL`, и полное отсутствие вызова для kprobe (нечего
было перехватывать), и полное совпадение с прошлым выводом о "разном
поведении бинарника" -- **этот прошлый вывод был неверным**: дело было
не в реальном `exynos_pd.ko`, а в нашем собственном флаге сборки.

Добавили `-DCONFIG_EXYNOS_PD=1`, пересобрали -- kprobe немедленно
сработал:

```
pd-probe: ENTRY domain_name="pd-embedded_g3d" (ptr=fffffffdfdc176fc)
 gpu_pixel_init -> kbasep_platform_device_init -> kbase_device_early_init
 -> kbase_device_init -> kbase_platform_device_probe
pd-probe: RETURN domain_name="pd-embedded_g3d" ret=ffffff8010d41840
```

Настоящая функция реально нашла домен и вернула валидный указатель.
GPU дошёл до `GPU max frequency initialized to 848000 KHz` (точное
совпадение с частотой из пользовательского разбора этой сессии), но
упал дальше: `DVFS init failed error = -22`.

Тот же паттерн повторился ещё дважды подряд -- каждый раз реальная,
уже загруженная на устройстве функциональность (CAL/cmupmucal) была
доступна, просто не вызывалась из-за недостающего флага:

- `gpu_dvfs_set_initial_level()` реально устанавливает частоты только
  под `#if IS_ENABLED(CONFIG_CAL_IF)` -- без него `ret` остаётся
  начальным `-1`, что интерпретируется как ошибка. Добавили
  `-DCONFIG_CAL_IF=1`.
- Заголовки cal-if (`pwrcal-env.h`) сами по себе имеют ДВЕ ветки --
  реальную для ядра Linux (`#ifdef CONFIG_SOC_GOOGLE`, использует
  `<linux/spinlock.h>` и т.д.) и firmware/bootloader-ветку (`#else`,
  включает несуществующий в нашем дереве `"types.h"`). Добавили
  `-DCONFIG_SOC_GOOGLE=1`.
- После этого modpost показал новые (ожидаемые) undefined-предупреждения
  для реальных, уже загруженных на устройстве символов из `cmupmucal.ko`
  (`cal_dfs_set_rate`, `cal_dfs_get_lv_num`, `cal_dfs_get_rate_asv_table`,
  `cal_dfs_get_max_freq`, `cal_dfs_get_min_freq`) -- `insmod` разрешил
  их все без единой ошибки "unknown symbol".

**Результат решающего теста: `Probed as mali0`.** Полный, успешный
probe настоящего, официального, открытого драйвера Google для этого
чипа -- ни одного "Failed to boot MCU", ни одной ошибки инициализации:

```
mali 28000000.mali: Register LUT 000a0800 initialized for GPU arch 0x000a0806
mali 28000000.mali: GPU identified as 0x2 arch 10.8.6 r0p0 status 4
mali 28000000.mali: Memory group manager successfully loaded
mali 28000000.mali: Protected memory allocator successfully loaded
mali 28000000.mali: Configured GPU_UTIL counter (Id: 4) from CSHW group for DVFS.
mali 28000000.mali: Probed as mali0
```

`/dev/mali0` не создаётся автоматически (на этой ОС нет udev/mdev,
ADR-011) -- создан вручную через `mknod` по major:minor из
`/sys/class/misc/mali0/dev`. `/sys/kernel/debug/mali0/gpu_memory`
показывает 0 байт выделений -- похоже, что CSF-прошивка (MCU) в этой
версии kbase грузится ЛЕНИВО, при первом реальном использовании GPU
(создание контекста/queue group), а не eagerly при probe (в отличие от
panthor, который загружает и запускает прошивку сразу при probe). Это
означает, что реальная, финальная проверка "запускается ли MCU и
исполняет ли прошивку" ещё не выполнена -- для этого нужен минимальный
userspace-инструмент, открывающий `/dev/mali0` и выполняющий базовый
ioctl-хендшейк (`KBASE_IOCTL_VERSION_CHECK` + создание контекста/queue
group), что триггерит реальную активацию GPU/MCU. Это отдельная,
новая по объёму задача (собственный C-инструмент под кросс-тулчейн),
не сделана в рамках этой сессии.

**Важный урок методологии, зафиксированный явно**: предыдущий вывод
в этом документе ("реальный `exynos_pd.ko` ведёт себя иначе, чем
показывает открытый исходник") был получен из честной, тщательной
диагностики (`pd-diag`), но оказался ОШИБОЧНЫМ -- истинная причина
была куда проще (наша собственная ошибка конфигурации сборки).
`pd-diag`'s собственный результат (домен существует, имя совпадает)
был технически верным и остаётся верным -- просто неверной была
интерпретация ("раз лукап не сработал при всех верных условиях, значит
дело в самом бинарнике"), поскольку в тот момент проверки лукап
вообще не выполнялся кодом kbase. `kretprobe` -- инструмент, предложенный именно для таких случаев --
и он напрямую опроверг неверную гипотезу, а не просто добавил ещё
одно косвенное подтверждение ей.

## ФИНАЛ: MCU-прошивка реально загрузилась и запустилась через настоящий kbase (2026-09-16, ещё позже)

Пользователь подтвердил: довести до конца минимальным userspace
ioctl-инструментом. Написали `gpu-probe-tools/gpu_probe_test.c` --
статически слинкованный (glibc, кросс-тулчейн `aarch64-linux-gnu-gcc`,
`-static`, так что рантайм-libc целевой ОС не важен) минимальный
клиент: `open("/dev/mali0")` + `KBASE_IOCTL_VERSION_CHECK` +
`KBASE_IOCTL_SET_FLAGS` + `KBASE_IOCTL_MEM_ALLOC` (одна страница,
CPU+GPU RW). Структуры и номера ioctl взяты напрямую из реальных
uapi-заголовков этого же исходника
(`mali_kbase_ioctl.h`/`csf/mali_kbase_csf_ioctl.h`), не выдуманы.

`/dev/mali0` не создаётся автоматически (нет udev/mdev, ADR-011) --
создали вручную через `mknod` по `major:minor` из
`/sys/class/misc/mali0/dev` (`10:104`, подтверждено `/proc/misc`
показывающим `104 mali0`).

Первый прогон (и даже просто `cat /dev/mali0` от busybox, для
изоляции -- не связано с нашим тестовым бинарником) сразу же

node, а **реальным, содержательным событием**: `open()` дошёл до
кода kbase, который лениво (при первом открытии, не при probe --
подтверждает гипотезу из предыдущего раздела) попытался загрузить

## Vulkan/userspace: настоящий Mali UMD создаёт VkDevice в обход libvulkan.so (2026-09-16, ещё позже)

С ядерным уровнем решённым, следующий вопрос: можно ли на этой ОС
запустить настоящий, проприетарный Mali userspace-драйвер (UMD) --
`vulkan.mali.so`/`libGLES_mali.so` -- а не только kernel-модуль.
Архитектура (по предложению пользователя): "остров совместимости" --
отдельный bionic-рантайм рядом с основным musl-миром ОС, без попытки
затащить Android целиком.

Фабричного образа под рукой не было; сначала попробовали
реконструировать `vendor`-раздел прямо на устройстве через liblp
(формат Android dynamic-partitions, полностью реверс-инжинирен и
проверен побайтово против известных размеров структур AOSP) и
`device-mapper` (`dm-linear`, через `<linux/dm-ioctl.h>` из реального
UAPI-заголовка ядра). Работало для чтения имён файлов, но упёрлось в
необъяснимое расхождение размеров (`ext4 bad geometry`) -- VABC/COW
проверили и исключили (нет `snapuserd`, нет `vendor_b`, `-cow`-раздел
слишком мал), в итоге пользователь предоставил настоящий фабричный
образ (`panther-cp2a.260705.006-factory-*.zip`, тот же build
`CP2A.260705.006`, что и на живом устройстве -- подтверждено
побайтовым совпадением UUID суперблока `vendor`). `vendor.img`/
`system.img` там -- обычные, нефрагментированные ext4-образы,
монтируются напрямую (`mount -o loop,ro`), без liblp/dm-mapper.
`com.android.runtime.apex` (внутри `system.img`) -- сам по себе
zip/JAR с ещё одним ext4-образом (`apex_payload.img`) внутри,
содержащим настоящие `libc.so`/`libdl.so`/`libm.so`/`linker64` (то, на
что символьные ссылки в `/system/lib64` в обычном виде не резолвятся).

Кросс-компиляция под bionic без NDK: тем же `clang-17.0.2`, что и для
kbase, с `--target=aarch64-linux-android30 -ffreestanding -nostdlib
-nostdinc`, линковка напрямую против извлечённых `.so` (`lld`,
`-Wl,-dynamic-linker,/system/bin/linker64`), свой `_start` (`-nostdlib`
= нет crt-объектов NDK). `resolve_deps.sh` (`llvm-readelf -d ... |
grep NEEDED`, транзитивное замыкание) нашёл ровно 46 нужных
библиотек по всем трём деревьям (vendor/system/bionic-apex) -- ни
одной недостающей.

### HAL discovery: libvulkan.so не работает без Android property-сервиса

`libvulkan.so`'s собственный механизм поиска ICD (`hw_get_module()` из
`libhardware.so`: свойство `ro.hardware.vulkan` -> имя файла
`vulkan.<имя>.so` -> `dlsym(handle, "HMI")`, `HMI` =
`HAL_MODULE_INFO_SYM_AS_STR`) не работает на этой ОС --
`vkEnumeratePhysicalDevices` стабильно возвращал 0 устройств, `dmesg`
после вызова -- абсолютно чист (ICD даже не пытался тронуть железо).
Прямая проверка `.dynsym` `vulkan.mali.so` через `llvm-nm -D`: там
всего 4 символа, `HMI` нет вообще. Зато `libGLES_mali.so` (прямая
зависимость `vulkan.mali.so`) экспортирует `HMI` как **данные**
(`D`-символ, не функция) -- и `dlsym()` по стандарту SysV ABI ищет
транзитивно по `DT_NEEDED`-зависимостям, так что
`dlsym(vulkan_mali_handle, "HMI")` находит его через `libGLES_mali.so`.

Написали `vk_probe.c` -- вручную воспроизводит ~10 строк настоящей
логики загрузчика AOSP (`hw_module_t`/`hwvulkan_module_t`/
`hw_device_t`/`hwvulkan_device_t`, ABI которых не менялся с момента
появления Vulkan в Android): `dlopen(vulkan.mali.so)` ->
`dlsym(handle, "HMI")` -> `module->methods->open(module, "vk0",
&device)` -> звать `device->CreateInstance` напрямую, в обход
`libvulkan.so` целиком.

Первая попытка: модуль находится и правильно себя идентифицирует
(`id=vulkan`, `name=Mali Vulkan Driver`), `open("vk0")` возвращает
успех (0) -- но `device->CreateInstance`/`GetInstanceProcAddr` **оба
NULL**. `dmesg` -- снова полная тишина, значит проблема ещё до
попытки тронуть `/dev/mali0`.

### Диагностика через собственный ptrace-трейсер (strace недоступен на этой ОС)

По предложению пользователя -- вместо дизассемблирования сделали
`strace`-подобную трассировку. Готового `strace` под эту ОС нет;
написали `sysprobe.c` -- минимальный `ptrace`-трейсер (glibc,
статическая линковка через `aarch64-linux-gnu-gcc -static`, ~160
строк): `PTRACE_TRACEME`/`PTRACE_SYSCALL`, разбор регистров AArch64
(`x8` = номер syscall, `x0..x5` = аргументы) через
`PTRACE_GETREGSET`, чтение путевых строк из памяти трассируемого
процесса через `PTRACE_PEEKDATA`. `ptrace` работает на уровне
ядра/процесса, независимо от libc, так что этот glibc-статический
трейсер прозрачно трассирует bionic-бинарник `vk_probe`.

Первый трейс сразу дал однозначный ответ:

```
newfstatat("/dev/__properties__") = -2   (ENOENT)
openat("/dev/__properties__")     = -2   (ENOENT)
```

-- и ни одного `connect()`/`socket()` за весь запуск. Значит: не
хватает не property-сервиса как демона (сокет не нужен для чтения), а
самого bionic property area (`/dev/__properties__`, shared-memory
trie, `__system_property_area` из `system_properties.cpp`) как
файловой структуры.

### Property area: настоящий сериализатор Google вместо реконструкции формата вручную

Вместо того чтобы реконструировать бинарный формат `property_info` по
памяти (тот же риск, что и с liblp) -- нашли, что реальная
`libc.so` (извлечённая из factory-образа) экспортирует нужные
writer-функции напрямую (`llvm-nm -D`):
`__system_property_area_init`, `__system_property_add`,
`__system_property_get` и др. (версии `LIBC_PLATFORM`/`LIBC` -- те же,
которыми пользуется `init`). Написали `propsetup.c` (тот же
bionic-кросс-компилятор, что и `vk_probe`), вызывающий их напрямую.

Трассировка (`sysprobe ./propsetup`) показала: `area_init()` пытается
открыть `/dev/__properties__/property_info` -- готовый бинарный
trie-файл, который на настоящем Android генерирует `init` при первой
загрузке из текстовых `*_property_contexts`. У нас его никогда не
было. При этом сами текстовые `/plat_property_contexts` и
`/vendor_property_contexts` неожиданно уже лежали в `/` устройства
(остаток более раннего этапа AoC-экстракции) и содержали все нужные
префиксы (`vendor.mali.` -> `vendor_arm_runtime_option_prop`,
`ro.hardware.vulkan`/`ro.board.platform` -> `exported_default_prop`,
оба `exact`).

Вместо реконструкции формата `property_info` вручную -- скачали
настоящий исходник Google (`system/core/property_service/
libpropertyinfoserializer` + `libpropertyinfoparser`,
android.googlesource.com, интернет с R620 есть) и собрали
хост-инструмент `mkpropinfo` на x86_64 (обычный `g++`, без
кросс-компиляции -- нужен только бинарный файл-результат):
`trie_builder.cpp`/`trie_serializer.cpp`/`property_info_parser.cpp` --
без изменений, единственная зависимость от `libbase`
(`android::base::Split()`) заменена трёхстрочным локальным шимом
(`android-base/strings.h`), чтобы не тащить всю `libbase`. Свой
маленький парсер текстовых `property_contexts`-строк (аналог
`ParsePropertyInfoLine`, без остальной части `libbase`). Прогнали
через настоящие `/plat_property_contexts`+`/vendor_property_contexts`
устройства -- получили 117344-байтный `property_info`, 1549 записей.

Положили файл в `/dev/__properties__/property_info` (`chmod 0644` --
`PropertyInfoAreaFile::LoadPath()` в реальном bionic требует
`uid==0 && gid==0 && !(mode & (S_IWGRP|S_IWOTH))`, проверено по
исходнику `property_info_parser.cpp`). После этого
`__system_property_area_init()` реально создал все per-context
`prop_area`-файлы (`u:object_r:vendor_arm_runtime_option_prop:s0` и
т.д., каждый через настоящий `prop_area::map_prop_area_rw()` из
`prop_area.cpp`) -- `fsetxattr()` для SELinux-контекста ожидаемо падал
(`Operation not supported`, нет SELinux/xattr на этой ФС), это не
фатально для чтения/записи самих значений. `__system_property_add()`
+ `__system_property_get()` в одном процессе подтвердили: значения
реально пишутся и читаются (`ro.hardware.vulkan=mali` и т.п.).

### Настоящая причина NULL callbacks оказалась не в properties

Повторный запуск `vk_probe` после появления property area: **всё ещё
`CreateInstance`/`GetInstanceProcAddr` = NULL**. Повторная трассировка
показала, что Mali UMD вообще ни разу не обращался к
`vendor_arm_runtime_option_prop` (контексту `vendor.mali.*`) -- только
стандартные bionic-собственные property-чтения при старте процесса
(`debug_prop`, `arm64_memtag_prop` и т.п., не имеющие отношения к
Mali). Значит гипотеза про properties была структурно верной
(инфраструктура была реально сломана), но не была причиной именно
этого симптома.

Реальная причина нашлась сверкой с настоящим `hardware.h` из AOSP
(`platform/hardware/libhardware`, `include_all/hardware/hardware.h`):
на `__LP64__` поле `reserved` и в `hw_module_t`, и в `hw_device_t`
объявлено как `uint64_t reserved[N]`, а не `uint32_t reserved[N]` --
наша ручная реконструкция структуры использовала `uint32_t`. Для
`hw_device_t` это даёт расхождение в 48 байт (`uint64_t[12]` = 96
байт против `uint32_t[12]` = 48 байт), а `hwvulkan_device_t`'s
`CreateInstance`/`GetInstanceProcAddr` идут сразу после
`hw_device_t common` -- то есть мы читали их из середины настоящего
(зануленного) `reserved`-паддинга реальной структуры, а не из
настоящих указателей. Поле `hw_module_t.reserved` этой ошибке не
подвержено (все читаемые нами поля идут ДО него), поэтому `id`/`name`/
`methods` читались верно с самого начала -- баг маскировался под
"драйвер тихо деградирует", хотя на самом деле деградировало только
наше собственное чтение структуры.

Исправили (`uint32_t` -> `uint64_t` в обоих `reserved[]`),
пересобрали, перезапустили:

```
vk-probe: device open OK, CreateInstance=0x0000007d91575fd0 GetInstanceProcAddr=0x0000007d91563fd0
vk-probe: calling REAL Mali UMD CreateInstance directly
vk-probe: CreateInstance result=0x0000000000000000   (VK_SUCCESS)
vk-probe: vkEnumeratePhysicalDevices ptr=0x0000007d91576500
vk-probe: enum result=0x0000000000000000 count=0x0000000000000001
vk-probe: device[0] name=Mali-G710
```

Добавили получение `vkGetPhysicalDeviceQueueFamilyProperties` и вызов
`vkCreateDevice` (одна графическая очередь, `queueFlags=0x17` --
GRAPHICS|COMPUTE|TRANSFER и ещё один бит, `queueCount=2`, реальные
параметры Mali-G710):

```
vk-probe: calling vkCreateDevice(queueFamily=0)
vk-probe: vkCreateDevice result=0x0000000000000000   (VK_SUCCESS)
vk-probe: VkDevice created OK, handle=0xb400007db19a7010
```

Трассировка этого запуска (`sysprobe ./vk_probe`) подтвердила: внутри
`vkCreateDevice` UMD реально делает `faccessat("/dev/mali0") = 0`,
затем несколько десятков настоящих `ioctl()` к kbase (version check,
set flags, allocation, создание контекста и т.п.) -- **все вернули
0/успех**. `dmesg` при этом остаётся чист -- ожидаемо: kbase не
логирует рутинные успешные ioctl'ы, только probe/прошивку/ошибки (что
уже подтверждено раньше в этом документе).

### Итог раздела Vulkan/userspace

Полная цепочка от bionic-приложения до реального GPU физически
работает на этой ОС: `dlopen/dlsym("HMI")` (в обход `libvulkan.so`) ->
настоящий Mali UMD -> `vkCreateInstance` (`VK_SUCCESS`) ->
`vkEnumeratePhysicalDevices` (находит `Mali-G710`) -> `vkCreateDevice`
(`VK_SUCCESS`) -> реальные ioctl к `/dev/mali0` -> `mali_kbase.ko`,
поднятый и проверенный в предыдущем разделе этого документа.

Ключевые уроки методологии, оба -- прямое следствие совета
пользователя не гадать по памяти, а проверять эмпирически или по
первоисточнику:

- Собственный минимальный `ptrace`-трейсер (нет `strace` под эту ОС)
  дал ту же диагностическую силу, что и штатный инструмент, без
  необходимости портировать его целиком.
- Формат `property_info` не реконструирован по памяти, а сгенерирован
  настоящим кодом Google (`libpropertyinfoserializer`, собранным как
  хост-инструмент из исходников с android.googlesource.com) -- и всё
  равно оказалось, что предполагаемая причина (properties) была не
  той самой; настоящий баг (`uint32_t` vs `uint64_t reserved[]`) нашли
  только сверкой с реальным `hardware.h`, а не предположением.

Инструменты (`sysprobe`, `propsetup`, `mkpropinfo`+собранный
`property_info`, обновлённый `vk_probe`) сохранены на R620
(`/home/mike/panthor-backport/gpu-probe-tools/` и
`/tmp/propinfo-build/`, вне git). Извлечённые деревья factory-образа
(`vendor-mount/`, `system-mount/`, `runtime-apex-mount/`) -- там же.

Не сделано: рендеринг реального кадра (submit command buffer,
swapchain/presentation через `saai-displayd`), оформление
bionic-моста как отдельного долгоживущего сервиса (`saai-gpud`),
persistent property area (переживающая перезагрузку -- сейчас
`/dev/__properties__` на tmpfs, создаётся вручную каждый раз).

## Real submit: команда доходит до железа, но MCU не квитирует CS-уровень (2026-09-16, ещё позже)

С рабочим `VkDevice` следующий вопрос -- реальный submit команды.
`vk_frame.c` (offscreen render pass, clear в красный, copy в
host-visible буфер) и `vk_exec01.c` (минимальный `vkCmdFillBuffer` +
`VkFence`, без render pass/image, по предложению пользователя --
"максимально тупая" команда, чтобы исключить лишние переменные)
показали одинаковую картину: `vkQueueSubmit()` возвращает успех, но
результат никогда не подтверждается.

### Первое зависание оказалось не в GPU, а в нашем собственном `_start`

`vk_frame`'s `vkQueueWaitIdle()` зависал намертво. `ptrace`-трейс
потоков (`/proc/<pid>/task/*/stack`) показал: сам Mali UMD корректно
создаёт два внутренних потока (`mali-event-hand` -- ждёт на `poll()`
уведомления о завершении, `mali-mem-purge` -- фоновый воркер) --
значит `pthread_create()` внутри UMD реально работает. Подозрение
сначала пало на наш собственный, вручную написанный `_start`
(`-nostdlib`, без вызова `__libc_init()`, без настройки TLS) -- он
пропускает нормальную bionic-инициализацию главного потока, что
теоретически могло сломать внутреннюю pthread-бухгалтерию UMD.
Пересобрали с настоящими NDK crt-объектами (`crtbegin_dynamic.o`/
`crtend_android.o` из `android-sdk/ndk/.../aarch64-linux-android/30/`,
NDK на сервере уже был, использован только ради двух `.o`-файлов
корректного старта -- сама программа по-прежнему линкуется против
настоящего extracted `libc.so`, не NDK-заглушки) -- зависание осталось
идентичным. Гипотеза экспериментально отклонена.

### ftrace: группа стартует и почти сразу уходит в idle

Включили полный набор `mali:*` ftrace-событий
(`/sys/kernel/debug/tracing/events/mali/enable`). И для render-pass
теста, и для голого `vkCmdFillBuffer`: `CSI_START` для 5 command
stream interfaces, `CSG_SLOT_START_REQ` -> `CSG_SLOT_RUNNING`,
затем в течение ~25 микросекунд -- `CSG_INTERRUPT_IDLE`,
`CSG_SLOT_STOP_REQ` -> `CSG_SLOT_STOPPED` ->
`CSF_GROUP_SUSPENDED_ON_IDLE`, GPU полностью выключается (MCU_OFF,
L2_OFF). `mali_KCPU_FENCE_SIGNAL`/`mali_KCPU_CQS_SET` (события,
которыми реальный Vulkan fence должен сигнализироваться) не
срабатывают ни разу за весь прогон.

Первая интерпретация ("раз CSI быстро дошёл до idle -- значит GPU
реально всё исполнил почти мгновенно") оказалась **поспешной и
неверной** -- следующий тест её прямо опроверг.

### Проверка "вслепую": буфер не изменился -- но это тоже был неверный вывод

Поставили `vkCmdFillBuffer(0xA5A5A5A5)` на буфер, заранее заполненный
`0x11111111`, прочитали память напрямую (без ожидания fence, просто
`usleep(200000)`) -- байты остались `0x11111111`. Показалось, что это
доказывает отсутствие реального исполнения. Пользователь указал на
методологическую дыру: `HOST_COHERENT`-память не требует явного
`vkFlushMappedMemoryRanges`, но сам факт когерентности не превращает
`usleep()` в синхронизационный примитив -- отсутствие исполнения
**не доказано**, только заподозрено. Это стало поводом перейти на
инструментальную, а не косвенную проверку.

### Kretprobe на `kbase_csf_process_queue_kick()`: CS_INSERT реально продвигается

Вместо разбора закрытого UMD или дальнейших догадок по буферу --
скомпилировали диагностику ПРЯМО в `mali_kbase.ko` (не отдельным
модулем): `csq_probe.c` добавлен в `Kbuild` самого `borr_mali_kbase`,
инициализация/деинициализация подключены двумя строками в реальные
`kbase_driver_init()`/`kbase_driver_exit()` (`mali_kbase_core_linux.c`).
Компиляция внутри дерева даёт компилятору посчитать реальные смещения
`struct kbase_queue` (`user_io_addr`, `csi_index`, `size`,
`base_addr`) -- тот же принцип осторожности, что и с `liblp`/property
area: не реконструировать layout по памяти, когда есть реальный
исходник и возможность собрать его как есть.

`kretprobe` на `kbase_csf_process_queue_kick(struct kbase_queue *queue)`
читает `CS_INSERT`/`CS_EXTRACT` (по офсетам `CS_INSERT_LO`/
`CS_EXTRACT_LO` из `mali_kbase_csf_registers.h`, `queue->user_io_addr`
-- input-страница -- и `queue->user_io_addr + PAGE_SIZE/8` --
output-страница, ровно как это делает сам kbase в
`kbasep_csf_dump_active_queue_sync_info()`) до вызова, сразу после и
ещё 5 раз с шагом 2мс. Результат для `csi=0` (единственная реально
используемая очередь для простого `vkCmdFillBuffer`):

```
ENTRY:       insert=0x40  extract=0x0
RETURN+0ms:  insert=0x40  extract=0x0
RETURN+2ms:  insert=0x100 extract=0x0
RETURN+10ms: insert=0x100 extract=0x0
```

`CS_INSERT` реально продвинулся (`0x40` -> `0x100`) -- UMD
действительно записал новые команды в ring buffer, это не пустая
очередь. Но `CS_EXTRACT` (это firmware-side курсор, который MCU
продвигает по мере чтения команд) не сдвинулся ни на бит за 10мс.
Это опровергло и первоначальную гипотезу ("быстрое реальное
исполнение"), и вторую ("пустая команда") -- правильная формулировка:
**UMD пишет реальные команды, но firmware их не читает**.

### Doorbell/request-ack handshake: CSG-уровень работает, CS-уровень -- нет

По предложению пользователя добавили второй `kretprobe`, на
`kbase_csf_ring_cs_kernel_doorbell(kbdev, csi_index, csg_nr, ...)`
(здесь `csg_nr` -- обычный параметр функции, не зависит от того,
успел ли `queue->group` уже быть присвоен) и третий, на низкоуровневый
`kbase_csf_ring_doorbell()` (реальная MMIO-запись в железо,
`EXPORT_SYMBOL`). Прочитали `CSG_DB_REQ`/`CSG_DB_ACK` и `CS_REQ`/
`CS_ACK` через `kbase_csf_fw_io_*` accessor'ы.

Первая попытка дала одни нули везде -- оказалось, собственная ошибка:
`kbase_csf_fw_io_group_read()`/`stream_read()` **всегда** читают
output-страницу (там, где ACK), а REQ живёт в input-странице и
требует отдельных `_input_read()`-вариантов
(`kbase_csf_fw_io_group_input_read()`/`stream_input_read()`,
подтверждено прямо в исходнике `mali_kbase_csf_fw_io.c`). После
исправления:

```
CSG_DB_REQ: 0x7 -> 0xf -> 0x1f   (хост взводит биты для каждого CSI)
CSG_DB_ACK: 0x0                   (firmware не квитирует НИКОГДА)
CS_REQ:     0x1501                (хост выставил валидный запрос)
CS_ACK:     0x0                   (firmware не квитирует НИКОГДА)
```

`kbase_csf_ring_doorbell(doorbell_nr=0)` реально вызывается (дважды
за прогон -- один "kernel doorbell" индекс общий на группу, поэтому
не по одному звонку на каждый из 5 CSI, а пакетно). Дизассемблирование
собранного `mali_kbase.ko` (`llvm-objdump -d`) подтвердило: `dmb osh`
присутствует ровно на том месте, что и в исходнике, перед чтением
`CSG_DB_ACK`/записью `CSG_DB_REQ` -- barrier не потерян компилятором.

### Топология и версия интерфейса -- чисты

Вывели через тот же probe: `fw_version=0x01050000` (совпадает
побайтово с тем, что реально показал boot-лог этого же прогона --
`Loading Mali firmware 0x1050000`, т.е. версия не разъехалась),
`group_num=8`, `csg[0].stream_num=8`, адреса firmware I/O страниц
(`kbdev->csf.fw_io.pages.groups_pages[0]`) -- валидные kernel VA,
отличные от `queue->user_io_addr` (это ожидаемо и корректно:
firmware I/O страницы -- отдельный, kernel-only интерфейс
request/ack, `user_io_addr` -- отдельный, userspace-mmap'd интерфейс
insert/extract; это две разные страницы по архитектуре CSF, не баг
адресации).

### Итог цикла

Полностью, инструментально, без единого предположения проверена и
подтверждена ВСЯ хост-driver сторона: UMD пишет реальные команды,
хост корректно формирует CS_REQ и CSG_DB_REQ, memory barrier на
месте, реальная аппаратная запись в doorbell происходит, версия и
топология firmware-интерфейса соответствуют тому, что реально
загрузилось. Единственное необъяснённое звено -- сама MCU-прошивка:
она успешно грузится и доводит CSG (группу-контейнер) до
`RUNNING`/`IDLE`, но никогда не квитирует CS-уровень (конкретный
command stream) внутри уже запущенной группы. Это открытый вопрос на
конец сессии, не тупик -- дальнейшая локализация потребует либо
исходников/документации самой прошивки (проприетарный ARM-блоб,
недоступен), либо сравнительной трассы того же теста под stock
Android на этом же железе.

Диагностика (`csq_probe.c`, встроенный в `mali_kbase.ko` через
`Kbuild`+две строки в `mali_kbase_core_linux.c`; `vk_frame.c`,
`vk_exec01.c`) сохранена на R620 в
`/home/mike/panthor-backport/gpu-probe-tools/` и в самом дереве
`borr_mali_kbase/`, вне git.

## Real submit: полный синтез -- GPU и KCPU честно работают, узкое место в userspace-уведомлении (2026-09-16, финал сессии)

### Инцидент: перезагрузка устройства от kretprobe на горячем пути

Попытка добавить `kretprobe` на `kbase_csf_kcpu_queue_process()`
(диспетчер KCPU-команд -- `kbase_kcpu_cqs_wait_process()`/
`cqs_set_process()` оказались заинлайнены компилятором, отсутствуют
в `/proc/kallsyms`, пришлось хукать сам диспетчер) вызвала **реальную
перезагрузку физического устройства**: эта функция вызывается
KCPU-worker потоком слишком часто, overhead kretprobe + цикл `printk`
внутри спровоцировали soft lockup, а в cmdline ядра стоит
`softlockup_panic=1` -> автоматическая паника -> ребут. `pstore`
не сохранил backtrace (пуст), но косвенные улики (watchdog cluster,
момент перезагрузки сразу после `rmmod` этой сборки) однозначны.
После ребута весь non-persistent стек (`mali_pixel`+DRM-хелперы,
`/vendor` дерево, `/dev/__properties__`, firmware-симлинк) пришлось
поднимать заново -- persistent `/data/saaios/vk-libs/` и
`/home/mike/panthor-backport/propinfo-build/property_info` на R620
уцелели и ускорили восстановление. **Урок методологии**: kretprobe
на функции, вызываемые из hot-path воркеров (в отличие от
редко-вызываемых `kbase_csf_process_queue_kick()`/
`kbase_csf_ring_cs_kernel_doorbell()`/`kbase_csf_ring_doorbell()`,
которые оказались безопасны для инструментирования), может уронить
всё устройство целиком -- сама по себе связь "эта функция вызывается
часто" не была заранее очевидна без пробы. Рискованный probe удалён
из `csq_probe.c` насовсем (закомментирован с объяснением, не
восстанавливать).

### Безопасная альтернатива: штатные debugfs-файлы вместо кастомных probe'ов

Вместо дальнейших kretprobe на горячих путях нашли, что реальный
kbase уже содержит полностью официальный, безопасный (обычный
`seq_file`-based debugfs `read`, не хук в hot path) механизм
интроспекции CSF-состояния -- три файла под
`/sys/kernel/debug/mali0/ctx/<pid>_<id>/` (появляются только пока
жив реальный `kbase_context`, т.е. пока наш тестовый процесс не
завершился -- пришлось добавить `sleep(10)` перед выходом из
`vk_exec01`, чтобы успеть прочитать):

- **`kcpu_queues`** -- состояние всех KCPU-очередей контекста:
  `Pending Commands`, `Enqueue err`, `Blocked`, `Fence context & seqno`.
- **`csf_sync`** -- декодированная информация о GPU- и KCPU-очередях
  (`kbasep_csf_sync_kcpu_dump_print()` + `kbasep_csf_sync_gpu_dump_print()`
  из `mali_kbase_csf_sync.c`, зарегистрированы как debugfs-файл
  `csf_sync` в `mali_kbase_csf_sync_debugfs.c` -- код для этого уже
  был в дереве, просто не был раньше замечен).
- **`groups`** -- самое ценное: `cs_insert`/`cs_extract` по каждой
  связанной GPU-очереди И **сырой побайтовый дамп самого ring
  buffer** (`SAVED_CMD_PTR`, каждое 64-битное слово command stream
  с адресом).

Плюс штатный firmware log (`/sys/kernel/debug/mali0/fw_traces`,
verbosity через
`/sys/devices/platform/28000000.mali/firmware_config/Log verbosity/cur`)
-- человекочитаемый поток событий MCU (`DB CSI`, `STATE X to Y`,
`EMUL ... OPC ... RES ...`, `Shader ON/OFF`, `TIMER ELAPSED`),
безопасный и официальный.

### Прочитано через 3-7 реальных секунд после submit -- совсем другая картина, чем через 10мс

Более ранний вывод (kretprobe, окно 10мс после kick) видел
`CS_EXTRACT`/`CS_ACK`/`CSG_DB_ACK` постоянно нулевыми и заключил, что
MCU "не квитирует CS-уровень". Прочитав `groups`/`csf_sync` через
3-7 РЕАЛЬНЫХ секунд после `vkQueueSubmit()` (а не 10мс), картина
оказалась другой:

```
queue:GPU-*-0-0 size:65536 cs_insert: 100 cs_extract: 100 ...
```

`cs_extract` реально догнал `cs_insert` -- ring buffer полностью,
без ошибок обработан firmware. `kcpu_queues` показал `Pending
Commands: 0`, `Blocked: 0`, `Enqueue err: 0` для всех очередей --
KCPU-сторона тоже полностью и безошибочно завершена. Это
воспроизвелось идентично на двух независимых запусках (после
перезагрузки устройства между ними), т.е. детерминированно, не
гонка. Firmware-side completion, судя по всему, реально занимает
секунды, а не миллисекунды -- вероятно, из-за energy-management
таймеров power-down (в firmware trace видны множественные `TIMER
ELAPSED` события между началом исполнения и итоговым
`CSG 0 STATE ... to 0`). Даже увеличенное до 5 секунд ожидание
`VkFence` через `vkGetFenceStatus()` в цикле не дождалось сигнала --
fence остаётся `VK_NOT_READY` несмотря на то, что GPU/KCPU честно
завершили работу.

### Побайтовый декод ring buffer: реальная ISA, не гадание

Полный дамп `groups` для единственной активно используемой очереди
(csi=0) сопоставлен с независимой, точной документацией CSF Command
Stream ISA (icecream95.gitlab.io, инструкции `MOV`/`ADD`/`WAIT`/
`SLOT`/`ENDPT`/`EVADD`/`EVSTR`/`CALL`/`TAILCALL` с точными
энкодингами верхнего байта). Полная расшифровка:

```
0x000  ENDPT modes=1            (0x22, маска доступных endpoint'ов)
0x008  SLOT #2                  (0x17, выбор scoreboard-слота)
0x040  MOV  X0x5a, #0x5ffff79000
0x048  ADD  X0x50, X0x5a, #0    (копия адреса, "MOV" через ADD #0)
0x050  MOV  W0x4a, #1
0x058  EVADD [X0x50], W0x4a, flags=5   (инкремент event-счётчика по адресу)
       -- тот же паттерн MOV/ADD(+8/+0x10/.../+0x20)/MOV/EVADD повторяется
          ещё 4 раза, обходя массив из 5 соседних 8-байтных
          event-счётчиков по адресам 0x5ffff79000..0x5ffff79028
0x0c0  WAIT scoreboard_mask=0x02   (0x03, ждёт именно slot 2 -- см. offset 0x008)
0x0c8  MOV  X8, #0x5fffff1ff8
0x0d0  MOV  W0x4a, #1
0x0d8  EVADD [...], ..., flags=1
```

Оба адреса, на которые ссылаются `MOV`+`EVADD` (`0x5ffff79000` и
`0x5fffff1000`), в `mem_allocs` debugfs оказались **отдельными,
одинаково помеченными флагом `245c00e` однострочными (1 страница)
выделениями** -- не совпадают по размеру/флагам с нашим 4КБ
`vkBuffer` (создан обычным `vkCreateBuffer`+`vkAllocateMemory`,
должен иметь более типичные флаги вроде большинства остальных
записей). То есть **весь этот command stream целиком -- это
event/sync-бухгалтерия** (`ENDPT`+5×`EVADD`+`WAIT`), не обращение
к нашему целевому буферу. Ни одной job-launch инструкции
(`RUN_COMPUTE`/`RUN_FRAGMENT`/`RUN_TILER` -- по документации ISA
их энкодинг публично не описан, "не особо интересны", но их
отсутствие среди полностью расшифрованных слов кольца означает, что
в этом конкретном ring buffer их физически нет) в кольце нет вообще.

### Итог всего цикла "real submit"

- **GPU CSF ring**: реально исполняется MCU-прошивкой от начала до
  конца, без единой ошибки (`cs_extract == cs_insert`, все `EVADD`
  вернули `RES 0`).
- **KCPU-очередь**: реально исполняется kbase-драйвером на хосте,
  без единой ошибки (`Pending: 0`, `Blocked: 0`, `err: 0`).
- **Реальной инструкции записи в целевой буфер в этом command stream
  нет вообще** -- то, что мы наблюдаем, целиком административная
  event/sync-синхронизация.
- **`VkFence` никогда не сигнализируется**, несмотря на честное
  завершение обеих сторон.
- Наиболее вероятное объяснение (не доказано дизассемблированием
  закрытого блоба, но согласуется со всеми фактами сессии): реальная
  запись данных в буфер и/или сигнализация `VkFence` выполняются
  Mali UMD **асинхронно, из отдельного worker-потока**
  (`mali-event-hand`, обнаружен ещё в начале этого под-расследования
  через `/proc/<pid>/task/*/stack`), который должен проснуться по
  `poll()` на файловых дескрипторах ядра (`/dev/mali0`-related
  eventfd, `malitl`-anon_inode) -- и этот `poll()` навсегда блокируется,
  так что вся цепочка "GPU закончил -> KCPU закончил -> UMD дописывает
  память/сигналит fence" рвётся именно на последнем, userspace-side
  шаге уведомления, а не на чём-либо GPU/kernel-driver-side.

Это не доказанный факт (требовало бы дизассемблирования
проприетарного `libGLES_mali.so`/`vulkan.mali.so` или прямого
исходника UMD, недоступных), а наиболее экономная гипотеза,
согласующаяся со всеми независимо проверенными фактами: работающий
GPU/kbase/KCPU, отсутствующая job-launch инструкция в конкретно
этом command stream, зависший `poll()` в реальном потоке
проприетарного UMD, никогда не сигнализируемый `VkFence`.

### Открытый вопрос на будущее

Что именно должно разбудить `mali-event-hand`'s `poll()` -- на каком
именно fd, какое событие ядро должно доставить и почему не доставляет
-- не выяснено. Реальный kbase-исходник даёт точную, безопасную для
инструментирования цепочку (все перечисленные функции вызываются
редко/по событию, не в hot-path воркера, в отличие от
`kbase_csf_kcpu_queue_process()`, уронившего устройство ранее в этом
цикле -- см. выше):

```
kbase_csf_handle_csg_sync_update()   -- firmware сообщила, что sync object изменился
        |
kbase_csf_event_signal()             -- atomic_set(&kctx->event_count, 1)
        |                               + kbase_event_wakeup_nosync(kctx)
_kbase_event_wakeup()
        |
wake_up_interruptible()
        |
kbase_poll()                         -- /dev/mali0's .poll fop; решает
        |                               EPOLLIN по kbase_event_pending()
mali-event-hand просыпается из poll()
```

Следующий безопасный шаг (не пробовали в этой сессии, ptrace-based,
без единого kretprobe на hot path):

1. Через уже существующий, доказанно безопасный `sysprobe`
   (ptrace-трейсер) перехватить вход/выход из `ppoll()` в потоке
   `mali-event-hand` и разобрать реальный `struct pollfd[]` --
   для каждого `fd`: номер, `events`, `revents`, и цель через
   `/proc/<pid>/fd/<n>` (сейчас известно только приблизительно --
   "/dev/mali0 или eventfd или malitl-anon_inode", нужен точный
   список и что каждый fd означает через `file_operations`).
2. Только если этого окажется недостаточно -- добавить `pr_info()`
   (не `kretprobe` на диспетчере, а точечные printk-и, либо
   kretprobe именно на `kbase_csf_event_signal`/`_kbase_event_wakeup`/
   `kbase_poll`/`kbase_csf_handle_csg_sync_update`, все редко
   вызываемые, не hot-path) и получить один таймлайн: T0 submit ->
   T1 EVADD исполнен -> T2 CSI завершён -> T3 sync-update IRQ? ->
   T4 event_signal? -> T5 event_count=1? -> T6 wake_up? -> T7 poll
   возвращается? -- первый пустой пункт и будет местом разрыва.

Рабочая гипотеза (не доказана дизассемблированием, но согласуется со
всеми фактами): submission у этого UMD может быть многофазным --
фаза 1 (event/sync bookkeeping, то что мы видели в ring buffer)
честно доходит до конца на GPU, но host так и не получает
sync-update уведомление обратно; поэтому UMD никогда не переходит к
фазе 2 (собственно `RUN_COMPUTE`/запись в буфер), которую мы поэтому
и не находим в текущем ring buffer -- не потому что её не должно
быть, а потому что до её эмиссии никогда не доходит очередь.

### Приоритет на следующую сессию

После этого цикла уже нет смысла возвращаться к power domains, CSF
firmware boot, doorbell/MMIO, `CS_REQ`/`CS_ACK`, декодированию command
stream или KCPU execution как к основным подозреваемым -- все эти
слои закрыты фактами, инструментально проверены и работают. Модель
разрыва теперь чистая:

```
vkQueueSubmit()
   |
UMD phase 1
   |
GPU CSF sync/event bookkeeping
   |
CS_EXTRACT == CS_INSERT
   |
KCPU queue empty / not blocked / no error
   |
kernel completion/event path
   ?
mali-event-hand wakes
   ?
UMD phase 2
   ?
real RUN_COMPUTE / fill
   ?
VkFence signal
```

Искать первый разрыв нужно строго в нижней половине этой схемы --
completion notification путь обратно в проприетарный UMD. Порядок
действий:

1. `sysprobe`: трассировать `ppoll()`/`poll()` в потоке `mali-event-hand`.
2. Разобрать реальный `struct pollfd[]` -- какие именно fd поток ждёт
   (номер, `events`, `revents`, цель через `/proc/<pid>/fd/<n>`).
3. `kbase_csf_event_signal()` -- вызывается ли вообще для этого submit.
4. `_kbase_event_wakeup()` -- доходит ли до `wake_up_interruptible()`.
5. `kbase_poll()` -- становится ли `/dev/mali0` readable
   (`kbase_event_pending()`) после завершения CSF/KCPU работы.
6. Определить, какой из этих шагов последний реально происходит --
   это и есть точка разрыва.

Если `kbase_poll()` возвращает readable, а `mali-event-hand` всё
равно не просыпается -- проблема в userspace/eventfd/`ppoll` ABI.
Если `kbase_poll()` никогда не становится readable после честно
завершённой CSF/KCPU работы -- разрыв внутри kernel event-delivery
пути. Все перечисленные функции вызываются редко/по событию, не в
hot-path воркера (в отличие от `kbase_csf_kcpu_queue_process()`,
уронившего устройство в этом цикле) -- безопасны для kretprobe при
необходимости, но начинать нужно с ptrace/`sysprobe`.
