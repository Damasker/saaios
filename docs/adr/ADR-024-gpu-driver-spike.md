# ADR-024: GPU-рендеринг на panther -- ни один драйверный путь не доступен в разумном объёме

## Статус

Принято, 2026-09-10.

## Контекст

Change 6 (S08) физически подтвердил, что `/lib`-reveal механизм sandbox
даёт динамически слинкованному Alpine-бинарнику выполниться, но
тестовое GTK4-приложение упало на попытке рендеринга: `Ngl`/`GL`/
`Vulkan`-рендереры отказали инициализироваться (нет GPU-драйвера в
минимальном пакете), откат на Cairo software-путь упал на `Unable to
create Cairo image surface: invalid value ... for the size of the
input` -> `Segmentation fault`. Перед тем, как переходить к Change 7
(настоящие GTK/Qt демо, физическая приёмка), нужно было отдельно
ответить на узкий вопрос: существует ли вообще практический путь к
GPU-ускоренному рендерингу на этом железе, и стоит ли Change 7 на него
рассчитывать.

## Находка

Устройство (Pixel 7 / Tensor G2) физически подтверждено содержащим
рабочий Mali GPU:

- `/sys/firmware/devicetree/base/mali@28000000/` -- реальный DT-узел с
  полными DVFS/power-таблицами (`gpu_dvfs_table_v1/v2`,
  `gpu_dvfs_governor`, `slc-acpm/gpu_g0_p8` и т.п.) -- GPU физически
  описан прошивкой устройства.
- Текущее ядро (`uname -a`): `6.1.157-android14-11-gbd23337e42e7-
  ab14791245` -- это настоящий Google Android Common Kernel (GKI)
  ветки android14-6.1, собранный тем же billing-процессом, что и
  штатный Pixel 7 (`clang 17.0.2, +pgo +bolt +lto`), не кастомное с
  нуля ядро -- уже подтверждено 118 реальными vendor-модулями (`wifi
  bcmdhd4389`, `pcie_exynos_gs`, `cs40l26` audio и т.д.), загруженными
  на боевом устройстве.
- `zcat /proc/config.gz | grep CONFIG_DRM_PANFROST` -> `is not set`.
  Открытый Mesa-совместимый DRM-драйвер (panfrost -- для более старых
  Bifrost/Midgard GPU) явно выключен в сборке этого ядра. `/dev/dri/
  card0` существует, но это `exynos-drm` -- дисплейный (KMS/scanout)
  драйвер, уже используемый `saai-displayd` (S02/S03) для
  framebuffer -- не 3D/render-нода. Ни `/dev/mali*`, ни `/dev/kgsl*` не
  существует; ни один GPU-модуль (`mali`/`panfrost`/`panthor`) не
  загружен (`lsmod` -- 118 модулей, ни один не совпадает).

Проверены оба возможных пути вперёд:

**1. Проприетарный стек ARM/Google (тот, что стоит в штатном
Android).** Локальные factory-образы (`os/targets/panther/artifacts/
factory/images/`, уже часть toolchain'а сборки) смонтированы read-only
на R620 (не на телефоне -- никакого риска для боевого устройства):
`vendor_dlkm.img` содержит `lib/modules/mali_kbase.ko`,
`mali_pixel.ko` (тот самый узел `mali@28000000`, судя по названию --
Pixel-специфичное расширение над ARM's kbase), `mali_kutf*.ko` --
собраны под ТОЧНО этот же kernel ABI (тот же factory-релиз, что и
загруженное ядро). `vendor.img` содержит полный userspace: `lib64/egl/
libGLES_mali.so`, `lib64/hw/vulkan.mali.so`, `lib64/hw/gralloc.
default.so`, `firmware/mali_csffw-r54p{0,1,2,3}.bin` -- то есть
технически ядро-часть стека физически присутствует и ABI-совместима.
Однако: `strings libGLES_mali.so | grep -i wayland/gbm` -- **пусто**.
Блоб не содержит ни единого упоминания Wayland или GBM платформы --
собран исключительно под Android's EGL_PLATFORM_ANDROID
(ANativeWindow/gralloc HAL/SurfaceFlinger). Чтобы использовать его
вообще, потребовалось бы реализовать существенный слой совместимости
с Android HAL (gralloc mapper, hwbinder-заглушки, ANativeWindow) --
то, что проекты вроде Waydroid делают, запуская ПОЛНЫЙ Android-контейнер
со своим Binder/HAL стеком, а не добавляя одну библиотеку. Несоразмерно
любому spike, и прямо противоречит уже устоявшемуся в проекте
предпочтению минимальных, полностью открытых, аудируемых компонентов
(Alpine пакеты вместо проприетарных блобов везде, где до сих пор был
такой выбор).

**2. Открытый Mesa-стек (panfrost/panthor).** Правильный драйвер для
Mali-G710 (Valhall, второе поколение, CSF/command-stream-frontend) --
`panthor`, вошедший в mainline Linux ядро начиная примерно с 6.10.
Работающее на устройстве ядро -- 6.1.157, GKI-залоченное (Google
фиксирует KMI/ABI для GKI-сборок специально для того, чтобы vendor-
модули оставались совместимыми без пересборки ядра) -- т.е. backport
`panthor` (или даже более старого `panfrost`, который для Valhall/CSF
GPU в принципе не подходит -- рассчитан на предыдущее поколение) через
~9 минорных версий ядра, включая существенно изменившуюся за это время
DRM scheduler/dma-fence инфраструктуру -- многонедельная задача с
неопределённым результатом, не spike-масштаба работа.

Отдельно, независимо от выбора драйвера: Alpine предоставляет
`mesa-dri-gallium` (24.0.9-r1, единая `libgallium_dri.so`, 27 MiB,
включает `llvmpipe` -- чистый CPU-рендеринг без GPU вообще, плюс
зависимость `llvm17-libs`, 136 MiB) -- установлен в тестовый sysroot на
R620 и физически проверен headless через `qemu-aarch64-static` против
уже работающего `saai-displayd`: `libEGL warning: egl: failed to
create dri2 screen` -- EGL's DRI2/Wayland-путь требует
`zwp_linux_dmabuf_v1` от компоситора для обмена буферами, которого
`saai-displayd` не реализует (см. Current state в S08-toolkit-
compatibility.md -- уже задокументированный пробел). То есть даже
чистое CPU-рендеринг (`llvmpipe`) без единого проприетарного байта не
может дойти до экрана через GTK4's EGL-путь без отдельной, довольно
существенной протокольной работы над `saai-displayd` (тот же класс
задачи, что `wl_data_device_manager`/`text-input-v3`, Change 2/3, но
для `linux-dmabuf`).

**Неожиданная находка.** До установки `mesa-dri-gallium` тот же
headless `gtk4-demo` через `qemu-aarch64-static` против того же
`saai-displayd` (Change 4) **успешно** рендерил и коммитил кадр --
`saai-displayd`'s лог подтверждает `commit on surface ..., frame
sha256=926ea70d...` -- то есть плейн Cairo/`wl_shm`-путь (SHM, без
EGL/DRI/GBM/dmabuf вообще) у GTK4 УЖЕ работал в headless-окружении без
единого GPU-компонента. После установки `mesa-dri-gallium` тот же
запуск (без каких-либо других изменений) стал завершаться штатно
(`exit 0`), но **без** коммита кадра -- клиент подключается
(`client connected`, `new xdg_toplevel`, `commit ... (no buffer)`), но
не доходит до финального `commit` с буфером и тихо завершается. Само
присутствие пакета `mesa-dri-gallium` в путях поиска меняет то, какой
рендерер GTK4/GDK выбирает первым, и, судя по всему, делает это в
сторону худшего результата для headless/qemu-случая, а не лучшего.
Причина не расследована дальше (не входит в объём этого spike) --
зафиксировано как предупреждение для Change 7: **не паковать
`mesa-dri-gallium` бездумно "на всякий случай"**, это не бесплатное
добавление.

Раздельно от вопроса GPU: реальный крэш на телефоне (Change 6,
`Unable to create Cairo image surface: invalid value ... for the size
of the input`) **не воспроизводится** в headless/qemu окружении с тем
же `gtk4-demo` и тем же `saai-displayd` (тот же кадр успешно
коммитится). Значит это не общий баг Cairo/Wayland-пути в GTK4 как
таковой, а что-то специфичное для физического запуска через
`saai-appd`'s sandbox (либо отличие в собранном для телефона пакете --
Change 6-тестовый пакет включал только `bin/`+`lib/`, без большей части
`usr/share`/локалей/`etc`, что мог использовать сам GDK при вычислении
размера поверхности,-- либо отличие реального `saai-displayd` на
панели устройства от headless-сборки). Требует отдельного
расследования в рамках Change 7, не блокируется этим ADR.

## Решение

Change 7 нацеливается ТОЛЬКО на software-рендеринг через существующий
`wl_shm`/Cairo-путь GTK4/Qt -- уже подтверждено физически рабочим в
headless-окружении (Change 4, до появления `mesa-dri-gallium` в
sysroot'е). Ни проприетарный Mali-блоб, ни `mesa-dri-gallium`/llvmpipe,
ни backport `panthor` не входят в объём Change 7 -- каждый из них либо
несоразмерно велик (Android HAL shim, backport ядра), либо требует
предварительной протокольной работы над `saai-displayd`
(`zwp_linux_dmabuf_v1`) и при этом не гарантированно лучше уже рабочего
пути (см. находку про регресс с `mesa-dri-gallium`). GPU-ускорение
остаётся открытым, не решённым вопросом -- не закрыто, просто явно вне
объёма текущего спринта; реализуемо в будущем только через открытый
`linux-dmabuf` + либо дождавшись/бэкпортировав `panthor`, либо
переоценив это решение при появлении новой информации (например, более
новое ядро в будущем OTA/сборке).

## Последствия

- Change 7 работает над тем же классом бага, что и упал на телефоне в
  Change 6 (`invalid value ... for the size of the input`), но теперь
  известно, что это НЕ GPU-driver вопрос -- сужает расследование до
  различий между headless/qemu и реальным физическим запуском через
  `saai-appd`'s sandbox, либо до состава самого тестового пакета.
- `saai-displayd` не получает `zwp_linux_dmabuf_v1` в этом спринте --
  явная, не молчаливая граница scope, как и в Change 4 с settings-
  порталом.
- Любое будущее решение упаковать `mesa-dri-gallium` (даже просто ради
  `llvmpipe`) требует отдельной физической проверки на регресс,
  аналогичной той, что обнаружена здесь -- не считать "software GL
  driver есть в пакете" синонимом "рендеринг работает или работает
  лучше".
- Проприетарный Mali/Android-HAL путь остаётся закрытым по архитектурным
  причинам (не лицензионным -- хотя это тоже отдельный, не
  рассмотренный здесь вопрос при использовании factory-блобов),
  задокументирован как сознательно не выбранный, не как "не
  рассматривался".

## Обновление: реальная попытка бэкпорта panthor -- дальше, чем ожидалось, и с точным местом остановки (2026-09-15/16)

По запросу пойти дальше spike-уровня этого ADR и реально попробовать
поднять открытый `panthor` (а не просто оценить объём) -- сделана
полная попытка, вплоть до физической загрузки собранных модулей на
реальном устройстве. Итог: три из четырёх собранных модулей грузятся
и работают на реальном ядре без единой ошибки; четвёртый (`panthor.
ko` сам) физически пробует железо и корректно, безопасно отваливается
на первом же шаге -- с точным, не гипотетическим диагнозом, почему.

### Подпись модулей и lockdown -- не стена

`CONFIG_MODULE_SIG_FORCE` не установлен, `CONFIG_SECURITY_LOCKDOWN_LSM`
не установлен -- неподписанные (tainted) модули физически можно
загружать. Это не тот же класс блокировки, что GSA у голоса (ADR-092).

### Точное дерево ядра -- нашлось, но без официального манифеста

`kernel/common` (`android.googlesource.com`) на ветке `android14-6.1-
lts`, коммит `1fd39c9383c2` ("Merge 6.1.157 into android14-6.1-lts"),
даёт SUBLEVEL, побайтово совпадающий с `uname -r` устройства. Но
официального `repo`-манифеста для точной комбинации "Pixel 7 (pantah)
+ ядро 6.1 + брендинг android14" не существует публично -- у pantah
в манифестах 6.1 начинается только с android15. Взято ближайшее
воспроизводимое: общий ACK-коммит с точным номером патч-версии.

### Тулчейн: KCFI-хеши эмпирически подтверждены идентичными

`CONFIG_CFI_CLANG=y`, `CONFIG_CFI_PERMISSIVE` не установлен -- жёсткий
KCFI, неверный компилятор рискует паникой ядра при `insmod`, не просто
ошибкой сборки. Точный внутренний Android-clang (`r487747c`) не нашёлся
публично (вычищен из видимой истории `prebuilts/clang/host/linux-x86`).
Вместо archaeology -- физическая проверка: собран тестовый `.c` с двумя
реальными сигнатурами функций ядра (`generic_file_llseek`,
`simple_attr_read`) через ванильный upstream LLVM 17.0.2 (официальный
релиз с github.com/llvm/llvm-project) с `-fsanitize=kcfi`, и
дизассемблирован результат. Оба embedded type-hash слова оказались
**побитово идентичны** реальным `__kcfi_typeid_*` из настоящего
заводского `.ko` (`0xe61887de`, `0xe866e2f4` -- проверено дважды,
разными сигнатурами). Причина: KCFI-хеш -- чистая функция от
Itanium-mangled сигнатуры типа, вычисляется в стабильной части
Clang'а, не в PGO/BOLT/mlgo-патчах Android-форка. Так что ванильный
LLVM 17.0.2 безопасен для этой конкретной задачи.

### `struct module`'s layout реально зависит от `.config`

Первая попытка `insmod` дала `disagrees about version of symbol
module_layout` даже при точном совпадении `vermagic`-строки (через
`.scmversion`). Причина найдена чтением `include/linux/module.h`:
`CONFIG_DEBUG_INFO_BTF_MODULES` добавляет в `struct module` поля
`btf_data`/`btf_data_size` -- реальное расширение размера структуры.
На устройстве этот конфиг включён (там есть `pahole`); в первой
локальной сборке -- нет (`pahole` не был установлен на R620). Установка
`dwarves`, включение `CONFIG_DEBUG_INFO_BTF_MODULES=y`, полная
пересборка -- разногласие исчезло. Отдельная ловушка по пути: попытка
одновременно синхронизировать `CONFIG_TRIM_UNUSED_KSYMS=y` с пустым
whitelist обрушила `Module.symvers` с 15735 до 1357 записей (пустой
whitelist -- значит "обрезать всё") -- пришлось откатить именно эту
часть, `TRIM_UNUSED_KSYMS` не влияет на `struct module`, значит
безопасно оставить выключенным локально.

### Реальный экспорт символов уже устройства ⊊ то, что есть в исходниках

`CONFIG_TRIM_UNUSED_KSYMS=y` на РЕАЛЬНОМ устройстве (в отличие от
локальной сборки) означает: символ может существовать в коде ядра
(и даже быть `EXPORT_SYMBOL`) и всё равно быть недоступен модулям,
если его нет в кураторском `android/abi_gki_aarch64_pixel` (и
остальных vendor-списках, они уже лежат прямо в дереве исходников).
Проверка ВСЕХ внешних символов всех 4 модулей против объединённого
списка из всех `abi_gki_aarch64_*`-файлов поймала это до, а не во
время `insmod`-цикла -- но `kvrealloc` (сигнатура сменилась ещё и
между версиями ядра, отдельная находка) проскочила при первой
проверке и подтвердилась только реальным `insmod`: `Unknown symbol
kvrealloc`. Итоговый список того, что есть в коде mainline, но не
экспортируется на этом реальном устройстве: `kvrealloc`, `cancel_work`
(есть `cancel_work_sync`), `__drmm_mutex_release` (обвязка
`drmm_mutex_init`), `kmem_cache_alloc_bulk`/`kmem_cache_free_bulk`
(есть поштучные `kmem_cache_alloc`/`_free`). Всё заменено локальными
реализациями через уже доступные примитивы -- не изменения ABI, чисто
обходные пути на уровне вызывающего кода.

### `struct drm_gem_object`'s ABI: BTF -- решающий инструмент

`drm_gpuvm` в mainline ожидает поле `gpuva` прямо в `struct
drm_gem_object`. Проверка через `/sys/kernel/btf/vmlinux` (реально
присутствует на устройстве) и `bpftool btf dump` подтвердила: у
реального ядра этого поля нет. Добавление его в локальную копию
заголовка означало бы рассинхронизацию layout с уже скомпилированным
`vmlinux` -- вместо этого `drm_gpuvm.c`'s 10 точек использования
переведены на отдельную side-table (hashtable по указателю на объект),
общая структура не тронута. Тот же BTF-инструмент -- рекомендуемый
способ проверять подобные вопросы впредь, не гадать.

### Итог: 3 из 4 модулей работают, четвёртый корректно и безопасно отказывает

Собранный бандл (`drm_exec.ko`, `drm_gpuvm.ko`, `gpu-sched.ko` --
принесённый из mainline v6.12 целиком, поскольку `CONFIG_DRM_SCHED` в
реальном ядре вообще не собран, значит риска для существующих
драйверов нет -- и `panthor.ko`, ~13000 строк) физически загружен на
устройство в порядке возрастания риска. `insmod` каждого из первых
трёх дал `exit 0`, ни одной ошибки в `dmesg`, устройство оставалось
полностью отзывчивым. `panthor.ko` тоже загрузился (`exit 0`) -- но
чтобы проверить реальный probe, потребовалось добавить `arm,malit6xx`
(реальный `compatible` GPU-узла устройства, не совпадающий со
штатными `rockchip,rk3588-mali`/`arm,mali-valhall-csf` в mainline) в
`dt_match[]`, локальный, не upstream патч. После этого probe
корректно и безопасно провалился на самом первом шаге:
`devm_clk_get(dev, NULL)` вернул `-ENOENT`, реальный GPU MMIO ни разу
не читался -- потому что devicetree-узел не содержит свойства
`clocks` вообще (только Samsung-проприетарные `gpu0_cmu_cal_id`/
`gpu1_cmu_cal_id`, схема управления частотой/питанием CMU/CAL, не
generic Linux clock framework). Это НЕ провал бэкпорта -- это точный,
физически подтверждённый диагноз следующего реального шага.

## Решение (обновлено)

Открытый `panthor` физически МОЖЕТ быть собран и загружен на этом
устройстве без единой правки в общих подсистемах ядра (`drm_gem.h`,
`drm_sched`, GEM/dma-resv API) -- весь риск был локализован в наших
собственных 4 модулях через side-table и точечные compat-обвязки.
Реальный bring-up GPU (а не просто успешный `insmod`) требует
отдельной, отдельно оцениваемой задачи: переписать
`panthor_device_init()`'s управление частотой/питанием под Samsung's
CMU/CAL API вместо `devm_clk_get`, что само по себе:
(а) не задокументировано публично для Tensor G2/gs201,

## Финальное уточнение: почему CAL/ACPM-путь закрыт, не просто отложен (2026-09-16)

Продолжая от найденного диагноза (нужен clock/power backend под
Samsung CMU/CAL вместо `devm_clk_get`) -- проверено, дошло ли это до
реального тупика или просто до следующей задачи по объёму сравнимой
с уже сделанной. Ответ: структурный тупик, не вопрос объёма работы.

`clk_exynos_gs.ko` (уже загружен на устройстве) реально экспортирует
`cal_vclk_enable`/`cal_vclk_dfs_set_rate`/`cal_vclk_disable` и
регистрируется как настоящий Linux common-clock-framework provider
(`samsung_clk_of_add_provider`) -- это НЕ полностью непубличная схема,
как казалось изначально. Но: (а) реальный GPU devicetree-узел не
содержит свойства `clocks`, только Samsung-специфичные
`gpu0_cmu_cal_id`/`gpu1_cmu_cal_id` (сырые значения `0x0B040006`/
`0x0B040005`), то есть достучаться до этого клока через штатный
`devm_clk_get()`/devicetree-phandle в принципе нельзя без live
DT-overlay; (б) прямой вызов `cal_vclk_enable()` по этим ID
дизассемблирован (`llvm-objdump` по `clk_exynos_gs.ko`) -- функция
принимает `struct vclk *`, с байтом-тегом типа на смещении `0x1c` и
spinlock-защищённым состоянием на `0x18`/`0x20`, но **ни одна
экспортированная функция не резолвит CAL ID в `struct vclk *`** --
эта таблица приватна внутри модуля. Единственный обходной путь --
`kallsyms_lookup_name()` для поиска этой внутренней таблицы вслепую по
дампу памяти -- но эта функция намеренно не экспортируется ядру с
Linux 5.7+ (подтверждено: отсутствует в `Module.symvers` этого
дерева), именно чтобы внешние модули не могли делать то, что здесь
потребовалось бы. Дальше -- это уже kprobe-обход намеренно
поставленного барьера защиты ядра, тот же класс границы, что GSA
firmware authentication у голоса (ADR-092) -- решено не переходить,
не потому что не получилось бы технически, а потому что это уже не
легитимная инженерная задача, а обход защиты.

### Итоговый статус GPU-направления

- Открытый `panthor`-стек (drm_gpuvm/drm_exec/drm_sched/panthor)
  реально собирается и грузится на этом устройстве -- подтверждено
  физически, не в теории.
- Реальный GPU bring-up (не просто успешный `insmod`) требует clock/
  power control через Samsung CMU/CAL API, доступ к которому для
  внешнего кода закрыт архитектурно (нет публичного lookup-пути от
  CAL ID к `struct vclk *`), не просто недокументирован.
- Это тот же класс закрытия, что проприетарный Mali/Android HAL путь
  выше в этом же ADR -- сознательно не продолженный, а не "не
  рассмотренный".
- Рабочее дерево (`/home/mike/panthor-backport/`) остаётся полезным
  артефактом (панthor реально грузится, полезно для будущих экспериментов
  не требующих реального управления частотой/питанием), но дальнейшее
  движение к полноценному GPU-ускорению на этом железе закрыто до
  появления либо публичной документации CAL API, либо официального
  Google-манифеста с реальным исходником `clk-exynos-gs`.
