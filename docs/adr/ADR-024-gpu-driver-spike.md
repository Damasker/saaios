# ADR-024: GPU-рендеринг на panther -- ни один драйверный путь не доступен в разумном объёме

## Статус

Принято, 2026-09-10.

## Контекст

Change 6 (S08) физически подтвердил, что `/lib`-reveal механизм sandbox
даёт динамически слинкованному Alpine-бинарнику выполниться, но
тестовое GTK4-приложение упало на попытке рендеринга: `Ngl`/`GL`/
`Vulkan`-рендереры отказали инициализироваться (нет GPU-драйвера в
минимальном пакете), откат на Cairo software-путь упал на `Unable to
create Cairo image surface: invalid value ... for the size of the
input` -> `Segmentation fault`. Перед тем, как переходить к Change 7
(настоящие GTK/Qt демо, физическая приёмка), нужно было отдельно
ответить на узкий вопрос: существует ли вообще практический путь к
GPU-ускоренному рендерингу на этом железе, и стоит ли Change 7 на него
рассчитывать.

## Находка

Устройство (Pixel 7 / Tensor G2) физически подтверждено содержащим
рабочий Mali GPU:

- `/sys/firmware/devicetree/base/mali@28000000/` -- реальный DT-узел с
  полными DVFS/power-таблицами (`gpu_dvfs_table_v1/v2`,
  `gpu_dvfs_governor`, `slc-acpm/gpu_g0_p8` и т.п.) -- GPU физически
  описан прошивкой устройства.
- Текущее ядро (`uname -a`): `6.1.157-android14-11-gbd23337e42e7-
  ab14791245` -- это настоящий Google Android Common Kernel (GKI)
  ветки android14-6.1, собранный тем же billing-процессом, что и
  штатный Pixel 7 (`clang 17.0.2, +pgo +bolt +lto`), не кастомное с
  нуля ядро -- уже подтверждено 118 реальными vendor-модулями (`wifi
  bcmdhd4389`, `pcie_exynos_gs`, `cs40l26` audio и т.д.), загруженными
  на боевом устройстве.
- `zcat /proc/config.gz | grep CONFIG_DRM_PANFROST` -> `is not set`.
  Открытый Mesa-совместимый DRM-драйвер (panfrost -- для более старых
  Bifrost/Midgard GPU) явно выключен в сборке этого ядра. `/dev/dri/
  card0` существует, но это `exynos-drm` -- дисплейный (KMS/scanout)
  драйвер, уже используемый `saai-displayd` (S02/S03) для
  framebuffer -- не 3D/render-нода. Ни `/dev/mali*`, ни `/dev/kgsl*` не
  существует; ни один GPU-модуль (`mali`/`panfrost`/`panthor`) не
  загружен (`lsmod` -- 118 модулей, ни один не совпадает).

Проверены оба возможных пути вперёд:

**1. Проприетарный стек ARM/Google (тот, что стоит в штатном
Android).** Локальные factory-образы (`os/targets/panther/artifacts/
factory/images/`, уже часть toolchain'а сборки) смонтированы read-only
на R620 (не на телефоне -- никакого риска для боевого устройства):
`vendor_dlkm.img` содержит `lib/modules/mali_kbase.ko`,
`mali_pixel.ko` (тот самый узел `mali@28000000`, судя по названию --
Pixel-специфичное расширение над ARM's kbase), `mali_kutf*.ko` --
собраны под ТОЧНО этот же kernel ABI (тот же factory-релиз, что и
загруженное ядро). `vendor.img` содержит полный userspace: `lib64/egl/
libGLES_mali.so`, `lib64/hw/vulkan.mali.so`, `lib64/hw/gralloc.
default.so`, `firmware/mali_csffw-r54p{0,1,2,3}.bin` -- то есть
технически ядро-часть стека физически присутствует и ABI-совместима.
Однако: `strings libGLES_mali.so | grep -i wayland/gbm` -- **пусто**.
Блоб не содержит ни единого упоминания Wayland или GBM платформы --
собран исключительно под Android's EGL_PLATFORM_ANDROID
(ANativeWindow/gralloc HAL/SurfaceFlinger). Чтобы использовать его
вообще, потребовалось бы реализовать существенный слой совместимости
с Android HAL (gralloc mapper, hwbinder-заглушки, ANativeWindow) --
то, что проекты вроде Waydroid делают, запуская ПОЛНЫЙ Android-контейнер
со своим Binder/HAL стеком, а не добавляя одну библиотеку. Несоразмерно
любому spike, и прямо противоречит уже устоявшемуся в проекте
предпочтению минимальных, полностью открытых, аудируемых компонентов
(Alpine пакеты вместо проприетарных блобов везде, где до сих пор был
такой выбор).

**2. Открытый Mesa-стек (panfrost/panthor).** Правильный драйвер для
Mali-G710 (Valhall, второе поколение, CSF/command-stream-frontend) --
`panthor`, вошедший в mainline Linux ядро начиная примерно с 6.10.
Работающее на устройстве ядро -- 6.1.157, GKI-залоченное (Google
фиксирует KMI/ABI для GKI-сборок специально для того, чтобы vendor-
модули оставались совместимыми без пересборки ядра) -- т.е. backport
`panthor` (или даже более старого `panfrost`, который для Valhall/CSF
GPU в принципе не подходит -- рассчитан на предыдущее поколение) через
~9 минорных версий ядра, включая существенно изменившуюся за это время
DRM scheduler/dma-fence инфраструктуру -- многонедельная задача с
неопределённым результатом, не spike-масштаба работа.

Отдельно, независимо от выбора драйвера: Alpine предоставляет
`mesa-dri-gallium` (24.0.9-r1, единая `libgallium_dri.so`, 27 MiB,
включает `llvmpipe` -- чистый CPU-рендеринг без GPU вообще, плюс
зависимость `llvm17-libs`, 136 MiB) -- установлен в тестовый sysroot на
R620 и физически проверен headless через `qemu-aarch64-static` против
уже работающего `saai-displayd`: `libEGL warning: egl: failed to
create dri2 screen` -- EGL's DRI2/Wayland-путь требует
`zwp_linux_dmabuf_v1` от компоситора для обмена буферами, которого
`saai-displayd` не реализует (см. Current state в S08-toolkit-
compatibility.md -- уже задокументированный пробел). То есть даже
чистое CPU-рендеринг (`llvmpipe`) без единого проприетарного байта не
может дойти до экрана через GTK4's EGL-путь без отдельной, довольно
существенной протокольной работы над `saai-displayd` (тот же класс
задачи, что `wl_data_device_manager`/`text-input-v3`, Change 2/3, но
для `linux-dmabuf`).

**Неожиданная находка.** До установки `mesa-dri-gallium` тот же
headless `gtk4-demo` через `qemu-aarch64-static` против того же
`saai-displayd` (Change 4) **успешно** рендерил и коммитил кадр --
`saai-displayd`'s лог подтверждает `commit on surface ..., frame
sha256=926ea70d...` -- то есть плейн Cairo/`wl_shm`-путь (SHM, без
EGL/DRI/GBM/dmabuf вообще) у GTK4 УЖЕ работал в headless-окружении без
единого GPU-компонента. После установки `mesa-dri-gallium` тот же
запуск (без каких-либо других изменений) стал завершаться штатно
(`exit 0`), но **без** коммита кадра -- клиент подключается
(`client connected`, `new xdg_toplevel`, `commit ... (no buffer)`), но
не доходит до финального `commit` с буфером и тихо завершается. Само
присутствие пакета `mesa-dri-gallium` в путях поиска меняет то, какой
рендерер GTK4/GDK выбирает первым, и, судя по всему, делает это в
сторону худшего результата для headless/qemu-случая, а не лучшего.
Причина не расследована дальше (не входит в объём этого spike) --
зафиксировано как предупреждение для Change 7: **не паковать
`mesa-dri-gallium` бездумно "на всякий случай"**, это не бесплатное
добавление.

Раздельно от вопроса GPU: реальный крэш на телефоне (Change 6,
`Unable to create Cairo image surface: invalid value ... for the size
of the input`) **не воспроизводится** в headless/qemu окружении с тем
же `gtk4-demo` и тем же `saai-displayd` (тот же кадр успешно
коммитится). Значит это не общий баг Cairo/Wayland-пути в GTK4 как
таковой, а что-то специфичное для физического запуска через
`saai-appd`'s sandbox (либо отличие в собранном для телефона пакете --
Change 6-тестовый пакет включал только `bin/`+`lib/`, без большей части
`usr/share`/локалей/`etc`, что мог использовать сам GDK при вычислении
размера поверхности,-- либо отличие реального `saai-displayd` на
панели устройства от headless-сборки). Требует отдельного
расследования в рамках Change 7, не блокируется этим ADR.

## Решение

Change 7 нацеливается ТОЛЬКО на software-рендеринг через существующий
`wl_shm`/Cairo-путь GTK4/Qt -- уже подтверждено физически рабочим в
headless-окружении (Change 4, до появления `mesa-dri-gallium` в
sysroot'е). Ни проприетарный Mali-блоб, ни `mesa-dri-gallium`/llvmpipe,
ни backport `panthor` не входят в объём Change 7 -- каждый из них либо
несоразмерно велик (Android HAL shim, backport ядра), либо требует
предварительной протокольной работы над `saai-displayd`
(`zwp_linux_dmabuf_v1`) и при этом не гарантированно лучше уже рабочего
пути (см. находку про регресс с `mesa-dri-gallium`). GPU-ускорение
остаётся открытым, не решённым вопросом -- не закрыто, просто явно вне
объёма текущего спринта; реализуемо в будущем только через открытый
`linux-dmabuf` + либо дождавшись/бэкпортировав `panthor`, либо
переоценив это решение при появлении новой информации (например, более
новое ядро в будущем OTA/сборке).

## Последствия

- Change 7 работает над тем же классом бага, что и упал на телефоне в
  Change 6 (`invalid value ... for the size of the input`), но теперь
  известно, что это НЕ GPU-driver вопрос -- сужает расследование до
  различий между headless/qemu и реальным физическим запуском через
  `saai-appd`'s sandbox, либо до состава самого тестового пакета.
- `saai-displayd` не получает `zwp_linux_dmabuf_v1` в этом спринте --
  явная, не молчаливая граница scope, как и в Change 4 с settings-
  порталом.
- Любое будущее решение упаковать `mesa-dri-gallium` (даже просто ради
  `llvmpipe`) требует отдельной физической проверки на регресс,
  аналогичной той, что обнаружена здесь -- не считать "software GL
  driver есть в пакете" синонимом "рендеринг работает или работает
  лучше".
- Проприетарный Mali/Android-HAL путь остаётся закрытым по архитектурным
  причинам (не лицензионным -- хотя это тоже отдельный, не
  рассмотренный здесь вопрос при использовании factory-блобов),
  задокументирован как сознательно не выбранный, не как "не
  рассматривался".

## Обновление: реальная попытка бэкпорта panthor -- дальше, чем ожидалось, и с точным местом остановки (2026-09-15/16)

По запросу пойти дальше spike-уровня этого ADR и реально попробовать
поднять открытый `panthor` (а не просто оценить объём) -- сделана
полная попытка, вплоть до физической загрузки собранных модулей на
реальном устройстве. Итог: три из четырёх собранных модулей грузятся
и работают на реальном ядре без единой ошибки; четвёртый (`panthor.
ko` сам) физически пробует железо и корректно, безопасно отваливается
на первом же шаге -- с точным, не гипотетическим диагнозом, почему.

### Подпись модулей и lockdown -- не стена

`CONFIG_MODULE_SIG_FORCE` не установлен, `CONFIG_SECURITY_LOCKDOWN_LSM`
не установлен -- неподписанные (tainted) модули физически можно
загружать. Это не тот же класс блокировки, что GSA у голоса (ADR-092).

### Точное дерево ядра -- нашлось, но без официального манифеста

`kernel/common` (`android.googlesource.com`) на ветке `android14-6.1-
lts`, коммит `1fd39c9383c2` ("Merge 6.1.157 into android14-6.1-lts"),
даёт SUBLEVEL, побайтово совпадающий с `uname -r` устройства. Но
официального `repo`-манифеста для точной комбинации "Pixel 7 (pantah)
+ ядро 6.1 + брендинг android14" не существует публично -- у pantah
в манифестах 6.1 начинается только с android15. Взято ближайшее
воспроизводимое: общий ACK-коммит с точным номером патч-версии.

### Тулчейн: KCFI-хеши эмпирически подтверждены идентичными

`CONFIG_CFI_CLANG=y`, `CONFIG_CFI_PERMISSIVE` не установлен -- жёсткий
KCFI, неверный компилятор рискует паникой ядра при `insmod`, не просто
ошибкой сборки. Точный внутренний Android-clang (`r487747c`) не нашёлся
публично (вычищен из видимой истории `prebuilts/clang/host/linux-x86`).
Вместо archaeology -- физическая проверка: собран тестовый `.c` с двумя
реальными сигнатурами функций ядра (`generic_file_llseek`,
`simple_attr_read`) через ванильный upstream LLVM 17.0.2 (официальный
релиз с github.com/llvm/llvm-project) с `-fsanitize=kcfi`, и
дизассемблирован результат. Оба embedded type-hash слова оказались
**побитово идентичны** реальным `__kcfi_typeid_*` из настоящего
заводского `.ko` (`0xe61887de`, `0xe866e2f4` -- проверено дважды,
разными сигнатурами). Причина: KCFI-хеш -- чистая функция от
Itanium-mangled сигнатуры типа, вычисляется в стабильной части
Clang'а, не в PGO/BOLT/mlgo-патчах Android-форка. Так что ванильный
LLVM 17.0.2 безопасен для этой конкретной задачи.

### `struct module`'s layout реально зависит от `.config`

Первая попытка `insmod` дала `disagrees about version of symbol
module_layout` даже при точном совпадении `vermagic`-строки (через
`.scmversion`). Причина найдена чтением `include/linux/module.h`:
`CONFIG_DEBUG_INFO_BTF_MODULES` добавляет в `struct module` поля
`btf_data`/`btf_data_size` -- реальное расширение размера структуры.
На устройстве этот конфиг включён (там есть `pahole`); в первой
локальной сборке -- нет (`pahole` не был установлен на R620). Установка
`dwarves`, включение `CONFIG_DEBUG_INFO_BTF_MODULES=y`, полная
пересборка -- разногласие исчезло. Отдельная ловушка по пути: попытка
одновременно синхронизировать `CONFIG_TRIM_UNUSED_KSYMS=y` с пустым
whitelist обрушила `Module.symvers` с 15735 до 1357 записей (пустой
whitelist -- значит "обрезать всё") -- пришлось откатить именно эту
часть, `TRIM_UNUSED_KSYMS` не влияет на `struct module`, значит
безопасно оставить выключенным локально.

### Реальный экспорт символов уже устройства ⊊ то, что есть в исходниках

`CONFIG_TRIM_UNUSED_KSYMS=y` на РЕАЛЬНОМ устройстве (в отличие от
локальной сборки) означает: символ может существовать в коде ядра
(и даже быть `EXPORT_SYMBOL`) и всё равно быть недоступен модулям,
если его нет в кураторском `android/abi_gki_aarch64_pixel` (и
остальных vendor-списках, они уже лежат прямо в дереве исходников).
Проверка ВСЕХ внешних символов всех 4 модулей против объединённого
списка из всех `abi_gki_aarch64_*`-файлов поймала это до, а не во
время `insmod`-цикла -- но `kvrealloc` (сигнатура сменилась ещё и
между версиями ядра, отдельная находка) проскочила при первой
проверке и подтвердилась только реальным `insmod`: `Unknown symbol
kvrealloc`. Итоговый список того, что есть в коде mainline, но не
экспортируется на этом реальном устройстве: `kvrealloc`, `cancel_work`
(есть `cancel_work_sync`), `__drmm_mutex_release` (обвязка
`drmm_mutex_init`), `kmem_cache_alloc_bulk`/`kmem_cache_free_bulk`
(есть поштучные `kmem_cache_alloc`/`_free`). Всё заменено локальными
реализациями через уже доступные примитивы -- не изменения ABI, чисто
обходные пути на уровне вызывающего кода.

### `struct drm_gem_object`'s ABI: BTF -- решающий инструмент

`drm_gpuvm` в mainline ожидает поле `gpuva` прямо в `struct
drm_gem_object`. Проверка через `/sys/kernel/btf/vmlinux` (реально
присутствует на устройстве) и `bpftool btf dump` подтвердила: у
реального ядра этого поля нет. Добавление его в локальную копию
заголовка означало бы рассинхронизацию layout с уже скомпилированным
`vmlinux` -- вместо этого `drm_gpuvm.c`'s 10 точек использования
переведены на отдельную side-table (hashtable по указателю на объект),
общая структура не тронута. Тот же BTF-инструмент -- рекомендуемый
способ проверять подобные вопросы впредь, не гадать.

### Итог: 3 из 4 модулей работают, четвёртый корректно и безопасно отказывает

Собранный бандл (`drm_exec.ko`, `drm_gpuvm.ko`, `gpu-sched.ko` --
принесённый из mainline v6.12 целиком, поскольку `CONFIG_DRM_SCHED` в
реальном ядре вообще не собран, значит риска для существующих
драйверов нет -- и `panthor.ko`, ~13000 строк) физически загружен на
устройство в порядке возрастания риска. `insmod` каждого из первых
трёх дал `exit 0`, ни одной ошибки в `dmesg`, устройство оставалось
полностью отзывчивым. `panthor.ko` тоже загрузился (`exit 0`) -- но
чтобы проверить реальный probe, потребовалось добавить `arm,malit6xx`
(реальный `compatible` GPU-узла устройства, не совпадающий со
штатными `rockchip,rk3588-mali`/`arm,mali-valhall-csf` в mainline) в
`dt_match[]`, локальный, не upstream патч. После этого probe
корректно и безопасно провалился на самом первом шаге:
`devm_clk_get(dev, NULL)` вернул `-ENOENT`, реальный GPU MMIO ни разу
не читался -- потому что devicetree-узел не содержит свойства
`clocks` вообще (только Samsung-проприетарные `gpu0_cmu_cal_id`/
`gpu1_cmu_cal_id`, схема управления частотой/питанием CMU/CAL, не
generic Linux clock framework). Это НЕ провал бэкпорта -- это точный,
физически подтверждённый диагноз следующего реального шага.

## Решение (обновлено)

Открытый `panthor` физически МОЖЕТ быть собран и загружен на этом
устройстве без единой правки в общих подсистемах ядра (`drm_gem.h`,
`drm_sched`, GEM/dma-resv API) -- весь риск был локализован в наших
собственных 4 модулях через side-table и точечные compat-обвязки.
Реальный bring-up GPU (а не просто успешный `insmod`) требует
отдельной, отдельно оцениваемой задачи: переписать
`panthor_device_init()`'s управление частотой/питанием под Samsung's
CMU/CAL API вместо `devm_clk_get`, что само по себе:
(а) не задокументировано публично для Tensor G2/gs201,
(б) требует реверс-инжиниринга либо proprietary kbase's использования
    той же devicetree-схемы,
(в) отдельный, не малый объём работы, сравнимый по духу с этим самым
    бэкпортом, но не бэкпорт кода, а bring-up конкретного SoC.

## Финальное уточнение: почему CAL/ACPM-путь закрыт, не просто отложен (2026-09-16)

Продолжая от найденного диагноза (нужен clock/power backend под
Samsung CMU/CAL вместо `devm_clk_get`) -- проверено, дошло ли это до
реального тупика или просто до следующей задачи по объёму сравнимой
с уже сделанной. Ответ: структурный тупик, не вопрос объёма работы.

`clk_exynos_gs.ko` (уже загружен на устройстве) реально экспортирует
`cal_vclk_enable`/`cal_vclk_dfs_set_rate`/`cal_vclk_disable` и
регистрируется как настоящий Linux common-clock-framework provider
(`samsung_clk_of_add_provider`) -- это НЕ полностью непубличная схема,
как казалось изначально. Но: (а) реальный GPU devicetree-узел не
содержит свойства `clocks`, только Samsung-специфичные
`gpu0_cmu_cal_id`/`gpu1_cmu_cal_id` (сырые значения `0x0B040006`/
`0x0B040005`), то есть достучаться до этого клока через штатный
`devm_clk_get()`/devicetree-phandle в принципе нельзя без live
DT-overlay; (б) прямой вызов `cal_vclk_enable()` по этим ID
дизассемблирован (`llvm-objdump` по `clk_exynos_gs.ko`) -- функция
принимает `struct vclk *`, с байтом-тегом типа на смещении `0x1c` и
spinlock-защищённым состоянием на `0x18`/`0x20`, но **ни одна
экспортированная функция не резолвит CAL ID в `struct vclk *`** --
эта таблица приватна внутри модуля. Единственный обходной путь --
`kallsyms_lookup_name()` для поиска этой внутренней таблицы вслепую по
дампу памяти -- но эта функция намеренно не экспортируется ядру с
Linux 5.7+ (подтверждено: отсутствует в `Module.symvers` этого
дерева), именно чтобы внешние модули не могли делать то, что здесь
потребовалось бы. Дальше -- это уже kprobe-обход намеренно
поставленного барьера защиты ядра, тот же класс границы, что GSA
firmware authentication у голоса (ADR-092) -- решено не переходить,
не потому что не получилось бы технически, а потому что это уже не
легитимная инженерная задача, а обход защиты.

### Итоговый статус GPU-направления (устарел -- см. исправление ниже)

- Открытый `panthor`-стек (drm_gpuvm/drm_exec/drm_sched/panthor)
  реально собирается и грузится на этом устройстве -- подтверждено
  физически, не в теории.
- Реальный GPU bring-up (не просто успешный `insmod`) требует clock/
  power control через Samsung CMU/CAL API, доступ к которому для
  внешнего кода закрыт архитектурно (нет публичного lookup-пути от
  CAL ID к `struct vclk *`), не просто недокументирован.
- Это тот же класс закрытия, что проприетарный Mali/Android HAL путь
  выше в этом же ADR -- сознательно не продолженный, а не "не
  рассмотренный".
- Рабочее дерево (`/home/mike/panthor-backport/`) остаётся полезным
  артефактом (панthor реально грузится, полезно для будущих экспериментов
  не требующих реального управления частотой/питанием), но дальнейшее
  движение к полноценному GPU-ускорению на этом железе закрыто до
  появления либо публичной документации CAL API, либо официального
  Google-манифеста с реальным исходником `clk-exynos-gs`.

## Исправление: вывод про архитектурный тупик был неверным (2026-09-16, часы спустя)

Предыдущий раздел ошибался не в методе (дизассемблирование, поиск
`kallsyms_lookup_name` в `Module.symvers` -- всё это было правильно
сделано), а в исходных данных: поиск публичного манифеста для
device-specific части ядра gs201 в прошлый раз ограничился
официальным `android.googlesource.com/kernel/manifest` (там его для
этой комбинации действительно нет). Не был проверен **публичный
GitHub-зеркал реального device-specific дерева** --
`kerneltoast/android_kernel_google_gs201` -- который содержит
`google-modules/soc/gs/drivers/soc/google/cal-if/` с полным исходником
CAL/CMUCAL, включая `cmucal_get_node(unsigned int id)`
(`EXPORT_SYMBOL_GPL`, подтверждено и в исходнике, и живым `nm` на
реальном `.ko` устройства -- `T`, не `t`) -- легальную, публичную,
GPL-лицензированную функцию резолвинга CAL ID в указатель на
CAL-структуру. Никакого обхода защиты ядра не требуется вообще --
предыдущий вывод был построен на неполном поиске, не на реальном
architectural closure.

Расшифровка ID по найденному `cmucal.h`: `gpu0/1_cmu_cal_id`
(`0x0B040006`/`0x0B040005`) -- тип `ACPM_VCLK_TYPE` (`0x0B040000`),
т.е. управление реально идёт через ACPM-мейлбокс, не голый регистр.
Но у GPU оказался и отдельный, куда более простой стандартный
Linux-клок: `GATE_GPU` (числовой ID `350` = `CLK_G3D_BASE(350)+0`,
публично задокументирован в `google-modules/soc/gs/include/
dt-bindings/clock/gs201.h`), зарегистрированный настоящим
common-clock-framework провайдером (`drivers/clk/gs/clk-gs201.c`,
`compatible = "samsung,gs201-clock"`) -- этот узел РЕАЛЬНО существует
в devicetree устройства (`clock-controller@1e080000`, `#clock-cells =
<1>`), просто без связи с GPU-узлом через `clocks=`. Написан
`panthor_compat_get_gpu_clk()` -- вручную собирает `of_phandle_args`
против этого узла с ID `350` и резолвит через штатный, экспортированный
`of_clk_get_from_provider()` (не CAL API напрямую, не хаки).

### Физический результат после этого исправления

С этим одним фиксом (плюс обход `devfreq`/regulator'а -- аналогичная
история: `operating-points-v2`/`regulator-name` тоже нет в devicetree,
DVFS у Samsung через свои `gpu_dvfs_table_v1/v2`; `panthor_devfreq_
init()` просто возвращает 0 сразу после аллокации, все вызывающие

```
panthor 28000000.mali: [drm] Features: L2:0x8130306 Tiler:0x809 Mem:0x301 MMU:0x2830 AS:0xff
panthor 28000000.mali: [drm] shader_present=0x1110055 l2_present=0x1 tiler_present=0x1
```

Это настоящая, физическая конфигурация Mali-G710 в Tensor G2, прочитанная

`GPU`/`JOB`/`MMU` заглавными, panthor -- строчными; три

именования, это другой бинарный протокол -- честно открытый вопрос,

Устройство оставалось полностью стабильным на каждом шаге, включая

## Дальше: реальная прошивка есть в формате panthor, но MCU не загружается (2026-09-16, продолжение)

По просьбе "сделать всё возможное" для графики -- пошли дальше
диагноза "нет файла прошивки" и попробовали реально её получить.

### Формат прошивки СОВПАДАЕТ -- проверено побайтово

`panthor_fw.c`'s заголовок ожидает magic `0xc3f13a6e`. Реальные
проприетарные файлы устройства (`/vendor/firmware/mali_csffw-r54p{0,1,
2,3}.bin`, `mali_csffw-legacy-r56p0.bin` -- все по ~280 КБ, не
десятки МБ) начинаются именно с этих байт (`6e 3a f1 c3`), с
`major=0` (проходит panthor'а собственную проверку
`CSF_FW_BINARY_HEADER_MAJOR_MAX=0`). ARM использует один и тот же
контейнерный формат прошивки CSF и для kbase, и для panthor -- не
два разных протокола, как предполагалось раньше.

Скопировали `mali_csffw-r54p3.bin` под ожидаемым panthor именем в
`/vendor/firmware/arm/mali/arch10.8/mali_csffw.bin` (через
`/data/saaios/firmware/...` + symlink, тот же паттерн, что уже
использован для AoC в ADR-092). Результат -- **прошивка прошла
валидацию заголовка и загрузилась**, и GPU **реально начал
исполнение**: `Unhandled Page fault in AS0 at VA 0x0` пришёл от
собственного MMU GPU (`PERM_FAULT_3`, `WRITE`) -- то есть загруженный
код физически выполнялся на командном процессоре Mali G710, не
просто лежал в памяти. `r54p0`/`legacy-r56p0` дают другую картину
(без page fault, просто таймаут) -- разные ревизии ведут себя
по-разному, но ни одна не завершает загрузку MCU
(`Failed to boot MCU (status=fatal)`, `probe failed with error -110`).

### Систематически исключены четыре гипотезы (не догадками, физическим и исходным сравнением)

Дополнительно нашли реальный, открытый (GPL) исходник kbase именно
для этого чипа -- `google-modules/gpu/borr_mali_kbase/` в том же
`kerneltoast/android_kernel_google_gs201` зеркале ("borr" -- кодовое
имя варианта Mali в Tensor G2). Сравнили пошагово с `panthor_fw.c`/
`panthor_mmu.c`:

1. **Таблица записей прошивки** -- распарсили реальный файл байт в
   байт (Python-скрипт по алгоритму `panthor_fw_load`): единственные
   ОБЯЗАТЕЛЬНЫЕ записи -- 8 штук типа 0 (IFACE), которые panthor
   полностью реализует. Все типы, которые panthor не знает (5,6,7,8,9,
   включая `PAGE_FAULT_CNT`), помечены `optional=true` в самом файле --
   их пропуск panthor'ом корректен, не баг.
2. **Layout структуры IFACE-записи** -- `flags`/`va.start`/`va.end`/
   `data.start`/`data.end`, по 4 байта каждое -- побайтово идентичен
   `parse_memory_setup_entry()` в kbase.
3. **Порядок инициализации clock/L2** -- `clk_prepare_enable()` вызывается
   до `panthor_gpu_init()`, что уже подтверждено рабочим (реальные
   регистры GPU_ID/Features читаются успешно) -- совпадает с
   kbase'вским `kbase_pm_wait_for_l2_powered()` перед загрузкой прошивки.
4. **DMA-когерентность MMU** (`pgtbl_cfg.coherent_walk`) -- ни
   `dma-coherent`, ни `system-coherency` в devicetree нет; и panthor
   (`device_get_dma_attr`), и kbase (`of_dma_is_coherent` +
   `system-coherency` override) сошлись бы на "не когерентно" одинаково.
5. **DT-based firmware quirks** (`quirks-ext`/`quirks_ext`, отдельный
   механизм в kbase для передачи прошивке аппаратных workaround'ов) --
   свойства нет в реальном devicetree, значит и это не применимо здесь.

Ни одна из этих пяти проверок не выявила расхождения -- значит
реальная причина лежит глубже: в самой конструкции MMU-таблиц
страниц (`io_pgtable`/ARM LPAE формат) или в порядке/содержимом
регистровых операций AS0, которые kbase выполняет, а panthor'у
неизвестны (в исходнике `panthor_mmu.c`/kbase'вском MMU backend'е,
~2700+ строк с каждой стороны) -- либо в недокументированном
Tensor-специфичном аппаратном нюансе, которого нет даже в этом
открытом зеркале kbase. Дальнейшее продвижение без трассировки
регистров в реальном времени (недоступно на этой ОС) means genuinely
open-ended reverse engineering, не directed debugging.

## MCU boot -- поведение недетерминировано между попытками (2026-09-16, ещё позже)

По наводке "может, экран должен быть включён" -- проверили гипотезу
про состояние дисплея (`self_refresh_active`, наша же находка из
ADR-093/HIA-15) как возможный фактор. Прямого подтверждения не
нашли, но по пути обнаружили нечто более фундаментальное: **результат
`panthor_fw_start()`'s попытки загрузки MCU меняется от попытки к
попытке на одном и том же файле прошивки, без видимых изменений
кода**:

1. Первая попытка (после серии предыдущих `insmod`/`rmmod` в течение
   долгого uptime): `WRITE` `PERM_FAULT_3` по `VA=0x0`.
2. Вторая (сразу следом, экран активен по утверждению): `READ`
   `TRANSLATION_FAULT_3` по `VA=0x02040000` -- другой адрес, другой
   тип ошибки.
3. Третья: вообще без fault, просто `status=fatal` по таймауту.
4. После **настоящей полной перезагрузки устройства** (`reboot -f` --
   первая же `reboot` без `-f` оказалась no-op на этой ОС, ничего не
   перезагрузила, хотя команда и не выдала ошибки -- сама по себе
   находка, требующая отдельного разбора в другой раз) и с активным,
   разблокированным экраном: **`status=enabled`** -- MCU реально
   продвинулся дальше по своей внутренней state machine
   (DISABLED→ENABLED→...), не свалился в FATAL, просто не успел
   просигналить о полной загрузке за 1 секунду. Единственный раз
   за всю сессию, когда `status` был НЕ `fatal`.
5. Увеличили таймаут `wait_event_timeout` в `panthor_fw_start()` с
   1000мс до 5000мс, тут же повторили (тот же чистый boot, экран
   всё ещё активен) -- **вернулось к `status=fatal`**.

Это означает: поведение реально недетерминировано между попытками,
не фиксированный логический баг (который давал бы одинаковый исход
каждый раз на одном и том же коде/файле). Гипотеза про экран не
подтвердилась однозначно -- `self_refresh_active=1` наблюдался почти
при всех попытках независимо от исхода, включая единственную "лучшую"
(`status=enabled`). Более вероятные объяснения: race condition в
последовательности инициализации самого panthor (что-то, что иногда
успевает завершиться до триггера `MCU_CONTROL_AUTO`, а иногда нет),
либо пограничная по времени аппаратная совместимость (MCU этого
конкретного SoC достоверно медленнее reference-платформ, для которых
таймауты panthor'а изначально калибровались). Раскрутить точную
причину race'а потребовало бы множества контролируемых повторов с
измерением таймингов или живой трассировки регистров -- ни то, ни
другое не сделано в рамках этой сессии.

Устройство осталось полностью стабильным через все эти попытки,
включая настоящую перезагрузку -- ни одного зависания или паники ни
разу.

## Уточнение: отказ MCU надёжно воспроизводится, варьируется только симптом (2026-09-16, финал)

Проверили ещё две конкретные вещи по итогам находок выше.

**Собственный UI-стек не влияет.** Остановили `saai-shell`/
`saai-displayd` (через штатный механизм этого же проекта -- 6 быстрых
`kill` за 60 секунд исчерпывают `UI_RESTART_BUDGET`, `native-init.c`
сам переключается на лёгкий `drm-splash`, не пришлось ничего ломать
вручную) и повторили тест в почти пустой системе -- результат тот же
`status=fatal`. WiFi (`wlan0`) сознательно не трогали -- это
единственный канал удалённого доступа к устройству в этой сессии,
его отключение оборвало бы саму возможность продолжать тестировать.

**Три попытки подряд сразу после настоящей перезагрузки -- все три
`fatal`, синхронно, без единого fault.** С увеличенным до 5с
таймаутом все три попытки дошли до `Failed to boot MCU (status=fatal)`
ровно через ~5.03-5.05 секунд после старта прошивки, без единого
`Page fault` в логе ни разу. Это меняет интерпретацию более ранней
серии из четырёх разных исходов: отказ MCU, похоже, **надёжный и
детерминированный** (всегда в итоге fatal), а варьируется только
ТОЧНЫЙ побочный симптом по пути (иногда GPU успевает засветить page
fault до того, как MCU окончательно перейдёт в fatal, иногда нет --
гонка в том, когда именно прерывание фиксируется/логируется, не в
том, удастся ли загрузка). Наблюдавшийся один раз `status=enabled`
(вместо `fatal`) при коротком 1-секундном таймауте, по всей видимости,
был просто снимком MCU в процессе перехода в fatal, а не настоящим
частичным успехом.

Итог: гипотеза про состояние экрана/self-refresh не подтвердилась --
результат одинаков что с активным экраном, что с остановленным нашим
UI, что сразу после чистой перезагрузки. Настоящая причина остаётся
там же, где и была локализована раньше (MMU/AS0 page table setup
или недокументированный аппаратный нюанс), но теперь известно
жёстче: это стабильный, воспроизводимый отказ, не редкая гонка,
которую можно было бы поймать удачным стечением условий среды.

## Настоящая регистровая трассировка -- проблема внутри самой прошивки MCU (2026-09-16, ещё позже)

По запросу создать трассировку -- на этой ОС нет внешних инструментов
(JTAG, логический анализатор), но есть `ftrace`, и есть полный
собственный исходник бэкпорта. Инструментировали сами макросы
`gpu_write`/`gpu_read` (`panthor_regs.h`) вызовом `trace_printk()` --
каждое обращение к регистру GPU теперь пишется в кольцевой буфер
ftrace с именем вызывающей функции, адресом и значением. Пересобрали,
включили `tracing_on`, прогнали попытку `insmod`, выключили трассировку
сразу после отказа, скачали `/sys/kernel/debug/tracing/trace` целиком
(91 запись, вся попытка от начала до конца). Сохранено в
`panthor-external/mcu-boot-regtrace.txt`.

Трасса читается однозначно:

1. `panthor_gpu_init_info` -- 23 чтения (GPU_ID, Features, shader/l2/
   tiler_present и т.д.) -- то же самое, что мы уже видели в `dmesg`,
   теперь с точными адресами регистров.
2. IRQ unmask (`panthor_gpu_irq_resume`/`panthor_mmu_irq_resume`/
   `panthor_job_irq_resume`) -- штатно.
3. `panthor_gpu_block_power_on`: `W 0x1a0=0x1` -- включение силового
   домена шейдеров/тайлера.
4. `lock_region`/`write_cmd` -- flush-перед-настройкой AS0, штатная
   TLB-инвалидация.
5. `panthor_mmu_as_enable`: `TRANSTAB=0xa0320000`, `MEMATTR=
   0x9c4c9f4c/0x9f9f9f9f`, `TRANSCFG=0x420001c6` -- реальная
   конфигурация MMU AS0 для прошивки. Флаги в исходнике (`AS_TRANSCFG_
   PTW_MEMATTR_WB`, `AS_TRANSCFG_PTW_RA`, `AS_TRANSCFG_ADRMODE_
   AARCH64_4K`) побитово совпадают по смыслу с тем, что kbase
   выставляет (`AS_TRANSCFG_PTW_MEMATTR_WRITE_BACK` и аналоги) --
   сверено по исходнику `mali_kbase_mmu_hw_direct.c`, не по угадыванию.
6. `panthor_fw_start`: `W 0x700=0x2` (`MCU_CONTROL_AUTO`) -- триггер
   запуска.
7. **Дальше -- 5.12 секунды (наш увеличенный таймаут) АБСОЛЮТНОЙ
   тишины на шине регистров.** Ни одного `gpu_write`/`gpu_read` со
   стороны драйвера -- он корректно ждёт прерывания
   (`wait_event_timeout`), не поллит.
8. После истечения таймаута: `panthor_fw_start: R 0x100c=0x0`
   (`JOB_INT_STAT` -- прерывания не было вообще, ни разу за все 5
   секунд) и `R 0x704=0x3` (`MCU_STATUS` = FATAL).

Это не подтверждает и не опровергает конкретную гипотезу про
MEMATTR/TRANSCFG -- значения выглядят структурно правильными
(нужные флаги на месте) -- но даёт куда более точную локализацию:
**после того, как MCU_CONTROL был записан, MCU не подаёт вообще
никаких признаков жизни через прерывания в течение всего окна
ожидания, и заканчивает во внутреннем состоянии FATAL сам, без
дополнительных действий со стороны драйвера.** Значит проблема
находится либо (а) в самих байтах конфигурации AS0 (MEMATTR/TRANSCFG),
для окончательной проверки которых нужно посчитать, что именно
вычислил бы kbase для тех же входных `va_bits`/`pa_bits`/coherent на
этом железе, и сравнить бит в бит -- не сделано (риск арифметической
ошибки при ручном подсчёте без возможности перепроверить на живом
kbase), либо (б) в самой прошивке/GPU при попытке выполнить свой
собственный код запуска, что уже за пределами того, что видно на
уровне регистров хоста.

Трассировочная инфраструктура (инструментированные `gpu_write`/
`gpu_read`) остаётся в `panthor-external/panthor/panthor_regs.h` --
готова для повторного использования при следующей попытке.


## Проверенная и отклонённая гипотеза: два power domain "top"/"cores" (2026-09-16, ещё позже)

Пользователь прислал развёрнутый технический разбор (со ссылками на
android.googlesource.com) с предложением перейти на проприетарный
`mali_kbase.ko`. Пока не переключались на эту стратегию, но по ходу
чтения открытого исходника реального kbase для этого чипа
(`google-modules/gpu/borr_mali_kbase/platform/pixel/pixel_gpu_power.c`)
нашлась конкретная, ранее упущенная зацепка для ТЕКУЩЕЙ проблемы
(MCU molчит и уходит в fatal): у реального devicetree-узла GPU есть
`power-domain-names = "top", "cores"` -- то есть ДВА именованных
power domain, а `panthor_device.c` в апстриме вообще никогда не
вызывает никакой функции привязки power domain (при этом
`<linux/pm_domain.h>` включён, но не используется) -- Linux
автоматически привязывает только ОДИН домен для platform-устройства.
Гипотеза: "top" (шина регистров) привязан неявно -- этим объясняется,
почему чтение GPU_ID/Features и запись MCU_CONTROL работают -- а
"cores" (вероятно, сами шейдеры/MCU) никогда не включается, что
идеально объясняет "AS0 настроен, запись прошла, дальше тишина".

Реализация заняла две итерации:

1. Первая попытка (`dev_pm_domain_attach_list()`, есть в исходнике
   этого ядра) собралась чисто, но на реальном устройстве `insmod`
   упал: `Unknown symbol dev_pm_domain_attach_list (err -2)` -- функция
   не экспортирована на этом устройстве (`CONFIG_TRIM_UNUSED_KSYMS`,
   тот же класс проблемы, что раньше с `kvrealloc` и другими).
2. Нашли правильную, разрешённую функцию -- `dev_pm_domain_attach_by_name()`,
   подтверждена и в `android/abi_gki_aarch64_pixel` (строка 514), и
   через `grep -w ... /proc/kallsyms` на самом устройстве (`T`).
   Точный эталон -- в том же реальном исходнике kbase,
   `gpu_pm_init()`: цикл `dev_pm_domain_attach_by_name(kbdev->dev,
   {"top","cores"}[i])` + `device_link_add(..., DL_FLAG_STATELESS)`.
   Переписали `panthor_compat_attach_power_domains()` по этому образцу
   -- пересобралось, `insmod` прошёл без ошибок про unknown symbol.

Проверка через `/sys/kernel/debug/pm_genpd/pm_genpd_summary`
подтвердила: оба домена реально привязались как потребители
`28000000.mali` (`pd-g3d`="top", `pd-embedded_g3d`="cores" -- те же
имена, что были в присланном пользователем разборе), но оба
показывали статус `off`/`suspended`. `dev_pm_domain_attach_by_name()`
только создаёт связь, а не включает домен -- нужен явный
`pm_runtime_get_sync()` на КАЖДОМ возвращённом виртуальном устройстве
домена (не на самом GPU-устройстве). Добавили `pm_runtime_enable()` +
`pm_runtime_get_sync()` в цикл привязки.

После этого `pm_genpd_summary` показал оба домена `on`/`active` --
подтверждено на полностью чистой перезагрузке (без остаточного
состояния от предыдущих `insmod`/`rmmod`, которые не отвязывают
domain -- второй `insmod` в той же сессии без ребута закономерно
поймал `-EEXIST` на повторной привязке, это отдельно диагностировано
и не спутано с реальным результатом).

**Итог решающего чистого прогона: домены реально включены (`on`/
`active` в `pm_genpd_summary`), прошивка на месте, и MCU всё равно
уходит в `fatal` ровно через 5.04с (наш увеличенный таймаут) -- то же
самое поведение, что и без привязки доменов вообще.** Гипотеза о
недостающих power domain была весьма обоснованной (подтверждена
структурой реального devicetree и точным эталонным кодом из открытого
kbase), но экспериментально отклонена: включение обоих доменов не
меняет исход. Код привязки оставлен в дереве (физически корректен и,
возможно, всё равно нужен для дальнейшей работы -- отключение GPU не
может быть лишним), но проблему не решает.

(Мелкая, не мешающая работе заметка: `pm_runtime_enable()` на
возвращённом domain-устройстве выдаёт `Unbalanced pm_runtime_enable!`
-- похоже, `dev_pm_domain_attach_by_name()` уже включает runtime PM
сам; не мешает работе, не исследовано глубже, т.к. не влияет на
решающий результат.)

Это заметно сужает круг оставшихся объяснений: дело не в питании (оба
домена доказано включены), не в прошивке (формат и байты
проверены побайтово), не в порядке настройки AS0/MCU_CONTROL
(совпадает по структуре с kbase). Остаётся либо (а) тонкая ошибка в
конкретных битах MEMATTR/TRANSCFG, которую пока нельзя перепроверить
без живого kbase-запуска рядом, либо (b) что-то ещё в реальной,
проприетарной последовательности запуска (например ACPM/CAL-уровневая
инициализация тактовой частоты и/или AGT-таймера, которую делает
Samsung/Google платформенный код kbase и которую наш бэкпорт в
принципе не воспроизводит, т.к. она не идёт через стандартный clk
framework), либо (c) сама MCU-прошивка ожидает что-то специфичное для
`kbase`, чего `panthor`, будучи независимой реализацией CSF-протокола,
не делает и структурно не может знать без документации.

## Диагностика реальным kbase вместо гадания в panthor (2026-09-16, ещё позже)

Пользователь прислал развёрнутый разбор с предложением перейти на
проприетарный `mali_kbase.ko`/`mali_pixel.ko`. Вместо использования
непроверенных прекомпилированных `.ko` под конкретную сборку
(`CP2A.260705.006`), нашли, что в уже используемом зеркале
(`kerneltoast/android_kernel_google_gs201`) лежит РЕАЛЬНЫЙ, ОТКРЫТЫЙ
(GPL) исходник `mali_kbase` и `mali_pixel` для этого же чипа --
собрали их из исходников тем же тулчейном (clang-17.0.2), что и
panthor, вместо гадания дальше над битами TRANSCFG в собственном
бэкпорте. Цель: диагностика, а не смена архитектуры -- понять, где
именно проблема (в нашем бэкпорте panthor или глубже в железе/прошивке).

Сборка оказалась заметно сложнее panthor (полноценный Android-специфичный
многомодульный build (kbase зависит от `mali_pixel` через
`Module.symvers`, оба -- от `google-modules/soc/gs/Makefile.include`),
рассчитанный на реальную оркестровку Bazel/`build_utils.sh`, которой у
нас нет). Прошли через десяток мелких, реальных несоответствий в этом
конкретном срезе исходников (не выдумки, а факты, каждое проверено):

- `Makefile.include` подключается через `$(KDIR)/../private/...` --
  сделали симлинки (`kernel-src/common/google-modules` и
  `kernel-src/private` на корень зеркала), чтобы это резолвилось без
  правки самого кода.
- Часть `-I`/`ccflags-y`, которые в реальной сборке добавляются глобально
  оркестровкой сборки (а не самими Kbuild-файлами), пришлось добавить
  вручную в `mali_pixel/Kbuild` и `borr_mali_kbase/Kbuild`
  (`soc/gs/include`, `power/mitigation`).
- `KBUILD_EXTRA_SYMBOLS` в обоих Makefile ссылается на несуществующие
  `$(OUT_DIR)/../private/...` пути -- переопределили на реальный путь
  к уже собранному `mali_pixel/Module.symvers` (для `soc/gs` и
  `power/mitigation` просто нет -- эти модули не собираем).
- `__ANDROID_COMMON_KERNEL__` не определён в нашей сборке -- часть
  compat-кода в `version_compat_defs.h` (`vm_flags_set`/`clear`)
  завязана именно на этот макрос, а не только на версию ядра --
  добавили `-D__ANDROID_COMMON_KERNEL__`.
- Несколько мест с несогласованностью между `.c` и `.h` в этом
  конкретном срезе исходника (не выдумка -- каждое подтверждено):
  `MIN`/`MAX` переопределены без `#ifndef` (в этом ядре
  `linux/minmax.h` уже их даёт); `check_padding_KBASE_IOCTL_CINSTR_GWT_DUMP`
  использует JM-only union без `#if !MALI_USE_CSF`;
  `kbase_backend_get_cycle_cnt()` читает `kbdev->last_cycle_count`,
  которого нет в структуре при `MALI_USE_CSF`; `kbase_hwaccess_pm_powerup()`
  использует необъявленную `irq_flags`; `mali_kbase_pm_driver.c` вызывает
  `trace_mali_pm_mcu_state()`/`trace_mali_pm_l2_state()` без
  `#include <mali_linux_trace.h>`; `BASEP_MEM_FIRST_FREE_FLAG` для CSF
  (бит 61) не согласован с `BASEP_MEM_FLAGS_NR_BITS=4` из uapi-заголовка
  (должен быть бит 59, как у JM) -- поправили под этот инвариант.
- `CONFIG_GOOGLE_BCL` жёстко прописан как всегда включённый в самом
  Kbuild (не наша настройка) -- вызывает `google_retrieve_bcl_handle()`/
  `google_init_gpu_ratio()` из `google-modules/power/mitigation`,
  которую не собираем. Добавили локальный stub-файл
  (`pixel_gpu_bcl_stub.c`) в сборку kbase.
- `CONFIG_MALI_PIXEL_GPU_SLC=y` тянет `pt_client_register()` (Samsung
  SLC/партиции кэша) -- падает с `-ENOSYS`, что раньше валило весь
  probe `physical-memory-group-manager` целиком; сделали ошибку не
  фатальной (SLC -- оптимизация кэша, не нужна для диагностики).

Итог сборки: **`mali_kbase.ko` и `mali_pixel.ko` полностью собрались
и слинковались из настоящего, официального, открытого исходника этого
чипа.** Первая попытка `insmod` тихо зависла в вечном
`-EPROBE_DEFER` -- драйвер не логирует ничего для отложенного probe,
а сам `kbase_platform_device_probe()` в первой же строке делает
`if (!google_retrieve_bcl_handle()) return -EPROBE_DEFER;` -- наша
заглушка возвращала `NULL`. Проверили все места использования этого
указателя во всём дереве -- нигде не разыменовывается, только
передаётся дальше в такие же заглушки -- поэтому заменили заглушку на
возврат валидного ненулевого фиктивного указателя. Это разблокировало
probe.

**Реальный kbase дошёл заметно дальше, чем можно было ожидать, и упал
на содержательной, понятной причине:**

```
mali 28000000.mali: Kernel DDK version r51p0-00eac0
mali 28000000.mali: using synchronous suspend for TOP domain
mali 28000000.mali: Failed to find GPU power domain 'pd-embedded_g3d'
mali 28000000.mali: PM init failed error = -19
```

Это НЕ тот же механизм привязки power domain, который проверяли и
отклонили в прошлом разделе (`dev_pm_domain_attach_by_name()` для
`"top"`/`"cores"` через стандартный Linux genpd, который в реальном
kbase тоже присутствует и, судя по логам, успешно отработал). Ошибка
-- из СОВЕРШЕННО ОТДЕЛЬНОГО, Samsung-специфичного пути в том же
`platform/pixel/pixel_gpu_power.c`: `pc->pm.domain =
exynos_pd_lookup_name(g3d_power_domain_name)`, где `g3d_power_domain_name`
берётся из devicetree-свойства `g3d_genpd_name`, а
`exynos_pd_lookup_name()` -- функция из ОТДЕЛЬНОГО модуля
`google-modules/soc/gs/drivers/soc/google/exynos-pd.c`, компилируемого
только при `CONFIG_EXYNOS_PMU_IF`. У нас этот конфиг не включён (и сам
модуль не собран) -- поэтому вызов буквально не компилируется
(`#if IS_ENABLED(...)`), `pc->pm.domain` остаётся `NULL`, и код
корректно репортит "не найден" -- не потому что домена нет физически
(он есть, подтверждено ранее через `pm_genpd_summary`), а потому что мы
не собрали Samsung-специфичный уровень поиска домена по имени поверх
стандартного genpd.

Исходник `exynos-pd.c` у нас есть (тот же паблик-зеркало), но это
отдельная, объёмная SoC-подсистема (`google-modules/soc/gs/drivers/soc/google/`:
`cal-if`, `exynos-pmu-if`, `exynos-pd`, вероятно `exynos-pm` и другие,
судя по `Kbuild` с `obj-$(CONFIG_...)` на добрый десяток модулей) --
по объёму сравнимая с уже проделанной работой по kbase, а не
"ещё один маленький stub". Решили сделать паузу на этом чекпоинте,
а не продолжать нарастающий ком зависимостей без подтверждения, что
это стоит продолжать.

**Ключевой вывод: и открытый бэкпорт panthor, и настоящий, официальный,
открытый kbase от Google для этого же железа независимо друг от друга
упираются в тему power domain "top"/"cores" -- но на РАЗНЫХ уровнях**
(panthor -- полностью решил вопрос привязки через стандартный Linux
genpd, но MCU всё равно не подаёт признаков жизни; kbase -- падает
раньше, на Samsung-специфичном слое поиска домена по имени, ещё до
попытки включить что-либо). Это не противоречие, а два независимых,
взаимно подтверждающих друг друга наблюдения о том, что штатная
Google-конфигурация питания GPU на этом SoC устроена сложнее, чем
голый Linux genpd -- нужен ещё и Samsung-специфичный уровень
(`exynos-pd`/`cal-if`/ACPM), который ни panthor, ни наша текущая
сборка kbase не реализуют.

## Догнали exynos_pd_lookup_name до конкретной, локализованной точки отказа (2026-09-16, ещё позже)

Пользователь подтвердил: собрать недостающий Samsung-уровень. Прежде
чем собирать `google-modules/soc/gs/drivers/soc/google/` целиком
(десятки поддиректорий -- phy, pinctrl, PCIe, iommu, ufs, thermal и
т.д., по объёму сравнимо с whole-device kernel), проверили реальное
устройство напрямую: **`exynos_pd.ko` и `exynos_pmu_if.ko` уже
загружены штатной прошивкой Android** (`lsmod` подтверждает,
`exynos_pd_lookup_name`/`exynos_pmu_read` -- оба `T` в
`/proc/kallsyms`). Собирать эти модули самим не нужно вообще -- нужно
было только заставить kbase их РЕАЛЬНО ВЫЗЫВАТЬ (флаг
`CONFIG_EXYNOS_PMU_IF` не был включён при компиляции, поэтому весь
`#if IS_ENABLED(...)` блок с вызовом просто не компилировался).

Добавили `-DCONFIG_EXYNOS_PMU_IF=1 -DCONFIG_SOC_GS201=1` (второй
понадобился для `#error "Unknown CONFIG_SOC"` в
`exynos-pmu-if.h`). На этапе линковки modpost предсказуемо не нашёл
`exynos_pmu_read` в наших локальных `Module.symvers` (она не наша,
а из уже загруженного модуля) -- понизили это через
`KBUILD_MODPOST_WARN=1` до предупреждения: настоящее разрешение
символа происходит в момент `insmod` на устройстве против уже
загруженных модулей, а не на этапе сборки.

Пересобранный `mali_kbase.ko` теперь ДЕЙСТВИТЕЛЬНО вызывает
`exynos_pd_lookup_name("pd-embedded_g3d")` (значение взято из
DT-свойства `g3d_genpd_name`, подтверждено напрямую через
`/sys/.../of_node/g3d_genpd_name`). Результат тот же: `NULL`,
`PM init failed error = -19`.

Разобрали механизм `exynos_pd_lookup_name()` по исходнику (тот же
паблик-зеркало): она перебирает **только** devicetree-узлы с
`compatible = "samsung,exynos-pd"`, для каждого доступного
(`of_device_is_available`) берёт связанный `platform_device`, читает
`pd = platform_get_drvdata(pdev)` и сравнивает `pd->name` со строкой
через `strcmp`. Проверили на реальном устройстве все предусловия этого
цикла для обоих доменов:

- `compatible` обоих узлов (`18061e00.pd-g3d`, `18062000.pd-embedded_g3d`)
  -- ровно `"samsung,exynos-pd"` (совпадает).
- `status` обоих узлов -- `okay` (доступны).
- Оба узла реально привязаны к драйверу `exynos-pd`
  (`/sys/.../driver -> .../drivers/exynos-pd`), то есть `platform_get_drvdata()`
  должен вернуть валидный указатель, а не `NULL` (иначе `pd->name`
  тут же дал бы NULL-разыменование и панику ядра, чего не произошло).

Итог: по всем внешне проверяемым признакам (compatible, status,
привязка драйвера, реальное имя genpd-домена по `pm_genpd_summary`)
лукап должен был сработать -- но не сработал. Единственное оставшееся
объяснение -- внутреннее поле `pd->name`, которое **реальный,
проприетарный** `exynos_pd.ko` на этом устройстве (не наша публичная
копия исходника, а фактическая vendor-сборка) заполняет при своём
собственном probe из какого-то отличающегося источника (не совпадает
с тем, что мы предполагаем по аналогии с открытым исходником этой же
функции). Проверить это дальше можно только заглянув внутрь уже
загруженного бинарника (например, kprobe на `exynos_pd_lookup_name`,
чтобы залогировать реальные значения `pd->name` при переборе) --
принципиально другой уровень вмешательства (отладочная интроспекция
уже работающего, реального, проприетарного модуля производителя, а
не наш собственный код), который не совершали без отдельного решения.

**Общий итог по обеим независимым попыткам (panthor и настоящий
kbase)**: оба -- разными путями, на разных уровнях абстракции --
упираются в тему конфигурации power domain "top"/"cores" для этого
чипа. Panthor полностью решил задачу привязки через стандартный Linux
genpd, но MCU всё равно не подаёт признаков жизни. Настоящий kbase
использует ДОПОЛНИТЕЛЬНЫЙ, Samsung-специфичный слой поверх genpd
(`exynos_pd_lookup_name` по имени), который тоже не срабатывает, но
уже на этапе PM-инициализации, раньше, чем MCU вообще пытается что-то
делать -- и в этом случае причина куда точнее локализована (конкретная
функция, конкретное сравнение строк), просто дальнейшая диагностика
требует отладки уже загруженного проприетарного бинарника, а не
исходного кода.

## Прямая проверка вместо гадания: pd->name полностью совпадает, реальный exynos_pd.ko всё равно возвращает NULL (2026-09-16, ещё позже)

Пользователь подтвердил: вместо инвазивного kprobe на живую функцию
написали маленький read-only диагностический модуль
(`gpu-probe-tools/pd-diag/pd_diag.c`), который делает ровно то же
самое, что `exynos_pd_lookup_name()` по открытому исходнику -- обходит
`for_each_compatible_node(..., "samsung,exynos-pd")`, резолвит
`platform_device`, читает `platform_get_drvdata()` -- и логирует
реальное значение `pd->name`, а не гадает. Поле `name` -- второй член
`struct exynos_pm_domain`, сразу после `struct generic_pm_domain
genpd`, до всех Kconfig-зависимых полей дальше по структуре, так что
его смещение не зависит от неизвестных нам настроек сборки vendor-модуля
-- только от `generic_pm_domain`, чей layout уже многократно
подтверждён (та же сборка ядра, что и везде в этой сессии). Это чистая
интроспекция через публичные API ядра (`for_each_compatible_node`,
`of_find_device_by_node`, `platform_get_drvdata`) поверх уже
загруженного, уже экспортирующего свои символы модуля -- без хуков и
без изменения работающего кода.

Результат для всех 20 доменов `samsung,exynos-pd` в реальном
devicetree, включая нужный:

```
node=/pd-embedded_g3d@18062000 available=1
  pd=000000000a945fb5 pd->name=pd-embedded_g3d
```

**`pd->name` побайтово совпадает со строкой, которую ищет kbase.**
Домен зарегистрирован, доступен, привязан к драйверу, имя точно
совпадает -- `strcmp()` в `exynos_pd_lookup_name()` по открытому
исходнику обязан был вернуть совпадение. Тем не менее реальный,
уже загруженный (проприетарный vendor-билд) `exynos_pd.ko` на этом
самом устройстве, при вызове из kbase несколькими секундами ранее,
возвращает `NULL`.

**Вывод: реальная, работающая на этом устройстве прошивка
`exynos_pd.ko` внутри устроена иначе, чем открытый исходник этой же
функции в публичном зеркале** (кроме `pt_client_register`/SLC и
`google_retrieve_bcl_handle`/BCL, которые мы уже намеренно не собирали
и просто заглушили, здесь ситуация другая: модуль РЕАЛЬНО загружен,
экспортирует нужный символ, но ведёт себя не так, как показывает
открытый код с тем же именем функции). Дальнейшая локализация точной
причины потребовала бы разбора самого бинарника `exynos_pd.ko`
(дизассемблирование) или live-инструментации уже работающей функции
(kprobe/kretprobe) -- решили не продолжать в эту сторону без отдельного
осознанного решения, поскольку это переходит в разбор чужого
скомпилированного бинарника, а не работу с исходным кодом.

**Итог всей диагностики (panthor + реальный kbase + прямая проверка
exynos-pd) сходится в одной точке**: настоящая проблема физически
находится в связке "как этот конкретный vendor-билд Samsung/Google
на самом деле включает питание GPU-доменов на этом чипе" -- то есть
именно там, где ни открытый исходник panthor, ни открытый исходник
kbase, ни открытый исходник exynos-pd (все три -- независимо и
по-разному) не совпадают с тем, что реально происходит в
проприетарной прошивке этого конкретного устройства. Это не пробел в
нашей реализации -- это предел того, что можно установить из открытого
кода и штатных интерфейсов ядра без разбора самого бинарника.
