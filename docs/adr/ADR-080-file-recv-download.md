# ADR-080: `file-recv` учится скачивать с устройства (S31)

## Статус

Принято, 2026-09-15.

## Контекст

ADR-073 построила `file-recv` (`PUT <path> <length>\n` + байты,
`/data/saaios/incoming/`) -- закрыла ровно одну сторону: положить
файл НА устройство без полной пересборки/`fastboot flash`. Забрать
что-то ОБРАТНО (лог, crash-report, что угодно под `/data/saaios/`)
всё ещё требовало serial-консоли и ручного `cat`/копирования -- сам
ADR-073 честно называл это открытым пунктом, roadmap зафиксировал
как S31.

Практическая мотивация была уже видна вживую этой сессией: диагностика
S28 (Маджонг SIGSEGV) и находка про недостающие модули зарядки (S27)
обе включали чтение логов (`/data/saaios/var/appd-crashes.log`,
`dmesg`) через serial-консоль построчно -- рабочий, но медленный путь.

## Решение

Тот же процесс (`file-recv`, порт 7777), новый глагол в том же
текстовом заголовочном протоколе: `GET <relative-path>\n` (без
длины -- сервер сам знает размер файла). Ответ: `OK <byte-count>\n`
+ ровно столько байт при успехе, одна строка `ERR ...\n` при отказе.

Сознательно НЕ ограничено `ALLOWED_PREFIX` (`/data/saaios/incoming/`,
как у `PUT`) -- это directory только для приёма загрузок, читать его
обратно означало бы просто возвращать клиенту то, что он сам только
что туда положил. `GET` резолвит путь от реального корня `/`
(тот же запрет на `..`/ведущий `/`, что и у `PUT`, ради симметрии
заголовка, не как значимая граница -- весь диск и так остаётся
читаемым доменом). Доверительная модель не расширяется -- та же
самая "доступен на этой LAN", что уже покрывает `PUT`, `pair-recv`,
`wpa_supplicant`'s управляющий сокет (ADR-073's собственный текст,
процитирован дословно в новом doc-комментарии над `handle_get()`).

## Test

Host: кросс-компиляция (`zig cc -target aarch64-linux-musl -static`)
чиста, автоматических C-тестов для `file-recv` в проекте нет
(соответствует прецеденту ADR-073 -- живая проверка на устройстве).

Device: бинарь пересобран и подменён на устройстве через тот же
`file-recv` (сам себя обновил, PUT-путём) + SSH, без пересборки
образа. Живые проверки:
- `GET data/saaios/var/appd-crashes.log` -- скачан существующий
  файл (тот самый crash-лог, оставшийся от диагностики S28 в этой же
  сессии), 336/336 байт, побайтово идентичен содержимому,
  прочитанному ранее через serial-консоль.
- `GET` несуществующего файла -- `ERR file not found or not a
  regular file`.
- `GET` директории (`data/saaios/var`) -- та же ошибка (не regular
  file, отклонено `S_ISREG`-проверкой).
- `GET ../etc/passwd` -- `ERR path must be relative with no ..
  component`, отклонено до всякого обращения к файловой системе.
- Регрессия: `PUT` по-прежнему работает (загружен тестовый файл уже
  после установки новой версии).

## Последствия

- Единственный оставшийся способ добраться до устройства без сети --
  serial-консоль -- остаётся резервным каналом на случай, если сам
  `file-recv`/сеть недоступны (не заменяется, а дополняется).
- Тот же паттерн ("текстовый заголовок, бинарное тело, один процесс,
  один порт") теперь симметричен в обе стороны -- любой будущий
  клиент (скрипт, вручную через `nc`/сырой TCP) может и класть, и
  забирать файлы одним и тем же простым протоколом.
- Не добавлено: листинг директорий, рекурсивное скачивание,
  сжатие. `GET` -- один файл за раз, тот же минимализм, что и `PUT`
  с самого начала (ADR-073).
