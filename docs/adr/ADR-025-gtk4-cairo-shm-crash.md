# ADR-025: GTK4/GDK падает на реальном железе при создании wl_shm-буфера -- не найдено в проекте, локализовано в апстриме

## Статус

Принято, 2026-09-10.

## Контекст

ADR-024 закрыл GPU-ускорение как вне объёма Change 7 и показал, что
Change 6's `gtk4-lib-probe` крашится через `Unable to create Cairo
image surface: invalid value ... for the size of the input` ->
`Segmentation fault`, и что этот крэш НЕ воспроизводится headless через
`qemu-aarch64-static` на R620 с теми же бинарниками и тем же
`saai-displayd`. Change 7 требовал понять природу этого расхождения
перед тем, как принимать GTK4 как рабочий toolkit.

## Находка

Последовательно исключены все правдоподобные причины, специфичные для
проекта:

1. **Не пробел в упаковке.** Тот же минимальный пакет (`bin/`+`lib/`+
   `share/X11/xkb`, без единого файла из остальной `usr/share`/`etc`)
   рендерит и коммитит кадр (`frame sha256=926ea70d...`) успешно через
   `qemu-aarch64-static` на R620 -- то есть отсутствующие ресурсы
   (fontconfig config, GSettings-схемы, D-Bus machine-id) дают только
   некритичные warning'и, не крэш.
2. **Не про `saai-displayd`'s hardware backend/keyboard-код.**
   Кросс-компилирован throwaway headless (`not(panther-hardware)`)
   `saai-displayd` для aarch64-musl (обычным stable-тулчейном --
   `build-saai-displayd.sh` жёстко требует `panther-hardware`+nightly
   build-std, пришлось повторить его env-переменные вручную с
   `RUSTFLAGS="-L native=<ADR-008 sysroot>/usr/local/lib"`, т.к.
   `-L`-путь к статическому `libxkbcommon.a` в `build.rs` заведён
   только под `panther-hardware`-фичу). Первая попытка (`seat.
   add_keyboard(...).ok()`) не помогла -- крэш xkbcommon оказался
   сигналом изнутри C-библиотеки при компиляции default keymap
   (`ADR-022`), не перехватываемым `Result`/`Option` на стороне Rust.
   Вторая попытка (полностью пропустить вызов `add_keyboard`,
   `keyboard: None` без единого обращения к xkbcommon) дала работающий
   headless compositor на РЕАЛЬНОМ железе (`pid` жив, слушает
   `WAYLAND_DISPLAY`). `gtk4-demo` против него -- **тот же самый крэш**,
   тот же `gdkdisplay-wayland.c:1494`. Значит DRM/hardware-backend
   `saai-displayd`'s (реальный, использованный в Change 6) НЕ виновник
   -- даже полностью безголовый, без единой keyboard/touch capability,
   compositor на том же самом железе крэшит идентично.
3. **Не зависит от сложности содержимого окна.** `gtk4-demo --run=dialog`
   (минимальный демо -- одна кнопка, один диалог) падает так же, как и
   полный `gtk4-demo` без аргументов (весь demo browser с иконками) --
   тот же файл:строка, то же сообщение. Отдельно `gtk4-demo-application`
   упал раньше и по другой причине (`GSettings schemas`, ожидаемо --
   пакет не включает `share/glib-2.0/schemas`), не информативно для
   этого вопроса.
4. **Не пиксмановский NEON-диспетчер.** `PIXMAN_DISABLE=arm-simd,arm-
   neon,arm-iwmmxt` не меняет исход -- тот же крэш, то же сообщение.
5. **Не общая проблема memfd/shm на ядре.** Отдельный throwaway
   aarch64-musl бинарник (`memfd-probe.c`, собран `zig cc`) вызывает
   `memfd_create`+`ftruncate`+`mmap` напрямую -- те же примитивы, что
   GDK's wl_shm backend использует -- на реальных размерах вплоть до
   `1080x2400x4 = 10 368 000` байт (реальный размер экрана панели) --
   **всё успешно**, ни одной ошибки. Ядро/musl/memfd полностью
   исправны.
6. **Принудительный Cairo-путь (`GSK_RENDERER=cairo`, пропуская Ngl/GL/
   Vulkan-каскад целиком) падает РАНЬШЕ и по-другому:**
   `Truncating shared memory file failed: Invalid argument` ->
   `Unable to create shared memory pool` -> `Trace/breakpoint trap`
   (другая строка, другое сообщение, другой сигнал -- `SIGTRAP` через
   `g_error()`, не `SIGSEGV`). Учитывая находку (5), это тоже не
   про сам `ftruncate` как системный вызов -- GDK передаёт ему
   некорректный размер, тот же класс дефекта (неверно посчитанный
   size), просто перехваченный в другой точке кода при другом порядке
   инициализации рендереров.

Итог: дефект детерминированно воспроизводится на РЕАЛЬНОМ Tensor G2
(aarch64) во всех протестированных конфигурациях compositor'а
(headless без единой capability, headless с touch/только реальный
panther-hardware) и НИКОГДА не воспроизводится под `qemu-aarch64-
static` на x86_64 host с идентичными бинарниками и протокольным
обменом. Не зависит от: упаковки/ресурсов, DRM/hardware backend,
клавиатуры/touch capability, сложности окна, pixman's NEON-диспетчера,
kernel memfd/shm примитивов. Указывает на дефект в самом GTK4/GDK's
Wayland-backend (Alpine's `gtk4.0` 4.14.4 aarch64-сборка) --
воспроизводимый только при исполнении на реальном aarch64 (не
эмуляции qemu-user), возможно связанный с UB (чтение неинициализированной
памяти/регистра при вычислении размера буфера -- qemu's транслированное
исполнение и реальное железо расходятся именно в таких случаях) либо с
иной архитектурно-специфичной веткой кода (NEON вне pixman'а, в самом
Cairo/GDK). Дальнейшая локализация требует поосточникового отладчика
(`gdb`/`rr`) на устройстве или бисекции версий GTK4/Cairo -- недоступно
через serial-console/qemu-инструментарий, использованный здесь.

## Решение

Зафиксировать как известный, детально расследованный, но нерешённый в
рамках этого спринта дефект апстрима (не в коде проекта). Оставить
открытым вопрос дальнейшего пути:

- добавить на устройство рабочий `gdb`/`gdbserver` для полноценной
  пост-мортем отладки (инфраструктурная инвестиция, не сделано здесь);
- попробовать другую версию/сборку Cairo/GTK4 (Alpine's `edge`/другая
  ветка, или собрать GTK4 сам from-source с другими флагами);
- переключить Change 7's основной toolkit на Qt/Kirigami (другой
  rendering-стек -- не факт, что тот же класс бага там отсутствует, не
  проверено);
- принять GTK4 как заблокированный для этого спринта, закрыть Change 7
  только через Qt, если тот работает.

Ни один путь не выбран этим ADR -- решение по следующему шагу остаётся
за пределами данной находки.

## Последствия

- Change 7 не может полагаться на голый `gtk4-demo`/Alpine's `gtk4.0`
  пакет "как есть" для физической приёмки на этом устройстве -- нужен
  либо другой toolkit, либо другая сборка GTK4/Cairo, либо
  дальнейшая, более глубокая отладка с реальным debugger'ом.
- Throwaway-диагностическая правка `saai-displayd/src/main.rs`
  (headless-без-клавиатуры вариант, "DIAGNOSTIC C7 PATCH") не для
  коммита -- откатывается после этого расследования, backup на R620
  (`/tmp/main-rs-backup-c7.rs`).
- Подтверждён (в третий раз за спринт, после ADR-022/023) полезный
  паттерн: `unshare -m` + `mount --bind` -- дешёвый, безопасный способ
  физически воспроизводить `sandbox.rs`'s `reveal_directory`-механизм
  без риска для реального `saai-appd`'s стека на устройстве.
