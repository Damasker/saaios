# ADR-035: `lo` fix in `native-init.c` and `init_boot` refresh, physically verified

## Статус

Принято, 2026-09-11.

## Контекст

ADR-034 (S10 Change 2) нашло и явно не исправило два операционных
пробела: (1) `native-init.c` никогда не поднимает loopback-интерфейс,
из-за чего любой native-компонент, обращающийся сам к себе по TCP
(включая `saai-taskd` -> `saaios-runtime`), получает таймаут вместо
мгновенного `connection refused`; (2) реально зашитый `init_boot`
(`saai-shell` хэш `87dbe83f...`) старше репозитория на весь объём S09
Change 2/3 -- у устройства после настоящей холодной перезагрузки нет
on-screen клавиатуры и экрана подтверждения. Пользователь явно
попросил закрыть оба пробела перед продолжением S10.

## Решение

**`native-init.c`**: новая `configure_loopback()` (тот же паттерн, что
уже существующая `configure_network()` для `usb0`) -- `busybox
ifconfig lo 127.0.0.1 netmask 255.0.0.0 up`, вызывается перед
`configure_network()` в основной последовательности `main()`.

**Пересборка `init_boot`**: полный официальный pipeline
(`build-native-c-image.sh`) с исходным `STOCK_INIT_BOOT` из
`artifacts/factory/images/init_boot.img`, `saaios-runtime`/
`saaios-console` пересобраны через `cargo build --profile pixel7`
(zig cross), `saai-displayd`/`saai-shell` -- через их собственные
nightly `build-std` скрипты, всё с текущего `HEAD` (`8c5c4e8...`,
коммит S10 Change 2). Собранный `saai-shell` оказался байт-в-байт
идентичен (`9d4df0ee...`) уже физически проверенному в ADR-032/ADR-034
бинарнику -- подтверждает, что в исходниках `saai-shell` с тех пор
действительно ничего не менялось.

## Физическая проверка

Тот же реальный Pixel 7. `fastboot flash init_boot_a` (текущий активный
слот -- `a`) собранным образом (`SHA-256 2d702be4...`,
`SOURCE_COMMIT 8c5c4e8...`), `fastboot reboot`.

- Холодная загрузка подтверждена: `/proc/uptime` = 13.49s сразу после
  флеша (не показание "тёплого" процесса).
- `sha256sum /saaios/saai-shell` = `9d4df0ee...` -- клавиатура и
  `Frame::TaskConfirm` теперь часть реально зашитого образа, не
  временной подмены.
- `ip link show lo` / `ip -4 addr show lo` -- `<LOOPBACK,UP,LOWER_UP>`,
  `inet 127.0.0.1/8 scope host lo` уже при старте, без единого ручного
  шага.
- `saai-entityd`, `saai-appd`, `saai-displayd`, `saai-shell`,
  `saaios-runtime` -- все пережили холодную перезагрузку и снова в
  списке процессов; `saaios-runtime` слушает `172.31.7.1:38127`
  (подтверждено `netstat`).
- **Главная проверка исправления**: `saai-taskd` (временно развёрнут
  на устройстве, не автозапускается -- по решению S09/ADR-030),
  запущенный с `--runtime-addr 172.31.7.1:38127`, обработал реальный
  `Intent` ("Сколько сейчас времени по системным часам?") через
  планировщика от создания `Intent` до `Result` за ~31 секунду --
  нормальная задержка ответа модели, а НЕ ~110-секундный таймаут,
  наблюдавшийся в ADR-034 до ручного `ip link set lo up`. Никакого
  ручного шага перед этим не потребовалось.

Полное touch-подтверждение клавиатуры/экрана согласия НЕ повторено в
этом раунде -- бинарник байт-в-байт идентичен уже физически
touch-проверенному в ADR-032/ADR-034 (тот же хэш `9d4df0ee`), так что
это была бы проверка того же самого кода, а не нового. Проверялась
именно механика доставки (реальный флеш вместо временной подмены) и
сама сетевая починка.

Все тестовые сущности (1 intent + task + action + result) и временные
файлы (`/data/saaios/system/test-lo-verify`,
`/data/saaios/system/test-s10c2` -- случайно оставшийся от прошлого
раунда каталог) удалены; `work` пуст. HTTP-сервер деплоя и временное
firewall-правило на хосте остановлены/убраны.

## Последствия

- Оба операционных пробела из ADR-034 закрыты физически: `lo`
  поднимается автоматически при каждой загрузке; зашитый `init_boot`
  снова соответствует `HEAD` репозитория.
- **Rollback**: партиция `init_boot_a` перезаписывается напрямую --
  A/B-откат на уровне SaaiOS ещё не построен (это S11's OTA/rollback
  gate). Восстановление не полагается на сохранённый бинарный образ:
  `dist/panther/`'s сайдкары (`SOURCE_COMMIT`, `INPUTS.SHA256`) делают
  любую прошлую сборку детерминированно воспроизводимой из исходников
  -- откат при необходимости means пересобрать нужный коммит и
  перепрошить, тот же принцип, что и рollback-раздел любого
  предыдущего ADR этой цепочки. Bootloader/fastboot остаётся доступен
  независимо от состояния userspace (через встроенный
  `/saaios/reboot-bootloader` либо аппаратную комбинацию клавиш); слот
  B остаётся нетронутым stock Android как независимый резервный путь.
- S10 Change 3 (расписания/триггеры) и Change 4 (memory со `space_id`)
  остаются открытыми, как и было зафиксировано в Definition of Ready.
