# ADR-037: S10 Change 3 -- schedule triggers physically verified end to end

## Статус

Принято, 2026-09-11.

## Контекст

ADR-036 решило: расписание -- новый native `entity_type`
(`saaios.schedule`) поверх `saai-entity-store`, оценивается periodic
tick'ом внутри уже существующего `saai-taskd`, и, когда просрочено,
создаёт обычный `saaios.intent` -- неотличимый от введённого вручную,
так что весь уже физически доказанный конвейер (Change 1/2) подхватывает
его без единого изменения. Этот ADR реализует и физически подтверждает
это решение.

## Реализация

**`model.rs`**: `SCHEDULE_TYPE`, `schedule_properties()`
(`every_secs`/`text`/`enabled`/`last_fired_at`/`fire_count`, полная
замена свойств при каждом обновлении -- та же семантика, что у
остальных сущностей этого модуля), читающие геттеры, и
`is_schedule_due()` -- чистая, полностью host-тестируемая функция
(отключено/нет `every_secs`/не просрочено -> не due; никогда не
считает malformed-состояние ошибкой, только "ещё не пора"). 9 новых
host-тестов.

**`lib.rs`**: `run()`'s реактивный цикл (`next_event().await`) получил
`tokio::select!` с `tokio::time::interval(5s)` -- не отдельный сервис
(ADR-030/036's "no new service unless something actually asks for
one"). Новый `evaluate_due_schedules()`: список `saaios.schedule` в
своём пространстве, для просроченных -- сперва обновляет
`last_fired_at`/`fire_count` самого расписания, затем создаёт
`saaios.intent` с тем же `text`, что и клавиатура кладёт вручную
(плюс `schedule_id` для трассировки, не влияющий на
`process_intent()`). `chrono` перенесён из dev- в обычные зависимости
(`Cargo.toml`).

## Физическая проверка

Тот же реальный Pixel 7. `saaios.schedule` создан напрямую
(`every_secs: 20, text: "Который сейчас час?", enabled: true`),
`saai-taskd` запущен вручную (по-прежнему не в `native-init.c`, тот
же прецедент, что Change 1/2) -- **без единого созданного вручную
`Intent`**:

- Первый tick (~5с после старта демона, расписание никогда не
  срабатывало -> due немедленно): расписание само создало `Intent`,
  который прошёл через уже существующий planner-мост (ADR-033/034) до
  `Done` -- `Task`/`Action`/`Result` появились в `work` полностью
  автоматически.
- Второе и третье срабатывания пришли строго на 20-секундном
  интервале (`fire_count` дошёл до 3 за ~41 секунду реального
  времени, три независимых цикла Intent -> Task -> Action -> Result,
  каждый `done`), подтверждая именно интервальную, а не только
  "сработало один раз при создании" логику.
- Ответы модели варьировались по качеству (один раз "Не удалось
  завершить диагностику", в другой раз честная оценка через
  `system.metrics`, в третий -- прямой ответ) -- ожидаемая вариативность
  локальной модели, не относится к самому механизму расписаний;
  конвейер `WorkflowStatus` в каждом случае корректно дошёл до `Done`.

18 тестовых сущностей (1 расписание, 4 intent, 4 task, 4 action, 5
result -- по числу реальных срабатываний за время теста) и временный
каталог удалены; `list_entities` в `work` после уборки -- пустой
список; `saai-taskd` остановлен.

## Решение

S10 Change 3 закрыт: расписание -- реальный, персистентный
(cold-reboot-переживающий по тому же фундаменту, что весь
`saai-entity-store`), space-scoped механизм, создающий обычные
`Intent`, проходящие тот же `WorkflowStatus`/confirmation-конвейер,
что explicit-путь S09 -- ни одного отдельного риск-класса, ни одного
изменения в `process_intent()`/`saai-shell`.

## Последствия

- `cron`/`at:HH:MM`-триггеры и explicit UI для создания расписания
  (сейчас только прямой `create_entity`, как `Intent` в S09 Change 2
  до клавиатуры) остаются вне этого Change.
- Опасный `Intent`, созданный расписанием (например, `action_kind:
  delete_entity`), пройдёт тем же путём, что и explicit dangerous
  intent -- `dangerous_action_of()` не различает источник Intent'а --
  это не проверялось отдельно в этом раунде, но следует напрямую из
  того, что `process_intent()` не изменился.
- Оставшийся кусок S10 -- memory, привязанная к пространству --
  по-прежнему отдельная, не начатая задача.
