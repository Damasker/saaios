# ADR-020: Capability vocabulary, effective grants и sandbox приложений

## Статус

Принято, 2026-09-10.

## Контекст

S05 (ADR-018) ввёл manifest с полем `capabilities` (например
`["space.entities.read", "space.entities.write"]`), но explicitly не
превращает их в разрешения: `saai-appd`'s doc-comment прямо говорит
"Requested capabilities only. S05 never turns these into grants."
Приложение сегодня запускается `Command::new(...).env_clear()` с
фиксированным набором переменных окружения -- без mount/network/syscall
изоляции. Инвариант из `application-platform.md` фиксирует это явно: "до
готового sandbox разрешены только доверенные тестовые приложения".

Ключевое ограничение платформы: вся система (native PID 1, `saai-appd`,
запущенные приложения) работает как единственный процесс-дерево под
root/uid 0 -- нет `/etc/passwd`, нет второго UID, нет traditional
multi-user Linux разделения. Любая изоляция должна работать ВНУТРИ
одного UID, не полагаясь на DAC (владелец/группа/права файла) как на
единственную границу -- при uid 0 DAC ничего не ограничивает.

Перед выбором механизма был запущен spike прямо на устройстве (Pixel 7,
kernel `6.1.157-android14-11-gbd23337e42e7-ab14791245`) -- отдельный
статически слинкованный C-бинарь, `fork()`+`unshare()` по одному флагу
за раз, чтобы не потерять родительский процесс при первом же провале:

```
CLONE_NEWNS  (mount namespace):    OK
CLONE_NEWNET (network namespace):  OK
CLONE_NEWPID (pid namespace):      FAIL errno=22 (Invalid argument)
CLONE_NEWIPC (ipc namespace):      OK
CLONE_NEWUTS (uts namespace):      OK
PR_SET_NO_NEW_PRIVS:               OK
```

`zcat /proc/config.gz | grep -i 'PID_NS\|USER_NS'` подтвердил причину на
уровне сборки ядра, не рантайм-политики (SELinux на этом ядре вообще
`Disabled`, `/sys/fs/selinux` не смонтирован):

```
# CONFIG_USER_NS is not set
# CONFIG_PID_NS is not set
```

`/proc/self/ns/` подтверждает то же самое -- в листинге нет ни `pid`, ни
`user` записей, только `cgroup`/`ipc`/`mnt`/`net`/`time`/`uts`. Это
осознанное усиление безопасности Android GKI (user namespaces -- частый
источник kernel privilege escalation, поэтому Google исторически
отключает `CONFIG_USER_NS` на боевых сборках; `CONFIG_PID_NS` не нужен
самой Android-модели изоляции, построенной на Zygote + отдельных UID на
каждое приложение, не на PID-неймспейсах). Это постоянное свойство
данного ядра, не то, что можно "включить" без пересборки ядра, которая
вне объёма этого ADR.

## Решение

### 1. Capability vocabulary v1

Небольшой фиксированный, версионированный список dotted-имён (то же
соглашение об именовании, что manifest schema уже проверяет в S05):

- `space.entities.read` / `space.entities.write` -- уже используются как
  пример в S05 manifest, теперь получают реальное значение;
- `net.internet` -- исходящий сетевой доступ;
- `clipboard.read` / `clipboard.write` -- через portal в `saai-shell`,
  не напрямую;
- `portal.open_file` -- право вызвать системный file picker; сам выбор
  файла -- согласие пользователя на конкретный файл в конкретный момент,
  не постоянный доступ к файловой системе.

Список расширяется по мере необходимости отдельными ADR-правками, не
произвольным добавлением строк в манифесты приложений -- манифест может
запросить только то, что есть в этом vocabulary (`saai-appd` уже
проверяет синтаксис имени; проверка принадлежности vocabulary -- новая
часть этого ADR).

### 2. Effective grants -- на установке, целиком

При установке (или первом запуске, если manifest пришёл в обход
установки) `saai-shell` показывает список запрошенных capability из
manifest и просит принять или отказаться -- целиком, без выбора по
одной штуке в v1. Explicit runtime-prompt на первое использование --
следующий шаг, не в объёме этой версии (per-capability детализация
позже не блокируется этим решением, просто не реализуется сейчас).

Решение хранится не как копия `manifest.capabilities`, а как отдельная
запись `{app_id, granted: [...], manifest_capabilities_hash}` в сторе
`saai-appd`. `manifest_capabilities_hash` -- это то, что делает согласие
не разовой дырой: если следующая версия manifest'а расширяет список
capability, hash меняется, старое согласие перестаёт быть валидным для
новых capability, и `saai-appd` обязан снова показать экран согласия
перед следующим запуском -- тихого повышения прав через обновление
manifest не бывает.

### 3. Process isolation -- те неймспейсы, что реально есть на этом ядре

`saai-appd`'s `spawn()` (сейчас голый `Command::new(...).env_clear()`)
получает `pre_exec()`-хук (`nix::sched::unshare`, `nix` уже используется
в `saai-displayd` -- не новая зависимость), вызывающий
`unshare(CLONE_NEWNS | CLONE_NEWNET | CLONE_NEWIPC | CLONE_NEWUTS)`
безусловно для каждого приложения, кроме случая явного `net.internet`
granted -- тогда `CLONE_NEWNET` не запрашивается вовсе (см. ниже, network
mediation).

`CLONE_NEWPID`/`CLONE_NEWUSER` не запрашиваются -- физически недоступны
на этом ядре (см. Контекст), не "пока не реализовано". Практическое
следствие явно зафиксировано в Известных ограничениях ниже, не скрыто.

Важная деталь API, подтверждённая тем же spike: `CLONE_NEWNS`/`NEWNET`/
`NEWIPC`/`NEWUTS`, в отличие от `NEWPID`/`NEWUSER`, переносят
ВЫЗЫВАЮЩИЙ процесс в новый неймспейс немедленно (man `unshare(2)`) --
поэтому `unshare()` внутри `pre_exec()` (то есть в уже forked child,
прямо перед `execve()`) действительно помещает сам процесс приложения в
новые mount/net/ipc/uts неймспейсы. Для `NEWPID` это было бы не так
(перенос затронул бы только будущих детей, не сам процесс) -- ещё одна
причина, почему `NEWPID` для этой архитектуры (один `fork+exec`, не
собственный init нового pid namespace) потребовал бы отдельного, более
сложного пути даже будь он доступен на этом ядре.

### 4. Filesystem mediation -- маскирование через bind-mount, не chroot

Полный `pivot_root` в собранный с нуля минимальный rootfs -- за пределами
объёма этой версии (потребовал бы собственной копии `busybox`, libc и
т.д. под каждое приложение). v1 работает поверх существующего дерева
`/data/saaios`, замаскировав то, что не должно быть видно:

- пустой `tmpfs` монтируется поверх родительских каталогов
  `/data/saaios/apps`, `/data/saaios/packages` и
  `/data/saaios/var/apps` (после `unshare(CLONE_NEWNS)`, private/rslave
  root -- `mount(NULL, "/", NULL, MS_REC | MS_PRIVATE, NULL)` первым
  шагом, чтобы эти монтирования не утекли обратно на хост);
- следом bind-mount возвращает НАЗАД только собственные каталоги этого
  приложения: `code_dir` (read-only через `MS_BIND` + remount
  `MS_RDONLY`) и `data_dir` (read-write) -- то есть приложение видит
  ровно одно дерево кода и одно дерево данных, не соседей по этим общим
  родителям;
- `/data/saaios/var/entities` (сырое хранилище S06) остаётся
  замаскировано тем же пустым `tmpfs` без bind-mount назад -- прямой
  доступ к espace/entity файлам закрыт полностью, единственный путь --
  IPC-сокет `saai-entityd` (уже так спроектирован в S06, здесь только
  физически закрывается прежде доступный, но не используемый обходной
  путь через сырые файлы);
- `/run/wayland` и `/run/saaios` (сокеты displayd/appd/entityd) остаются
  видны без изменений -- они и так единственная точка входа в
  соответствующие сервисы, маскировать нечего;
- `portal.open_file`: выбранный пользователем через `saai-shell` файл
  bind-mount'ится в приватный (для этого mount namespace) путь только
  на время сессии приложения -- отдельный протокол portal, не входит в
  эту ADR детально, фиксируется здесь только как точка входа.

### 5. Network mediation -- всё или ничего, без частичной фильтрации

Без `net.internet` в effective grants: `CLONE_NEWNET` запрашивается,
приложение получает новый network namespace без единого интерфейса,
кроме loopback -- реального пути наружу нет вообще (не iptables-фильтр,
который потенциально можно обойти, а отсутствие самого сетевого стека
снаружи).

С `net.internet`: `CLONE_NEWNET` не запрашивается вовсе, приложение
использует тот же network namespace, что и вся система (полный доступ,
без per-app файрвола). Прицельная фильтрация (белый список хостов и
т.п.) -- будущая работа, не блокируется этим решением, но не
реализуется в v1: bool-переключатель "сеть есть / сети нет" полностью
закрывает Acceptance criteria этого шага и не требует держать отдельный
network namespace с настроенным veth+NAT для промежуточного случая.

### 6. Syscall mediation -- seccomp-bpf через `seccompiler`

Без `CLONE_NEWPID`/`CLONE_NEWUSER` мониторинг/ограничение системных
вызовов -- единственный работающий барьер против того, что иначе решали
бы неймспейсы (в первую очередь: возможность процесса, всё ещё
технически root, напрямую воздействовать на другие процессы в системе).
seccomp-фильтр устанавливается в том же `pre_exec()`, после
`PR_SET_NO_NEW_PRIVS` (уже подтверждён spike'ом) и после настройки
mount namespace, непосредственно перед `execve()`.

Библиотека: [`seccompiler`](https://crates.io/crates/seccompiler) --
чистый Rust, тот же компилятор seccomp-BPF, что использует Firecracker
(AWS) в продакшене, ноль новых C-зависимостей и кросс-компиляции (в
отличие от `libseccomp`) -- то, что реально нужно (компиляция короткого
deny-списка в BPF-байткод), без C toolchain-обвязки.

Deny-list v1 (allow-by-default, явно запрещены только опасные для этой
конкретной модели угроз вызовы -- список растёт отдельными ADR-правками
по мере находок, не считается исчерпывающим на старте):

- `ptrace` -- нет технической причины приложению трассировать что-либо;
- `kill`, `tkill`, `tgkill` -- без PID namespace это единственный барьер
  против сигнала произвольному чужому процессу;
- `mount`, `umount2`, `pivot_root`, `chroot` -- mount namespace уже
  настроен `saai-appd` до `execve()`, приложению незачем его менять;
- `unshare`, `setns`, `clone` с `CLONE_NEW*`-флагами -- запрет escape
  из уже назначенных неймспейсов;
- `reboot`, `init_module`, `delete_module`, `kexec_load` -- очевидный
  system-wide impact, не относится к прикладному процессу;
- `personality` -- частый вектор обхода других syscall-митигаций.

### 7. Системный permission surface

Экран согласия (раздел 2) рисуется `saai-shell` тем же SUI/action
механизмом, что уже используют root-разделы (`root.sui`, ADR-017) --
новый экран, не новый рендер-путь.

### 8. Portals

`clipboard.read`/`write` и `portal.open_file` идут через `saai-shell`
(уже держит границу доверия для lock/focus, ADR-015) по IPC, не через
прямой доступ приложения к системному clipboard или произвольным путям
файловой системы. Конкретный wire-протокол portal -- отдельная задача
внутри S07, не фиксируется этим ADR построчно.

## Последствия

- `saai-appd`'s `spawn()` перестаёт быть голым `Command::new(...)` --
  получает mount/net/ipc/uts настройку и seccomp-фильтр на каждый
  запуск, для каждого приложения без исключений (кроме `net.internet`
  для сетевого namespace).
- Новая зависимость `seccompiler` (pure Rust) в `saai-appd`.
- Формат хранения grants в `saai-appd`'s сторе меняется -- добавляется
  запись согласия с hash запрошенных capability, независимая от самого
  manifest.
- `saai-shell` получает новый экран согласия и, позже в рамках S07,
  клиент portal-протокола.
- Инвариант "до готового sandbox разрешены только доверенные тестовые
  приложения" из `application-platform.md` становится закрываемым --
  после этого ADR "готовый sandbox" перестаёт быть открытым вопросом,
  превращается в конкретный, физически проверенный набор гарантий.

## Известные ограничения (осознанные, не отложенные баги)

- **Нет PID-изоляции.** Приложение видит `/proc` всей системы (список
  процессов, их `cmdline` и т.п.) -- `CONFIG_PID_NS` физически
  недоступен на этом ядре (см. Контекст). Смягчено, не устранено:
  seccomp блокирует `ptrace`/`kill`/`tkill`/`tgkill`, то есть
  приложение не может фактически воздействовать на чужой процесс, даже
  видя его существование. Метаданные (какие процессы запущены) --
  остаточная утечка, не действие.
- **Нет UID-изоляции.** `CONFIG_USER_NS` недоступен, второй реальный UID
  через traditional Linux user management не заведён (нет
  `/etc/passwd`, этот ADR не меняет это). Вся защита несёт mount
  namespace (что видно на диске) + seccomp (что можно сделать) -- DAC не
  участвует вообще, а не "участвует слабо".
- **`net.internet` -- бинарный переключатель**, не per-host allowlist.
  Приложение с этим capability видит ту же сеть, что и вся система,
  без ограничений.
- **`portal.open_file`/clipboard протокол** зафиксирован здесь только
  на уровне точки входа (кто через кого), не wire-формата -- отдельная
  задача внутри S07.
- **Resource limits (cgroups: память/CPU) не входят в этот ADR** --
  отдельный, не входящий в capability vocabulary вопрос (crash-loop
  budget из S05 остаётся единственной защитой от процесса, потребляющего
  ресурсы).

## Отклонённые альтернативы

### bubblewrap

Готовый, проверенный временем sandboxing-инструмент (тот же механизм
использует Flatpak) -- но новая C-зависимость, требующая кросс-компиляции
по схеме ADR-008, ради функциональности, которая целиком собирается из
`unshare()`+`seccompiler`, уже доступных без единой новой C-зависимости
(`nix` уже в дереве через `saai-displayd`). Тот же принцип, что уже
применялся в ADR-010 (libseat) и ADR-011 (libinput) -- не тащить внешний
инструмент ради механизма, который прямые системные вызовы дают
напрямую и с полным контролем.

### Только DAC/UID-разделение, без неймспейсов

Требовало бы либо `CONFIG_USER_NS` (физически недоступен на этом ядре
-- не вопрос выбора), либо заведения traditional multi-UID Linux
окружения (`/etc/passwd`, `setuid`-биты, стандартная модель прав) --
architectural сдвиг всей ОС, не совместимый с её текущей моделью "один
процесс-дерево под root, PID 1 -- собственный C-бинарь, не systemd/init
с пользовательскими сессиями". Даже будь это сделано, DAC при
единственном РЕАЛЬНОМ пользователе (не отдельные Linux-аккаунты на
приложение, а единственный оператор телефона) не защищает от процесса,
которому просто дали не тот UID по ошибке конфигурации -- разница в
несколько строк кода, не структурная граница, которую даёт mount
namespace.

### Полноценный `pivot_root` в собранный с нуля минимальный rootfs

Даёт более полную изоляцию файловой системы (приложение не видит вообще
никакой части хост-дерева, а не "то, что не замаскировано отдельно"),
но требует поддерживать отдельный минимальный корень (busybox, libc,
нужные `.so`) под каждое приложение -- заметно больше веса и
эксплуатационной сложности, чем даёт польза на этом этапе (одно
доверенное demo-приложение, S05). Пересмотр -- когда появится реальный
недоверенный сторонний код, для которого маскирования общих каталогов
уже не будет достаточно.
