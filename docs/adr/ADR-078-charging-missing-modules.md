# ADR-078: телефон не заряжался под SaaiOS -- двух модулей ядра не хватало (S27)

## Статус

Принято, 2026-09-15.

## Контекст

Замечено рано в проекте (роадмап S27): подключённый к USB телефон под
SaaiOS показывает "Not charging" бесконечно, батарея реально
разряжается, а не заряжается. Заряд работает только в fastboot/
bootloader (там своя, независимая от основной ОС, логика). Живая
диагностика на устройстве (`/sys/class/power_supply/*`) показала:
`usb`/`tcpm-source-psy-...` оба `online=1` (USB-PD контракт реально
согласован на уровне TCPC), но `main-charger`/`gcpm` оба постоянно
"Not charging", `maxfg/current_now` отрицательный (реально течёт из
батареи, не в неё).

`dmesg` показывал повторяющийся паттерн при каждой загрузке:
```
google_cpm: wireless power supply not found, retrying...
google_cpm: gcpm_init_work retries=N dc_not_done=1 tcpm_ok=1 wlc_ok=0
...
google_cpm: google_cpm init_work done 1/2 pps=1 wlc_dc=0
```
Первая гипотеза (`dc_not_done=1` блокирует что-то критичное из-за
отсутствия беспроводной зарядки) не подтвердилась при чтении
реального исходника `google_cpm.c` (публичный AOSP репозиторий
`kernel/google-modules/bms`, ветка `android-gs-pantah-6.1-android16`,
склонированная прямо на build-сервере -- `dc_not_done` в этой версии
драйвера влияет только на диагностический вывод, retry-цикл
завершается по отдельному счётчику `chg_psy_retries` независимо от
него). `unbind`/`bind` драйвера `google_cpm` через sysfs (с явного
разрешения пользователя -- реальное железо) тоже не помогло:
идентичный цикл повторился, тот же тупик.

Ключевая находка: `/sys/devices/platform/google,charger/` -- реальный
узел устройства из device tree -- существовал, но НЕ ИМЕЛ
привязанного драйвера вообще (`google_charger` отсутствовал в
`/sys/bus/platform/drivers/`, в отличие от `google_cpm`, который там
был). То же самое для `google,battery`. `google_cpm` -- это только
роутер/селектор пути питания (провод vs беспроводная зарядка); именно
`google_charger` (публичный AOSP-драйвер, отдельный `.c`-файл в том же
`bms` репозитории) реально считает MSC-состояние (JEITA-температура,
CV/CC логика) и говорит зарядной микросхеме включить ток. Без него
`google_cpm` мог только выбирать путь, но НИКТО не авторизовал
реальный заряд.

`.ko`-файлы `google-charger.ko`/`google-battery.ko` не нашлись нигде
в собственных артефактах проекта -- НО оказались физически уже
присутствующими на живом устройстве по пути `/lib/modules/`
(подтверждено: `ls -la /lib/modules/google-charger.ko` -- реальный
файл, тот же размер, что и в `vendor_kernel_boot.img`'s ramdisk).
Причина: `vendor_boot.img`/`vendor_kernel_boot.img` -- штатные,
никогда не тронутые этим проектом разделы (пересобирается только
`init_boot`); загрузчик сам объединяет их initramfs с нашим в единый
образ ДО того, как наш `native-init.c` вообще запускается. Значит,
это не отсутствующий артефакт, а просто два пропущенных вызова
`insmod` в `native-init.c`'s собственном списке модулей.

## Диагностика: откуда взялись эти два файла

Публичный AOSP-репозиторий `kernel/google-modules/bms`
(`android.googlesource.com`) склонирован напрямую на build-сервере
(интернет доступен). Ветка `android-gs-pantah-6.1-android16`
(`pantah` = кодовое имя kernel-дерева для Pixel 7/7 Pro в AOSP)
содержит `google_cpm.c`, `google_charger.c` и т.д. -- достаточно для
понимания реального поведения драйвера без догадок. Канонический
порядок загрузки модулей (`vendor_kernel_boot.img`'s собственный
`lib/modules/modules.load`, физически распакованный `magiskboot`'ом
прямо из фабричного образа `os/targets/panther/artifacts/factory/
image-panther-cp2a.260705.006.zip`) подтвердил и порядок, и сам факт,
что `google-battery.ko`/`google-charger.ko` -- штатные, ожидаемые
модули для этого железа.

## Решение

Два `insmod`-а добавлены в `native-init.c`'s `usb_modules[]` (та же
группа, где уже жили `max77759-charger.ko`/`tcpci_max77759.ko`/
`google-cpm.ko`), сразу после `google-cpm.ko` -- порядок, вживую
проверенный до правки кода: `insmod google-battery.ko` +
`insmod google-charger.ko` на уже загруженном устройстве по SSH,
оба вернули `rc=0`, `google,charger`/`google,battery` тут же появились
как привязанные драйверы, а `dmesg` показал полный, настоящий цикл
согласования MSC-зарядки (`chg_s=Charging chg_t=Fast`, реальный ток
~1.9А) в течение секунды. Только после этого живого подтверждения
правка была внесена в исходник и пересобран весь образ.

## Test

Host: кросс-компиляция `native-init.c` (`zig cc`) чиста. Полная
сборка `build-native-c-image.sh` укладывается ровно в 8388608 байт
(бюджет раздела).

Device: дважды подтверждено живьём.
1. До правки кода: ручной `insmod` обоих модулей на уже
   загруженном устройстве -- зарядка реально включилась
   (`main-charger`/`gcpm`/`maxfg`/`battery` все "Charging",
   `current_now` ~1.9-1.9А), подтверждено визуально на экране
   (растущий процент/индикатор).
2. После правки и полной перепрошивки `init_boot_a`: чистая
   перезагрузка, `google,battery`/`google,charger` привязались
   автоматически (`ls /sys/bus/platform/drivers/`), `dmesg`
   показал полный цикл согласования уже через ~33 секунды после
   старта БЕЗ какого-либо ручного вмешательства
   (`chg_s=Charging chg_t=Fast`, `ib=~1.66А`, `MSC_TTF: est:5424
   (90min)`), подтверждено визуально на экране повторно.

## Последствия

- `battery/capacity` первые секунды после загрузки `google_battery`
  читался как `0` -- самостоятельно исправляется через несколько
  циклов опроса (fuel gauge модель уже была прогружена `max1720x`
  раньше, `google_battery` просто ещё не успел синхронизироваться в
  момент самой первой проверки) -- не отдельный баг, не
  зафиксировано никакой дальнейшей правки.
- Расследование заодно подтвердило рабочий паттерн для будущих
  подобных проблем: живой SSH-доступ (ADR-073/074) + публичные
  AOSP kernel/google-modules репозитории (открытый исходный код,
  доступны по HTTPS) дают реальный, не догадочный путь к диагностике
  любого другого "непонятного" драйверного поведения на этом
  железе -- не только зарядки.
- SSH-пейринг (ADR-074) пришлось переустанавливать заново в начале
  этой сессии -- `/tmp` build-сервера был очищен между сессиями
  (вероятно, перезагрузка сервера), унеся с собой ранее одобренный
  приватный ключ. Ключ на устройстве (`authorized_keys` на `/data`)
  пережил это без проблем -- переустановка потребовалась только на
  стороне build-сервера. Открытый пункт для будущего: приватные ключи
  для доступа к устройству стоит хранить где-то более стабильном, чем
  `/tmp` (например, `~/.ssh/` -- фактически туда они и переехали в
  рамках этой же переустановки).
