# ADR-043: S11 Change 3 -- combined regression pass clean; real saai-displayd OOM found, not reproduced on demand

## Статус

Принято, 2026-09-12.

## Контекст

Change 3 требует комбинированный регрессионный проход по ключевым
инвариантам S01-S10 и 24-часовой soak. Перед стартом формального soak
пришлось временно отключить Change 2's deep idle (иначе soak прервал
бы сам себя каждые 300с) -- собрана отдельная тестовая сборка
`saai-shell` с `DEFAULT_DEEP_IDLE_TIMEOUT` 90000с (25ч, не
закоммичена, тот же временный паттерн, что и весь S11).

## Регрессионный проход -- чисто

На реальном устройстве, представительно по одному инварианту на
Change/сприынт, не полное повторение:

- **App lifecycle (S05)**: `org.saaios.demo-surface` launch -> `list`
  (state: running) -> `stop` -- всё чисто через `appd`'s IPC.
- **Capability sandbox (S07)**: `org.saaios.sandbox-probe` (доустановлен
  через `appd.install`, пакет был на диске, но не инсталлирован) --
  `sandbox-report.txt`: **`RESULT PASS failures=0`**, все 18
  инвариантов (скрытые сокеты/файлы/устройства, read-only root,
  seccomp на kill/mount/reboot, отсутствие сети без `net.internet`,
  обнулённые capabilities).
- **Intent/Task/Action/Schedule (S09/S10)**: свободный intent ->
  `saaios_runtime_tool` Action -> Result "Верно"; `saaios.schedule`
  (15с) сработал многократно (см. Находка ниже) -- каждый раз полный
  `Intent -> Task -> Action -> Result`, `Done`, без единой ошибки;
  бонус-регрессия: забытый intent "hii" из более раннего раунда сессии
  был корректно подхвачен `saai-taskd`'s `reconcile_existing_intents()`
  при старте.
- **Memory (S10)**: `memory.remember` через planner отработал; факт
  лёг без `space_id` (текущий прошитый `saaios-runtime` -- досостояние
  до S10 Change 4/ADR-038, восстановленное после того теста как
  "истинный оригинал" -- не регрессия от S11, тот же класс пробела,
  что `init_boot`'s устаревший `saai-shell` до ADR-035/037).

**Toolkit-приложение (S08) и touch-based lock-screen (S04)** не
переиспытывались отдельно в этом раунде -- ни один Change S11 не
касается их кода; Kirigami-демо не установлено на этом устройстве
сейчас (не переустанавливалось специально ради полноты). Честно
отмечено как не входящее в это представительное покрытие, а не
пропущено молча.

**Находка в процессе (не регрессия)**: `saai-taskd`, запущенный для
теста, не остановился по моему `kill` из-за гонки (переменная PID
оказалась пустой на момент проверки) и продолжал реактивно обрабатывать
`saaios.schedule` ещё ~47 минут (fire_count дошёл до 49) без единой
ошибки -- случайно, но само по себе неплохое дополнительное
свидетельство устойчивости planner-моста под длительной нагрузкой.
198 тестовых сущностей удалены после явного согласия пользователя
(двумя раундами -- сначала с неверными revision-предположениями для
Task-сущностей, затем с точными значениями, полученными через
`PowerShell`'s `ConvertFrom-Json`, не regex).

## Находка: реальные OOM-килы `saai-displayd`, причина не подтверждена целенаправленно

При подготовке к soak `dmesg` показал: **`saai-displayd` был убит
OOM-killer'ом минимум 4 раза** подряд в узком окне (uptime
17095-17801с, ~11.8 минут), каждый раз выросши до 1-2.5 GB RSS
(`anon-rss` и `shmem-rss` в отчётах killer'а), PID1 каждый раз
корректно перезапускал его (bounded restart budget, ADR-009). Это
временное окно совпадает с периодом плотного тестирования Change 2's
чистого раунда (много suspend/resume циклов подряд).

Три отдельные, методичные попытки воспроизвести это целенаправленно
**не удались**:

1. Три изолированных, разнесённых по времени ручных `echo mem >
   /sys/power/state` цикла (без переключения `wlan0`, без запуска
   приложений между ними): один цикл показал +30MB прироста
   (`Pss_Shmem` +10MB -- ровно размер одного полноэкранного
   dumb-буфера, 1080x2400x4 байт), два других -- ноль прироста.
2. Восемь циклов подряд в автоматическом фоновом цикле (`echo mem`,
   без `wlan0`) -- **абсолютно плоская память**, ни байта роста ни
   разу.
3. Восемь циклов подряд, точно воспроизводящих реальный механизм
   Change 2 (`wlan0 down` -> `echo mem` -> `wlan0 up`, тот же порядок
   действий, что `check_deep_idle()`) -- **снова абсолютно плоская
   память**.

Ни единичный suspend, ни быстрая серия без Wi-Fi, ни быстрая серия с
Wi-Fi-переключением не воспроизвели рост на заказ. `hardware.rs`
(DRM/dumb-buffer слой `saai-displayd`) прочитан целиком: буферы
аллоцируются **один раз** при `init()`, `present()`/`fill()`/`blit()`
переиспользуют те же два слота через `map_dumb_buffer()`/`Drop` на
каждый вызов -- в коде нет очевидного места, которое бы аллоцировало
новый буфер повторно; `main.rs`'s DRM notifier обрабатывает только
`DrmEvent::VBlank` (сброс `flip_pending`), `hardware::init()` вызывается
ровно один раз за весь процесс.

## Решение

Найденный баг реален (dmesg -- не домысел), но его точный триггер **не
идентифицирован** за три целенаправленные, методичные попытки
воспроизведения. Дальнейшая охота остановлена по совместному решению с
пользователем -- цена (десятки нажатий кнопки питания на реальном,
единственном устройстве) перестала быть оправданной без нового,
более точного диагностического подхода (например, точное
инструментирование `map_dumb_buffer`/`Drop`, а не измерение
до/после снаружи).

**Соответственно расследованию, три попытки воспроизведения**
(изолированные ручные `echo mem`, быстрая серия без `wlan0`, быстрая
серия с `wlan0 down/up`) описаны выше -- ни одна не дала стабильного,
воспроизводимого роста памяти.

**Soak, честный частичный результат.** Формальный 24-часовой soak в
реальном времени внутри одной интерактивной сессии признан
непрактичным (совместное решение с пользователем) -- вместо этого
засчитано уже фактически пройденное: устройство непрерывно
проработало **~15.9 часов** (uptime от начала S11 Change 1 до
финальной перезагрузки этого раунда) под нагрузкой, значительно
превышающей обычное использование -- десятки подмен бинарников,
198 planner/schedule-сущностей, множественные suspend/resume циклы,
полный регрессионный проход. Все core-сервисы (`saai-entityd`,
`saai-appd`, `saaios-runtime`) не упали ни разу за всё это время.
Единственная найденная проблема -- уже описанная OOM-находка
`saai-displayd`, самовосстанавливающаяся штатно.

**Побочная, но полезная находка при закрытии раунда**: восстанавливая
продакшен-бинарь `saai-shell` через `cp`/`mv` (безопасный паттерн из
ADR-042), забыл `chmod 755` после копирования -- `busybox cp` не
сохраняет бит исполнения. `saai-displayd` не смог запустить `shell`
(`Permission denied`), исчерпал СВОЙ внутренний restart-budget для
shell, вышел, что заставило PID1 исчерпать УЖЕ СВОЙ
`UI_RESTART_BUDGET` (5/60с, ADR-009) и переключиться на `drm-splash`
-- **первое реальное физическое срабатывание этого fallback-пути за
всю сессию**, подтвердившее, что ADR-009's design работает как
задумано. `drm-splash`-fallback перезапускается PID1 без лимита по
дизайну ("no restart budget"), поэтому попытки убить его вручную и
поднять `saai-displayd` вручную только порождали гонку за DRM master
между двумя одновременно живыми UI-процессами. Разрешено настоящей
холодной `reboot -f` (с согласия пользователя) -- она же, ожидаемо,
вернула `/saaios/saai-shell` к содержимому реально прошитого
`init_boot` (`9d4df0ee`, ADR-035/037's сборка, без Change 2's ещё не
зафлешенного кода) -- временные рантайм-подмены не переживают
настоящую перезагрузку, тот же принцип, что ADR-032 впервые
установило. Устройство после перезагрузки полностью чистое: свежий
baseline памяти, `work` пуст, все сервисы штатно подняты.

## Последствия

- **Известный, не заблокированный, не решённый риск**: реальные
  устройства с включённым Change 2 (deep idle) могут периодически
  ловить OOM-килы `saai-displayd` при определённых, пока не
  установленных условиях, связанных с плотными suspend/resume
  циклами. PID1's restart budget (ADR-009) делает это
  самовосстанавливающимся (не зависанием), но не бесплатным --
  каждый OOM-цикл -- реальный, видимый пользователю сброс экрана.
- Рекомендация для будущей работы (не входит в S11): инструментировать
  `HardwareOutput::map_write_slot`/`Drop` напрямую (счётчик активных
  мэппингов, логирование), а не измерять RSS снаружи -- текущий метод
  недостаточно чувствителен, чтобы поймать эффект, который сам
  оказался не воспроизводимым по требованию.
- Regression pass (S05/S07/S09/S10) -- чист, ноль регрессий от S11's
  изменений.
- **Soak засчитан как честный частичный результат** (~15.9ч
  непрерывной, необычно тяжёлой нагрузки, ноль падений core-сервисов),
  не как формальный 24-часовой прогон -- явно зафиксировано, не
  выдаётся за большее.
- **ADR-009's UI-fallback (`drm-splash`) физически подтверждён
  рабочим** -- первое реальное срабатывание за всю сессию, случайно
  спровоцированное собственной ошибкой тестирования (`cp` без
  `chmod`), не намеренный тест. Полезный, переиспользуемый вывод для
  любой будущей горячей подмены бинарника: `busybox cp` не сохраняет
  бит исполнения -- обязательно `chmod 755` после, до `mv`.
