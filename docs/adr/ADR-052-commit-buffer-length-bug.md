# ADR-052: тормоза переключения вкладок -- `with_buffer_contents` хешировал весь пул, не буфер

## Статус

Принято, 2026-09-13.

## Контекст

Пользователь сообщил о двух связанных, но разных наблюдениях после
физической проверки ADR-051:

1. Сразу после разблокировки переключение вкладок какое-то время
   почти не работало визуально, затем "само чинилось" через
   несколько касаний -- расследовано отдельно (см. "Побочная
   находка" ниже), причина оказалась не в этом баге.
2. После того как переключение "починилось", оно всё равно
   ощутимо тормозило -- заметная пауза между тапом и появлением
   новой вкладки. Пользователь прямо попросил выяснить, ресурсы ли
   это ОС или что-то иное.

Временная диагностика (`eprintln!` с миллисекундами через уже
существующее поле `presentation_started`, plus замер вокруг самого
`Sha256::update`) показала: между `touch up` и `saai-shell`'s
собственным `commit()`, долетающим до `saai-displayd`, проходило
900-1150мс на каждое переключение -- и почти всё это время уходило
на одну строку в `saai-displayd::commit()`:

```rust
let bytes = unsafe { std::slice::from_raw_parts(ptr, len) };
let mut hasher = Sha256::new();
hasher.update(bytes);
```

`len` в этом коде -- НЕ размер закоммиченного буфера. Собственная
документация `smithay::wayland::shm::with_buffer_contents` прямым
текстом говорит: "The first argument is a pointer to the contents of
the **pool**", "The second argument is the length of the contents of
the **pool**". Пул `wl_shm_pool` в клиенте растёт (обычно удвоением)
по мере того как `SlotPool` выделяет в нём новые слоты за время
жизни процесса -- и НИКОГДА не уменьшается. Использование `len`
вместо настоящего размера буфера (`data.stride * data.height`, где
`data: BufferData` уже присутствовал в сигнатуре замыкания и
использовался для метаданных кадра, но не для среза) означало, что
каждый `commit()` хешировал (и, при генуинно новом кадре, копировал
через `extend_from_slice`) **весь растущий пул**, а не ~10МБ одного
кадра.

Замер это подтвердил напрямую: `saai-shell` со своей стороны рисовал
корректные `1080x2400x4 = 10 368 000` байт (собственная диагностика
клиента это подтвердила), но `saai-displayd` хешировал 41 472 000
байт (4x) в одном раунде теста и 82 944 000 байт (8x) в другом --
оба кратны настоящему размеру кадра, оба выросли между раундами
(процесс перезапускался между ними, что и объясняет разную кратность
-- пул каждый раз начинает расти заново). Время хеширования росло
линейно вместе с размером: ~477мс на 4x, ~954мс на 8x.

## Решение

Считать байты буфера из `data.offset` на `data.stride * data.height`
байт, а не всю `len`-байтовую область пула:

```rust
let buffer_len = data.stride as usize * data.height as usize;
let end = (data.offset as usize).saturating_add(buffer_len);
let bytes: &[u8] = if end <= len {
    unsafe { std::slice::from_raw_parts(ptr.add(data.offset as usize), buffer_len) }
} else {
    eprintln!("saai-displayd: commit buffer geometry (offset={} len={buffer_len}) exceeds pool length {len}, skipping", data.offset);
    &[]
};
```

Проверка `end <= len` -- защита от некорректной геометрии (не должна
срабатывать для нашего единственного доверенного клиента, но чтение
за пределы пула было бы небезопасным `unsafe`-доступом без неё).
Единственное место использования `with_buffer_contents` во всём
проекте -- других мест с той же ошибкой нет (проверено `grep`).

## Test

Host: `cargo test -p saai-displayd` (обе фичи) -- все тесты зелёные,
включая 3 теста `is_new_content` из ADR-049, не тронутые этим
изменением. `cargo clippy -p saai-displayd` чист. Один тест
(`advertises_wl_data_device_manager` при `--features
panther-hardware`) падает и на чистом HEAD без этого фикса --
предсуществующий, требует реального DRM/KMS, не связан с изменением.

Device (тот же `cp && mv` + `chmod`, ADR-042; финальный hash
`0ec481aef7f5605063eb642482654dc18088b0eed345b8716b26f9b8750323bd`,
подтверждён через `sha256sum /proc/<pid>/exe`):

- **До фикса:** хеш от 4x-8x раздутого буфера, 477-955мс на каждое
  переключение вкладки, видимая задержка "тап -> новая вкладка"
  порядка секунды.
- **После фикса:** хеш стабильно от честных 10 368 000 байт,
  119-144мс на каждое переключение, без роста от раунда к раунду.
  Пользователь подтвердил физически: "стало значительно лучше".

## Побочная находка (не устранена, честно зафиксирована)

Отдельно от этого бага пользователь заметил: сразу после
разблокировки (или после длительного простоя) отклик заметно хуже,
чем через пару минут активного использования -- "как будто
выкручиваешь приржавевший болт". По ощущению это похоже на
CPU DVFS/governor, разгоняющий частоту процессора после периода
простоя, а не на программную ошибку в этом или предыдущих ADR --
`/proc/loadavg` в состоянии покоя показал 0.12, память в норме, явных
признаков ресурсного голода не найдено. Классический sysfs-путь
`cpufreq` (`/sys/devices/system/cpu/cpu*/cpufreq/scaling_cur_freq`)
на этом ядре не существует (другая схема управления частотой на
Tensor/Exynos) -- точный механизм не идентифицирован, дальнейшее
расследование не проводилось по границам этого ADR. Открытый вопрос
для будущей работы, если пользователь сочтёт остаточную задержку
после длительного простоя всё ещё существенной после этого фикса.

## Последствия

- Каждый `commit()` от `saai-shell` (и любого будущего клиента)
  теперь стоит ровно столько, сколько стоит реальный размер его
  кадра -- без накопительного роста в течение сессии.
- Тот же баг ранее делал ADR-050's "переиспользование буфера"
  (`clear()` + `extend_from_slice(bytes)`) дороже, чем задумано --
  копировался весь раздутый `bytes`, а не настоящий кадр; это
  автоматически исправлено тем же изменением, отдельный код не
  понадобился.
- Устойчивая производительность переключения экрана (~120мс) теперь
  не зависит от истории сессии (сколько кадров уже было отрисовано с
  момента запуска `saai-shell`).
