# ADR-048: S12 Change 5 -- health confirmation, boot attempt limit, автоматический откат

## Статус

Принято, 2026-09-12.

## Контекст

Change 5 -- последняя задача S12: health confirmation после обновления,
ограниченный счётчик boot attempts, автоматический откат при провале
health-check, физически продемонстрирован через намеренно нездоровую
тестовую сборку.

Ключевая находка перед реализацией: `saai-appd`/`saai-entityd` живут на
`/data/saaios/system/` (обновляются заменой файла), а `saai-shell`/
`saai-displayd`/`saaios-runtime` -- внутри ramdisk `init_boot_a`
(обновляются только через Change 4's механизм). Значит честный тест
"сломанного OTA-обновления" обязан менять содержимое самого
`init_boot_a`, а не файл на `/data` -- иначе тест не проверял бы
реальный OTA-путь Changes 2-4.

## Решение

**Механизм** -- три независимых, слабо связанных куска, ни один не
вшит в `native-init.c` (тот же принцип "доказать перед вшиванием", что
ADR-030/046/047):

- **`counter.rs`** -- персистентный счётчик попыток, обычный текстовый
  файл (`/data/saaios/system/boot-attempts`). `increment`/`reset`/
  `read`, отсутствие файла читается как 0.
- **`health.rs`** -- process-presence проверка: сканирует `/proc/*/
  cmdline`, сравнивает basename `argv[0]` с ожидаемым именем.
  Намеренно не протокольная проверка (не round-trip в каждый сервис) --
  этого достаточно, чтобы отличить "сервис поднят" от "сервис не
  запустился/упал", что и требовалось для этого теста; более глубокая
  per-service проверка -- честно не реализованная будущая работа.
- **`saai-ota-health` CLI**: `record-attempt` (инкремент счётчика --
  симулирует то, что будущий `native-init.c` вызвал бы в начале
  загрузки), `check` (опрашивает процессы до `--budget-secs`, при
  полном здоровье сбрасывает счётчик, иначе оставляет и завершается с
  ошибкой), `maybe-rollback` (если счётчик >= `--limit`, вызывает уже
  проверенный `saai-ota-write restore` как subprocess для каждого
  раздела и сбрасывает счётчик). `maybe-rollback` не содержит
  собственного кода записи раздела -- полностью переиспользует
  ADR-047's `saai-ota-write`.

**Тестовая нездоровая сборка -- реальная, через настоящий OTA-путь.**
Точная копия реально прошитого `init_boot_a` (`dist/panther/
stale-saaios-panther-init_boot.img.20260911T1358Z`, SHA-256
`2d702be4...`, побайтово совпадает с backup устройства из ADR-047)
взята как основа; `magiskboot` unpack/cpio/repack заменил
`saaios/saaios-runtime` (3.26 МБ) на тривиальный `int main(){return
1;}` (3.94 КБ, aarch64-linux-musl static). Итоговый образ --
8388608 байт (укладывается в лимит раздела), отличается от текущего
ровно одним файлом. Подписан `saai-ota-sign` (версия 0.15.0, только
`init_boot_a` в манифесте).

## Test -- host

`cargo test -p saai-ota-health` -- 8/8: поиск процесса по basename
`argv[0]` (инжектируемый `--proc-root` для тестов); отсутствие
процесса -- не паникует; отчёт обо всех отсутствующих, не только
первом; несуществующий `/proc` -- всё "отсутствует", не паника.
Счётчик: чтение отсутствующего файла как 0; инкремент персистентен;
сброс; повреждённое содержимое читается как 0, не паникует. `cargo
clippy --all-targets` и `cargo fmt -- --check` чисты. `cargo build
--workspace` чист. Кросс-компиляция чиста, hash
`c355290a7db01abb0071945aa80dffcd09867c187f2d6bf3a642c3535e5ec90d`.

## Test -- реальное устройство, с явным согласием пользователя перед drill'ом

**Впервые в проекте: реальная установка генуинно другого контента через
полный OTA-путь.** `saai-ota-stage` скачал и проверил сломанный
`init_boot_a` (8388608 байт, хеш сошёлся); `saai-ota-write install`
записал его в реальный раздел, попутно свежим backup сохранив ИСХОДНЫЙ
хороший образ (`2d702be4...`, совпал с известным).

**Три реальных "плохих" перезагрузки подряд**, каждая: `reboot -f` ->
устройство поднимается полностью штатно (kernel, Wi-Fi, Bluetooth, UI,
`native userspace ready`, `slot A marked successful` в `boot.log`), но
`ps` подтверждает отсутствие `saaios-runtime` (ровно 4 из 5 core-
процессов). `record-attempt` дал count=1, 2, 3 соответственно; `check
--budget-secs 8` каждый раз честно вернул `UNHEALTHY ... missing:
saaios-runtime` после полного тайм-аута опроса, счётчик не сброшен.

**Автоматический откат.** На count=3 (== `--limit 3`) `maybe-rollback`
вызвал `saai-ota-write restore` для `init_boot_a` -- восстановлен
байт-в-байт исходный хороший образ, счётчик сброшен в 0.

**Финальная перезагрузка -- полное восстановление.** `reboot -f` ->
`ps` показывает ВСЕ 5 core-сервисов, включая `saaios-runtime`;
`saai-ota-health check` вернул `healthy`, exit 0; независимая проверка
(`saai-ota-write backup` в throwaway-файл + `sha256sum`) подтвердила
точное байт-в-байт совпадение с исходным хорошим образом
(`2d702be4948678d4a751396477e3ed47a4c1fc5f5e1aa1a7be806683ef430351`).

Итого 4 настоящие перезагрузки подряд (3 плохие + 1 восстановительная),
все прошли ровно как спроектировано. `installed-version` возвращён к
`0.10.0`; тестовые staging/counter-файлы удалены; deploy-сервер и
firewall-правило убраны на Windows-хосте; канонические backup-файлы
(`init_boot_a.img.bak`, `vendor_boot_a.img.bak`) оставлены на
устройстве.

## Последствия

- Полный цикл S12's Acceptance criteria физически подтверждён на одном
  реальном раунде: подписанный manifest с генуинно другим контентом
  принят и установлен; намеренно нездоровая сборка обнаружена
  health-check'ом; ограниченный boot attempt limit сработал; автоматический
  откат восстановил последний физически подтверждённый рабочий образ;
  устройство пережило 4 настоящих cold reboot подряд.
- **Ничего не вшито в `native-init.c`.** `record-attempt`/`check`
  вызывались вручную по serial, имитируя то, что будущая интеграция в
  boot-critical путь делала бы автоматически. Реальное вшивание --
  осознанно отдельное, будущее решение, не входящее в S12 (тот же
  принцип, что ADR-030 закрепило для `saai-taskd`).
- **Тайминг-пробел ADR-046 не устранён.** `mark_current_slot_successful()`
  по-прежнему вызывается сразу после "native userspace ready",
  безусловно -- в трёх из четырёх перезагрузок этого раунда `boot.log`
  показал `slot A marked successful` даже когда `saaios-runtime` не
  поднялся. Реальный ABL-бутлоадер (если он вообще читает этот бит,
  что не подтверждено) не получил бы сигнала о нездоровье через этот
  канал. Это здесь не чинится -- находка остаётся открытой,
  задокументированной, для решения при будущем вшивании в
  `native-init.c`.
- Health-check -- process-presence, не протокольный round-trip;
  честно ограничено, не выдаётся за полную проверку живости.
