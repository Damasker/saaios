# ADR-050: saai-displayd OOM -- buffer reuse, честный остаток на экстремальной нагрузке

## Статус

Принято, 2026-09-12.

## Контекст

ADR-049 закрыл ~79% лишней нагрузки, пропуская дорогое копирование
для commit'ов с неизменным содержимым, но честно оставил открытым
случай ГЕНУИННО нового кадра: каждый такой commit по-прежнему
аллоцировал свежий `Vec<u8>` (~10МБ) через `bytes.to_vec()`,
немедленно отбрасывая предыдущий буфер. Рекомендация ADR-049 --
переиспользовать уже выделенный буфер вместо этого. Этот ADR
реализует и физически проверяет это доработку.

## Решение

`SurfaceFrame::pixels` теперь не заменяется целиком при каждом новом
кадре, а **забирается из `HashMap` (`remove`), переиспользуется через
`clear()` + `extend_from_slice()` внутри замыкания `with_buffer_
contents` (оно `FnOnce`, что позволяет безопасно передать `Vec`
владением и получить обратно) и вставляется назад**. `clear()` не
уменьшает capacity; `extend_from_slice()` переиспользует существующую
аллокацию, если новых байт не больше, чем уже выделено -- для
поверхности с постоянным размером кадра (подавляющее большинство
реальных случаев) это означает **ноль новых аллокаций после первого
кадра**, вместо аллокации+освобождения на каждый генуинно новый
commit. Совпадающий digest (ADR-049) по-прежнему пропускает даже
`clear()+extend_from_slice()` целиком -- буфер остаётся нетронутым.
Новая поверхность (нет что переиспользовать) по-прежнему аллоцирует
один раз -- неизбежно и корректно.

## Test

Host: `cargo test -p saai-displayd` (обе комбинации фичи) -- все
существующие тесты + 3 теста `is_new_content()` из ADR-049 зелёные,
без изменений (сама функция не тронута, изменился только вызывающий
код). `clippy` чист. Кросс-компиляция чиста, hash
`24de56e85415c6126353377a0851beca244c3b4497b5b990974a4a63a70caaa1`.

Device (та же runtime-подмена, `cp && mv` + `chmod`, ADR-042):
**точно тот же эскалирующий burst-тест, что дал 670МБ в ADR-049**
(40 касаний @0.5с -> 40 @0.3с -> 60 @0.25с) -- теперь **рост
остановился на 346МБ и не продолжился на самом агрессивном из трёх
уровней** (было: 346 -> 670МБ на этом же уровне; стало: 346 -> 346МБ).

**Честный остаток, не устранённый.** Ещё более экстремальный
синтетический темп (80 касаний за ~16 секунд, интервал 0.2с -- около
5 касаний/сек непрерывно, быстрее реалистичного человеческого
взаимодействия) всё же поднял RSS до **1.3 ГБ** -- в точности
диапазон настоящих OOM-килов из ADR-043. Проверено: ни `saai-displayd`,
ни `saai-shell` не падали и не пересоздавались за это время (те же PID
до и после), задействованы ровно 3 стабильные, давно существующие
поверхности (не разрастание новых) -- точный механизм на этом
экстремальном темпе не идентифицирован, дальнейшая охота остановлена
по совместному решению с пользователем: реальный инцидент ADR-043
случился при человеческих нажатиях кнопки (физически ограничены
темпом человека, далеко от 5 касаний/сек синтетики), так что этот
остаточный риск оценён как открытый, но не блокирующий для
реалистичного сценария использования.

## Последствия

- Реалистичная нагрузка (соответствующая исходному инциденту
  ADR-043) теперь физически подтверждена не растущей -- порог, при
  котором рост вообще начинается, сдвинут значительно выше.
- Экстремальный, superhuman-темп всё ещё может воспроизвести рост до
  OOM-диапазона -- задокументировано честно, не выдаётся за полностью
  решённое. Точный механизм на этом темпе остаётся открытым вопросом
  для будущей работы, если реальная эксплуатация когда-либо покажет
  сопоставимую по интенсивности нагрузку (маловероятно при обычном
  использовании реальным человеком).
- `saai-shell` не менялся ни в этом раунде, ни в ADR-049.
