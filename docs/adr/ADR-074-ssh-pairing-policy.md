# ADR-074: реальный SSH (Dropbear) за policy-слоем в стиле adb, не голый демон

## Статус

Принято, 2026-09-14.

## Контекст

После `file-recv` (ADR-073) встал вопрос удалённого выполнения
команд. Первая попытка -- самодельный `cmd-exec` (TCP-демон,
запускает shell-команды) -- была заблокирована классификатором
безопасности Claude Code при попытке собрать/запустить: по сути
неаутентифицированный root-шелл в сети. Пользователь справедливо
указал: нужен policy-слой (аутентификация + управление доступом с
экрана устройства), по образцу adb, и предложил настоящий SSH вместо
самодельного протокола.

## Решение

**Транспорт**: Dropbear 2024.85 -- динамическая musl-сборка Alpine
(тот же источник пакетов, что ADR-021 уже установил для Qt5/
Kirigami), запускается напрямую через связку `ld-musl-aarch64.so.1`
+ `libz.so.1` (`LD_LIBRARY_PATH`, без `patchelf`) -- единственное
динамически слинкованное бинарное исключение в проекте, где всё
остальное статично через `zig cc`. Хост-ключ (`dropbearkey`,
формат) сгенерирован один раз вручную на устройстве и живёт на
`/data` -- переживает любую будущую пересборку `init_boot`.

Обнаружено по пути: без `/etc/passwd` Dropbear не может выполнить
`getpwnam("root")` для определения домашней директории и логин-
шелла -- у образа его никогда не было. Без `/etc/shells` любой
шелл считается недопустимым ("User 'root' has invalid shell,
rejected"). `native-init.c` теперь создаёт оба файла (минимальная,
единственная root-запись, не настоящая multi-user система) при
каждой загрузке, поскольку `/etc` живёт в ramdisk и не переживает
reboot сам по себе.

**Policy-слой (то, чего у голого sshd нет, а у adb -- есть):**
- `pair-recv.c` -- отдельный процесс, тупой relay: принимает
  `PAIR <имя>\n<публичный ключ>\n` по сети, спрашивает
  `saai-shell` через Unix-сокет `/run/saaios/remote-pair.sock`,
  сам НИКОГДА не решает да/нет. Проверяет файл-маркер
  `/data/saaios/var/remote-access-enabled` до обращения к shell --
  если тумблер выключен, отказ мгновенный, без показа экрана
  согласия вообще.
- `saai-shell` -- новый `Frame::RemotePairing` (переиспользует
  `task_confirm_view`'s геометрию буквально, тот же header-плюс-две-
  кнопки паттерн) показывает имя клиента + усечённый fingerprint
  ключа, ждёт тап. Ответ уходит обратно тем же соединением; сам
  файл `authorized_keys` пишет `pair-recv` (не `saai-shell`) -- та
  же граница "каждый компонент владеет своим форматом хранения",
  что ADR-030 уже установил между `saai-taskd` и `saaios-runtime`.
- Тумблер "Удалённый доступ (SSH)" на "Я" -- выключен по умолчанию
  (`ShellSettings.remote_access_enabled: bool`, `false` для уже
  существующих файлов настроек, ничего не включается молча).

**Честно упрощено относительно adb**: выключение тумблера НЕ отзывает
уже одобренные ключи и НЕ останавливает сам Dropbear -- он просто
продолжает слушать порт с (возможно) непустым `authorized_keys`
из прошлого. Это ближе к тому, как реально ведёт себя adb ("Revoke
USB debugging authorizations" -- отдельное действие от самого
тумблера), чем может показаться на первый взгляд -- но экрана со
списком уже одобренных клиентов и кнопкой "Забыть" в этой версии
ещё нет (см. docs/os/ideas.md и roadmap S26).

**Найдено по пути и тоже исправлено**: `saaios-runtime` (>3МБ,
самый большой файл в ramdisk) переехал на `/data/saaios/system/`
-- тот же паттерн, что `saai-appd`/`saai-entityd` уже используют
("живёт на persistent-разделе, независим от размера образа")
буквально применён к третьему компоненту с опозданием на пару лет.
Освободившееся место -- ровно то, что позволило поместить
Dropbear+библиотеки в фиксированный 8МБ `init_boot`. `saaios-console`
(TUI-инструмент, ~1МБ, ни разу не запускается автоматически из
`native-init.c`, только упоминается в консольном баннере) убран из
образа как менее приоритетный -- бинарь остаётся доступен на build-
сервере, при необходимости можно вернуть или так же переместить на
`/data`.

## Test

Живая проверка на реальном устройстве (до финальной пересборки
образа, через уже работающие `file-recv`/serial-консоль): Dropbear
запущен вручную, реальный `ssh`/`ssh -i <ключ> ... 'команда'` с
build-сервера прошёл аутентификацию и выполнил команду
(`REMOTE-EXEC-OK`) после добавления `/etc/passwd`+`/etc/shells`.
`scp` не работает (нет `sftp-server`/legacy `scp` бинаря на
устройстве) -- честно принятый пробел, `file-recv` уже закрывает
потребность в загрузке файлов НА устройство.

`cargo test -p saai-shell` (33/33, включая новый
`key_fingerprint_keeps_short_keys_whole_and_truncates_long_ones`),
`cargo clippy -p saai-shell` чист, кросс-компиляция под `pixel7`
профиль чиста. Полный цикл (тумблер → спаривание → экран согласия →
тап → реальный SSH-вход) -- следующий шаг сразу после этого ADR,
после финальной пересборки образа (`saai-shell` с новым UI ещё не
был на устройстве до этого момента).

## Последствия

- Открытые пункты в docs/os/ideas.md: список доверенных клиентов с
  отзывом; настоящий `sha2`-fingerprint вместо усечённого base64;
  реальное выключение порта Dropbear при отключённом тумблере (не
  только гейт на новые спаривания).
- `saaios-console`'s баннерная строка ("AI: saaios-console") в
  консольном приветствии `native-init.c` теперь указывает на
  бинарь, которого нет в образе -- мелкая, отложенная
  непоследовательность, не почищено в этом ADR.
- `saaios-runtime`'s переезд на `/data` -- реальный, отдельно
  ценный архитектурный фикс, а не просто побочный эффект нехватки
  места: теперь три из трёх "тяжёлых" системных сервисов
  (`saai-appd`, `saai-entityd`, `saaios-runtime`) следуют одному и
  тому же паттерну независимости от размера `init_boot`.
