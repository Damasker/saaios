# ADR-031: S09 Change 2 -- минимальный вертикальный срез физически подтверждён: реальный тап -> Intent -> Task -> Action -> Result

## Статус

Принято, 2026-09-11.

## Контекст

ADR-030 решило модель данных (`Intent`/`Task`/`Action`/`Result` -- новые
`entity_type` в native `saai-entity-store`, не Platform Track). ADR-029
решило текстовый ввод (bespoke touch-hit-test клавиатура в
`saai-shell`, ранее throwaway-спайк, не закоммичен). Change 2 (S09
Scope, третий пункт) требовал первый реальный, минимальный, сквозной
срез: одна Intent-строка -> один Task с одним неопасным Action ->
Result, видимый в `Сейчас`, физически подтверждённый на устройстве --
не в теории.

## Реализация

**`services/saai-taskd`** (новый native-демон, НЕ добавлен в
`native-init.c`'s boot-последовательность -- та же осторожность, что
S06/S07 уже применяли: сначала физически доказать workflow, потом
решать про автозапуск, отдельным шагом):

- `src/model.rs` -- чистая, без IO, схема и логика: `entity_type`
  константы (`saaios.intent`/`saaios.task`/`saaios.action`/
  `saaios.result`), `WorkflowStatus` (`pending`/`running`/
  `waiting_confirmation`/`done`/`failed`/`cancelled`) с
  `valid_transition()`, намеренно вouching ТОЛЬКО за переходы, которые
  Change 2 реально использует (`Pending->Running`, `Running->Done`,
  `Running->Failed`) -- `waiting_confirmation`/`cancelled` остаются
  недекларированными до Change 3, а не угаданы заранее.
  Идемпотентность -- `has_task_for_intent()` по свойству `intent_id`.
  Единственное неопасное Action -- `run_echo_action()`: детерминированный
  echo (uppercase + счёт символов/слов), ничего не трогает вне
  собственных аргументов. 15 unit-тестов.
- `src/client.rs` -- отдельный, последовательный (не non-blocking,
  как `saai-shell`'s собственный) async-клиент `saai-entity-protocol`'s
  wire-протокола: одна команда в полёте одновременно, буферизация
  `Subscribe`-событий, пришедших вперемешку с ответом на текущий запрос.
  3 wire-теста (fake-entityd тот же паттерн, что `entityd_client.rs`'s
  собственный тест).
- `src/lib.rs` -- `Daemon::reconcile_existing_intents()` (catch-up при
  старте/после рестарта) + `Daemon::run()` (реактивный цикл по
  `Subscribe`-событиям), оба используют одну и ту же идемпотентность.

**`services/saai-shell`** (реальная, закоммиченная версия ADR-029's
клавиатуры, не throwaway):

- `entityd_client.rs`: добавлен `create_entity()` -- единственный
  write-путь, который понадобился клиенту до сих пор.
- `main.rs`: `Frame::IntentInput`, `intent_view()`/`intent_action_at()`
  (та же `Node`/`layout()`/`hit_test()` система, что `root_view()`/
  `consent_view()`), настоящая (не 6-клавишная спайк) строчная
  QWERTY-раскладка (`INTENT_KEY_ROWS`) плюс Отмена/␣/⌫/Отправить.
  `handle_intent_input_action()` -- единственная функция, которая
  реально пишет: `intent:send` вызывает `create_entity` с
  `entity_type="saaios.intent"` в `self.selected_space_id` (текущее
  ВЫБРАННОЕ пространство, не хардкод -- важно, см. Находки ниже).
  3 новых hit-test теста (клавиатура), 1 обновлён (счётчик content
  actions). Итого 19 тестов.
- `render.rs`: `draw_intent_input()`.
- `ui/root.sui`: новая карточка `new-intent` на странице `now`
  ("Новое намерение").

Хост-проверка: `cargo test/fmt/clippy -p saai-taskd -p saai-shell`
зелёные (15 + 19 тестов), `cargo build --workspace` (кроме
`saai-displayd`, у которого на VM пред-существующий, не связанный с
этим изменением пробел -- нет `libxkbcommon-dev`) зелёный.

## Физическая проверка

Устройство физически было подключено не к серверу сборки (R620), а к
Windows-хосту этой сессии -- через USB-serial-консоль (`COM13`,
115200) и `UsbNcm`-сетевой интерфейс (`172.31.7.1`, устройство уже
загружено в SaaiOS, боевые `saai-entityd`/`saai-appd`/`saai-displayd`/
`saai-shell` уже работали). Файлы доставлялись через одноразовый
HTTP-сервер (`System.Net.HttpListener` в PowerShell) поверх этого же
NCM-линка -- диагностирован и снят один затык: Windows Defender
Firewall молча дропал входящие TCP на порт раздачи, из-за чего
busybox `wget` на устройстве висел до собственного таймаута, а не
падал сразу с "connection refused".

**Ядро воркфлоу** (`saai-taskd` против боевого `saai-entityd`, без UI):
через уже существующий на устройстве `unix-json-request` (тестовый
inструмент, `os/targets/panther/tools/unix-json-request.c`, уже
скомпилирован и лежал в `/data/saaios/system/`) создан
`saaios.intent` с текстом "hello change two" в пространстве `home`.
`saai-taskd` (кросс-собран, hash сверен, запущен вручную) отреагировал
через `Subscribe`, создал `Task`->`Action`->`Result` за миллисекунды:
`"16 симв., 3 слов -> HELLO CHANGE TWO"` (16 символов и 3 слова у
"hello change two" -- верно). Проверено через `list_entities`: все
четыре `entity_type` присутствуют с правильными перекрёстными
ссылками (`intent_id`/`task_id`/`action_id`).

**Идемпотентность физически проверена реальным рестартом**: `kill` +
повторный запуск `saai-taskd` -- `reconcile_existing_intents()` НЕ
создал второй `Task` для уже обработанного `Intent` (лог пуст,
`grep -c saaios.task` после рестарта = 1, не 2).

**Реальный тап по реальной клавиатуре**: написан и кросс-собран новый
инструмент `os/targets/panther/tools/uinput-touch.c` -- протокол-B
синтетический touch через `/dev/uinput`
(`ABS_MT_POSITION_X`/`ABS_MT_POSITION_Y`/`ABS_MT_TRACKING_ID` +
`SYN_REPORT`), сверенный построчно с `saai-displayd/src/touch.rs`'s
реальным парсером -- не упрощённый `BTN_TOUCH`/`ABS_X`/`ABS_Y`
(протокол A), который `saai-displayd` не читает вообще.
`/dev/input/touchscreen`-символинк переключён на новое синтетическое
устройство (`mknod` вручную -- по-прежнему нет hotplug-демона, ADR-028's
находка остаётся в силе). `saai-shell`'s боевой бинарник временно
подменён (`cp`+`mv`, атомарно, минуя "text file busy") на новую
сборку, оригинал сохранён и хэш-сверен байт-в-байт (`34653527...` --
та же цепочка хэшей, что ADR-029 уже зафиксировало). Пять тапов через
FIFO-управляемый `uinput-touch` (разблокировка, карточка "Новое
намерение", буквы `h`/`i`, "Отправить") дважды независимо создали
реальный `saaios.intent` с текстом `"hi"` -- лог `saai-shell` сам
подтвердил: `saai-shell: submitted intent "hi"`.

**Ложный след, зафиксирован явно.** Первая проверка результата (запрос
`list_entities` к пространству `home`) не нашла новых сущностей.
Гипотеза "displayd открывает `/dev/input/touchscreen` один раз при
своём старте, символинк после этого не действует" выглядела
правдоподобно (и физически верна как общий факт) -- displayd был
дополнительно перезапущен на всякий случай. Реальная причина оказалась
иной: `get_selection` показал, что боевая, ранее выбранная
пользователем актуальная пространство -- `work`, не `home`. Оба тапа
физически сработали с первого раза; `saai-shell`'s код корректно
создаёт `Intent` в `self.selected_space_id` (реальном текущем выборе),
а не в хардкоженном `home` -- это правильное, не ошибочное поведение.
Перезапуск `saai-displayd` оказался избыточным, но безвредным шагом
устранения неполадок. Второй `saai-taskd` (`--space work`) подобрал
оба зависших `Intent` через `reconcile_existing_intents()` --
`"reconciled 2 pre-existing intent(s)"`, оба корректно обработаны
(`"2 симв., 1 слов -> HI"`).

**Откат тестовой оснастки, полностью выполнен:**
`uinput-touch`'s устройство уничтожено штатно (команда `quit` через
FIFO), `/dev/input/touchscreen` возвращён на реальный `event2`,
`saai-shell`'s боевой бинарник восстановлен из бэкапа (хэш `34653527...`
сверен на восстановленном работающем процессе), `saai-taskd` остановлен
(не входит в боевой набор служб), 8 тестовых сущностей
(`intent`×2/`task`×2/`action`×2/`result`×2, все "hi") удалены из
`work` -- с явным подтверждением пользователя после того, как
auto-mode классификатор заблокировал массовое удаление без него.
Временное правило Windows-файрвола и HTTP-сервер остановлены/удалены.
Финальная проверка: `work` пуст, боевые `saai-displayd`/`saai-shell`
работают, `readlink /dev/input/touchscreen` -> `event2`.

## Решение

S09's Change 2 (минимальный вертикальный срез) закрыт: `Intent`
физически вводится через реальную, закоммиченную on-screen клавиатуру
`saai-shell`, `saai-taskd` реактивно и идемпотентно превращает его в
`Task -> Action -> Result` через уже существующий `saai-entityd`, всё
подтверждено на реальном Pixel 7 -- не в теории, не через debug-путь.

`saai-taskd` намеренно НЕ добавлен в `native-init.c` -- он не является
частью боевого набора служб до отдельного решения об автозапуске
(вопрос "когда/как это должно стартовать при загрузке" не тот же
вопрос, что "работает ли сам workflow", и не решается этим ADR).

## Последствия

- S09's Scope's "НЕ входит" пункты (planner/AI-планы, automation,
  `Входящие`-экран, полная интеграция с `saaios-runtime`) остаются вне
  рамок -- ничего в Change 2 их не затронуло.
- Открытый вопрос для Change 3: подтверждение опасного Action,
  переживающее cold-reboot (S09's Acceptance criteria в целом) --
  `WorkflowStatus::WaitingConfirmation`/`Cancelled` уже в словаре
  (ADR-030), но без переходов/производителя состояния, целенаправленно.
- `saai-taskd`'s автозапуск при боевой загрузке (правка `native-init.c`)
  -- отдельная, ещё не начатая задача.
- Найден и задокументирован реальный (не гипотетический) режим отладки:
  всегда явно проверять `get_selection` перед тем как делать выводы о
  "куда делась сущность", а не предполагать `home` по умолчанию --
  относится к любой будущей физической проверке entity-store поведения.
