# ADR-069: S25 -- размер текста и контраст без переписывания каждого вызова отрисовки

## Статус

Принято, 2026-09-13.

## Контекст

Последний пункт исходного запроса серии ("размер шрифта, контраст",
явно НЕ ещё одна смена гарнитуры -- см. более раннее решение по S13
закрыть тему выбора шрифта на Montserrat). `render.rs` передаёт
литеральный размер (`38.0`, `42.0`, `54.0` и т.д.) в ~40 отдельных
вызовов `draw_text`/`draw_text_centered`, и использует ~90 вызовов
`fill_rect`/`draw_text` с именованными цветовыми константами
(`BACKGROUND`, `SURFACE`, `TEXT`, ...) по всему файлу. "Правильный"
с точки зрения чистой архитектуры путь -- протащить параметр
масштаба/контраста через каждый такой вызов -- means трогать
практически весь файл ради одного спринта, с кратно возросшим риском
регрессии в уже физически подтверждённых экранах.

## Решение

**Размер текста**: `render::set_text_scale(pct)` хранит множитель в
одном `AtomicU32` (биты `f32`, `std` не имеет `AtomicF32`), который
`draw_text`/`draw_text_centered` читают сами в начале, домножая свой
`size`-параметр -- ни один из ~40 существующих call sites не
изменился. Единственная плата -- небольшой участок общего для
процесса состояния вместо чистого потока данных через параметры;
приемлемо, потому что этот процесс всегда рисует ровно один UI на
одном потоке -- гонок данных здесь в принципе быть не может.

**Контраст**: `render::apply_contrast_boost(pixels, pct)` -- один
проход по уже отрисованному кадру целиком (растяжение каждого байта
от точки 128 в сторону 0/255), вызывается явно из `main.rs` после
каждого из трёх мест, что пишут в реальный Wayland-буфер (`draw()`,
`present_status_bar`, `present_lock_pin_entry`), а не как вторая
цветовая палитра, протянутая через каждый `fill_rect`. `0` --
байт-в-байт no-op, гарантированно не меняющий уже подтверждённый
рендеринг при выключенном контрасте (значение по умолчанию).

Обе настройки -- новые карточки "Размер текста"/"Контраст" на "Я"
(строки 12-13), тот же cycle-по-пресетам паттерн, что и
яркость/громкость/etc: `TEXT_SCALE_LEVELS_PCT = [85,100,125,150]`,
`CONTRAST_LEVELS_PCT = [0,50,100]`.

## Test

Host: `cargo test -p saai-shell` (32/32 ok, включая
`contrast_boost_zero_is_a_byte_for_byte_no_op`/`contrast_boost_
pushes_values_away_from_the_midpoint`), `cargo clippy -p saai-shell`
чист, кросс-компиляция под `pixel7` профиль чиста.

Device: отложено (ADR-058). Особое внимание при финальной проверке:
поскольку `contrast_pct`/`text_scale_pct` по умолчанию `0`/`100`
(отключено/без изменений), весь остальной уже физически
подтверждённый UI должен выглядеть на устройстве байт-в-байт так же,
как до этого спринта -- если это не так, `apply_contrast_boost`'s
"0 -- no-op" гарантия сломана и требует немедленного разбора прежде
чем считать остальные 11 спринтов серии подтверждёнными.

## Последствия

- Оба механизма (глобальный atomic для масштаба, явный
  пост-процесс-вызов для контраста) выбраны ради минимального blast
  radius на уже работающий код, а не потому что это "идеальная"
  архитектура -- честно не идеал, а осознанный компромисс.
- `text_scale`'s `AtomicU32` -- первое (и пока единственное) место в
  `saai-shell`, использующее `std::sync::atomic` вместо явной
  передачи состояния через `&mut self`/параметры; если в будущем
  появится второй похожий кейс, стоит пересмотреть, не пора ли
  вводить настоящий параметр вместо повторения этого паттерна.
