# ADR-072: устанавливаем настоящее третье приложение (Маджонг) через реальный Install RPC

## Статус

Принято, 2026-09-13.

## Контекст

Пользователь попросил: "установи стороннее приложение, например
маджонг" -- уточнил, что цель не сама игра, а доказать, что ОС
умеет устанавливать сторонние приложения. Готового маджонга для этой
архитектуры нет нигде (aarch64-musl, собственный Wayland-протокол,
sandbox/capability модель S07) -- единственные два существующих
приложения (`org.saaios.demo-surface`, Kirigami-демо S08) написаны
специально для этой ОС её же авторами, а не независимо.

`saai-appd` уже имеет полный, ранее не используемый для НОВОГО
приложения путь: `ClientRequest::Install { package_path }` ->
`Store::install()` копирует директорию (`manifest.toml` + `bin/
<exec>`) в `apps/<id>/`, откуда приложение становится обычным
запускаемым через `Launch`. Ни `saai-shell`, ни какой-либо другой
компонент никогда не отправлял `Install` для чего-то, кроме того,
что уже было на диске с самого начала -- этот RPC путь существовал,
но не был провёрен для по-настоящему нового пакета.

Критическое ограничение, обнаруженное при подготовке: `package_path`
-- путь НА САМОМ УСТРОЙСТВЕ (appd просто копирует локально), но на
устройстве нет ни SSH, ни adb, ни лёгкого способа положить файл
(та же проблема, что и с деплоем `saai-shell` в течение всей серии
S14-S25) -- единственный проверенный канал -- полная пересборка и
`fastboot flash init_boot_a`.

## Решение

- Новое приложение `org.saaios.mahjong` (`services/saai-mahjong`) --
  простая игра "найди пару" (6x4 = 24 плитки, 12 пар), написанная с
  нуля как независимый Wayland-клиент (`wayland-client`/`wayland-
  protocols` напрямую, без `smithay-client-toolkit` -- тот же выбор,
  что и у `saai-demo-surface`), без общего кода с `saai-shell`.
  `capabilities = []` в манифесте -- не запрашивает ничего, поэтому
  `Launch` никогда не требует экрана согласия (ADR-020).
- Тот же бинарь умеет устанавливать сам себя: `saai-mahjong
  --install [package-dir] [socket]` подключается к `/run/saaios/
  appd.sock` и отправляет `Install` тем же newline-delimited JSON
  протоколом, что уже использует `saai-shell`'s `appd_client`.
  Отдельный бинарь-установщик (`saai-install-app`) был написан
  первым, но снят: две статически слинкованные копии `saai-app-
  protocol`/`serde_json` в двух маленьких бинарях стоили дороже, чем
  одна `--install` ветка в этом одном -- на счету был каждый байт
  фиксированного 8МБ `init_boot`-раздела (первая полная сборка с
  обоими бинарями превысила лимит на 153984 байта).
- Пакет (`manifest.toml` + сам бинарь) бандлится в `init_boot`
  напрямую в `build-native-c-image.sh` (`saaios/packages/
  org.saaios.mahjong/`), а не через отдельный package-каталог в
  `dist/` -- собственного лёгкого канала доставки на устройство всё
  ещё нет, и заводить его для одного приложения было бы больше
  работы, чем сам спайк. Установка всё равно требует реального шага
  (`saai-mahjong --install` с серийной консоли) -- бандлинг в образ
  доставляет БАЙТЫ на диск, но не делает приложение "уже
  установленным" (оно физически лежит в `saaios/packages/`, а не в
  `apps/`, пока `Install` не скопирует его).

## Test

Host: `cargo build`/`cargo clippy -p saai-mahjong` чисты. Кросс-
компиляция под `pixel7` профиль чиста, итоговый образ -- ровно
8388608 байт (в пределах лимита раздела).

Device: физическая проверка -- следующий шаг после этого ADR:
`saai-mahjong --install` с серийной консоли, затем запуск через
"Сейчас" (иконка в сетке S23), реальная игра тапами.

## Последствия

- Открытый пункт: у ОС до сих пор нет собственного лёгкого канала
  "положить файл на устройство без полной пересборки/flash" --
  каждое новое стороннее приложение (или обновление уже
  установленного) сегодня требует того же самого полного цикла.
  Это настоящее ограничение, а не то, что этот спринт был обязан
  решить -- он лишь ещё раз подтвердил его существование и показал,
  что сам путь `Install` работает корректно, когда файлы всё-таки
  оказались на диске.
- `Fonts::load()` в `saai-mahjong` указывает на `/saaios/fonts/
  Montserrat-{Regular,SemiBold}.ttf` -- те же пути, что ADR-070
  исправил для `saai-shell` -- а не на устаревшие `Inter-*.ttf`,
  которые всё ещё указаны (и уже не существуют) в `saai-demo-
  surface`'s собственном `render.rs` (не исправлено этим ADR --
  вне зоны действия, `demo-surface` не тестировался и не менялся
  здесь).
