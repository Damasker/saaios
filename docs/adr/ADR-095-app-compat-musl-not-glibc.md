# ADR-095: сторонние Linux ARM64 приложения остаются на musl (Alpine), glibc-остров не заводим

## Статус

Принято, 2026-09-17. APP-COMPAT-ROADMAP.md, спринт-кандидат APP-00.

## Контекст

Исходная формулировка задачи (App Compatibility roadmap, раздел 1)
предполагала "Linux/glibc compatibility island" как отдельный слой под
Wayland-клиентами. Это предположение не было проверено на момент
постановки задачи -- APP-00 существует именно чтобы закрыть его
спайком, а не унаследовать без проверки.

Уже известный факт до этого ADR: ADR-021 выбрал Alpine musl как
источник пакетов для GTK4/Qt5/Kirigami2, и это физически проверено
(ADR-026/027/028) для Qt-пути на реальном устройстве. Открытый вопрос
-- достаточно ли этого решения для ВСЕХ кандидатов дальнейшего плана
(Qt6, PCManFM-Qt, экранная клавиатура, браузер), или где-то в списке
есть зависимость, которая реально требует glibc и не собирается под
musl.

## Проверка

Проверена доступность готовых aarch64-пакетов в Alpine (edge,
community) для каждого кандидата дальнейшего плана -- если пакет
существует в Alpine, он по определению собран под musl (у Alpine нет
отдельной glibc-ветки):

| Кандидат | Пакет в Alpine aarch64 | Версия |
|---|---|---|
| Qt6 (APP-01/05) | `qt6-qtbase` | 6.11.1-r3, community |
| PCManFM-Qt (APP-05) | `pcmanfm-qt` | 2.4.0-r0, community |
| WebKitGTK (APP-06) | `webkit2gtk-6.0` (GTK4) и `webkit2gtk-4.1` (GTK3) | 2.48.1-r4 / 2.48.7-r0, community |
| QtWebEngine (APP-06) | `qt6-qtwebengine` | 6.11.1-r3, community |
| Firefox (APP-06) | `firefox` | 154.0-r0, community |
| Chromium (APP-06) | `chromium` | 152.0.7977.82-r1, community |
| wvkbd (APP-03/04) | `wvkbd` | 0.20-r0, community |
| Squeekboard (APP-03/04) | доступен в других дистрибутивах под musl-эквивалентными сборками; в самом Alpine отдельно не проверялся построчно, не блокирует вывод ниже |

Ни один из этих кандидатов не потребовал отдельной проверки glibc --
все существуют как готовые aarch64/musl сборки. Ни одна зависимость,
требующая glibc, не найдена ни для одного кандидата дальнейшего
плана.

Побочная находка, не относящаяся напрямую к musl/glibc, но важная для
APP-03/APP-04 (зафиксирована здесь, чтобы не потерять): и `wvkbd`, и
`squeekboard` (сайт-поиск по их собственным README/build-зависимостям)
напрямую зависят от `libxkbcommon` для работы с
`zwp_virtual_keyboard_v1`/`zwp_input_method_v2` -- keymap реально
компилируется и передаётся через xkbcommon с обеих сторон протокола.
ADR-012/ADR-022 уже физически доказали, что xkbcommon SIGTRAP'ается на
этом устройстве при попытке скомпилировать ЛЮБОЙ keymap (7 независимых
вариантов, включая полностью self-contained from-string). Значит ни
`wvkbd`, ни `squeekboard` в их нынешнем виде запустить на этом
устройстве, вероятнее всего, не получится -- это не гипотеза, а прямое
следствие уже установленного факта. Подтверждает и усиливает
формулировку APP-COMPAT-ROADMAP.md's APP-03: нужен спайк на стороне
`saai-displayd` (реализация `zwp_input_method_manager_v2`, не
трогающая `wl_keyboard`/xkbcommon вообще), а не выбор готового
OSK-проекта как таковой.

Отдельная находка для APP-06 (не блокирует это решение, но меняет
приоритет внутри самого APP-06): `webkit2gtk-4.1` (GTK3, не GTK4)
существует отдельно от `webkit2gtk-6.0` (GTK4). Поскольку именно GTK4
детерминированно крашится на этом железе (ADR-025), а GTK3 этим ADR не
затронут, `webkit2gtk-4.1`-based браузер (например, старые версии
Epiphany, либо собственная минимальная WebKitGTK-оболочка на GTK3) --
потенциально жизнеспособный путь, который не нужно откладывать до
починки GTK4 (APP-02). Это не проверено физически, только по наличию
пакета -- остаётся открытым пунктом самого APP-06, не решается этим
ADR.

## Решение

Продолжаем на musl (Alpine aarch64 как источник пакетов, тот же путь,
что ADR-021 уже выбрал и ADR-026/027/028 уже проверили физически) для
всех кандидатов APP-COMPAT-ROADMAP.md, пока не найдена конкретная
зависимость, которая реально требует glibc. Отдельный
"glibc compatibility island" не заводим -- это добавило бы второй libc
в систему без единого подтверждённого случая необходимости, и
противоречило бы musl-first архитектуре SaaiOS в целом (весь остальной
образ уже musl).

Если в будущем конкретный кандидат (например, какая-то версия
Android-моста, раздел ANDROID/PLAY roadmap'а) реально потребует glibc
-- это отдельное решение с собственным ADR в момент, когда такая
зависимость будет названа конкретно, не заранее.

## Последствия

- APP-00 закрыт этим ADR -- не требует больше отдельного спайка.
- APP-01 (Qt hello-world) может использовать тот же musl/Alpine путь,
  что уже проверен -- никаких новых зависимостей от этого решения.
- APP-03 (`zwp_input_method_manager_v2` без keymap) подтверждён как
  реальный, не гипотетический блокер для ЛЮБОГО существующего
  OSK-проекта, не только "какого-то одного из них" -- усиливает
  приоритет этого спайка перед APP-04.
- APP-06 (браузер) получает уточнение: GTK3-путь (`webkit2gtk-4.1`)
  стоит проверить параллельно с Qt-путём (`qt6-qtwebengine`), не
  дожидаясь APP-02 (починка GTK4) -- оба варианта не задействуют
  сломанный GTK4 code path.
- Ничего не меняется в текущем боевом образе -- это решение о будущей
  работе, не код и не деплой.
