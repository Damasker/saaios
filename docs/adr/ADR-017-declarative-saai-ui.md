# ADR-017: Декларативный Saai UI вместо ручного рисования экранов

## Статус

Принято, 2026-09-08.

## Контекст

Первый вертикальный срез `saai-shell` доказал работу Wayland, lock surface,
touch и четырёх корневых разделов, но сам интерфейс строится процедурно:
Rust-код вычисляет прямоугольники, вручную заполняет SHM-буфер и отдельно
повторяет те же размеры в hit-testing. Такой подход годится как аппаратная
диагностика, но не как платформа смартфона:

- визуальная структура, ввод и состояние легко расходятся;
- текст, локализация, accessibility и темы требуют специальных веток в коде;
- каждый новый экран увеличивает один системный бинарь и требует его
  пересборки;
- приложения не получают общий UI-контракт;
- проверка на устройстве уже показала неоднозначный результат: все четыре
  вкладки получили touch и изменили состояние, но крайние вкладки визуально
  казались неработающими из-за тестовой двухканальной палитры.

Заимствовать Android XML, QML или HTML как системную модель означало бы
унаследовать чужой lifecycle, API и границы безопасности. SaaiOS нужна своя
маленькая модель, рассчитанная на один touch-экран, объекты системы и
управляемые действия.

## Решение

Ввести **Saai UI** из трёх слоёв:

1. `saai-ui-core` — типизированное дерево представления, layout, hit-testing,
   style tokens и семантические роли. Layout и hit-testing используют один и
   тот же рассчитанный прямоугольник узла.
2. UTF-8 разметка `.sui` — декларативное описание дерева, привязок и действий.
   В ней нет произвольного кода, доступа к файлам или сети.
3. build-time компилятор `saai-ui-compiler`, который проверяет `.sui` и
   превращает её в компактное типизированное представление. На раннем boot
   пути не будет текстового парсера и соответствующей цены в размере/времени.

Минимальный словарь первой версии:

- `screen`, `stack`, `row`, `column`, `spacer`;
- `text`, `icon`, `button`, `tabs`, `list`;
- размеры `fill`, `content`, фиксированный `dp`, padding и safe insets;
- style tokens вместо произвольных цветов в каждом экране;
- `id`, семантическая роль, localization key;
- односторонняя привязка к модели и именованные действия вида
  `select_root(now)`, но не скрипты.

Пример целевой формы (синтаксис фиксируется тестами компилятора до объявления
стабильной версии):

```sui
screen root {
  column {
    content bind=current_root fill
    tabs bind=current_root action=select_root {
      tab now   label="Сейчас"       icon=now
      tab inbox label="Входящие"     icon=inbox
      tab spaces label="Пространства" icon=spaces
      tab me    label="Я"            icon=person
    }
  }
}
```

`saai-shell` владеет системной моделью и преобразует действия UI в команды.
Рендерер сначала остаётся CPU/SHM-клиентом Wayland; DRM и композиция остаются
исключительно в `saai-displayd`. Шрифт Inter из текущего образа подключается
через общий текстовый примитив, а не отдельный код каждого экрана.

Сначала создаётся типизированное промежуточное дерево и на него переносится
корневой экран. Текстовый frontend `.sui` добавляется поверх уже проверенной
семантики. Это не позволяет синтаксису разметки случайно определить неверную
архитектуру runtime.

## Последствия

Положительные:

- один источник истины для layout, отрисовки и touch;
- экран можно проверять snapshot/layout-тестами без телефона;
- системная оболочка и будущие приложения получают общий визуальный язык;
- локализация, темы, масштабирование и accessibility становятся свойствами
  платформы;
- разметка не получает полномочий приложения и не может обойти capability.

Цена:

- появляется собственный формат и компилятор, которые нужно версионировать;
- до стабилизации v1 разрешены несовместимые изменения синтаксиса;
- качественный текст потребует отдельного растеризатора/кэша глифов;
- текущий цветной экран четырёх разделов остаётся только диагностическим
  прототипом и подлежит замене, а не развитию.

## Отклонённые альтернативы

### Продолжать рисовать интерфейс вручную в `saai-shell`

Оставляет layout и hit-testing разными реализациями и не даёт платформы для
приложений. Уже первый экран создал визуально неоднозначное поведение.

### Android XML, QML/Kirigami или HTML/CSS как системный формат

Эти технологии могут поддерживаться для сторонних приложений позднее (S08),
но не становятся внутренним контрактом SaaiOS. Иначе устройство наследует
чужой runtime, lifecycle и модель разрешений раньше, чем сформированы свои.

### Только Rust DSL/макросы

Подходит для прототипа типизированного дерева, но навсегда связывает каждый
экран с компиляцией системного бинаря и не даёт переносимого формата пакета
приложения. Поэтому Rust-представление — внутренний IR, не публичный язык UI.

### JSON/TOML как постоянная разметка

Можно использовать как временный диагностический формат, но они плохо
выражают вложенное визуальное дерево и создают лишний синтаксический шум.
`.sui` остаётся маленьким предметным языком с версионируемой схемой.

## Проверка

- parser-negative tests: неизвестный узел, свойство, действие и schema version
  отвергаются с координатой ошибки;
- layout tests: safe insets, четыре вкладки и разные размеры экрана;
- единый hit-test по рассчитанному дереву, включая крайние пиксели;
- golden render для root/lock screen и шрифтов;
- на Pixel 7 все четыре вкладки имеют текст, отдельный selected state и
  физически различимый результат;
- idle не вызывает перерисовку неизменившегося дерева.
