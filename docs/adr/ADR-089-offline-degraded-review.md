# ADR-089: HIA-19 offline/degraded -- ревизия

## Статус

Принято, 2026-09-15.

## Контекст

`docs/os/sprints/HIA-ROADMAP.md`'s HIA-19: один docs-only проход по
каждому системному сервису (`saai-appd`, `saai-entityd`, `saai-taskd`,
`saai-shell`) с вопросом "что происходит без сети/без AI" --
зафиксировать, что уже верно, и найти реальные пробелы. ADR нужен
только если пробел реально найден -- один найден (см. ниже), поэтому
этот документ существует вместо простой правки `ideas.md`.

Метод: не гипотеза -- для каждого сервиса прочитаны реальные
`Cargo.toml`-зависимости (есть ли вообще сетевой клиент в дереве
зависимостей) и прослежены реальные пути вызова там, где зависимость
нашлась, до места, где ошибка либо гасится, либо всплывает.

## Ревизия по сервисам

### `saai-appd`

Зависимости: `libc`/`nix`/`seccompiler`/`clap`/`serde`/`tokio`/... --
ни одного сетевого клиента в дереве вообще. Установка приложений --
`Store::install(package_root: impl AsRef<Path>)`, берёт локальную
директорию (доставленную через `file-recv`, ADR-069), не удалённый
реестр. Крэши приложений логируются локально (`log_crash_
diagnostic`, ADR-075, пишет в `/data/saaios/var/appd-crashes.log`).
**Без сети/без AI: без эффекта -- этот сервис никогда не трогает ни
то, ни другое.**

### `saai-entityd`

Зависимости: `saai-entity-store`/`chrono`/`clap`/`serde_json`/
`thiserror`/`tokio`/`uuid` -- тоже ни одного сетевого клиента.
Единственный транспорт -- Unix domain socket
(`/run/saaios/entityd.sock`). Хранилище -- файлы на `/data`
(event-sourced, `saai-entity-store`), без какой-либо облачной
синхронизации/бэкапа. **Без сети/без AI: без эффекта.**

### `saai-taskd` -- единственный сервис с реальной сетевой
зависимостью

`runtime_bridge.rs` (ADR-033) открывает `TcpStream::connect(addr)` к
`saaios-runtime` -- НЕ локальному процессу на самом телефоне.
`--runtime-addr`'s собственный doc-comment в `main.rs` называет его
прямо: "a USB-NCM address of whatever host is connected right now".
То есть настоящий ИИ (`saaios-runtime`, Platform Track) физически
живёт не на устройстве, а на подключённом по USB-NCM хосте -- то
есть в реальном автономном использовании (телефон не подключён
кабелем к машине разработки) этот хост попросту не существует.

Хорошая новость: этот путь уже устойчив на уровне демона. Каждый
вызов `runtime_bridge::diagnose`/`confirm` обёрнут в `match` --
любая `BridgeError` (недоступный хост, обрыв, некорректный ответ) не
паникует и не убивает `saai-taskd`, а вызывает `fail_task()`, которая
пишет `status: "failed"` + `error: <сообщение>` на саму `saaios.task`-
сущность и продолжает жить дальше (`process_intent`'s возвращаемый
тип -- `Result<(), ClientError>`, `BridgeError` никогда наружу не
протекает). Это верно и на старте (`reconcile_existing_intents`
вызывает тот же `process_intent`, значит и её `?` никогда не
сработает из-за недоступного `saaios-runtime`), и во время работы.
**`system-intelligence.md`'s собственная формулировка ("планировщик
может быть локальным, удалённым или полностью отключённым") уже
прямо предполагает именно этот сценарий -- отказоустойчивость самого
демона тут была осознанным решением, не случайностью.**

### `saai-shell`

Зависимости: ни одного сетевого клиента (`fontdue`/`nix`/`base64`/
`sha2`/протокольные крейты/`smithay-client-toolkit`). Все три
внутренних подключения (`appd`/`entityd`/`portal`) -- Unix-сокеты.
Wi-Fi/Bluetooth-экраны (S19/S20) уже честно показывают "Не
подключено"/статус поиска, не падают и не виснут без сети. SSH-
пейринг (ADR-074/082-085) -- локальная сеть/USB-NCM, не облако.
Реконнект `entityd`/`appd` уже проверен многократно за время этого
проекта (падение/восстановление сокета не роняет сам `saai-shell`).
**Без сети (кроме одного случая ниже): без эффекта, уже показывает
честные "недоступно"-состояния везде, где это касается пользователя.**

## Найденный реальный пробел

Задача, для которой `saaios-runtime` оказался недоступен, получает
`status: "failed"` -- это ЕДИНСТВЕННЫЙ путь без сети/AI, который
реально ничего не делает "тихо" на уровне демона (см. выше). Но
`saai-shell`'s `inbox_pending_tasks()` фильтрует строго по
`status == "waiting_confirmation"` -- `"failed"` никогда не попадает
в список "Входящие". Полный текстовый поиск по `main.rs` не находит
НИ ОДНОГО места, которое читает `"failed"`/`WorkflowStatus::Failed`
вообще. `fail_task()` также не создаёт `saaios.notification`.

Итог: пользователь набирает свободный текст в "Новое намерение",
жмёт отправить -- `saai-shell` просто закрывает поле ввода
(`println!` в консоль, которую пользователь не видит) без какого-
либо подтверждения успеха. Если `saaios-runtime` недоступен (обычное
состояние для нететерированного телефона сегодня), намерение исчезает
насовсем и без следа -- задача физически существует в сторе со
`status: "failed"` и осмысленным `error`, но НИГДЕ не отображается.
Ни ошибки, ни объяснения, ни способа узнать, что что-то пошло не так,
кроме прямого чтения `/data/saaios/var/entities/...` по SSH.

## Решение

Найден и в тот же день исправлен (пользователь выбрал чинить сейчас,
а не оставлять открытым пунктом). `fail_task()` и
`fail_confirmed_action()` (второй, отдельный путь отказа -- уже
подтверждённое действие само не выполнилось при исполнении, не при
диагностике) теперь оба вызывают новый `notify_task_failed(title,
message)`, создающий `saaios.notification` (`body` = само сообщение
об ошибке, `kind: "task_failed"`) -- та же инфраструктура, что уже
показывает уведомления в "Входящие" и открывает их через HIA-07's
Object View (ADR-088), без единого нового экрана. Новая константа
`NOTIFICATION_TYPE` в `model.rs`, тот же `"saaios.notification"`, что
`saai-shell`'s собственная (не общая, отдельно объявленная в каждом
бинаре -- тот же паттерн, что уже был у `TASK_TYPE`/`ACTION_TYPE`).

Намеренно best-effort: `notify_task_failed` не пробрасывает свою
ошибку наружу (`self.conn.create_entity(...).await` без `?`,
только `eprintln!` при неудаче) -- сбой создания САМОГО уведомления
не должен превращать уже сделанную (и более важную) запись `status:
"failed"` в падение демона уровнем выше (`process_intent`'s вызывающий
код на старте может`std::process::exit(1)` при пробросе ошибки).

Не исправлено этим шагом (отдельный, более крупный вопрос): сам
`saai-shell` по-прежнему нигде не знает, доступен ли `saaios-runtime`
ВООБЩЕ, до отправки намерения -- нет статус-индикатора вроде "AI
недоступен" на экране ввода. Остаётся в `docs/os/ideas.md`.

## Test

`saai-taskd`'s `Daemon`-методы (`fail_task`/`fail_confirmed_action`
и всё, что их вызывает) не покрыты host-юнит-тестами в принципе --
`lib.rs` не имеет `mod tests` вообще, только `model::`/`client::`/
`runtime_bridge::` тестируют чистую логику и wire-уровень по
отдельности (тот же баланс "чистая логика тестируется исчерпывающе,
интеграция проверяется физически", что уже был у ADR-033). Проверено
физически: реальный `saai-entityd` и `saai-taskd` запущены локально
на build-сервере (scratch `--store-root`/`--socket`, не устройство),
`--runtime-addr 127.0.0.1:1` (гарантированно отказывает в
соединении), создан настоящий `saaios.intent` напрямую по протоколу
`saai-entityd`. Результат подтверждён чтением записанных на диск
сущностей: `saaios.task` со `status: "failed"` и реальным
`error`-сообщением, плюс новый `saaios.notification` с тем же
сообщением в `body` и `kind: "task_failed"` -- ровно то, что теперь
покажет "Входящие"/Object View на реальном устройстве, без единого
изменения на стороне `saai-shell` (её код для показа уведомлений уже
был готов, HIA-07). `cargo test -p saai-taskd`: 44/44 без
регрессий. `cargo clippy -p saai-taskd --all-targets` чист.

## Последствия

- `docs/os/ideas.md`: пункт про исчезающие задачи закрыт; пункт про
  отсутствующий индикатор доступности AI на экране ввода остаётся
  открытым.
- `saai-taskd` по-прежнему не подключён к `native-init.c`'s boot-
  последовательности (см. `lib.rs`'s собственный doc-comment) -- этот
  фикс никак это не меняет, физическая проверка на реальном
  устройстве той же формы, что ADR-033, этим ADR не проводилась.
