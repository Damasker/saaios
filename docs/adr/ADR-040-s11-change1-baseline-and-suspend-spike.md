# ADR-040: S11 Change 1 -- baseline latency/memory numbers and mem-suspend feasibility, physically measured

## Статус

Принято, 2026-09-11.

## Контекст

S11's Definition of Ready called Change 1 обязательным первым спайком:
реальные числа для daily-use путей (ни один из S01-S10 не имел
зафиксированного бюджета) и физическая проверка, безопасен ли
`mem`-suspend на этом никогда не усыплявшемся ранее ядре/железе, --
без обоих любой budget/idle-Acceptance в этом спринте был бы
предположением, не измерением.

## Замеры

Тот же реальный Pixel 7. Три независимых холодных `reboot -f`,
`dmesg`'s собственные kernel-timestamp'ы (не оценка по стенным часам):

**Холодная загрузка (PID1 -> "native userspace ready"):** 7.078с /
7.094с / 7.104с -- разброс 26мс, среднее ~7.09с. `saai-displayd`
("UI slot started") стартует значительно раньше, на ~3.43с -- разница
между этим и итоговым 7.09с приходится на Wi-Fi/Bluetooth/USB
gadget/`saaios-runtime`-запуск, не на сам UI-путь; отдельного
timestamp'а на "первый кадр экрана" сегодня нет -- `saai-displayd`/
`saai-shell` не пишут в `boot.log`, только PID 1 пишет. Не
инструментировано в этом Change (не входило -- "без нового кода").

**Запуск приложения (`org.saaios.demo-surface`, ADR-013/ADR-027):**
IPC circuit `appd.launch` (запрос -> `{"result":"launched",...}` ответ,
замерено секундомером хоста поверх serial, не оценка): 50мс / 47мс /
43мс. Это **latency спавна процесса**, не визуальной готовности --
честно помечено отдельно, полная touch-to-photon задержка потребовала
бы камеры или нового кода, вне этого Change.

**Planner-цикл Intent -> Result:** переиспользованы уже физически
снятые в этой же сессии замеры (ADR-034, ADR-037, ADR-039) --
31с (S10 Change 2's первый реальный тест), 10.9с / 5.3с / 4.1с (S10's
memory-тесты). Заметный разброс -- реальная задержка ответа локальной
модели (`qwen2.5:3b-instruct` на подключённом хосте), не свойство
самого механизма; повторный отдельный замер не проводился как
избыточный (те же условия, тот же мост, ничего не изменилось с S10).

**Память сразу после холодной загрузки** (только системные сервисы,
без прикладной нагрузки): 258 708 KB used из 7 619 724 KB total.

## `mem`-suspend: физически подтверждён рабочим, с важной оговоркой

`echo mem > /sys/power/state`, с явного согласия пользователя перед
первой попыткой (риск -- устройство могло не проснуться, потребовав
физического вмешательства). Результат по `dmesg`'s собственным
timestamp'ам:

- `[263.970] PM: suspend entry (deep)` -> `[264.436] PM: suspend exit`
  -- полный, чистый цикл, ~465мс.
- Резюмировано через ~227мс (`[264.197]`) --
  `pm_system_irq_wakeup: 403 triggered dhdpcie_host_wake` -- разбудил
  **сам Wi-Fi-чип** (`bcmdhd4389`) через собственный host-wake IRQ, не
  serial-пробник хоста (тот пришёл заметно позже и получил мгновенный,
  нормальный ответ -- система была уже полностью проснувшейся к этому
  моменту).
- Один некритичный kernel `WARNING` при входе (`pci_pm_suspend`:
  "PCI PM: State of device not saved by dhdpcie_pm_suspend") -- known
  rough edge Wi-Fi-драйвера при suspend, не паника, не Oops, система
  продолжила работать штатно.
- **USB-NCM и serial пережили полный цикл без единого ручного
  вмешательства** -- следующая serial-команда сразу после ответила
  корректно, `saaios-runtime` остался слушать `172.31.7.1:38127`. Это
  был главный риск, ради которого спайк требовал отдельного согласия
  -- снят полностью.
- Все пять native-сервисов (`entityd`/`appd`/`displayd`/`shell`/
  `saaios-runtime`) физически подтверждены живыми и работоспособными
  после цикла, память не просела (251 520 KB used -- в пределах
  нормального разброса от 258 708 KB до цикла).

**Оговорка, решающая для Change 2**: пока `wlan0` активен, устройство
самопробуждается почти немедленно после входа в `mem` -- держать
реальный длительный простой в `mem` невозможно без предварительного
"усыпления" или отключения Wi-Fi-чипа перед входом (или явного
принятия, что Wi-Fi временно недоступен в глубоком простое).

## Решение

Change 1 закрыт: реальные бюджеты latency/памяти для холодной загрузки,
запуска приложения и planner-цикла зафиксированы (см. выше, не
предположения). `mem`-suspend физически безопасен на этом
железе/ядре в узком, уже проверенном смысле (полный цикл, ноль потери
USB/serial/сервисов) -- но требует явной обработки Wi-Fi-состояния
перед входом, чтобы реально держать простой, а не мгновенно
возвращаться. Change 2 должен строиться вокруг этого: усыпление/
отключение Wi-Fi перед `mem`, а не голый `echo mem` из
`saai-shell`'s idle-проверки.

## Последствия

- Change 2's дизайн сужен конкретной находкой: нужен явный шаг
  "прежде чем спать -- увести Wi-Fi в состояние, не поднимающее
  host-wake", иначе Change 2's Acceptance ("реальное снижение
  энергопотребления в простое") не выполнится -- устройство будет
  бесконечно засыпать/просыпаться, а не реально экономить.
- `pci_pm_suspend`'s WARNING по `bcmdhd4389` -- известный, не
  блокирующий рабочий цикл драйверный шум; не исправляется в этом
  Change, отмечен как есть.
- Touch-to-photon латентность (полная визуальная готовность, не только
  IPC-спавн) остаётся неинструментированной -- явный, не
  предрешаемый здесь пробел для будущей работы, если понадобится.
