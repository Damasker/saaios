# ADR-009: Supervision и DRM-master handoff для UI-процесса на panther

## Статус

Принято, 2026-09-07.

## Контекст

S03's Current state (см. `docs/os/sprints/S03-panther-displayd.md`)
зафиксировал факт: `native-init.c` `start_display_splash()` (строка 1140)
делает ровно один `fork()+execl()` для `drm-splash`, не возвращает pid,
нигде не сохраняет его. Финальный reaper-цикл `main()` (строки 1424-1432)
знает только про `console_pid` — любой другой процесс, включая
`drm-splash`, молча пожирается `waitpid(-1, ...)` без последствий. Упавший
`drm-splash` не перезапускается — экран остаётся мёртвым до следующей
холодной перезагрузки.

S03's Scope требует двух вещей одновременно: (а) механизм restart/fallback
для UI-процесса, которого сегодня вообще нет, и (б) протокол передачи
DRM-master между `drm-splash` и будущим `saai-displayd`, поскольку оба
хотят открыть и стать master `/dev/dri/card0`. Это решение закрывает оба
вопроса — они оказались сильно проще вместе, чем порознь (см. ниже).

## Решение

### DRM-master: явный протокол handoff не нужен

`/dev/dri/card0` open + master — эксклюзивный ресурс на уровне ядра;
master автоматически освобождается, когда закрывается последний fd
держателя, что гарантированно происходит при выходе процесса (SIGKILL
включительно — ядро закрывает все fd при `exit`/реапинге, отдельного
cleanup-кода не требуется).

Если `native-init.c` гарантирует **последовательное**, а не параллельное
владение UI-слотом — то есть новый процесс стартует только после того,
как `waitpid()` реально забрал предыдущий (не просто "процесс мёртв", а
"уже реапнут родителем") — то новый процесс всегда открывает
`/dev/dri/card0` в момент, когда никто им не владеет, и автоматически
становится master без какой-либо координации между `drm-splash` и
`saai-displayd`. Явный сигнал "отдай master" не нужен вообще.

Следствие: **никогда не может быть двух одновременно запущенных
UI-процессов** — ни во время обычной работы, ни во время restart. Это
architecture-level инвариант, а не деталь реализации.

### Supervision: единый ui_slot с бюджетом перезапусков и fallback-бинарём

Обобщение существующего паттерна `console_pid` на UI-слот:

```c
struct ui_slot {
    const char *primary_path;   /* "/saaios/drm-splash" сегодня;
                                    "/saaios/saai-displayd" начиная с
                                    более позднего шага S03 */
    const char *fallback_path;  /* "/saaios/drm-splash" — всегда */
    pid_t pid;
    int restart_count;
    time_t window_start;
    int using_fallback;
};
```

- Restart-бюджет: не более N перезапусков (N=5, как рабочая цифра — точная
  величина фиксируется физическим тестом на шаге 6, не заранее) в
  скользящем окне T (T=60s). Мгновенный crash-loop (десятки рестартов в
  секунду) исчерпывает бюджет за секунды, не подвешивая систему.
- Как только бюджет primary исчерпан: `using_fallback = 1`, дальнейшие
  падения перезапускают `fallback_path` тем же механизмом (с отдельным,
  более щедрым или вообще неограниченным бюджетом — `drm-splash` уже
  физически проверен как стабильный fallback, ограничивать его бюджет
  нет причины). Возврат к primary происходит только через холодную
  перезагрузку — не пытаемся угадывать "может, теперь заработает" в
  рамках одной загрузки.
- Пока primary == fallback == `drm-splash` (текущий шаг, до появления
  `saai-displayd` в этом слоте), это вырождается в простой bounded
  self-restart — наблюдаемое поведение шага 3 из Change: несколько раз
  подряд убить `drm-splash`, проверить, что он поднимается снова, без
  утечки DRM master (проверяется тем, что новый процесс успешно
  становится master — если бы предыдущий его не отпустил, `SETCRTC`/
  аналог упал бы с `EBUSY`/`EACCES`).

### Readiness как отдельный сигнал от "процесс существует"

UI-бинарь обязан напечатать одну конкретную строку-маркер в свой
stdout (уже перенаправляемый в `/run/<binary>.log`) в течение
bounded-окна после старта (`READY_TIMEOUT`, рабочая цифра 5s). Пока
маркер не увиден — падение или timeout считаются одним и тем же
событием "не смог стартовать" для бюджета перезапусков; после — обычное
"упал во время работы", тот же бюджет, но факт "хотя бы раз стартовал"
можно логировать отдельно для диагностики.

Это **не** трогает `start_hardware_watchdog()` — hardware watchdog
остаётся полностью decoupled (per Current state), продолжает кормиться
независимо от того, готов UI или нет. Readiness здесь — вход только для
supervision-логики UI-слота, не для аппаратного watchdog.

Маркер для `saai-displayd` уже существует по факту (S02): строка
`saai-displayd: listening on WAYLAND_DISPLAY=...` в stdout. Для
`drm-splash` эквивалентного маркера может не быть — если нет, шаг 3
добавляет одну строку в `drm-splash.c` при первом успешном modeset,
либо supervision временно считает "процесс пережил READY_TIMEOUT без
падения" достаточным критерием готовности именно для этого бинаря (не
блокирует шаг 3, уточняется по факту чтения кода при реализации).

## Последствия

Положительные:

- ноль изменений в `start_hardware_watchdog()`/GSA-коде — полностью
  ортогонально;
- один и тот же supervision-код обслуживает и текущий `drm-splash`-only
  случай, и будущий `saai-displayd`-primary случай — шаг 3 (изолированный
  тест на `drm-splash`) и шаг 6 (реальное подключение `saai-displayd`)
  используют одну и ту же машинерию, не два разных;
- отсутствие explicit handoff протокола убирает целый класс багов
  (рассинхронизация "кто сейчас должен быть master") ценой одного
  структурного инварианта (строго последовательный `waitpid` перед
  следующим `fork`), который легко проверить и легко сломать по ошибке —
  поэтому явно зафиксирован здесь как инвариант, не как деталь.

Цена решения:

- любой будущий сценарий "два UI-поверхности одновременно" (например,
  overlay поверх основного UI) потребует пересмотра этого ADR — сейчас
  сознательно вне scope (per README's "лизинг/secondary display... не
  проектировать заранее, пока нет причины трогать DRM напрямую" — тот же
  принцип, применённый и здесь);
- restart-бюджет — эвристика с рабочими цифрами (N=5, T=60s,
  READY_TIMEOUT=5s), не выведенными аналитически; уточняются физическим
  тестом на шаге 6, значения в этом ADR — отправная точка, не финал.

## Отклонённые альтернативы

### Явный сигнал "отдай master" между процессами (сокет/сигнал)

Технически рабочий вариант (то, что предполагалось изначальной
формулировкой Scope S03: "как второй процесс узнаёт, что можно/нужно
брать master"), но добавляет протокол и состояние ради того, что и так
гарантируется последовательным `waitpid`-перед-`fork` — лишняя
поверхность для багов без функционального выигрыша при текущем
"один UI-процесс за раз" инварианте.

### Одновременная работа drm-splash и saai-displayd (lease/secondary output)

Требует DRM lease API или multi-plane координацию, которую README
`os/targets/panther/` сам называет "survey what's available only once
Phase 3 [сейчас S03] reached, do not design this yet" — преждевременно
без конкретной продуктовой причины показывать оба UI одновременно.
