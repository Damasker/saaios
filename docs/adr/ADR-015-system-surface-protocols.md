# ADR-015: Протоколы для системных поверхностей `saai-shell`

## Статус

Принято, 2026-09-08.

## Контекст

`application-platform.md` требует для `saai-shell`: "системные слои,
lock surface и безопасное перекрытие приложений" — но не называет
конкретный протокол. Инвариант безопасности из того же документа:
"системный запрос разрешения нельзя подделать обычной поверхностью" —
значит выбор протокола должен давать это гарантированно, не по
соглашению между приложениями.

Прочитан код `smithay` 0.7.0 (не только описание протоколов):

- `smithay::wayland::session_lock` — реализация `ext-session-lock-v1`
  (стандартный, специально для lock screen'ов протокол из
  wayland-protocols' ext-серии). `SessionLockManagerState::new::<D, F>(
  &display, filter: F)`, где `filter: Fn(&Client) -> bool` — global
  создаётся с фильтром клиентов на уровне протокола, не полагаясь на
  доверие приложения. Обычная поверхность физически не может стать
  lock-поверхностью — `ExtSessionLockV1`/`LockSurface` — отдельные
  протокольные объекты, не `wl_surface` с ролью по соглашению.
- `smithay::wayland::shell::wlr_layer` — реализация `wlr-layer-shell`
  (де-факто стандарт для панелей/status bar/notification overlay в
  Wayland-экосистеме — Sway, Hyprland, Phosh и другие используют его
  именно для этого класса поверхностей, не для lock screen'ов).
  `WlrLayerShellState::new_with_filter::<D, F>(&display, filter: F)` —
  та же модель фильтрации по клиенту.
- Обе реализации уже входят в `smithay` без отдельной cargo-фичи (тянутся
  вместе с `wayland_frontend`, транзитивная зависимость
  `wayland-protocols-wlr` в Cargo.lock уже присутствует с S02/S03, просто
  не использовалась) — **нулевая новая C-зависимость, нулевая новая
  кросс-компиляция**.
- Оба `filter`-замыкания получают `&Client`; идентификация клиента —
  `client.get_credentials(&display_handle) -> Result<Credentials,
  InvalidId>` (`wayland-server` 0.31.14), возвращает PID/UID/GID через
  `SO_PEERCRED` сокета. UID/GID бесполезны для фильтрации на этой
  системе — всё работает от root (ADR-010's предпосылка), но **PID
  полезен**: `saai-displayd` сам форкает `saai-shell` (ADR-014) и знает
  его точный pid ещё до того, как тот вообще подключился к сокету.

## Решение

Два протокола, каждый для своей задачи, не один "универсальный":

- **`ext-session-lock-v1`** — для lock screen. Единственный протокол,
  дающий именно ту гарантию, которая нужна ("нельзя подделать") —
  секьюрити-модель встроена в сам протокол (explicit lock/unlock цикл,
  `SessionLocker`-подтверждение после отрисовки чёрного кадра на всех
  выходах), а не выведена из соглашения "эта поверхность выглядит как
  lock screen".
- **`wlr-layer-shell`** — для остальных системных поверхностей (статус-
  бар, навигационный оверлей, системные панели/overlay из scope этого
  спринта). Даёт anchor/exclusive-zone/layer (background/bottom/top/
  overlay) семантику, которая реально нужна для этого класса
  поверхностей и не пытается быть чем-то другим.

Оба global'а регистрируются в `saai-displayd` с `filter`, замкнутым на
PID процесса, который `saai-displayd` сам породил как `saai-shell`
(ADR-014). Любой другой клиент, даже подключившийся к тому же
Wayland-сокету, не видит эти globals вообще — не "видит, но получает
отказ", а протокольно не может их забиндить (`GlobalDispatch` фильтр
работает на уровне advertisement).

Обычные приложения (будущие, S05+) продолжают видеть только
`xdg_wm_base`/`xdg_toplevel`/`xdg_popup` — им обоих новых globals не
видно вообще, не только не нужно.

## Последствия

Положительные:

- гарантия "нельзя подделать" — протокольная, не по соглашению;
  выполняет инвариант application-platform.md буквально;
- нулевая новая C-зависимость/кросс-компиляция — обе реализации уже в
  зависимостях `smithay`, просто не delegated;
- `wlr-layer-shell` — не изобретаемый велосипед: тот же протокол,
  которым уже пользуются другие мобильные/desktop Wayland-компоновщики
  для того же класса поверхностей, будущая совместимость с
  инструментами отладки/анализа Wayland-трафика (`wev`, `wayland-utils`)
  бесплатна.

Цена решения:

- два протокола вместо одного — больше кода в `saai-displayd`
  (`SessionLockHandler` + `WlrLayerShellHandler`, два `delegate_*!`), но
  оправдано: `wlr-layer-shell` физически не даёт lock-специфичных
  гарантий (например, нет "no input passthrough" на уровне протокола,
  это даёт `ext-session-lock-v1`'s explicit lock-cycle), использовать
  его одного для lock screen'а означало бы reimplементировать
  секьюрити-инвариант поверх протокола, для этого не спроектированного;
- PID-based фильтрация ломается, если `saai-shell` когда-нибудь
  перезапускается ВНЕ модели ADR-014 (например, если решение о владении
  процессом позже изменится) — фильтр должен обновляться вместе с
  текущим известным pid при каждом рестарте (уже естественно то же
  место кода, что и сам `fork`/`waitpid` в ADR-014's supervision-цикле,
  не отдельная синхронизация).

## Отклонённые альтернативы

### Только `wlr-layer-shell`, lock screen — просто top/overlay layer surface

Технически рисует то же самое, но не даёт протокольной гарантии
эксклюзивности ввода при блокировке — пришлось бы вручную реализовывать
"не пропускать touch/keyboard нижним поверхностям, пока показан
конкретный layer surface" внутри `saai-displayd`'s собственной input-
маршрутизации, дублируя то, что `ext-session-lock-v1` уже даёт как часть
протокольного контракта. Больше своего кода ради худшей гарантии.

### Собственный минимальный протокол для обоих случаев

Отклонено по той же причине, что и везде в этом проекте, где
рассматривалась "своя реализация против стандартного протокола/
библиотеки" (ADR-007's сравнение Smithay/сырой wayland-server) — здесь
особенно: `ext-session-lock-v1` уже прошёл ревью сообщества именно на
security-свойства, которые нужны, переизобретать его — необоснованный
риск для самого чувствительного места платформы (lock screen).
