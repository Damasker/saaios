# ADR-098: per-app приватный session D-Bus в saai-appd, закрывает APP-05, ADR-097

## Статус

Принято, 2026-09-17. Физически проверено на реальном Pixel 7.

## Контекст

ADR-097 нашёл точный блокер для PCManFM-Qt: без session D-Bus оно тихо
завершается (exit 0, без диагностики) до создания окна, потому что
интерпретирует отсутствие шины как "уже запущен другой экземпляр".
SaaiOS не имел ни одного D-Bus daemon вообще. ADR-097 сознательно не
решал, заводить ли общую шину -- общая шина потенциально открывает
inter-app-канал связи, не покрытый существующей моделью capability, ей
из `services/saai-appd/src/lib.rs`.

## Решение

Не общая шина -- **отдельный `dbus-daemon` процесс на каждое
приложение**, запускаемый и останавливаемый самим `saai-appd`
(`services/saai-appd/src/supervisor.rs`, не внутри песочницы
приложения). Ни один другой процесс никогда не подключается к чужому
сокету -- значит это не новый inter-app-канал, а просто способ
удовлетворить тулкиты, которым для проверки "не запущен ли уже другой
экземпляр" аппаратно нужен D-Bus. Новая capability не понадобилась.

Реализация:
- `SandboxPaths::dbus_socket: PathBuf` (`sandbox.rs`) -- раскрывается в
  песочницу приложения тем же способом, что `wayland_socket`/
  `portal_socket` (bind-mount в `/run`), но guarded по существованию
  файла (та же конвенция, что `reveal_fonts`) -- сборка без
  задеплоенного `dbus-daemon` (host-тесты, образ без него) просто не
  раскрывает ничего, приложение падает тем же образом, что и раньше,
  без нового режима отказа.
- `AppRuntime::dbus_daemon: Option<Child>` (`supervisor.rs`) --
  сознательно НЕ в общем `children: Vec<Child>`: та структура завязана
  на crash-restart/`pids()`/`single_instance`-логику самого приложения,
  подмешивание туда демона сломало бы подсчёт крашей и светило бы его
  pid наружу через `list`.
- `AppSupervisor::ensure_dbus_daemon()` -- по одному вызову на
  `launch()` и на каждый crash-restart в `poll()`: переиспользует живой
  daemon, иначе стартует `dbus-daemon --nofork --config-file=... 
  --address=unix:path=/run/saaios/dbus/<app_id>.sock`, ждёт появления
  файла сокета (bounded poll, 500ms потолок, реально появляется на
  порядки быстрее). Толерантно: если бинарник не задеплоен по
  `dbus_binary_dir` (по умолчанию `/data/saaios/system/dbus`),
  возвращает путь сокета без демона за ним -- то же поведение, что было
  до этого ADR.
- `stop()`/`Drop` останавливают демон и удаляют файл сокета вместе с
  остановкой самого приложения.
- `DBUS_SESSION_BUS_ADDRESS` выставляется в окружении процесса
  приложения безусловно (как `QT_QPA_PLATFORM` и т.п.) -- toolkit,
  которому это не нужно, просто это игнорирует.

Артефакт `dbus-daemon` -- тот же источник и модель доверия, что
Kirigami/PCManFM-Qt (Alpine aarch64 v3.20, `os/targets/panther/
build-session-dbus.sh`, ADR-021/095), НЕ приложение -- системный
компонент, деплоится один раз в `/data/saaios/system/dbus`, не через
`saai-appd`'s store/manifest.

Единственная реальная новая находка при сведении в физический тест:
Alpine's `dbus-daemon` динамически слинкован с жёстко зашитым
`/lib/ld-musl-aarch64.so.1` (`PT_INTERP`) -- в отличие от приложения
(`sandbox.rs` монтирует его собственный `lib/` на `/lib` внутри ЕГО
mount namespace), этот демон работает прямо на реальном корне
устройства, где `/lib` никогда не содержит загрузчика вообще (весь
first-party код здесь статический именно поэтому). Решено `patchelf
--set-interpreter`/`--set-rpath` на путь, где этот компонент реально
лежит (`/data/saaios/system/dbus/lib/...`) -- воспроизводимо встроено в
`build-session-dbus.sh`, не осталось ручным шагом. Без этого каждый
запуск падал с "No such file or directory" при exec(), ещё до какой-либо
D-Bus-специфичной ошибки.

## Проверка

`services/saai-appd`'s полный тестовый набор (34 unit + 2 integration)
проходит без изменений -- новая логика толерантна к отсутствующему
бинарнику, host-тесты его не имеют.

Полный физический цикл на боевом устройстве, БЕЗ единого ручного
обхода песочницы (в отличие от ADR-097's спайка):
- Собранный `saai-appd` (с этими изменениями) hot-swap'нут на живом
  устройстве (`mv` поверх работающего бинарника, `kill`, native-init
  автоматически перезапустил тот же pid-слот новым бинарником --
  подтверждено по `sha256sum` и по новому pid).
- `install` -> `launch` `org.saaios.demo.pcmanfm`: `saai-displayd.log`
  показывает `client connected`, `new xdg_toplevel`, `focus set`,
  несколько реальных commit'ов с одинаковым content-hash -- то же, что
  ADR-097's ручной спайк, но теперь через настоящий `saai-appd launch`,
  без какого-либо `dbus-daemon`, запущенного мной вручную. `ps aux`
  подтвердил: PCManFM-Qt и его собственный приватный `dbus-daemon`
  оба живы, каждый со своим pid.
- `list` показывает `state: "running"`, `pids: [<pcmanfm-pid>]` --
  pid демона корректно НЕ просочился в этот список.
- `stop`: оба процесса (приложение и его demon) исчезли, файл сокета
  `/run/saaios/dbus/org.saaios.demo.pcmanfm.sock` удалён.
- `remove`: пакет снова отсутствует в `list`. Тестовый пакет и все
  временные файлы передачи удалены с устройства после проверки (тот же
  принцип, что ADR-027/097).

## Последствия

- APP-05 (файловый менеджер) закрыт: PCManFM-Qt устанавливается,
  запускается и рендерится через обычный `saai-appd launch`, без
  какого-либо ручного вмешательства. `docs/os/sprints/
  APP-COMPAT-ROADMAP.md` обновлён.
- Любое будущее приложение, которому нужен D-Bus по той же причине
  (single-instance, GVolumeMonitor и т.п. -- APP-06 и, вероятно, почти
  любой сложный сторонний Linux-порт), автоматически получает эту же
  инфраструктуру бесплатно -- ничего специфичного для PCManFM-Qt в
  реализации нет.
- Модель безопасности не расширена: ни одна новая capability не
  добавлена, ни один новый inter-app-канал не появился -- каждая шина
  приватна одному приложению и его собственному демону.
- Известное ограничение, не решённое здесь: если демон приложения
  падает САМ (не приложение), пока приложение продолжает работать,
  `poll()` этого не замечает и не перезапускает демон -- D-Bus для этого
  запуска молча перестаёт работать до следующего полного `stop`/
  `launch`. Не наблюдалось физически, но не проверялось намеренным
  killом демона в процессе теста -- честно зафиксировано как
  ограничение первой версии, не как проверенное поведение.
