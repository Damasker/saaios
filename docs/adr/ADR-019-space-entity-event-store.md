# ADR-019: Пространства, сущности и журнал событий

## Статус

Принято, 2026-09-09.

## Контекст

S04 показывает четыре имени контекста, но прежняя реализация сохраняет только
числовой индекс в `/data/saaios/var/ui/active-space`. Карточки оболочки не
являются данными: после переключения пространства сервисы пока продолжают
видеть один общий набор объектов. S06 должен ввести постоянную схему без
переноса базы данных в `saai-shell` и без обещания sandbox до S07.

Запись должна переживать потерю питания между системными вызовами. Обычный
JSONL с дописыванием может оставить оборванную последнюю строку, а обновление
журнала и отдельного снимка невозможно сделать одним файловым `rename`.

## Решение

Единственным писателем становится будущий `saai-entityd`. Библиотека
`saai-entity-store` задаёт versioned-модели `Space`, `Entity` и `Event`, а
daemon позже предоставляет IPC оболочке и приложениям.

### Идентичность и границы

- встроенные space id: `home`, `work`, `personal`, `saaios`;
- пользовательский space id — нормализованный lowercase slug, не путь;
- entity id и event id — UUID;
- каждая entity всегда содержит ровно один `space_id`; запрос списка всегда
  требует явный `space_id`;
- тип entity — lowercase dotted token; title и JSON-object properties имеют
  ограничения длины и общего сериализованного размера;
- неизвестная schema и неизвестные поля отвергаются.

### Layout v1

```text
/data/saaios/var/entities/
  schema-version
  selection.json
  spaces/<space_id>/
    space.json
    events/<sequence>-<event_id>.json
    entities/<entity_id>.json
```

Event-файлы неизменяемы и публикуются через temporary file, `fsync`, atomic
`rename` и `fsync` родительского каталога. Последовательность монотонна внутри
одного пространства. Журнал является источником истины; entity-файлы — только
проекция для чтения.

Изменение сначала публикует событие, затем атомарно заменяет проекцию. Если
процесс или питание пропали между шагами, открытие store повторно проигрывает
валидные события и достраивает проекции. Temporary-файлы не считаются
событиями. Повреждённый уже опубликованный event не игнорируется молча: space
переходит в read-only error до восстановления из backup.

Удаление — tombstone event, а не стирание истории. Межпространственное
перемещение в S06 не является неявным update: это отдельная явная операция с
событием происхождения; первая вертикаль его не реализует.

### Bootstrap и миграция

Первый запуск идемпотентно создаёт четыре встроенных пространства. Legacy
индекс `0..3` отображается в `home/work/personal/saaios` и атомарно записывается
в `selection.json`. Некорректное или отсутствующее значение даёт `home`.
Legacy-файл остаётся без изменений как rollback-вход до физической приёмки.

## Последствия

Положительные:

- space является настоящей серверной границей выборки;
- незавершённая запись восстанавливается из неизменяемого журнала;
- UI можно перезапустить или заменить без потери данных;
- schema допускает будущие capability checks и синхронизацию без смены id.

Ограничения S06:

- файловая изоляция процессов, grants, шифрование per-space и portals входят в
  S07; пока entity service принимает только доверенных системных клиентов;
- event log не является telemetry и не покидает устройство;
- compaction, cloud sync и multi-device conflict resolution не входят в v1.

## Отклонённые альтернативы

### Хранить всё в состоянии shell

Связывает пользовательские данные с жизненным циклом UI и позволяет обходить
будущую policy boundary.

### Один изменяемый JSON-файл

Прост, но не даёт журнал происхождения и сложнее надёжно восстанавливает
операцию, оборванную между связанными изменениями.

### SQLite в init_boot

Это зрелый вариант на будущее, но сейчас добавляет библиотеку и размер до
проверки модели. Filesystem log достаточен для ограниченной первой вертикали;
wire/schema остаются пригодны для замены backend отдельным ADR.
