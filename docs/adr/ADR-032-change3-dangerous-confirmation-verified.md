# ADR-032: S09 Change 3 -- dangerous Action confirmation physically verified across a real cold reboot

## Статус

Принято, 2026-09-11.

## Контекст

S09's Threat/privacy impact section (established at Definition of Ready)
требовало: опасный `Action` обязан требовать явного, вновь запрошенного
подтверждения при каждом возобновлении после cold reboot, не
кэшированного "да" из предыдущей сессии. Change 2 (ADR-031) построило
только неопасный путь (`echo`, выполняется немедленно). Change 3 -- первый
опасный `Action` (`delete_entity`), пауза на подтверждение, и физическое
доказательство, что пауза переживает настоящую холодную перезагрузку, а
не только рестарт демона.

## Реализация

**Модель (`saai-taskd/src/model.rs`)**: `DELETE_ENTITY_ACTION_KIND` --
удаление другой сущности в том же пространстве. Классификатор
`dangerous_action_of(intent)` явно требует
`properties.action_kind == "delete_entity"` и валидный
`properties.target_entity_id` -- обычный текст с клавиатуры (только
`text`) никогда не попадает на этот путь; парсинг "удали X" из
свободного текста -- задача S10's planner, не эта. Новые переходы в
`valid_transition()`: `Pending->WaitingConfirmation`,
`WaitingConfirmation->Running` (подтверждено), `WaitingConfirmation->
Cancelled` (отклонено) -- явно НЕТ `WaitingConfirmation->Done` напрямую
и нет пути, зависящего от reboot/restart, к `Running` -- возобновление
входит в ту же самую внешнюю-подтверждение развилку, что и обычный
живой тап.

**Демон (`saai-taskd/src/lib.rs`)**: опасный intent создаёт Task+Action
сразу в `WaitingConfirmation` и останавливается -- `process_dangerous_
intent()` ничего не исполняет. Обратная реакция построена без
трекинга "было ли" в памяти процесса: любое событие о `saaios.task` с
текущим `status=="running"` вызывает `try_resume_confirmed_task()`,
которая смотрит на ТЕКУЩИЙ статус связанного `Action` -- исполняет
только если он ещё `WaitingConfirmation` (для уже исполненного --
идемпотентный no-op). То же для `status=="cancelled"` ->
`try_cancel_pending_action()`, помечающая Action `Cancelled`, если он
ещё не выполнен -- без этого audit trail оставлял Action зависшим в
`waiting_confirmation` навсегда после отклонения (найдено и исправлено
в процессе физической проверки, до коммита). `reconcile_confirmed_
tasks()` при старте демона catch-up'ит оба случая (Running и Cancelled)
-- и НИЧЕГО не делает для `WaitingConfirmation`: это единственное,
что имеет значение для S09's Threat/privacy impact требования.

**UI (`saai-shell`)**: `Frame::TaskConfirm`, `task_confirm_view()`/
`task_confirm_action_at()` -- та же `Node`/`layout()`/`hit_test()`
система и геометрия, что `consent_view()`. `pending_task_confirmation()`
читает `self.selected_entities` напрямую (уже актуализируется через
`saai-entityd`'s `Subscribe`) -- никакого собственного состояния
клиента, поэтому после cold reboot экран подтверждения появляется
ровно из того, что реально лежит в сторе, без кэша. `confirm_pending_
task()` пишет ПОЛНУЮ копию `properties` с одним изменённым полем
`status` -- `saai-shell` не знает и не должно знать словарь `saai-
taskd` (kind/input), только `title`, которое уже человекочитаемо.

## Физическая проверка

Продолжение сессии, тот же реальный Pixel 7 (COM13-serial + USB-NCM на
этом Windows-хосте, не на R620).

**Путь подтверждения**: создан throwaway target (`test.throwaway`) +
опасный intent (`delete_entity`) через уже присутствующий на устройстве
`unix-json-request`. `saai-taskd` (кросс-собран, запущен вручную)
корректно поставил Task/Action в `waiting_confirmation` и НЕ исполнил
их (проверено повторно через 3с ожидания). Реальный физический тап
(тот же `uinput`-протокол-B метод, что ADR-031, синтетическое
touch-устройство + временная подмена боевого `saai-shell`-бинарника) по
кнопке "Подтвердить" -- `saai-taskd` отреагировал через `Subscribe`,
удалил target, создал Result, Task стал `done`.

**Путь отклонения**: второй target + опасный intent, тап "Отклонить".
Первая попытка ложно "не сработала" -- реальная причина: между
действиями прошло больше 60с (`IDLE_TIMEOUT`), экран сам заблокировался,
и одиночный тап просто разблокировал его вместо взаимодействия с
экраном подтверждения (видно в `saai-displayd`'s логе:
`touch down ... locked=true` -> `unlocked by touch`). Повтор с тапом
разблокировки прямо перед тапом отклонения -- сработало: Task
`cancelled`, target цел. Обнаруженный тут же пробел (Action оставался
`waiting_confirmation` навсегда) исправлен в `saai-taskd` ДО коммита
(`try_cancel_pending_action`) и физически перепроверен -- рестарт
демона подтянул Action в `cancelled` через `reconcile_confirmed_tasks`.

**Cold reboot -- главное доказательство**. Третий target + опасный
intent, Task создан `waiting_confirmation`. `reboot` (без `-f`) не
сработал -- uptime после команды остался 23ч+ (кастомный `native-
init.c`, судя по всему, не реализует протокол graceful-shutdown,
которого ждёт штатный путь `reboot`); `reboot -f` сработал: `uptime`
после -- 2 минуты, все боевые PID (`saai-entityd`/`saai-appd`/
`saai-displayd`/`saai-shell`) новые. Task остался `waiting_confirmation`
(revision не изменилась), target цел -- персистентность entity store
через настоящий cold reboot подтверждена для ЭТОЙ конкретной сущности
(не только обобщённо, как S06 уже показало для `Space`/`Entity`
вообще). `saai-taskd` не в списке процессов после ребута (не в
`native-init.c`, по дизайну) -- запущен вручную заново: reconcile
корректно НЕ тронул `waiting_confirmation` Task (пустой лог, дважды
перепроверено чтением стора). Синтетический touch + подмена
`saai-shell` повторены после ребута (оба сбрасываются перезагрузкой,
как и ожидалось для init_boot ramdisk) -- реальный тап "Подтвердить"
**после** cold reboot корректно исполнил Action и удалил target.

**Побочная находка, зафиксирована честно**: до этой перезагрузки
`/saaios/saai-shell` показывал хэш `34653527...`, который весь этот
сеанс (включая ADR-029/ADR-031) трактовался как "боевой оригинал".
После настоящего cold reboot файл вернулся к `87dbe83f...` -- значит
`34653527` был версией, живущей только в памяти записываемого rootfs с
какой-то более ранней части этой длинной сессии (никогда не
переживавшей reboot до этого момента), а НЕ содержимым реально
зашитого `init_boot`-образа. `87dbe83f` подтверждён пользователем как
верный ориентир для восстановления и использован для этого начиная с
данного ADR; расхождение само по себе не расследовалось дальше (не
входит в Change 3) и явно называется здесь, а не скрывается.

**Откат тестовой оснастки, полностью выполнен**: `uinput`-устройство
уничтожено штатно, `/dev/input/touchscreen` восстановлен на `event2`,
`/saaios/saai-shell` восстановлен к `87dbe83f` (сверен байт-в-байт на
перезапущенном процессе), `saai-taskd` остановлен, 12 тестовых
сущностей удалены из `work` с явным подтверждением пользователя (тот
же auto-mode классификатор снова корректно потребовал подтверждения
на bulk-delete). Финальная проверка: `work` пуст, боевые процессы
работают неизменными.

## Решение

S09's Threat/privacy impact требование выполнено и физически
подтверждено на реальном железе через настоящий cold reboot, не
рестарт процесса: опасный `Action` приостанавливается, ждёт живого
touch-подтверждения, переживает cold reboot в состоянии ожидания без
автозапуска, и исполняется только после нового, не кэшированного
подтверждения -- как до, так и после перезагрузки. Отклонение оставляет
связный audit trail (Task и Action оба `cancelled`).

## Последствия

- S09's Acceptance criteria по подтверждению опасного Action и
  cold-reboot закрыты физически. Идемпотентность самого удаления
  (`delete_target_entity` возвращает `Ok(false)`, не ошибку, если цель
  уже отсутствует) тоже часть этого доказательства, хоть и не
  тестировалась отдельным повторным подтверждением в этом раунде.
- `saai-taskd` по-прежнему не в `native-init.c` -- вопрос автозапуска
  остаётся отдельной, не начатой задачей.
- Обнаруженное расхождение бинарных хэшей (`34653527` vs `87dbe83f`)
  -- открытый вопрос за пределами этого ADR: если `34653527` содержал
  осмысленные отличия от `87dbe83f`, эти отличия сейчас физически
  утеряны с этим reboot. Стоит проверить при следующей возможности,
  не откладывая надолго.
- `saai-shell`'s confirm-экран текущей реализации показывает только
  первый найденный `waiting_confirmation` Task в выбранном пространстве
  -- множественные одновременные опасные Task (не встречалось в этом
  раунде) -- сценарий для будущего Change, не гипотеза, которую стоило
  разрабатывать заранее.
