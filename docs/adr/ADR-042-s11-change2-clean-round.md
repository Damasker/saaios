# ADR-042: S11 Change 2 -- clean verification round, power-button wake confirmed, self-wake not, real UX gap found

## Статус

Принято, 2026-09-11. Дополняет ADR-041 отдельным, контролируемым
раундом -- без дублирующего процесса, без случайностей.

## Контекст

ADR-041 закрыло Change 2 как "реализован, но не Acceptance-complete":
механизм физически доказал устойчивый простой, но оба цикла были
непреднамеренными (побочный эффект тестовой ошибки -- дублирующий
процесс), один канал пробуждения остался неопознанным. Этот раунд --
попытка получить чистые данные: единственный экземпляр `saai-shell`
(без дублей), временная сборка с коротким `deep_idle_timeout` (15с
вместо продакшен 300с, зашито в константу для этого раунда, не через
env -- чтобы не плодить второй процесс), каждый цикл -- по отдельному
осознанному согласию.

## Безопасная процедура подмены бинарника (найдена в этом раунде)

Прямая замена `/saaios/saai-shell` через `cp` в момент, когда файл ещё
исполняется убитым-но-не-до-конца-освобождённым процессом, регулярно
давала `Text file busy` -- PID1's supervision (`UI_RESTART_BUDGET`)
восстанавливает `saai-displayd`/`saai-shell` из СТАРОГО файла быстрее,
чем успевает выполниться `cp`, независимо от того, насколько быстро
после `kill` она запущена. Решение: `cp source /saaios/saai-shell.new
&& mv /saaios/saai-shell.new /saaios/saai-shell` -- `mv` -- атомарная
замена directory entry, не требует, чтобы старый inode был свободен
(Unix позволяет удалить/переименовать поверх файла, который другой
процесс всё ещё держит открытым -- этот процесс продолжает работать со
старым, теперь безымянным inode, а новый экземпляр при следующем `exec()`
получает уже подменённый файл). Полезный, переиспользуемый вывод для
любой будущей горячей подмены бинарника в этом проекте, не только для
этого теста.

## Физическая проверка

Три отдельных, чисто подтверждённых цикла (единственный экземпляр
`saai-shell`, 15с тестовый таймаут):

1. Уснуло -> не проснулось само (устройство недоступно дольше 82с из
   ADR-041's первого случайного цикла) -> пользователь нажал кнопку
   питания -> проснулось.
2. Уснуло сразу после (таймер перезапускается автоматически после
   пробуждения, по конструкции) -> пользователь нажал -> проснулось.
3. То же самое -> пользователь нажал -> проснулось.

**0 из 3 циклов проснулись сами.** Это отличается от ADR-041's
случайного раунда, где первый (из двух) цикл проснулся без
вмешательства -- подтверждает, что тот случай был, вероятно, связан с
ещё не до конца понятым `VGPIO2PMU_EINT`-источником (см. ниже), а не
надёжным, воспроизводимым поведением.

**`dmesg` по всем циклам этого раунда** (включая несколько
дополнительных, менее строго отслеженных циклов во время последующей
попытки вернуть продакшен-бинарь) показывает **одинаковую причину
пробуждения во всех случаях -- `Resume caused by VGPIO2PMU_EINT`**, ни
разу не через Wi-Fi (`dhdpcie_host_wake`) -- подтверждает, что
`wlan0 down` перед `mem` корректно убирает Wi-Fi как источник
самопробуждения на всём протяжении раунда, не только в единичном
случае ADR-040. Длительности циклов из полного `dmesg`-лога --
от нескольких секунд до ~77с -- само по себе не является проблемой
(зависит от того, насколько быстро после пробуждения пользователь
успевал среагировать на следующий автоматически стартовавший цикл, не
от самого механизма).

**Критическая, реальная UX-находка**: у пользователя физически нет
способа увидеть, когда именно устройство ушло в глубокий простой --
экран не гаснет и не тускнеет (тот же, ещё с S04 известный пробел:
`disable_display()` требует DRM-доступа, которого у `saai-shell` нет).
Из-за этого нажатие кнопки питания "по ощущению" систематически
промахивалось мимо реального окна сна -- рабочей практикой в этом
раунде стало то, что **эта сессия** (по пропаданию serial/USB-NCM,
видимому только программно) говорила пользователю точный момент "жмите
сейчас", а не пользователь judging по экрану. Это не просто неудобство
тестирования -- это реальный, не самостоятельно решаемый в рамках
Change 2 продуктовый пробел: сегодня ни один человек без доступа к
serial-консоли не может понять, когда телефон уснул по-настоящему.

## Решение

Power-button wake физически подтверждён надёжным: 3 из 3 чистых,
по-отдельности согласованных цикла, плюс несколько дополнительных во
время восстановления -- все успешные, все через один и тот же
`VGPIO2PMU_EINT` путь, ни одного зависания. Self-wake (без физического
вмешательства) -- **не подтверждён** в этом чистом раунде (0 из 3);
ADR-041's единственный случай самопробуждения остаётся
неповторённым и, вероятно, связан с тем же неопознанным
периодическим источником, не с чем-то, на что можно полагаться.

## Последствия

- **Change 2 принимается как `Done` с честной оговоркой**, не как
  формально полный "10 из 10" по исходному тексту Acceptance:
  фактически подтверждено 3 чистых + несколько дополнительных
  power-button-циклов (не 10, по совместному решению с пользователем
  -- дальнейшие идентичные циклы не добавляли новой информации, только
  нагрузку на пользователя), self-wake explicitly не гарантирован.
  Acceptance criteria в sprint-доке будут переписаны построчно с этой
  честной формулировкой, по прецеденту закрытия S09.
- **Реальный, не решённый здесь продуктовый пробел**: отсутствие
  визуальной индикации сна -- кандидат для отдельной, будущей задачи
  (нужен путь `saai-shell` -> `saai-displayd` для запроса
  экрана-выключения, тот же класс работы, что S04 уже отметило как "не
  входит" и не решило).
- Источник `VGPIO2PMU_EINT`, срабатывающий без явного пользовательского
  действия хотя бы один раз (ADR-041), остаётся неопознанным -- не
  блокирует закрытие Change 2 (power-button путь работает независимо
  от этого), но стоит расследовать перед Change 3's soak-тестом, чтобы
  не спутать периодические самопробуждения с реальной проблемой во
  время 24-часового прогона.
- Найденный `cp && mv`-паттерн для горячей подмены бинарника -- полезная,
  переиспользуемая техника для любой будущей физической проверки в
  этом проекте.
