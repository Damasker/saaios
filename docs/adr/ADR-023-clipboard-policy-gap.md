# ADR-023: Clipboard через policy -- smithay's data-device не даёт точки перехвата

## Статус

Принято, 2026-09-10.

## Контекст

ADR-021 (S08 Change 2) реализовал `wl_data_device_manager` через
smithay's `DataDeviceState` с полностью no-op `SelectionHandler`/
`DataDeviceHandler` -- нужно было только для того, чтобы GTK4 вообще
согласился открыть дисплей (`_gdk_wayland_display_open()` требует этот
global безусловно). Это дало реальный, рабочий clipboard между
клиентами, но явно задокументированным известным пробелом: без единой
проверки против `saai-appd`'s grants (S07). Change 5 должен был закрыть
этот пробел -- проверять `Capability::ClipboardRead`/`ClipboardWrite`
перед тем, как позволить клиенту записать или прочитать selection.

## Находка

Чтение исходника smithay 0.7.0 (`wayland/selection/data_device/
device.rs`, `wayland/selection/offer.rs`) показало, что ни одна из двух
операций не даёт точки перехвата, через которую compositor мог бы
реально ОТКАЗАТЬ в операции:

- **Запись** (`wl_data_device::Request::SetSelection`,
  `device.rs:118-137`): `handler.new_selection(...)` вызывается, но
  **после** того, как проверка фокуса уже пройдена, и **до** того, как
  `seat_data.borrow_mut().set_clipboard_selection::<D>(...)`
  выполняется безусловно, независимо от того, что делает
  `new_selection()`. Сигнатура `fn new_selection(&mut self, ...)` не
  возвращает значения, которое могло бы отменить операцию --
  `SelectionHandler` в этой версии API это чисто FYI-уведомление, не
  гейт.

  Отдельно: сам код перед этим требует `seat.get_keyboard()` -- `Some(
  keyboard) if keyboard.client_of_object_has_focus(...)`, иначе
  `SetSelection` тихо игнорируется целиком (`_ => { debug!(...);
  return; }`). На `panther-hardware`-сборке (ADR-012, `wl_keyboard`
  никогда не подключается) это означает, что запись в clipboard **уже
  безусловно блокируется** сегодня -- но случайно, не через
  capability-проверку, а как побочный эффект отсутствия клавиатуры.
  Хрупкая защита: если когда-нибудь `wl_keyboard` появится на этой цели
  (например, через путь из ADR-022), она молча исчезнет, ничего не
  заменив её.

- **Чтение** (`wl_data_offer::Request::Receive`, `offer.rs:120-170`):
  обрабатывается через собственный низкоуровневый `ObjectData<D>`,
  привязанный напрямую к объекту `wl_data_offer` в момент его создания
  (`SelectionOffer::new`) -- **минуя** обычный `Dispatch<WlDataOffer,
  ..., D>` механизм совсем. Это внутренняя, непубличная машинерия
  smithay; в текущем API нет способа подписаться на этот запрос или
  отклонить его вообще, даже как уведомление.

Это третий случай в этом же спринте (после ADR-022's input-method-v2),
когда абстракция smithay 0.7.0 не даёт нужной детализации для
capability-модели SaaiOS -- паттерн, не единичный случай.

## Решение

Задокументировать и не блокировать S08 этим -- clipboard через
smithay's `wl_data_device_manager` остаётся закрытым известным
пробелом, не тихо забытым:

1. Реальная capability-проверка (`Capability::ClipboardRead`/
   `ClipboardWrite` из S07) для нативного Wayland clipboard **не
   реализована** и не может быть реализована в текущем API smithay без
   одного из:
   - написать `wl_data_device_manager` вручную, в обход smithay's
     модуля -- реальный геймплей на обеих операциях уже есть сейчас
     (ADR-021), но больший объём низкоуровневого wire-протокола;
   - патчить/форкнуть smithay, добавив hook-точки в `device.rs`/
     `offer.rs` -- чистый API на будущее, новый слой поддержки и
     расхождение с upstream.

   Ни один путь не выбран -- решается отдельно, при появлении бюджета.
2. Случайная блокировка записи на `panther-hardware` (отсутствие
   `wl_keyboard`) остаётся как есть -- не считается решением проблемы,
   явно помечена как хрупкая в коде и здесь.
3. S07's собственный portal-протокол (`saai-shell`, S07 Change 7) --
   отдельный, уже правильно capability-gated канал для clipboard,
   которым пользуется explicitly-написанный под него код (например
   `saai-demo-surface`'s `SAAIOS_PORTAL_ROUNDTRIP` режим). Он не
   заменяет нативный Wayland clipboard для немодифицированных GTK4/Qt
   приложений -- они говорят на wl_data_device_manager, не на нашем
   протоколе -- но остаётся единственным путём, где реальная
   capability-проверка уже физически работает и подтверждена (S07
   Evidence).

## Последствия

Положительные:

- находка не позволила потратить время на код, который выглядел бы
  рабочим, но не мог бы реально отклонить чтение вообще (ObjectData
  путь непубличен) -- лучше найти это сейчас через чтение исходника,
  чем через баг-репорт после того, как приложение обошло grants;
- случайная блокировка записи на реальном железе -- не решение, но
  снижает текущий практический риск до нуля для этого конкретного
  устройства, пока не выбран путь вперёд.

Цена решения:

- нативный Wayland clipboard (в отличие от S07's portal) остаётся вне
  capability-модели SaaiOS на неопределённый срок -- задокументированный,
  не скрытый разрыв между "то, что декларирует manifest" и "то, что
  реально проверяется" для этого конкретного канала;
- если `wl_keyboard` когда-либо появится на `panther-hardware` (путь из
  ADR-022 это допускает) без предварительного решения этого ADR,
  clipboard-запись начнёт работать без единой проверки -- нужно явно
  свериться с этим ADR перед тем, как включать клавиатуру.
