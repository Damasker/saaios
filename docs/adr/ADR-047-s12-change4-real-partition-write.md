# ADR-047: S12 Change 4 -- реальная запись в загрузочный раздел (saai-ota-write)

## Статус

Принято, 2026-09-12.

## Контекст

S12's Definition of Ready поставил Change 4 самой рискованной задачей
спринта: реальная запись обновления в единственный доступный
SaaiOS-слот (A), с резервной копией и восстановлением как
rollback-путём (слот B закрыт owner policy, см. S12's Current state).
Это первая во всём проекте попытка писать в реальный, загрузочно-
критичный GPT-раздел (`init_boot_a`/`vendor_boot_a`) изнутри работающей
SaaiOS -- максимальный blast radius на сегодня, требующий явного
согласия пользователя перед первой реальной попыткой (получено).

## Решение

Новый сервис `services/saai-ota-write` (одноразовый CLI, тот же
принцип "доказать перед вшиванием в init", что ADR-030/ADR-046):

- **`partition_io.rs`** -- вся опасная механика разложена так, чтобы
  read/write/verify/restore-логика была полностью host-тестируемой
  против обычных файлов, а на реальном устройстве проверялась только
  сама *резолюция* раздела (уже проверенный ADR-044's механизм,
  переиспользован, не изобретён заново):
  - `resolve_partition_device_node()` -- тот же скан `PARTNAME` по
    `/sys/class/block/*/uevent`, что `create_partition_node()` в
    `native-init.c`, с инжектируемым корнем директории для
    host-тестов (по аналогии с `ab_status.rs`'s `SAAIOS_AB_ROOT`).
  - `backup_write_verify()` -- читает текущее содержимое `target`,
    атомарно сохраняет в `backup_path`, пишет новое содержимое,
    перечитывает и сверяет по префиксу длины записанного (раздел
    может быть больше образа -- хвост не трогается и не важен). При
    любой ошибке после успешного backup -- автоматическая попытка
    восстановить `target` из только что снятой резервной копии.
  - `restore_from_backup()` -- ручной путь отката.
- **CLI**: `backup` (только чтение, копия текущего содержимого в
  файл), `raw-write` (пишет локальный файл в раздел, backup
  обязателен), `restore` (пишет backup обратно), `install`
  (реальный путь: повторно верифицирует staged-manifest -- ничего из
  Change 3's вывода не считается доверенным без переповторной проверки,
  файлы могли устареть -- затем backup+запись+verify для каждого
  раздела манифеста). `--unsafe-test-target-override` у `install`
  перенаправляет один раздел на обычный файл вместо резолва
  реального устройства -- только для тестирования интеграции,
  никогда не используется в реальной установке.

## Test -- host (полностью безопасно, без устройства)

`cargo test -p saai-ota-write` -- 7/7: резолюция раздела по точному
совпадению `PARTNAME` (не по подстроке -- `init_boot_a` не совпадает
с `init_boot_a_extra`/`init_boot`); отсутствующий раздел
диагностируется точно; backup+write+verify цикл; раздел больше образа
(хвост не трогается); ручное восстановление; **автоматическое
восстановление при отказе записи** (target сделан read-only на
хосте, где процесс НЕ root -- запись падает, автоматический restore
запускается, итоговое содержимое не повреждено). `cargo clippy
--all-targets` и `cargo fmt -- --check` чисты. `cargo build
--workspace` чист. Кросс-компиляция `aarch64-unknown-linux-musl`/
`pixel7` чиста, hash
`cf58e98755d8b6d9d9a7a8c29b9701871c2c467e9cf2400ef8fee2be9690ff06`.

**Честная асимметрия, не пробел.** На устройстве весь процесс работает
от root -- обычный `chmod 444` не создаёт реальный отказ записи (root
игнорирует биты прав), поэтому "восстановление при отказе" физически
воспроизведено только на хосте (где тестовый процесс не root), не на
устройстве. Сама логика восстановления идентична независимо от uid
вызывающего -- это ограничение техники индукции отказа в конкретной
среде, не разная логика.

## Test -- реальное устройство, с явным согласием пользователя перед первой попыткой

Полностью безопасная часть сначала: `install` прогнан дважды через
`--unsafe-test-target-override` на scratch-файлы (не разделы) --
staged-контент Change 3's манифеста (2097152/1048576 байт случайных
байт) корректно записан в scratch-файлы, backup содержал именно
исходное (другое случайное) содержимое -- оба хеша сверены независимо
`busybox sha256sum`. Второй прогон с `chmod 444` на scratch-target
(деструктивный тест) не выявил отказа по той же причине -- root.

**Реальная запись в `init_boot_a`/`vendor_boot_a` -- с явным согласием
пользователя, полученным перед первой попыткой.** Решение по
минимизации риска: контент не меняется (self-write-back -- прочитанные
байты пишутся обратно в тот же раздел), начиная с менее критичного
`vendor_boot_a`, затем `init_boot_a`; после каждой записи -- настоящий
cold reboot. Генуинно другой контент (случайные Change 2/3 фикстуры)
на реальный раздел не писался -- это гарантированно сломало бы
загрузку; настоящий разный-контент update откладывается до Change 5
(там нужна намеренно нездоровая сборка для health-check drill).

1. **Backup обоих разделов** (только чтение): `vendor_boot_a` --
   67108864 байт, хеш `6e7be35de39fca996a9836f1dcd23265a30b40c710
   010208355d1a070184378c` -- **точно совпал** с уже задокументированным
   в `docs/os/targets/panther/README.md` SHA-256 оригинального
   `saaios-pixel7-vendor_boot-a.img` (`6E7BE35DE3...184378C`) --
   независимое подтверждение корректности резолюции и чтения раздела
   ещё до единой записи. `init_boot_a` -- 8388608 байт, хеш
   `2d702be4948678d4a751396477e3ed47a4c1fc5f5e1aa1a7be806683ef430351`
   (не совпадает с исходным S01-образом -- ожидаемо, `init_boot_a`
   пересобирался и перепрошивался несколько раз с тех пор, ADR-035 и
   другие).
2. **Реальная запись `vendor_boot_a`** (те же 67108864 байта обратно):
   успех, внутренняя verify прошла. Настоящий `reboot -f` -- чистая
   загрузка, `/proc/uptime` сброшен (21.07с), все core-сервисы подняты
   по одному разу, `boot.log` содержит `native userspace ready` и
   `slot A marked successful`, неотличимо от любой другой чистой
   загрузки за весь проект.
3. **Реальная запись `init_boot_a`** (те же 8388608 байт обратно, со
   свежим backup непосредственно перед записью для максимальной
   осторожности -- совпал байт-в-байт со снятым в шаге 1): успех.
   Настоящий `reboot -f` -- чистая загрузка (`uptime` 19.56с), core-
   сервисы подняты штатно, тот же `boot.log`-паттерн.
4. **Финальная независимая проверка после обеих перезагрузок**: оба
   раздела прочитаны заново (`backup` в throwaway-файлы) -- хеши
   идентичны шагу 1 байт-в-байт, ноль дрейфа за весь цикл
   запись->перезагрузка->перезагрузка.

Тестовые scratch-каталоги и промежуточные backup-варианты удалены
после раунда; `/data/saaios/system/backup/{init_boot_a,
vendor_boot_a}.img.bak` оставлены на устройстве как канонический
задел для Change 5. Deploy HTTP-сервер и firewall-правило убраны.

## Последствия

- Механизм записи раздела (ADR-044's решение) физически подтверждён
  работающим на реальных `init_boot_a`/`vendor_boot_a` -- не только
  прочитан, но и записан, с последующей настоящей перезагрузкой.
- **Не протестирован путь "запись действительно другого контента + что
  происходит при отказе на реальном разделе"** -- намеренно отложено
  до Change 5, у которого уже запланирована намеренно нездоровая
  тестовая сборка; выполнение self-write-back в Change 4 было
  осознанным решением минимизировать риск, а не полной демонстрацией
  "install реального обновления". Честно не выдаётся за большее.
- Автоматическое восстановление при отказе записи подтверждено только
  на хосте (root на устройстве обходит обычные права файлов) -- честно
  зафиксированная асимметрия среды, не разница в логике.
- Резервные копии обоих разделов остаются на `/data/saaios/system/
  backup/` -- Change 5 должен явно решить, обновляет ли их каждый
  `install`, или они статичны до следующего явного backup.
