# ADR-046: S12 Change 3 -- staged verified download на устройстве (saai-ota-stage)

## Статус

Принято, 2026-09-12.

## Контекст

S12's Definition of Ready поставил Change 3 третьей задачей: staged
verified download на реальном устройстве -- манифест и разделы
скачиваются через уже существующий download-клиент в
`/data/saaios/update-staging`, с полной проверкой размера/SHA-256/
подписи до какого-либо шага, трогающего раздел, и физическими
негативными сценариями (прерванная загрузка, повреждённый файл,
неверная подпись, чужая модель, запрещённый downgrade).

DoR буквально называл `busybox wget` как download-клиент. Решение
этого ADR -- **использовать `reqwest` вместо `busybox wget`**:
`crates/model-provider` (используется `saaios-runtime`, уже реально
работает на этом самом устройстве, вызывая Ollama на хосте через
USB-NCM) уже проверенно использует `reqwest` на этом же aarch64/musl
таргете через тот же `zig cc`-тулчейн -- не новый риск, а уже
физически проверенный путь. `reqwest` даёт потоковую загрузку с
инкрементальным хешированием (не нужно держать файл в памяти дважды)
и структурированную обработку ошибок transport'а, которых у
минимального `busybox wget` из этой прошивки нет. Это не меняет
системные границы, протокол или формат данных (просто HTTP GET по
тому же USB-NCM каналу в тот же staging-каталог) -- новый ADR не
требуется для этого выбора по правилам `DEVELOPMENT_PROCESS.md`,
фиксируется здесь для прозрачности решения.

## Решение

Новый сервис `services/saai-ota-stage` (одноразовый CLI, не демон --
тот же паттерн "доказать перед вшиванием в `native-init.c`", что
ADR-030 для `saai-taskd`; кросс-компилируется тем же `zig cc`-пайплайном,
`os/targets/panther/build-saai-ota-stage.sh`):

1. Определяет `device_target` через уже существующий
   `system_tools::system_identity()` (тот же `androidboot.hardware`,
   что уже физически подтверждён с S01).
2. Читает `installed_version` из `/data/saaios/system/
   installed-version` (новый файл; если отсутствует -- `0.0.0`,
   честный дефолт "OTA ещё ни разу не устанавливала версию на этом
   устройстве"). Change 3 только читает этот файл -- запись в него
   принадлежит будущему Change 4/5, после подтверждённо успешной
   установки.
3. Скачивает подписанный manifest по `--manifest-url`, парсит,
   вызывает `saai-ota-manifest::check_installable()` -- **до скачивания
   любого раздела**. Отказ здесь означает, что staging-каталог даже не
   создаётся.
4. Для каждого раздела манифеста скачивает `<manifest-url-каталог>/
   <name>.img` потоково, инкрементально хешируя (`Sha256::update` на
   каждый чанк) и считая байты -- никогда не держит файл целиком в
   памяти дважды. Пишет во временный `<name>.img.tmp` в
   `--staging-dir` (по умолчанию `/data/saaios/update-staging`).
5. По завершении потока сверяет реальные размер+SHA-256 с манифестом
   через новую `saai_ota_manifest::verify_partition_digest()`
   (добавлена этим Change -- `verify_partition_bytes` теперь тонкая
   обёртка над ней для вызывающих с байтами в памяти уже разом, как
   `saai-ota-sign verify`). При совпадении -- атомарный `rename()`
   `.tmp` в финальное имя (тот же `cp && mv`-принцип, что ADR-042).
   При несовпадении -- `.tmp` удаляется, ничего с этим именем не
   появляется в staging-каталоге.
6. Каждый раздел проверяется независимо -- отказ одного не
   останавливает попытку для остальных (полезно для диагностики,
   какой конкретно раздел испорчен); итоговый код выхода -- ошибка,
   если хоть один раздел не прошёл.

## Test -- физически на реальном устройстве (не эмуляция)

Прошито на устройство через USB-NCM (`busybox wget` -- только для
переноса самого нового бинарника и `verifying.pub` на телефон, сама
загрузка манифеста/разделов идёт через `saai-ota-stage`'s `reqwest`).
Раздающий HTTP-сервер -- тот же throwaway `serve-deploy.ps1` на
`172.31.7.2:8877`, что и в S11, с тем же временным firewall-правилом
(создано и удалено этим же раундом).

Пять сценариев, каждый -- реальный сетевой запрос по USB-NCM,
результат сверен независимо (`busybox sha256sum` на устройстве, не
только вывод самого инструмента):

1. **Валидный manifest + валидный artifact** -- принято, оба раздела
   (2097152 и 1048576 байт) скачаны и застейджены в `/data/saaios/
   update-staging`; `sha256sum` на устройстве независимо подтвердил
   точное совпадение с манифестом.
2. **Чужая модель устройства** (`target=some_other_phone`) --
   отклонено до создания staging-каталога (`ls: No such file or
   directory`).
3. **Downgrade** (installed_version == manifest.version, `0.14.0`) --
   отклонено с точным сообщением `manifest version 0.14.0 is not newer
   than installed version 0.14.0`, staging-каталог не создан.
4. **Испорченная подпись** (один hex-символ подписи изменён) --
   отклонено (`signature does not verify against manifest body`),
   staging-каталог не создан.
5. **Прерванная/усечённая загрузка** -- отдельный `manifest.json`
   объявляет тот же полный размер/хеш `init_boot_a`, что и сценарий 1,
   но реально раздаваемый файл в этом сетевом расположении обрезан до
   524288 байт (симулирует реальный обрыв передачи по USB-NCM
   детерминированно, не через таймингову гонку). Результат: `init_boot_a`
   отклонён с точным несовпадением (`expected ... size=2097152, got ...
   size=524288`), его `.tmp`-файл удалён, в staging-каталоге нет
   `init_boot_a.img`; `vendor_boot_a` (полный, не тронутый) при этом
   успешно застейджен независимо -- итоговый код выхода ненулевой.

Дополнительно (host, не устройство): `cargo test -p saai-ota-manifest`
-- 17/17 (два новых теста на `verify_partition_digest`, включая
усечённый-по-байтам сценарий, тот же принцип, что физический тест 5).
`cargo clippy -p saai-ota-manifest -p saai-ota-stage --all-targets` --
чисто. `cargo fmt -- --check` -- чисто. `cargo build --workspace` --
чисто. Кросс-компиляция `aarch64-unknown-linux-musl`/`pixel7`-профиль
-- чисто, hash `7377228b12b70253a8041b3a5da85e574ff01a75b80cec3a486146a3375fcf1d`.

Устройство после раунда: `uptime` вырос монотонно (5069s -> 5352s),
`free` стабилен (~336 МБ used, без роста), все core-сервисы
(`saai-entityd`/`saai-appd`/`saai-displayd`/`saai-shell`/
`saaios-runtime`) -- по одному экземпляру, без падений. Тестовый
staging-каталог удалён после раунда; `/data/saaios/ota-c3-test/`
(бинарник + `verifying.pub`) и `/data/saaios/system/
installed-version` (сейчас `0.10.0`, тестовое значение) оставлены на
устройстве как рабочий задел для Change 4.

## Последствия

- **Не реализована настоящая byte-range resumability** ("возобновляемая
  staged-загрузка" из исходного черновика S12). Change 3's Acceptance
  требовал только: прерванная загрузка не проходит проверку и не
  пишется мимо staging-каталога -- это подтверждено; полноценный
  докачивание с байта обрыва не реализовано и не входило в
  зафиксированный Definition of Ready буквально. Отмечается как
  известное ограничение, не выдаётся за большее.
- Раздел скачивается и проверяется независимо от остальных -- не
  атомарно по всему манифесту сразу. Для Change 3's целей (полностью
  read-only относительно реальных разделов) это безопасно; Change 4
  должен явно решить, требует ли запись в реальный раздел
  all-or-nothing поведения по всему манифесту сразу, или
  per-partition-достаточно.
- `installed-version`-файл создан этим Change как read-only вход;
  кто и когда его пишет после успешной установки -- открытый вопрос
  для Change 4/5, не решается здесь.
- `saai-ota-stage` -- одноразовый инструмент, не демон, не запускается
  `native-init.c` -- та же осторожность, что ADR-030 закрепил для
  `saai-taskd`.
