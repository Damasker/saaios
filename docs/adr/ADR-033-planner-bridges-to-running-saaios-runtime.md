# ADR-033: S10 Change 1 -- planner bridges to the already-running on-device saaios-runtime, not a new native model stack

## Статус

Принято, 2026-09-11.

## Контекст

S10's Definition of Ready назвало три кандидата для того, как свободный
текст `Intent` превращается в предложенный `Action`: (A) `saai-taskd`
вызывает уже развёрнутый и реально работающий на этом Pixel 7
`saaios-runtime` через его существующий TCP-протокол; (B) новый tool
внутри `saaios-runtime`, пишущий напрямую в `saai-entityd`; (C)
собственный, независимый от Platform Track, вызов модели прямо внутри
`saai-taskd`. Второй вопрос Change 1: что означает "planner только
создаёт предложения; policy исполняет" конкретно для S09's
`WorkflowStatus` словаря.

## Находка

Прочитан реальный код (`services/saaios-runtime/src/main.rs`): протокол
поверх TCP и Unix -- один и тот же `handle_client()`, одно соединение
на один запрос, JSON без обёртки CBOR (`Envelope::to_cbor`/`from_cbor`
существуют в `crates/protocol`, но фактически не используются этим
путём) -- `{"op": "diagnose", "text": "...", "stream": false}` ->
`ClientResponse{ok, diagnose, pending, tool_result, ...}`. `pending:
Option<PendingDto{call_id, tool, arguments, summary}>` -- уже готовый,
существующий сигнал "модель предложила потенциально опасное действие,
не выполнила его" -- ровно то, что нужно для моста к S09's
`WaitingConfirmation`.

Физически проверено с этого Windows-хоста напрямую по TCP
(`172.31.7.1:38127`, тот же USB-NCM канал, без захода в консоль
устройства):

1. `{"op":"ping"}` -> `{"ok":true,...}` -- протокол жив.
2. `{"op":"diagnose","text":"Сколько свободно места на диске?"}` ->
   модель (`qwen2.5:3b-instruct` через Ollama на этом хосте) сама
   вызвала `system.disk`, `policy` вынес `verdict: allow`
   ("read-only / low-risk tool"), инструмент выполнен немедленно, дан
   реальный (пусть и не идеальный у 3B-модели) финальный ответ. Никакого
   `pending`.
3. `{"op":"diagnose","text":"Останови процесс с pid 999, пожалуйста"}`
   -> модель вызвала `process.kill_request`, `policy` вынес `verdict:
   ask_user` ("tool `process.kill_request` requires confirmation"),
   инструмент НЕ выполнен -- вернулся `pending` с `call_id`/`tool`/
   `arguments`/`summary` и тем же `correlation_id`/`session_id`.
4. `{"op":"confirm", ..., "confirmed":false}` для этого `call_id` ->
   `tool_result: {ok:false, error:"user cancelled"}` -- отказ реально
   срабатывает и не выполняет действие.
5. Новый опасный запрос -> новый `pending` -> `{"op":"confirm", ...,
   "confirmed":true}` (безвредный несуществующий pid) ->
   `execution failed: pid 999999 not found` -- подтверждение реально
   доходит до исполнения (безвредно провалилось только потому, что pid
   не существует, не из-за политики).

Замечена не-детерминированность маленькой модели: одна и та же
по-русски по-разному сформулированная просьба ("убей" vs "останови")
иногда не приводит ни к какому вызову инструмента вообще, только к
текстовому "не удалось" ответу -- нормальный, ожидаемый исход
свободного текста через LLM, не баг моста.

Риск-классификация (`allow`/`ask_user`/`deny`) целиком уже находится в
Platform Track's `policy-engine`/`tool-registry` (`ToolSpec.risk`/
`requires_confirmation`) -- та же логика применяется независимо от
того, кто инициировал вызов (явный CLI, как в S09/ADR-032's тестах,
или модель) -- нет отдельного, более мягкого порога для
ИИ-инициированных вызовов, поскольку это тот же самый код одного и
того же уже работающего процесса.

## Решение

**Кандидат A**: `saai-taskd` (Change 2's работа -- новый небольшой мост
внутри него или рядом) отправляет свободный текст `Intent` как
`{"op":"diagnose","text":...}` уже работающему `saaios-runtime` по его
существующему TCP-протоколу. Ответ определяет `WorkflowStatus`
напрямую, без нового native-классификатора риска:

- `pending` отсутствует -- ответ уже полностью выполнен и безопасен
  (Platform Track's `policy-engine` сам решил `allow`). `saaios.task`
  создаётся сразу `Done`, `saaios.result` -- из `diagnose.summary`. Тот
  же паттерн, что Change 2's `echo`, просто источник текста -- модель,
  а не детерминированная функция.
- `pending` присутствует -- `saaios.task`/`saaios.action` создаются
  `WaitingConfirmation` (тот же словарь, что ADR-032), `Action`'s
  `input` хранит `{tool, arguments, call_id, correlation_id,
  session_id}` -- всё, что нужно, чтобы позже отправить `{"op":
  "confirm", ...}`. Подтверждение/отклонение идёт через УЖЕ
  существующий `Frame::TaskConfirm` в `saai-shell` (ADR-032) без
  единого изменения UI -- только новый `Action`'s `kind` (например,
  `saaios_runtime_tool`) и новый исполнитель в `saai-taskd`,
  отправляющий `confirm` вместо `delete_entity`.

Кандидаты B и C отклонены: B сделал бы `saaios-runtime` вторым
писателем в `saai-entity-store` (два независимых пути создания
`Task`/`Action`, дублирующий риск рассинхронизации, которого ADR-030
уже сознательно избежало для `policy-engine`/`tool-registry`); C
означал бы дублирование уже полностью рабочего `model-provider`/
`ai-runtime`/`policy-engine` стека внутри `saai-taskd`, без единой
причины, поскольку A решает ту же задачу поверх уже развёрнутой,
физически проверенной инфраструктуры, причём с идентичной, не более
мягкой риск-политикой.

**Второй вопрос**: "planner только создаёт предложения; policy
исполняет" означает буквально -- `pending` из ответа `saaios-runtime`
это ЕДИНСТВЕННЫЙ сигнал, решающий `WaitingConfirmation` vs `Done`.
Native OS Track не вводит собственную, отдельную от уже работающей
`policy-engine`, классификацию риска для ИИ-предложенных действий --
это было бы либо избыточным дублированием (уже показано верным для
`allow`-случая), либо, что хуже, потенциально более слабым отдельным
порогом. Единственное, что native OS Track добавляет поверх --
собственное, S09's, требование живого touch-подтверждения для всего,
что `saaios-runtime` само пометило `ask_user`, вместо того чтобы
доверять удалённому `Confirm`-запросу без физического жеста (что и так
уже требуется для explicit-Action-пути, ADR-032).

## Последствия

- Change 2 (минимальный вертикальный срез S10): новый `saaios_runtime`
  Action kind в `saai-taskd`, TCP-клиент к `172.31.7.1:38127` (или
  сконфигурированному адресу -- хардкод IP не переносим за пределы этого
  устройства/этой физической настройки, нужен параметр), маппинг
  `pending`/no-`pending` на `WorkflowStatus`. Никаких изменений в
  `saai-shell` не требуется -- `Frame::TaskConfirm` уже общий.
- `saaios-runtime`'s недоступность (выключен, Ollama-хост отключён) --
  `saai-taskd`'s TCP-вызов должен фейлиться явно (`saaios.task` ->
  `Failed`, не зависание) -- Change 2 должен явно проверить и это,
  Threat-раздел S10 уже требовал: "отключение модели не ломает ручное
  управление".
- Расписания/триггеры и memory-с-пространством по-прежнему не решены
  этим ADR -- явно вне Change 1/2, как и было зафиксировано в
  Definition of Ready.
- Сетевая граница подтверждена физически, не только по конфигурации:
  модель достижима только через USB-NCM к явно подключённому хосту --
  ничего в Change 1 её не расширило.
