# SaAIOS Pixel 7 embodiment — UX-спецификация

Статус: ready for implementation  
Спринт: S01 — system identity  
Экран: Pixel 7, 1080×2400, touch-first

## 1. Цель

Телефон воспринимается как самостоятельная SaAIOS, работающая на Pixel 7.
Модель — одна из системных возможностей, а не главный экран, персонаж или
единственный способ управления.

Сохраняются четыре корневых раздела:

- `Сейчас` — состояние устройства и одна ведущая возможность продолжить;
- `Входящие` — результаты, предупреждения и запросы подтверждения;
- `Пространства` — контексты и ручной доступ к системным модулям;
- `Я` — локальность, политика, устройство и приватность.

Вне scope: новые приложения, Scheduler, многоагентность, новая
информационная архитектура и полный редизайн оболочки.

## 2. Что исправить в текущей оболочке

1. Четыре системных блока имеют постоянные имена: `DEVICE`,
   `SET AN INTENT`, `DEVICE ACTIONS`, `SYSTEM RESULT`.
2. Модель не получает отдельную ведущую карточку и не подменяет системный
   статус.
3. `CHECK_DEVICE` возвращает структурированные наблюдения, а не текст ИИ.
4. Предложение действия не выглядит выполненным до подтверждения результата
   системной службой.

## 3. Системная идентичность

### Постоянные признаки

- На lock screen: `SaAIOS` и `Pixel 7`.
- В `Сейчас`: текущий Space, системный статус и строка намерения.
- В `Я`: `SaAIOS на Pixel 7`, версия образа, `Локальная система`.
- Название модели не показывается в системной шапке.

### Иерархия экрана `Сейчас`

1. status bar;
2. selector Space;
3. заголовок `Сейчас`;
4. ведущая карточка `DEVICE`;
5. постоянная строка `SET AN INTENT`;
6. блок `DEVICE ACTIONS`;
7. последний `SYSTEM RESULT`, если он существует;
8. четыре корневых раздела.

### Ведущая карточка — штатное состояние

```text
DEVICE
SaAIOS READY
Pixel 7 · LOCAL SYSTEM

[CHECK DEVICE]  [DEVICE DETAILS]
```

Если часть служб ещё не готова:

```text
DEVICE
SaAIOS STARTING
4 OF 6 SYSTEM SERVICES READY

[VIEW STARTUP]
```

Эти четыре системные метки и строки состояний для S01 фиксируются на английском.
Названия корневых разделов остаются русскими; не смешивать альтернативные
варианты одних и тех же меток.

## 4. SET AN INTENT

Строка присутствует во всех четырёх корневых разделах и не выглядит как поле
чата.

### Точные строки

- постоянная метка: `SET AN INTENT`
- placeholder: `What should SaAIOS do?`
- при недоступной модели: `Find a setting or device action`
- заголовок клавиатуры: `SET AN INTENT`
- подсказка над клавиатурой: `Describe the result you want`
- кнопки: `CANCEL`, `CONTINUE`
- во время принятия: `ACCEPTING INTENT…`
- ошибка: `INTENT NOT ACCEPTED`
- повтор: `TRY AGAIN`

### Поведение

- Tap открывает клавиатуру с сохранением текущего Space.
- Submit создаёт намерение, но не заявляет о выполнении действия.
- Пустой submit ничего не делает.
- Повторный tap во время submit не создаёт дубль.
- Back закрывает клавиатуру и сохраняет введённый текст в пределах текущего
  сеанса.
- При недоступной модели ручная навигация остаётся доступной; поле может искать
  системный модуль или принять текст для последующей обработки.

## 5. CHECK DEVICE

В коде и telemetry действие называется `CHECK_DEVICE`. Видимая строка:
`CHECK DEVICE`.

Это системная проверка, не запрос к модели. Минимальный набор наблюдений:
display, touch, storage, battery, Wi‑Fi, Bluetooth, audio и runtime. Проверка
ничего не перенастраивает и не выдаёт предположение за факт.

### Состояние 1 — ожидание

Используется после принятия команды, пока первый probe ещё не ответил.

```text
CHECK DEVICE
WAITING FOR SYSTEM SERVICES
CHECK WILL START AUTOMATICALLY

[CANCEL]
```

Через 2 секунды показать конкретную ожидаемую службу:
`WAITING FOR: STORAGE`. Не использовать бесконечный spinner без текста.

### Состояние 2 — выполнение

```text
CHECKING DEVICE
DISPLAY AND INPUT
STEP 2 OF 6

[STOP]
```

Строка шага принимает только значения:

- `DISPLAY AND INPUT`
- `POWER`
- `STORAGE`
- `NETWORK`
- `AUDIO AND BLUETOOTH`
- `LOCAL SERVICES`

Не показывать искусственный процент. Завершённые шаги получают текст
`CHECKED`; текущий — `CHECKING`; остальные — `WAITING`.

### Состояние 3 — результат

Успех:

```text
SYSTEM RESULT
DEVICE READY
8 OBSERVATIONS · NO ACTIONS

[VIEW DETAILS]  [DONE]
```

Частичный результат:

```text
SYSTEM RESULT
NETWORK NEEDS ATTENTION
7 OF 8 OBSERVATIONS RECEIVED

[VIEW DETAILS]  [RETRY]
```

Копия результата появляется во `Входящих` как `DEVICE CHECK RESULT`.
Корневая карточка не превращается в историю чата.

### Состояние 4 — ошибка

```text
SYSTEM RESULT
CHECK NOT COMPLETED
NO RESPONSE FROM BLUETOOTH

[RETRY BLUETOOTH]  [VIEW DETAILS]
```

Для неизвестной ошибки:

```text
SYSTEM RESULT
CHECK NOT COMPLETED
SYSTEM SERVICE STOPPED

[RETRY]  [CLOSE]
```

Безопасный код показывается в деталях: `DEVICE_CHECK_FAILED`. Нельзя писать
`DEVICE BROKEN`, если известен только timeout probe.

## 6. DEVICE ACTIONS

Блок показывает доступные системные операции, но не изображает их уже
выполненными. Минимальный набор S01:

```text
DEVICE ACTIONS
DISPLAY  ·  AUDIO
NETWORK  ·  BLUETOOTH
```

Tap открывает системную панель выбранного модуля. Если операция меняет
состояние, до выполнения показывается:

```text
ACTION PROPOSED
SET BRIGHTNESS TO 35%
CONFIRM TO CONTINUE

[CONFIRM]  [CANCEL]
```

После ответа системной службы запись перемещается в `SYSTEM RESULT`:

```text
ACTION COMPLETED
BRIGHTNESS SET TO 35%
SYSTEM SERVICE · NOW
```

Timeout или отказ не маркируются как выполненное действие. Повторное касание
не создаёт вторую операцию с тем же `action_id`.

## 7. SYSTEM RESULT: факт, предположение и действие

Тип всегда обозначается словом; один цвет недостаточен.

### Наблюдаемый факт

Маркер: `OBSERVED`  
Шаблон: `<объект>: <наблюдаемое значение>`  
Подпись: `SOURCE: <служба> · <время>`

Примеры:

```text
OBSERVED
WI-FI: NOT CONNECTED
SOURCE: SYSTEM · NOW
```

```text
OBSERVED
BATTERY: 71% · DISCHARGING
SOURCE: MAXFG · 04:12
```

### Предположение модели

Маркер: `MODEL ASSUMPTION`  
Шаблон: `<осторожная формулировка>`  
Подпись: `NOT VERIFIED BY SYSTEM`

Пример:

```text
MODEL ASSUMPTION
NETWORK MAY BE OUT OF RANGE
NOT VERIFIED BY SYSTEM
```

Запрещённые формулировки без evidence: `CAUSE FOUND`, `FIXED`,
`DEVICE HEALTHY`.

### Выполненное действие

Маркер: `ACTION COMPLETED`  
Шаблон: `<что изменено>`  
Подпись: `<исполнитель> · <время>`

Пример:

```text
ACTION COMPLETED
BRIGHTNESS SET TO 35%
SYSTEM SERVICE · 04:14
```

Предложенное, но не выполненное действие:

```text
ACTION PROPOSED
CONNECT TO HOME WI-FI
CONFIRMATION REQUIRED
```

## 8. Переходы

```text
Сейчас
  ├─ DEVICE / CHECK DEVICE → WAITING → RUNNING
  │                                      ├─ SYSTEM RESULT → Входящие + Сейчас
  │                                      └─ ERROR RESULT → Входящие
  ├─ DEVICE / DEVICE DETAILS → Обзор устройства
  ├─ DEVICE ACTIONS → Панель модуля → PROPOSED → COMPLETED | ERROR
  └─ SET AN INTENT → Клавиатура → ACCEPTED | ERROR

Входящие
  └─ SYSTEM RESULT → Сведения → Назад во Входящие

Пространства
  └─ Системные модули → ручной путь без модели

Я
  └─ SaAIOS на Pixel 7 → версия, локальность, политика
```

Lock во время проверки не отменяет её. После unlock открывается `Сейчас`, а
текущий статус проверки остаётся видимым. Reboot переводит незавершённую
проверку в результат `CHECK INTERRUPTED BY RESTART`; автоматический повтор
не запускается.

## 9. Edge cases

- **Модель недоступна:** CHECK_DEVICE работает; строка намерения предлагает
  ручной поиск; никаких красных системных ошибок только из-за модели.
- **Нет сети:** факт `Wi‑Fi: не подключён`; это не ошибка всей проверки.
- **Probe timeout:** показать имя службы и сохранить частичные факты.
- **Двойное касание:** один `check_id`, один запуск.
- **Поворот/смена DRM mode:** layout остаётся в design space 1080×2400;
  hit-regions пересчитываются тем же transform.
- **Экран погас:** проверка продолжается без принудительного wake.
- **Пользователь остановил:** `CHECK STOPPED`, частичные факты доступны,
  действий не было.
- **Устаревший факт:** после 60 секунд подпись `UPDATED 1 MIN AGO` и
  действие `REFRESH`.
- **Противоречие модели системе:** системный факт показывается первым;
  предположение получает строку `CONFLICTS WITH CURRENT OBSERVATION`.
- **Действие требует согласия:** до подтверждения тип остаётся
  `ACTION PROPOSED`.
- **Нет места для результата:** показать `RESULT NOT SAVED`; текущий
  экран не должен заявлять, что запись выполнена.

## 10. Ограничения текста и touch

- Заголовок: до 24 знаков, одна строка.
- Основной вывод: до 32 знаков в строке, максимум две строки.
- Служебная подпись: максимум две строки.
- Одна карточка — одна главная мысль.
- Не более двух действий в одной строке; primary слева.
- Минимальная touch-цель: 120×120 design px.
- Расстояние между соседними целями: не менее 24 design px.
- Ни одно состояние не полагается только на цвет, анимацию или spinner.
- Динамический текст обрезается безопасно; IMEI, адреса устройств, ключи и
  prompt пользователя не попадают в системные карточки или журнал.

## 11. Визуальная приёмка

- За 5 секунд без взаимодействия человек называет продукт `SaAIOS` и
  устройство `Pixel 7`, а не «чат с ИИ».
- На `Сейчас` первым читается состояние устройства, вторым — доступное
  действие, третьим — строка намерения.
- `OBSERVED`, `MODEL ASSUMPTION`, `ACTION PROPOSED` и `ACTION COMPLETED`
  различимы
  в grayscale и при выключенной анимации.
- Все строки помещаются на 1080×2400 без clipping при фактических Inter
  Regular/Semibold.
- Waiting, running, result и error не меняют геометрию Back и нижней навигации.
- Строка намерения выглядит как системная команда, не как bubble/чат.

## 12. Физическая приёмка на Pixel 7

1. Cold boot без модели: ручные разделы и CHECK_DEVICE доступны.
2. Запустить CHECK_DEVICE и физически увидеть четыре состояния с
   воспроизводимым timeout одного test probe.
3. Сверить каждый показанный факт с sysfs/service source.
4. Заблокировать и разбудить экран во время проверки; input не утекает,
   состояние сохраняется.
5. Дважды быстро нажать primary CTA; существует один запуск.
6. Остановить проверку; никакое системное действие не выполняется.
7. Получить результат во `Входящих`, открыть сведения и вернуться Back.
8. Проверить все touch-цели по краям, BGRX-цвета, кириллицу и отсутствие
   tearing на 1080×2400×60.
9. Намеренно остановить shell; recovery UI и USB-консоль остаются доступны.
10. В журнале нет prompt, секретов и идентификаторов Bluetooth; есть только
    `check_id`, переход состояния, source и безопасный error code.

## 13. Definition of Done для программиста

- Все строки берутся из одного набора констант, а не дублируются по render
  functions.
- CHECK_DEVICE не вызывает модель и не изменяет настройки.
- Реализована явная state machine:
  `idle → waiting → running → result | error | cancelled`.
- Fact/assumption/proposal/action представлены разными типами данных до
  rendering, а не определяются по тексту.
- Переходы покрыты unit-тестами; двойной submit и stale result — negative
  tests.
- 12 deterministic preview frames дополнены четырьмя состояниями CHECK_DEVICE.
- Физические пункты раздела 12 записаны как evidence; без них Pixel embodiment
  не считается принятым.
