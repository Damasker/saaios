# Графическая и прикладная платформа SaaiOS

## Назначение

Целевая платформа запускает собственную оболочку SaaiOS и независимые
приложения, не превращаясь в сборку KDE, GNOME или Android. Архитектурное
решение зафиксировано в
[ADR-005](../../adr/ADR-005-owned-wayland-application-platform.md).

## Целевая схема

```text
┌──────────────────────────────────────────────────────────────┐
│                         приложения                           │
│  SaaiOS native       GTK/libadwaita       Qt/Kirigami        │
└───────────────┬──────────────────┬──────────────────┬─────────┘
                │                  Wayland             │
┌───────────────▼──────────────────────────────────────▼─────────┐
│ saai-shell                    saai-appd                        │
│ lock/status/navigation        manifests/lifecycle/crash loop  │
└───────────────┬───────────────────────────┬─────────────────────┘
                │ Wayland                   │ service IPC
┌───────────────▼───────────────────────────▼─────────────────────┐
│ saai-displayd         context/entity/event/policy/workflow     │
│ DRM, surfaces, input, focus, composition, output policy       │
└───────────────┬───────────────────────────┬─────────────────────┘
                │                           │
┌───────────────▼───────────────────────────▼─────────────────────┐
│ Linux kernel: DRM/KMS, input, audio, network, storage, power  │
└────────────────────────────────────────────────────────────────┘
```

Текущий `drm-splash` остаётся параллельным минимальным boot/recovery UI, а не
клиентом нового стека. PID 1 запускает fallback, пока `saai-displayd` и
`saai-shell` не сообщили о готовности; при crash loop система возвращается к
fallback без потери USB-консоли.

## Ответственность компонентов

### `saai-displayd`

- владеет DRM master и физическим scanout;
- применяет проверенную для Pixel 7 упаковку BGRX на границе вывода;
- принимает поверхности Wayland и собирает кадр;
- маршрутизирует touch/keyboard события только активной поверхности;
- управляет focus, fullscreen, popups и системными слоями;
- не знает о `Space`, объектах, модели или содержимом карточек.

### `saai-shell`

- рисует lock screen, статус, системные панели и четыре корневых раздела;
- показывает состояние сервисов и запросы разрешений;
- переключает приложения и восстанавливается после собственного падения;
- не получает DRM master и не читает evdev напрямую.

### `saai-appd`

- читает и валидирует декларативный manifest;
- назначает устойчивый `app_id`, каталог данных и набор capability;
- запускает процесс с фиксированным окружением и отслеживает его состояние;
- ограничивает crash loop и сообщает событие оболочке;
- не выдаёт разрешение самостоятельно: решение принимает policy service.

### Сервисный слой

UI получает проекции объектов и отправляет команды, но не является базой
данных. Смена `Space` меняет область видимости сущностей и памяти на стороне
сервисов, а не только подпись главной карточки.

Системный интеллект также не живёт внутри UI: identity, capability,
наблюдения, policy, action и verification описаны в
[system-intelligence.md](system-intelligence.md) и ADR-006.

## Минимальный manifest приложения

Первая версия описывается документированной схемой и содержит как минимум:

```toml
schema = 1
id = "org.saaios.example.notes"
name = "Заметки"
exec = "bin/notes"
version = "0.1.0"
ui = "wayland"
single_instance = true
capabilities = ["space.entities.read", "space.entities.write"]
```

Manifest не является разрешением. Он только объявляет запрос; эффективный
набор выдаёт policy service для конкретного пользователя и пространства.

Устанавливаемые приложения и runtime-библиотеки размещаются под
`/data/saaios/apps`, а не в ограниченном `init_boot`. Изменяемые данные одного
приложения находятся в отдельном каталоге под `/data/saaios/var/apps`.

## Очерёдность протоколов

### Базовая вертикаль

- `wl_compositor`, `wl_surface`, `wl_region`;
- `wl_shm` с проверенными форматами;
- `wl_output` и целочисленный scale;
- `wl_seat`, `wl_touch`, keyboard focus;
- стабильный `xdg_wm_base`, `xdg_toplevel`, `xdg_popup`.

### Системная оболочка

- системные слои, lock surface и безопасное перекрытие приложений;
- управление списком toplevel;
- отключение/пробуждение output;
- virtual keyboard и text-input после появления первого поля ввода.

### После функциональной стабильности

- clipboard и drag-and-drop через policy/portal;
- fractional scale;
- `linux-dmabuf`, explicit sync и аппаратная композиция;
- XWayland только как необязательный пакет совместимости.

## Инварианты безопасности

- заблокированный экран не передаёт touch или keyboard приложению;
- системный запрос разрешения нельзя подделать обычной поверхностью;
- один клиент не видит буферы, события ввода или данные другого клиента;
- shell не обходит policy service для пользовательских данных;
- сетевой доступ не подразумевается наличием Wayland-подключения;
- до готового sandbox разрешены только доверенные тестовые приложения;
- секреты, калибровка и userdata не попадают в образ или Git.

## Наблюдаемость и восстановление

Каждый компонент публикует readiness, версию протокола, причину последнего
выхода и счётчик рестартов. В журнал не записываются содержимое буфера обмена,
текст полей и секретные параметры. После трёх падений за короткое окно app или
shell останавливается; для compositor включается проверенный DRM fallback.

## Открытые решения

До соответствующего измеримого спринта не фиксируются:

- формат межсервисного IPC поверх уже принятой гибридной модели;
- постоянная схема entity store;
- GPU backend Pixel 7.

Эти решения принимаются отдельными ADR после измеримого прототипа, а не по
предпочтению toolkit.

Framework compositor зафиксирован после Sprint 01 в
[ADR-007](../../adr/ADR-007-minimal-wayland-rs-compositor.md): ограниченная
реализация на сгенерированных bindings `wayland-rs`.
