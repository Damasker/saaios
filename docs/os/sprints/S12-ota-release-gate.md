# Sprint 12 — OTA и release gate

## Паспорт

- Состояние: `Ready` (2026-09-12).
- Зависит от: S01-S11 (все `Done`). S04 -- узкий, но реальный
  precedent: `fastboot flash init_boot_a` + `--set-active=a` +
  `fastboot reboot` уже физически подтверждены надёжными несколько раз
  за проект (S04's Evidence, `product=panther`, `current-slot=a`,
  `unlocked=yes`) -- это precedent для "flash+reboot цикл работает",
  не precedent для настоящего двух-слотового SaaiOS OTA (такого
  прецедента в проекте нет вообще, см. Current state).
- Архитектурные решения: партиционный write-механизм ещё не выбран --
  это предмет Change 1's спайка, намеренно не предрешается в этом
  документе (см. Scope). `services/saaios-runtime/src/ab_status.rs`
  признан нерелевантным реальным слотам этого устройства (уже
  отмечено в S11's Definition of Ready как решение, передаваемое
  сюда) -- не переиспользуется для slot-detection; реальный slot
  читается из `androidboot.slot_suffix` (`/proc/bootconfig`), уже
  корректно читается `crates/system-tools::boot_slot_from`.
- Рабочий fallback: пока Change'и этого спринта не приняты или
  откатываются, единственный путь обновления остаётся сегодняшним --
  ручной `fastboot flash` с хоста в bootloader-режиме, физически
  проверенный весь проект (S01-S11).

## Goal

Новый стек можно безопасно и проверяемо обновить на тестовом Pixel 7:
подписанный manifest и artifact, staged verified download, запись без
риска для активного загружаемого слота, ограниченное число boot
attempts, health confirmation и автоматический откат на последний
физически подтверждённый рабочий образ -- всё физически проверено на
реальном устройстве, а не предположено. Переход от сохранённого
Android в слоте B к второму SaaiOS-слоту и настоящий cross-slot A/B
hardware failover -- явно вне скоупа этого Definition of Ready (см.
Scope).

## Current state

Проверено на реальном устройстве и по коду перед написанием этого
Definition of Ready (не предполагается).

**Единственный реально доступный SaaiOS-слот -- A; слот B закрыт
политикой.** Подтверждено `docs/os/targets/panther/README.md`: SaaiOS
установлена и проверена только в слоте A (`init_boot_a` +
`vendor_boot_a`), слот A отмечен загрузчиком успешным. Слот B хранит
штатный Android (`CP2A.260705.006`) как аварийный возврат и явно
закрыт для использования SaaiOS до отдельного, специально
подтверждённого этапа после готовности внешнего factory recovery,
которого сегодня не существует. Следствие: настоящее аппаратное A/B
двух-SaaiOS-слотовое переключение физически невозможно проверить в
рамках этого документа без нарушения уже принятой owner policy --
Acceptance criteria этого документа сформулированы вокруг единственного
доступного слота, не двух.

**В SaaiOS нет ни одного пути писать раздел изнутри себя.** Проверено
напрямую на устройстве этой сессией: `/dev/block/by-name/` не
существует (`ls: No such file or directory`) -- native PID1
(`native-init.c`) никогда не создаёт GPT-based символьные ссылки на
разделы, в отличие от штатного Android `init`/`fs_mgr`. `/proc/
partitions` показывает только сырые числовые узлы (`sda1`..`sda31`,
`sdb1`..`sdb10`, `sdc*`, `sdd*`) без привязки к имени раздела. Ни в
одном файле репозитория (`.c`/`.rs`) нет кода, парсящего GPT или
пишущего в произвольный раздел изнутри работающей SaaiOS. Все образы
за весь проект (S01-S11) устанавливались исключительно через `fastboot
flash`/`--set-active` с хоста, пока телефон в bootloader-режиме -- ни
разу автономно, изнутри работающей системы.

**Реальный `boot_slot` уже физически подтверждён читаемым.**
`androidboot.slot_suffix = "_a"` подтверждён напрямую в `/proc/
bootconfig` этого запущенного устройства этой сессией (не в `/proc/
cmdline`, где параметра нет) -- совпадает с тем, что `crates/
system-tools/src/lib.rs::boot_slot_from` уже проверяет оба источника.
Это единственный уже интегрированный, живой источник A/B-состояния.

**`ab_status.rs` -- нерелевантный, неподключённый код.**
`services/saaios-runtime/src/ab_status.rs` реализует статус-модуль над
вымышленной директорией `/var/lib/saaios/ab` (`A`/`B`, `current`-
симлинк, `BOOT_OK`-маркер) -- никак не связан с реальным
bootloader-уровневым механизмом этого устройства; на телефоне
`SAAIOS_AB_ROOT` не задан, `read_ab_status` возвращает `enabled:
false`. Решение (уже намеченное в S11's DoR, подтверждается здесь):
признаётся нерелевантным реальным слотам, не адаптируется -- OTA
использует `androidboot.slot_suffix`/GPT-факты напрямую, не этот
модуль.

**Нет ни одной существующей крипто-подписи в проекте.** `grep` по всем
`Cargo.toml` и исходникам на `ed25519`/`dalek`/`ring =`/`rsa =`/
`Signature` -- ноль совпадений (уже проверено при написании S11's DoR,
подтверждено повторно здесь). Манифесты приложений (S05/S07) явно не
подписаны ("пока только доверенные приложения"). Схема подписи
manifest/artifact для OTA -- полностью новая работа, без готового
прецедента для переиспользования.

**Download-клиент уже есть, свободное место для staging достаточно.**
`busybox` на устройстве включает applet `wget` (подтверждено `busybox
2>&1 | grep -i wget` на реальном телефоне). `/data` (`saaios-data`,
F2FS) -- 109.9 ГБ, занято ~1 ГБ, 108.9 ГБ свободно -- достаточно для
staged-загрузки любого реалистичного полного системного artifact.
`/metadata` -- всего 62 МБ, занято 70% (18.5 МБ свободно) -- слишком
мал для staging, годится только под маленькие boot/update-state
файлы, как и сегодня.

**Существующая дисциплина хешей -- задел, не замена подписи.**
`DEVELOPMENT_PROCESS.md` уже требует SHA-256 + commit для каждого
установленного образа (используется весь проект, S01-S11) -- это
integrity/provenance-запись, а не аутентификация; сама по себе не
защищает от подмены artifact на пути доставки, только позволяет
заметить несовпадение после факта. Подпись (Change 2) добавляет именно
это недостающее свойство.

**Bootloader уже физически реализует часть A/B-механики независимо от
SaaiOS.** `fastboot --set-active=a/b` уже использовался весь проект и
физически переключает активный слот на уровне GPT-атрибутов
бутлоадера -- отдельный от Android/SaaiOS механизм, встроенный в сам
bootloader этого Pixel. Взаимодействует ли native init хоть как-то с
bootloader-уровневым tries-remaining/successful-битом (аналог
Android's `markBootSuccessful()`) -- неизвестно, не проверялось;
открытый вопрос для Change 1's спайка, не предполагается здесь.

## Scope

- входит:
  - Change 1 (спайк, обязателен первым): установить, как SaaiOS
    физически пишет раздел на этом устройстве -- ADR по итогам. Два
    кандидата на исследование без предрешения: (а) нативный
    GPT-резолвер partition-by-name + прямая запись поверх `sdaN`-узла
    изнутри нового компонента (например `saai-updated`) -- полностью
    автономный OTA, но новый, рискованный, ранее не существовавший
    код рядом с загрузочными разделами; (б) переиспользование уже
    проверенного `fastboot`-пути -- staged/verified часть работает
    автономно на устройстве, а сама запись раздела продолжает
    требовать управляемого reboot-to-bootloader и хоста/companion-
    процесса с `fastboot flash`, то есть не полностью autonomous OTA.
    Спайк только читает разделы (GPT-заголовок/записи с диска) для
    проверки, что атрибуты вообще интерпретируемы из Linux userspace
    без vendor-инструментов -- ничего не пишет на этом шаге;
  - Change 2: схема подписи manifest + artifact (вероятно ed25519 --
    лёгкий, чистый Rust, без OpenSSL на устройстве) и формат versioned
    manifest (device model/hardware id, версия, min-version для
    anti-downgrade, список разделов с SHA-256 и размером, подпись
    поверх всего). Полностью host-testable: fixture-файлы (валидная
    подпись, испорченная подпись, повреждённый artifact, чужая модель
    устройства, downgrade) проверяются без единого изменения на
    телефоне;
  - Change 3: staged verified download на устройстве -- реальный
    (тестовый) manifest+artifact через уже работающий `busybox wget`
    по USB-NCM (тем же паттерном, что `serve-deploy.ps1` в S11) в
    `/data/saaios/update-staging`; полная проверка размера, SHA-256 и
    подписи до какого-либо шага, трогающего раздел. Негативные
    сценарии физически на устройстве: прерванная загрузка, повреждённый
    файл, неверная подпись, чужая модель, запрещённый downgrade --
    каждый явно отвергается, ничего не пишется мимо staging-каталога;
  - Change 4: сама запись, по механизму, выбранному в Change 1 --
    честно ограничена единственным доступным SaaiOS-слотом (слот B
    закрыт политикой, см. Current state). Проверяется как safe
    in-place update с откатом на резервную копию текущего образа как
    rollback-путём, не как настоящий cross-slot A/B failover -- это
    явно не то же самое, и Acceptance criteria не подразумевают
    обратного;
  - Change 5: health confirmation после обновления (core-сервисы
    подняты и отвечают в пределах бюджета из S11/ADR-040, без crash
    loop) + ограниченный счётчик boot attempts + автоматический откат
    при провале health-check, физически продемонстрирован через
    намеренно нездоровую тестовую сборку.
- не входит: переход от сохранённого Android в слоте B к второму
  SaaiOS-слоту (отдельный, специально подтверждённый этап после
  готовности внешнего factory recovery -- ни один из них не существует
  сегодня); настоящий cross-slot A/B hardware failover (недостижим без
  входа выше); UI для запуска/показа прогресса обновления (может
  понадобиться позже отдельным изменением, не блокирует эту сервисную
  инфраструктуру); доставка обновления по сети, отличной от уже
  проверенного USB-NCM (Wi-Fi-доставка -- будущая работа).

## Change

1. Спайк: механизм записи раздела -- ADR (партиционный резолвер vs
   fastboot-путь), только чтение GPT на устройстве, ничего не пишется.
2. Подпись + versioned manifest, полностью host-testable.
3. Staged verified download на устройстве в `/data`, никаких
   изменений разделов.
4. Запись обновления в единственный доступный SaaiOS-слот (A) с
   backup/restore как rollback-путём -- честно не cross-slot failover.
5. Health confirmation + boot attempt limit + автоматический откат,
   физически продемонстрирован на намеренно нездоровой сборке.

## Acceptance criteria

- манифест и artifact без валидной подписи отвергаются до какой-либо
  записи раздела -- подтверждено негативным тестом;
- запрещённый downgrade и artifact для другой модели устройства
  отвергаются -- подтверждено;
- прерванная или повреждённая staged-загрузка не доходит до записи
  раздела -- подтверждено физически на устройстве;
- запись обновления не портит активный загружаемый слот при отказе на
  любом шаге -- подтверждено через backup/restore drill (не через
  cross-slot failover, см. Scope);
- после обновления намеренно нездоровой тестовой сборкой срабатывает
  ограниченный boot attempt limit и автоматический откат на последний
  физически подтверждённый рабочий образ -- подтверждено физически;
- обновлённый образ переживает настоящий cold reboot -- подтверждено;
- честно зафиксировано и не выдаётся за большее: переход слота B и
  настоящий cross-slot A/B hardware failover не проверялись и не
  входили в этот спринт.

## Threat / privacy impact

- новая полномочная поверхность: компонент, способный писать в
  загрузочный раздел -- максимальный blast radius в проекте на
  сегодня; каждый шаг Change 1 и Change 4 требует явного согласия
  пользователя перед первой реальной попыткой, тем же паттерном, что
  S11's suspend-спайк;
- приватный ключ подписи никогда не хранится на устройстве и не
  коммитится в git -- только публичный ключ верификации встраивается
  в образ; сам приватный ключ -- на R620 либо отдельном офлайн-
  хранилище, вне скоупа кода этого спринта, но явно фиксируется как
  требование до первого реального подписанного релиза;
- staged download использует уже изолированный USB-NCM-канал (S01,
  `saaios-runtime` слушает только на USB-интерфейсе) -- не открывает
  новую сетевую поверхность;
- телеметрия обновления (что скачано, когда, успех/откат) -- без
  пользовательского контента, тем же принципом, что уже действующий
  audit log (S10).

## Rollback

- до Change 4: ни один Change не меняет ни один установленный раздел
  устройства -- откат не требуется, сегодняшний `fastboot`-путь
  остаётся рабочим без изменений;
- после Change 4/5: последний физически подтверждённый рабочий образ
  слота A, сохранённый как backup до записи; ручной `fastboot flash` с
  хоста остаётся рабочим fallback независимо от состояния нового кода.
