## Goal

Строка намерения (Intent) создаёт наблюдаемый, переживающий перезапуск
рабочий процесс (Task -> Action -> Result) с audit trail, а не только
разовый чатовый запрос.

## Current state

Проверенные факты (прочитан код, не предположения):

- **Text input отсутствует в native UI вообще.** `saai-shell`'s
  `main.rs:425` явно ставит `KeyboardInteractivity::None`
  ("No pointer/keyboard handling -- this is a touchscreen-only", строка
  867) -- нет ни одного экрана ввода текста нигде в текущем native
  UI. `saai-displayd` не подключает `wl_keyboard` вообще (ADR-012,
  физическое отсутствие клавиатуры на устройстве). Отдельно, для
  сторонних Wayland-клиентов (не `saai-shell`), ADR-022 физически
  доказал, что полноценный `input-method-v2`/OSK-путь через
  `libxkbcommon` крашится на этом устройстве при попытке скомпилировать
  ЛЮБОЙ keymap (7 независимых вариантов, включая полностью
  self-contained) -- это НЕ актуально напрямую для `saai-shell` (первое
  лицо, не третья сторона через generic Wayland-протокол), но
  подтверждает, что общий xkbcommon-путь на этом железе в принципе
  недоступен, значит любая клавиатура для ввода Intent должна обойтись
  без `libxkbcommon`/`zwp_input_method_manager_v2` целиком. Прецедент:
  `drm-splash.c` уже реализует touch-hit-test поверх собственной
  растровой раскладки для своего legacy UI, без единого обращения к
  xkbcommon -- рабочий пример того же класса решения для `saai-shell`.
- **Нет модели `Intent`/`Task`/`Action`/`Result` нигде в репозитории
  (решено ADR-030: новые `entity_type` в `saai-entity-store`, не новая
  инфраструктура).** `saai-entity-store` (S06) знает `Space`/`Entity`/
  `Event`, но `Entity.entity_type: String` уже универсальна (dotted-
  token, произвольные `properties: Map<String, Value>` до 64 КБ) --
  workflow-состояние (`pending`/`running`/`waiting_confirmation`/
  `done`/`failed`/`cancelled`) и идемпотентность (через `revision`,
  уже встроенный optimistic-concurrency механизм) укладываются в эту
  схему без изменений самого store.
- **Platform Track (`crates/`, ADR-001/ADR-004) прочитан на уровне
  кода, не только API -- переиспользование физически не работает
  (ADR-030).** `crates/policy-engine/src/lib.rs`: `session_allows` --
  `Mutex<HashSet<String>>` в памяти процесса, обнуляется при рестарте.
  `PendingConfirmation` -- обычная struct, создаётся как локальная
  переменная внутри `ai-runtime`'s `handle_user_text_inner`
  (`crates/ai-runtime/src/lib.rs:336`) и живёт ровно в рамках одного
  tokio-таска одного запроса -- НИЧЕГО не персистентно, ни между
  запросами одного процесса, ни тем более через рестарт. S09's
  Acceptance ("переживает холодную перезагрузку") физически
  невыполнимо на этом фундаменте без переписывания `policy-engine`/
  `ai-runtime` под персистентную модель -- переиспользование не
  экономит работу. `automation-engine` (`TriggerKind`/`AutomationRule`)
  ближе к S10's Scope, не к S09 напрямую. Подтверждено также: ни один
  native OS Track сервис не зависит от `protocol`-крейта (`grep` по
  всем `Cargo.toml`) -- два рантайма сегодня физически не делят ни
  строчки кода. ADR-004's "Platform later consumes OS services through
  the same tool/policy/event APIs it already has" остаётся названным
  направлением, сознательно не реализуемым в S09 (ADR-030).
- **S06 уже физически доказало, что "не переиспользовать Platform
  Track напрямую" -- рабочий, не гипотетический паттерн; ADR-030
  повторяет тот же прецедент.** S06-doc's собственное Current state
  отдельно отметило: "memory-store и audit-log существуют отдельно, но
  не имеют `space_id` и не являются entity store" -- и S06 построило
  `saai-entityd` заново, native, а не расширило `memory-store`/
  `audit-log`. Та же дилемма теперь решена тем же способом для
  `policy-engine`/`tool-registry`/`automation-engine`.
- **ADR-020's capability vocabulary (S07) статичен и приложение-
  ориентирован** (`SpaceEntitiesRead/Write`, `NetInternet`,
  `ClipboardRead/Write`, `PortalOpenFile`) -- ни одна capability не
  описывает "выполнить произвольное системное действие от имени
  намерения", это отдельный, не пересекающийся риск-профиль.

## Scope

**Входит (Change 1 -- обязательно первым, спайк + ADR, без исключений):**

- Решить и физически подтвердить: как вообще вводится текст Intent на
  этом устройстве. Кандидат A -- собственная, bespoke, touch-hit-test
  экранная клавиатура внутри `saai-shell` (тот же класс решения, что
  `drm-splash.c`, БЕЗ `libxkbcommon`/`zwp_input_method_manager_v2`
  целиком, посимвольная UTF-8 сборка строки на стороне `saai-shell`,
  не generic Wayland text-input протокол). Кандидат B -- голосовой ввод
  (нет ни единой существующей зависимости/спайка под это в репозитории
  -- если это кандидат, весь путь STT нужно исследовать с нуля, что,
  скорее всего, выводит его за пределы разумного объёма одного Change).
  Результат -- ADR с физическим доказательством выбранного пути
  (реальный тап по реальной раскладке возвращает реальную строку в
  `saai-shell`'s коде, подтверждено на устройстве, не в теории).
- ~~Решить и задокументировать ADR-ом: `Intent`/`Task`/`Action`/
  `Result`~~ -- **решено, ADR-030**: новые `entity_type` значения
  (`saaios.intent`, `saaios.task`, `saaios.action`) поверх уже
  существующей `saai-entity-store`'s схемы (S06), НЕ отдельный новый
  store/daemon. Platform Track's `policy-engine`/`tool-registry` НЕ
  портируются и не переиспользуются как библиотека (физически не
  персистентны, см. Current state) -- native OS Track строит
  независимый эквивалент, как уже сделал S06 для `memory-store`/
  `audit-log`, оставляя ADR-004's конвергенцию будущей, отдельной
  задачей.
- ~~Минимальный вертикальный срез ПОСЛЕ Change 1's решений~~ --
  **сделано и физически подтверждено, ADR-031 (Change 2)**: одна
  Intent строка -> один Task с одним неопасным Action -> Result,
  видимый в `Сейчас` через уже существующий S06 UI-паттерн
  (`selected_entities` -- самая недавно обновлённая сущность выбранного
  пространства). Новый native-демон `services/saai-taskd` (реактивный
  по `Subscribe`, идемпотентный по `intent_id`, НЕ добавлен в
  `native-init.c`) + реальная on-screen клавиатура в `saai-shell`
  (закоммиченная версия ADR-029's спайка). НЕ полный workflow каталог,
  НЕ `Входящие`-экран -- это по-прежнему отдельный, больший Change.

**Не входит:** planner/AI-generated планы (S10), automation/триггеры/
schedules (S10, уже частично покрыто `automation-engine`), любое
действие, требующее сетевого доступа или изменения других пространств
(остаётся под S07's уже существующей capability-моделью без
расширения), голосовой ввод (если Change 1 не выберет его явно),
полная интеграция с Platform Track's `saaios-runtime` (ADR-004's
конвергенция -- отдельная, не эта, задача, если Change 1 её не выберет
явно первым шагом).

## Test

- host: unit-тесты новой Intent/Task/Action схемы (invalid state
  transitions, idempotency -- повтор одного и того же Intent/event не
  повторяет уже совершённое необратимое действие) -- без телефона, по
  аналогии с S06's schema tests;
- host: negative -- Task, ожидающий подтверждения опасного Action, не
  исполняет его без явного подтверждения; отменённый Task не
  продолжает выполняться после отмены;
- device: физический тап по экранной клавиатуре (если это выбор
  Change 1) собирает реальную строку, видимую в `saai-shell`;
- device: cold-reboot -- Task в состоянии "ожидает подтверждения"
  переживает холодную перезагрузку и не исполняется автоматически при
  старте (тот же класс инварианта, что S07's grants-persistence).

## Acceptance criteria

- пользователь физически может ввести текстовую строку намерения на
  реальном устройстве (не в теории, не через serial-консоль дебаг-путь);
- сценарий создаётся, приостанавливается на подтверждении опасного
  Action, подтверждается, возобновляется после холодной перезагрузки и
  оставляет связный audit trail;
- повтор одного и того же события/команды не повторяет необратимое
  действие (идемпотентность физически проверена, не только по коду);
- Task/Action виден в `Сейчас` в реальном времени на реальном touch UI.

## Threat / privacy impact

Task/Action -- первый механизм в native OS Track, способный выполнять
произвольное действие от имени пользователя без прямого touch-жеста в
момент исполнения (Task может возобновиться после reboot без нового
явного тапа) -- принципиально другой риск-профиль, чем S07's per-app
capability grants (которые всегда требуют живого touch consent-экрана).
Опасные Action обязаны требовать явного, вновь запрошенного
подтверждения при каждом возобновлении после reboot, не кэшированного
"да" из предыдущей сессии -- иначе это тихо обходит S07's весь
consent-паттерн новым путём.

## Rollback

Не устанавливать/не включать Intent/Task/Action целиком -- `saai-shell`
и весь S05-S08 путь работают без единого изменения (ничего в Scope не
трогает существующий touch/app-lifecycle код, кроме Change 1's
экранной клавиатуры, которая сама по себе аддитивна -- новый UI-экран,
не замена существующего).
