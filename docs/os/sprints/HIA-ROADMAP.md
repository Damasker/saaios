# HIA Roadmap: от текущего SaaiOS к Human Interface Architecture v2

## Статус документа

Одноустройственный HIA-трек выполнен с оговорками, записанными ниже. Визуальное
доведение этих сущностей и собственного набора компонентов продолжается в
[Visual System delivery roadmap](VISUAL-ROADMAP.md); этот документ остаётся
историей архитектурных инициатив и зависимостей. Источник идей --
[Human Interface Architecture v2](../architecture/human-interface-architecture-v2.md)
(HIA/PCE-инициативы из разделов 69 и 115 того документа). Этот файл
берёт тот список и заново расставляет приоритеты под то, что у нас
реально есть: **одно физическое устройство** (Pixel 7), никакого
второго узла, никакого голоса, никакого Orb -- и переупорядочивает
всё под тот же принцип, что уже провёл проект через S00-S32:
ADR-first, физически проверяемый вертикальный результат, не больше
двух недель на спринт (`docs/os/DEVELOPMENT_PROCESS.md`).

Это НЕ обещание, что все 45 инициатив документа будут сделаны. Это
честная перестановка: что можно начать прямо сейчас на одном
телефоне, что требует голоса/распознавания речи (тяжёлая, отдельная
задача), и что физически не может даже начаться, пока не появится
второй доверенный вычислительный узел (весь PCE-трек).

## Как читать таблицы

Каждая строка -- кандидат в спринт, не сам спринт. Перед тем как
войти в `docs/os/sprints/README.md`'s основной трек, каждая строка
должна пройти Definition of Ready: одна цель, исходное состояние,
критерии приёмки с негативным сценарием, способ проверки без
телефона где возможно, откат, риски, ADR или явная пометка, что
нового архитектурного решения не требуется. Ссылка в колонке "HIA"
указывает на исходный раздел документа-источника.

## Фаза 0: уже фактически сделано или почти сделано

Часть словаря HIA уже существует в SaaiOS под другими именами --
не нужно "открывать" эти инициативы заново, только честно связать их
с документом-источником.

| HIA | Что уже есть | Где |
|---|---|---|
| HIA-09 Capability-driven UI | Полная capability/consent модель, UI появляется только при наличии granted capability | ADR-020, S07 |
| (частично) HIA-01 Space Graph | Пространства существуют как сущности, entity ↔ space many-to-many через `saai-entityd` | S06 |
| (частично) HIA-19 Offline/degraded | Проект уже offline-first по построению -- ни один системный путь не требует облака | S00-S32 в целом |

## Фаза 1: фундамент на одном устройстве

Ничего здесь не требует голоса, второго узла или нового железа --
только расширение уже работающего `saai-entityd`/`saai-shell`.
Порядок важен: ContextFrame (HIA-02) нужен Context Light (HIA-03) и
Object View (HIA-07) выигрывает от реального Space Graph (HIA-01).

### HIA-01: Space Graph v2

- **Статус**: Done (первая итерация), ADR-086, 2026-09-15. Реализовано
  и проверено вживую: lifecycle (temporary/emerging/stable/archived)
  как `saaios.space-lifecycle`-сущность в системном пространстве,
  жест "тап по уже выбранной карточке" циклит его, карточка
  показывает метку. Связи (`saaios.space-relation`) -- только чтение
  и отображение (`space_relation_targets()`), создание связей UI не
  имеет -- честно отложено, см. ADR-086 "Последствия". Lifecycle пока
  не влияет ни на одно наблюдаемое поведение кроме собственной
  метки (исходный критерий "temporary не показывается в общем списке
  дольше суток без активности" и негативный сценарий с `archived` и
  Intent/Task pipeline -- НЕ реализованы и не проверялись, остаются
  открытыми, если/когда к HIA-01 вернутся ещё раз).
- **SOM (ADR-118)**: canonical future для entity↔space many-to-many —
  `saaios.in-space` Relationship, не `Entity.space_id`. Legacy
  `saaios.space-relation` читается как раньше. Экран «Пространства»
  показывает union physical `list_entities` + semantic members
  (`list_space_members`); карточка не переезжает между разделами.
- **OAM (ADR-119)**: semantic verbs over SOM objects — `ObjectActionSpec`
  binds to existing `ToolSpec`/`PolicyEngine`/`saaios.action`. Не
  переиспользует слово capability. Первый crate без Object View.
- **IRAB (ADR-120)**: Intent фиксирует focused `ObjectRef` в момент
  submit. Orb не владеет NLU. Детерминированный resolver обходит
  модель для explicit/pronoun inspect; `diagnose` — fallback.
- **WSV2 (ADR-121)**: не новый HIA sprint. Work Scheduler остаётся
  `saai-taskd`; DAG/ready/verification — [WORK-ROADMAP.md](WORK-ROADMAP.md).
  Сейчас/Orb не становятся scheduler dashboard. Phone UI — WORK-08.
- **UI v1 destination**: принятые концепт-борды
  [product-visual-target-v1.md](../ui/product-visual-target-v1.md)
  (`Сейчас` / `Пространство` / `Объект` / `Намерение` / `Система` + Orb).
  Это конечная точка первой версии интерфейса, не текущий Pixel screenshot.
- **World Model (ADR-122)**: Observation/freshness, не Health=`Stale`.
  `saai-deviced` — WORLD-03. Сейчас не рисуем выдуманное «всё Healthy».
- **Attention (ADR-123)**: derived projection, не Entity. Не новый HIA
  sprint. NOW/Inbox/Orb позже читают один resolver; Visual grammar Orb
  (ADR-116) не меняется.
- **UAM (ADR-124)**: единый язык authority. Confirmation — evidence, не
  бессрочный grant. SSH остаётся admin channel. Pixel — AUTH-10.
- **MLP (ADR-125)**: память остаётся Platform `memory-store`. Не SOM
  entity. Compact key = `(space_id, key)`. Модель не объявляет факты.
  Learning — после scoped typed memory. Pixel — MEM-10.
- **Goal**: пространства образуют граф (parent_of/related_to/
  contains/usually_with/exclusive_with), не плоский список; у
  каждого пространства есть lifecycle (temporary/emerging/stable/
  archived).
- **Текущее состояние**: `saaios.space` -- плоская сущность без
  связей и lifecycle; список на "Пространства" statичен, создаётся
  вручную.
- **Приёмка**: новый `entity_type` для связи между двумя
  пространствами (или properties-поле на самой space-сущности,
  решить при спайке); UI на "Пространства" показывает хотя бы одну
  связь визуально; lifecycle влияет хотя бы на одно наблюдаемое
  поведение (например `temporary` не показывается в общем списке
  дольше суток без активности). Негативный сценарий: пространство
  без единой связи/с lifecycle `archived` не ломает существующий
  Intent/Task pipeline (S09).
- **Host-тестируемо**: да, entity graph логика не требует телефона.
- **Rollback**: новый entity_type/свойство, старые пространства без
  него продолжают работать как раньше.
- **ADR**: нужен -- решение о форме связи (отдельные relation-
  сущности vs properties-массив) дорого менять позже.

### HIA-02: ContextFrame Engine

- **Статус**: Done (первая итерация), ADR-087, 2026-09-15. Реализовано
  и проверено вживую: `ContextFrameEntry{space_id, confidence,
  source}`, два реальных источника (`Manual` -- тап, `Wifi` --
  подключение к сети, сопоставленной через `saaios.space-signal`),
  автопереключение через тот же `select_space()`, что и ручной тап.
  Негативный сценарий подтверждён вживую: потеря Wi-Fi-сигнала
  откатывает на последний ручной выбор, не оставляет пусто.
  Bluetooth как второй физический источник НЕ реализован (нет
  фонового демона для тихого опроса присутствия -- `bt-scan` сам
  блокируется на ~8с) -- честно отложено, см. ADR-087 "Последствия".
  Создание `saaios.space-signal` не имеет UI -- тот же паттерн,
  что ADR-086 оставила для `saaios.space-relation`.
- **Goal**: несколько активных пространств одновременно, каждое со
  своей confidence/source/timestamp, вместо одного
  `selected_space_id`.
- **Текущее состояние**: `saai-shell`'s `selected_space_id: String`
  -- ровно одно активное пространство, переключается вручную.
- **Приёмка**: `ContextFrame` как новый внутренний тип (не
  обязательно entity) с списком `(space_id, confidence, source)`;
  минимум два реальных источника активации -- `manual` (тап) и один
  физический (Wi-Fi SSID уже реально сканируется с S19, Bluetooth
  устройство уже реально обнаруживается с S20 -- оба готовые,
  проверенные сигналы, не гипотеза). Негативный сценарий: потеря
  Wi-Fi/Bluetooth сигнала не оставляет ContextFrame пустым молча --
  откатывается на `manual`/последнее известное.
- **Host-тестируемо**: логика активации -- да; реальное
  срабатывание от Wi-Fi/BT -- только на устройстве.
- **Rollback**: `selected_space_id` может остаться производным полем
  (top-confidence запись ContextFrame) -- ничто, что уже читает его,
  не ломается.
- **ADR**: нужен -- это меняет фундаментальную модель "текущего
  контекста" для всего остального проекта.

### HIA-03: Context Light

- **Статус**: Done, 2026-09-15 (без отдельного ADR -- как и
  предполагалось ниже, прямое расширение `draw_status_bar`/S13).
  Реализовано и проверено вживую: цвет хранится как
  `saaios.space-color`-сущность в системном пространстве (тот же
  паттерн, что `saaios.space-lifecycle`/`saaios.space-color`),
  меняется тапом по новой карточке "Цвет пространства" на "Я"
  (6-значный фиксированный цикл: Обычный/Синий/Зелёный/Оранжевый/
  Фиолетовый/Розовый, та же форма, что `SpaceLifecycle`). Квадратик
  цвета рисуется в статус-баре слева от времени, ДО проверки
  `fonts.is_some()` -- виден даже если системный шрифт не загрузился.
  Негативный сценарий подтверждён тестом и вживую: пространство без
  записи получает `SpaceColor::Default` (обычный бирюзовый `ACCENT`),
  не пустоту и не краш.
- **Goal**: цвет пространства как минимальный визуальный сигнал (точка
  в статус-баре), без текстовых баннеров вроде "YOU ARE IN HOME MODE".
- **Текущее состояние**: пространства не имеют цвета вообще; статус-
  бар показывает время/заряд/Wi-Fi-иконку (S13).
- **Приёмка**: у пространства есть цвет (property на сущности,
  пользователь может сменить); точка нужного цвета в статус-баре,
  всегда видна, ничего больше не показывает по умолчанию. Негативный
  сценарий: пространство без явно заданного цвета получает
  детерминированный дефолт (не показывает "пусто"/не крашит рендер).
- **Host-тестируемо**: цветовая логика -- да; рендер на реальном
  экране -- на устройстве.
- **Rollback**: чисто аддитивно, точка просто не рисуется, если
  выключить.
- **ADR**: не нужен -- прямое расширение уже существующего
  статус-бара (S13), не новая архитектура.

### HIA-07: Universal Object View

- **Статус**: Done, ADR-088, 2026-09-15. Реализовано и проверено
  вживую: `Frame::ObjectView` заменил старый task-only `TaskConfirm`
  целиком -- `saaios.task` (шапка/статус/related-намерение/
  Подтвердить-Отклонить) и `saaios.notification` (шапка/статус/
  Скрыть) рендерятся через один и тот же `object_view`/`draw_object_
  view`. Негативный сценарий (незнакомый `entity_type`) покрыт
  тестом: реальный заголовок, непустой статус из properties, без
  действий -- не пусто, не падает.
- **Goal**: один общий "экран объекта" (шапка + состояние + related
  + действия) для любого типа сущности, вместо разрозненных
  списков-строк.
- **Текущее состояние**: сущности показываются только как строки
  списка ("Входящие", "Пространства") -- нет ни одного экрана
  "открыть один конкретный объект целиком".
- **Приёмка**: тап по любой строке "Входящие" открывает Object View
  вместо (или в дополнение к) текущей модалке; минимум два разных
  `entity_type` рендерятся через один и тот же View-код с разным
  содержимым related/actions. Негативный сценарий: неизвестный/новый
  `entity_type` без специальной обработки всё равно открывает
  осмысленный (не пустой, не крашащий) View.
- **Host-тестируемо**: да, layout/hit-test тем же `Node`/`layout()`
  паттерном, что и весь остальной UI этого проекта.
- **Rollback**: старые списочные экраны можно оставить работать
  параллельно до полной уверенности.
- **ADR**: нужен -- это новый переиспользуемый UI-примитив уровня
  `root_view()`/`consent_view()`.

### HIA-08: Surface abstraction (минимальная версия)

- **Статус**: Done, 2026-09-15 (без ADR, как и предполагалось ниже).
  `Surface`/`SurfaceCapabilities` (`touch`, `always_on_display`) +
  `known_surfaces()` -- реестр из одной записи ("Pixel main display",
  `touch: true`, `always_on_display: false`), залогирован один раз
  при старте, нигде не читается обратно и не меняет рендер --
  подтверждено вживую (новая сборка развёрнута без пересборки образа,
  ADR-082, тапы/отклик экрана без изменений). Покрыто тестом
  (`known_surfaces_is_a_registry_of_exactly_one_real_surface`).
- **Goal**: понятие Surface существует в коде как реестр, даже если
  в нём ровно одна запись ("Pixel main display").
- **Текущее состояние**: устройство и экран -- одно и то же
  неявно, нигде не названы раздельно.
- **Приёмка**: тип `Surface` с полем `capabilities`, один
  инстанс, заполненный из уже известных фактов (touch, DRM display).
  Ничего в рендере не должно измениться для пользователя -- это
  чисто внутренний рефакторинг, готовящий место для будущего AOD
  (HIA-15) или второго Surface.
- **Host-тестируемо**: да, чистая структура данных.
- **Rollback**: тривиален, тип просто не используется, если убрать.
- **ADR**: не нужен -- явно помечено как "заготовка", не архитектурное
  решение о будущих Surface.

### HIA-19: Offline/degraded -- ревизия, не код

- **Статус**: Done, ADR-089, 2026-09-15. Прочитаны зависимости и
  прослежены реальные пути вызова всех четырёх сервисов.
  `saai-appd`/`saai-entityd` не имеют сетевого клиента в дереве
  зависимостей вообще. `saai-taskd`'s единственная сетевая
  зависимость (`saaios-runtime` через USB-NCM, ADR-033) уже
  устойчива на уровне демона -- недоступность гасится в `fail_task()`,
  не роняет процесс. `saai-shell` уже честно показывает
  "недоступно"-состояния везде, где сеть касается пользователя
  (Wi-Fi/Bluetooth/entityd-реконнект). Найден один реальный пробел:
  задачи со `status: "failed"` (в т.ч. из-за недоступного
  `saaios-runtime`) нигде не были видны пользователю --
  `inbox_pending_tasks()` фильтрует строго по `waiting_confirmation`.
  Исправлено в тот же день (roadmap разрешал оставить как открытый
  пункт, но чинить дешевле, чем откладывать): `fail_task()`/`fail_
  confirmed_action()` теперь создают `saaios.notification`,
  переиспользуя готовую HIA-07/Object View (ADR-088) без единого
  нового экрана -- физически проверено локальным запуском реального
  `saai-entityd`+`saai-taskd`, см. ADR-089 "Test". Оставшийся
  открытый пункт (тоже из ADR-089): нет индикатора доступности AI на
  экране ввода намерения.
- **Goal**: явно задокументировать, что уже верно (offline-first по
  построению), и найти реальные пробелы, если есть.
- **Текущее состояние**: не проверено целенаправленно, только
  получено "бесплатно" по ходу S00-S32.
- **Приёмка**: один docs-only проход по каждому системному сервису
  (`saai-appd`, `saai-entityd`, `saai-taskd`, `saai-shell`) с
  вопросом "что происходит без сети/без AI" -- зафиксировать в ADR
  или в `docs/os/architecture/system-intelligence.md`. Не код, если
  реальных пробелов не найдено.
- **Host-тестируемо**: да, это анализ, не имплементация.
- **Rollback**: не применимо (docs-only).
- **ADR**: только если найден реальный пробел, требующий решения.

## Фаза 2: Orb -- смена парадигмы интерфейса

Самая рискованная, самая крупная фаза -- фактически переписывание
`saai-shell`'s главного экрана. Требует Фазы 1 (Orb должен отражать
реальные ContextFrame/Space данные, не заглушки). Сознательно
разбито так, чтобы таб-бар и Orb могли **сосуществовать** первый
спринт, а не переключаться одним большим прыжком без пути назад.

### HIA-04a: Orb -- базовое состояние (спайк, coexist с таб-баром)

- **Статус**: Done, ADR-090, 2026-09-15. Throwaway-патч развёрнут
  прямо на боевой `saai-shell` (живёт на `/data`, ADR-082 -- hot-swap
  вместо ADR-029's изоляции/`uinput`), физически подтверждены все три
  факта: квадратик рисуется поверх содержимого, тап по нему пойман и
  залогирован с точным активным `current_page`, тап по другой вкладке
  таб-бара продолжает работать как обычно. Патч отменён (`git
  checkout --`) сразу после проверки -- в репозитории не остался, как
  и предполагала методология.
- **Goal**: физически подтвердить, что точка-манипулятор (Orb) может
  рисоваться и ловить тапы поверх существующего UI этого проекта,
  без замены таб-бара -- та же методология, что ADR-029 уже
  использовала для клавиатуры (throwaway-спайк перед постоянным
  кодом).
- **Текущее состояние**: нет Orb вообще; вся навигация -- таб-бар
  (S04).
- **Приёмка**: `●` рисуется в фиксированной позиции экрана поверх
  "Сейчас" (или любой вкладки), тап регистрируется, лог печатает
  какая вкладка была активна. Throwaway -- не обязан сохраняться в
  репозитории, как и первый спайк клавиатуры.
- **Host-тестируемо**: частично (layout/hit-test), реальный тач --
  только на устройстве.
- **Rollback**: `git checkout --` спайка, как ADR-029.
- **ADR**: да, по итогам спайка -- фиксирует, что Orb физически
  работает поверх существующего рендер-пайплайна, до того как
  строить постоянную версию.

### HIA-04b: Orb -- состояния и жесты (постоянная версия)

- **Статус**: Done, ADR-091, 2026-09-15. `Frame::Orb` с тремя

## Фаза 3: голос и Tiered Intelligence

Самая тяжёлая, наименее определённая фаза -- честно помечена как

шагов", по прецеденту ADR-022 (`libxkbcommon` физически не взлетел

### Спайк (не сам HIA-06): голос на этом железе вообще возможен?

- **Статус**: Done, ADR-092, 2026-09-15. Результат: **физически
  заблокирован**, не теоретически. Capture-PCM-устройства реальны
  (14 штук), mixer-роутинг работает и держит состояние, настоящий
  21 МБ `aoc.bin` корректно симлинкован в `/vendor/firmware`
  (автозагрузка включена) -- но `FW Revision` остаётся `0x0` даже
  после ручного `force_reload` (который сам сработал --
  `restart_count` вырос), и реальный захват на трёх разных
  capture-эндпоинтах (`tinycap`, кросс-скомпилирован из уже
  присутствовавшего `tinyalsa`-дерева) вернул 0 байт аудио на всех
  трёх. Конкретные числа: ~10.03 с задержки на попытку (фиксированный
  таймаут, не зависит от запрошенной длительности), `user 0.00s /
  sys 0.00s` CPU (всё время в блокирующем ожидании). Tier 1
  физически не запущен -- аудио-пайплай не выдаёт данных, обрабатывать
  нечего. Capability-модель (`saai-appd`) не содержит ни одной
  audio-возможности вообще. HIA-06 не начинается -- см. ADR-092
  "Решение" для честного плана следующего реального шага.
- **Углублённое исследование, 2026-09-15** (см. "Обновление" в
  ADR-092): нашёлся точный, окончательный корень. Реальный `aocd`
  (Android-бинарник из `vendor.img`) запущен напрямую на устройстве
  через `linker64`+bionic-библиотеки (без chroot). `dmesg` показал:
  прошивка AoC реально загружается и репортит версию, но `GSA: FW
  authentication failed: -16` -- secure element (класс Titan M)
  отклоняет проверку подлинности подписанного образа. Криптографическая
  граница доверия, не конфигурация -- дальше означало бы обход
  аутентификации прошивки, вне объёма легитимного спайка. HIA-06
  остаётся закрыт с точным, не гипотетическим диагнозом.
- **Goal**: физически проверить, что микрофон доступен из sandbox
  (`capabilities`, ADR-020) и что ХОТЯ БЫ Tier 1 (крошечный локальный
  классификатор активности речи, не полное распознавание) реально
  запускается на Pixel 7 под этой ОС.
- **Приёмка спайка**: да/нет с конкретными числами (задержка,
  использование CPU/батареи) -- не "должно работать в теории".
- **ADR**: обязателен по итогам, независимо от результата (как
  ADR-022 зафиксировала отрицательный результат для клавиатуры).

## Фаза 4: аппаратные пробелы, найденные по ходу проекта

### HIA-15: AOD -- минимальная поверхность

- **Статус**: Done (спайк), ADR-093, 2026-09-15. Результат: **ДА**.
  `/sys/kernel/debug/dri/0/state` в состоянии покоя прямо показал
  `self_refresh_active=1`/`self_refresh_aware=1` на реальной
  Samsung-панели (`sdc-s6e3fc3-p10`) -- generic DRM self-refresh
  helper уже включается автоматически, без единой строчки нового
  кода `saai-displayd`. Найден и конкретный, actionable блокер
  для того, чтобы это держалось в обычной работе: `saai-shell`'s
  `refresh_statusbar_if_due()` безусловно перерисовывает статус-бар
  каждую секунду, а `saai-displayd` компонует всё в один shared
  framebuffer одним `present()` -- значит тиканье часов само по себе
  держит CRTC "активным" вечно. Измерение потребления (fuel gauge,
  ~10 замеров 1 Гц в покое и во время тапов) показало ~2 мА в обоих
  состояниях -- разницы, отличимой от шума, не обнаружено (суммарное
  потребление этой минималистичной ОС уже низкое в обоих случаях).
  Полный AOD UI по-прежнему отдельные спринты, но с известным первым
  реальным шагом (не мешать self-refresh во время блокировки), не
  гипотезой.
- **Follow-up реализован, 2026-09-15** (см. "Обновление" в ADR-093):
  `StatusBarSnapshot`-дедуп в `present_status_bar()` + аналогичный
  дедуп в `apply_appd_message()` для рутинных `appd.list()`-ответов
  (второй, отдельно найденный источник безусловных flip'ов). Живая
  проверка: 209 коммитов статус-бара за 188 мин простоя (≈1/мин,
  вместо ~11000), `self_refresh_active=1` подтверждён. По пути
  уточнилось, что заблокированное состояние уже держало self-refresh
  и без этого фикса -- реальный выигрыш именно в окне "разблокировано,
  но бездействие".
- **Goal**: физически подтвердить, поддерживает ли панель Pixel 7
  low-power self-refresh режим под этим кастомным DRM-стеком
  (`saai-displayd`, ADR-010/011/012) -- документ явно требует
  спайк-сначала для этого класса вопроса.
- **Текущее состояние**: "Change step 5" (см. шапку `saai-shell`'s
  main.rs) уже честно зафиксировала это как известный пробел --
  "экран просто остаётся включённым вместо dim-then-blank" --
  задолго до этого документа.
- **Приёмка**: спайк отвечает да/нет на "может ли панель работать в
  низкопотребляющем режиме под нашим DRM-стеком", с реальным
  измерением потребления. Полный AOD UI (документ раздел 38) --
  отдельные спринты после положительного спайка.
- **ADR**: обязателен по итогам, как и голосовой спайк.

## Фаза 5: Personal Computing Environment -- явно отложено

Всё, что документ называет PCE-01..PCE-25 (раздел 115), требует
**второго физического доверенного вычислительного узла**,
участвующего в рантайме (не просто build-сервера, как home-server
сегодня) -- Resource Scheduler, Capability Leasing, Placement
Policy, всё это бессмысленно спринт-планировать до того, как есть
хотя бы два реальных узла для физической проверки, тот же принцип,
что весь этот проект уже применяет к любому "должно работать в
теории" утверждению.

Список инициатив (для памяти, не для спринт-планирования сейчас):

```text
PCE-01  Device Transparency
PCE-02  Logical Entity Identity
PCE-03  Replica Manager
PCE-04  Content Addressing / Version Model
PCE-05  Personal Fabric Membership
PCE-06  Node Identity / Trust
PCE-07  Capability Advertisement
PCE-08  Capability Leasing
PCE-09  Resource Scheduler
PCE-10  Placement Policy
PCE-11  Data Gravity / Cost Model
PCE-12  Durable Distributed Tasks
PCE-13  Idempotent Actions
PCE-14  Network Partition Semantics
PCE-15  Surface Handoff
PCE-16  Runtime Resolver
PCE-17  Software Entity
PCE-18  Compatibility Knowledge Base
PCE-19  Remote Interactive Execution
PCE-20  Game Streaming Pipeline
PCE-21  Entitlement / Purchase Boundary
PCE-22  Provenance
PCE-23  Backup / Replica Policy
PCE-24  Environment Recovery / Bootstrap
PCE-25  Physical Multi-node Test Lab
```

`PCE-25 Physical Multi-node Test Lab` -- единственный пункт из этого
списка, который вообще МОЖЕТ стать реальным спринтом раньше
остальных, поскольку он не требует, чтобы остальная архитектура уже
существовала -- это просто "физически подключить второй узел и
довести до него сетевую связность", тот же класс работы, что
`file-recv`/SSH (ADR-073/074) уже сделали для build-сервера ↔
телефон. Если/когда появится второй узел -- начинать здесь, не с
Resource Scheduler.

## Итог: следующий реальный шаг

Одноустройственная последовательность HIA-01 → HIA-02 → HIA-03 → HIA-04 и
связанные Object View, offline, accessibility и developer-surface работы
завершены с приведёнными в документе доказательствами и ограничениями.

Следующий исполнимый шаг — **VUI-01: semantic tokens and calibrated palette**
из [Visual System delivery roadmap](VISUAL-ROADMAP.md). Голос остаётся
заблокирован аппаратной авторизацией AoC (ADR-092). PCE не начинается до
появления второго физического runtime-узла; когда он появится, первым шагом
остаётся PCE-25 Physical Multi-node Test Lab.
