# Sprint 11 — Производительность, idle и стабильность ежедневного использования

## Паспорт

- Состояние: `In progress` (2026-09-11, Change 1 закрыт и физически
  подтверждён, ADR-040; Change 2 реализован и частично физически
  подтверждён, но НЕ закрыт по Acceptance -- ADR-041, нужен отдельный
  чистый раунд проверки; Change 3 не начат).
- Зависит от: S01-S10 (все `Done`).
- Архитектурные решения: GPU-ускорение уже закрыто как физически
  нереализуемое на этом железе (ADR-024, S08) -- пункт "GPU только при
  доказанной пользе" из первоначального черновика S11 не требует
  нового решения, только ссылки. Change 1 (ниже) -- обязательный спайк
  для двух вопросов без готового ответа: реалистичные бюджеты
  latency/memory (нет базовых измерений) и физическая
  осуществимость deep idle на этом ядре/железе.
- Рабочий fallback: если Change'и этого спринта не приняты или
  откатываются, весь S01-S10 стек продолжает работать без единого
  изменения -- это спринт об измерении и, где оправдано, экономии
  ресурсов уже работающей системы, не о новой функциональности.

## Goal

SaaiOS становится измеримо стабильной для ежедневного использования на
тестовом Pixel 7: реальные бюджеты latency/памяти для уже
реализованных путей (S01-S10), физически подтверждённые, не
предполагаемые; полная регрессия по всему стеку пройдена одним
раундом; там, где кернел уже это позволяет -- реальная экономия
энергии в простое, а не только сегодняшняя блокировка экрана.

## Current state

Проверено на реальном устройстве и по коду перед написанием этого
Definition of Ready (не предполагается).

**Разделение исходного S11.** Черновик roadmap объединял
performance/idle/GPU-регрессию с полноценным OTA/release gate
(подписанные обновления, staged-запись, автооткат, recovery drill).
Это два независимых, оба крупных вертикальных результата -- OTA
самостоятельно критичен по безопасности и требует инфраструктуры
подписи, которой в репозитории нет вообще (`grep` по всем `Cargo.toml`
на `ed25519`/`Signature`/`rsa` -- ноль совпадений). Оба за один спринт
не помещаются (`DEVELOPMENT_PROCESS.md`'s "не более двух недель, делить
до реализации"). OTA/release gate вынесен в отдельный **S12**, со своим
Definition of Ready позже; этот документ -- только performance/idle/
стабильность.

**GPU уже закрыт.** ADR-024 (S08): проприетарный Mali-блоб собран
только под Android's HAL, открытый `panthor` требует ядро >=6.10 против
GKI-залоченного 6.1.157 устройства. Это не переоценивается здесь --
"GPU только при доказанной пользе" из исходного текста S11
удовлетворяется ссылкой на уже принятое решение, не новым спайком.

**Реальный software-A/B статус-модуль существует, но не подключён к
реальным слотам этого устройства.** `services/saaios-runtime/src/
ab_status.rs` читает `/var/lib/saaios/ab` (переопределимо
`SAAIOS_AB_ROOT`) -- директорию с `A`/`B` поддиректориями, `current`
симлинком и `BOOT_OK`-маркером. Это не тот механизм, которым эта
сессия реально управляла весь спринт (`fastboot flash init_boot_a`/
`--set-active=a` на настоящих bootloader-уровневых слотах). На
реальном устройстве `/var/lib/saaios/ab` не существует --
`read_ab_status` возвращает `enabled: false`. Модуль -- готовый, но
никогда не подключённый к реальному состоянию код; OTA (S12) должен
либо подключить его к настоящим слотам, либо признать нерелевантным --
не предрешается здесь.

**Idle сегодня -- только UI-блокировка, не энергосбережение.**
`saai-shell`'s `IDLE_TIMEOUT` (`services/saai-shell/src/main.rs:117`,
60с) переводит экран на экран блокировки после отсутствия касаний --
UX-механизм (S04), не энергетический. Ничего в native-стеке не
переводит систему в состояние пониженного энергопотребления.

**Кернел физически поддерживает suspend-to-RAM/hibernate, никогда не
использованные.** Проверено напрямую: `/sys/power/state` содержит
`freeze mem disk` -- полный набор системных sleep-состояний ядра
доступен, включая `mem` (suspend-to-RAM). `/sys/power/wake_lock`
существует и пуст -- Android-style wakelock sysfs-интерфейс
присутствует, никем не используется (значит и не блокирует sleep).
Наивные пути cpufreq (`/sys/devices/system/cpu/cpu0/cpufreq/`,
`/sys/devices/system/cpu/cpufreq/`) не показали ничего -- реальный
governor/scaling узел на этом SoC не найден с первой попытки, требует
отдельного исследования, не предполагается. `/sys/class/power_supply/`
содержит `maxfg` (fuel gauge), `usb`, `main-charger`, `gcpm`,
`tcpm-source-psy-i2c-max77759tcpc` -- реальная батарейная/зарядная
телеметрия физически доступна, ничем из native-стека не читается
сегодня.

**Нет никакой perf/idle/soak-оснастки.** `find` по репозиторию на
`*benchmark*`/`*perf*`/`*latency*`/`*soak*` -- ноль файлов. Ни один
путь S01-S10 (cold boot, app launch/switch S05, planner intent
round-trip S10) не имеет зафиксированного числового бюджета --
каждый физически проверялся на факт работы в своём спринте, не на
скорость.

**Данные для замеров частично уже собираются.** `automation-engine`'s
periodic `system.metrics`-опрос (~30с, S10) уже пишет
`cpu_usage`/`mem_used_pct`/`load_average` в audit log
(`/data/saaios/var/runtime/audit.jsonl`) -- готовая, но не
используемая для soak-анализа инфраструктура.

**Текущий baseline** (снят при этом Definition of Ready, uptime ~1.5ч
после обычной загрузки, только системные сервисы, без прикладной
нагрузки): `free` -- 7 619 724 KB всего, 425 460 KB used, 6 939 564 KB
free; 284 записи в `ps`. Не budget, просто точка отсчёта для Change 1.

## Scope

- входит:
  - Change 1 (спайк, обязателен первым): (а) снять реальные замеры
    latency для уже реализованных daily-use путей -- холодная загрузка
    до готового `Сейчас` (не только "userspace ready" из boot.log, а
    именно первый кадр интерактивного shell), запуск/переключение
    demo-приложения (S05), полный planner-цикл Intent -> Result (S10)
    -- без нового кода, только инструментирование уже существующих
    путей; (б) определить, безопасно ли и чем именно входить в `mem`
    (suspend-to-RAM) на этом конкретном ядре/железе -- рискованная
    проверка (см. Threat/privacy impact), требует явного согласия
    перед первой реальной попыткой; по итогам обоих пунктов -- ADR с
    конкретными числовыми бюджетами вместо предположений;
  - Change 2: реализовать и физически подтвердить один реальный
    механизм экономии энергии в простое, вытекающий из находок Change
    1 -- вероятно "экран выключен + `mem`" после продлённого простоя,
    с гарантированным пробуждением по touch/power-button и
    сохранением USB-NCM/serial для продолжения разработки; если
    Change 1 покажет, что `mem` небезопасен на этом железе (не
    просыпается, роняет USB-гаджет необратимо) -- Change 2 сужается до
    задокументированного отказа с обоснованием, не форсируется;
  - Change 3: комбинированный регрессионный проход -- один раунд,
    физически повторяющий ключевые уже написанные проверки S01-S10
    (не переизобретая их) на устройстве после Change 1/2, чтобы поймать
    регрессии от экономии энергии/измерений; 24-часовой soak
    с использованием уже существующего `system.metrics`-опроса,
    анализ audit log на утечки памяти/restart loops.
- не входит: GPU-ускорение (закрыто, ADR-024); OTA/подписанные
  обновления/staged-запись/автооткат/recovery drill (S12); любая новая
  пользовательская функциональность; батарейная телеметрия как часть
  UI (сбор -- да, если дёшево получить в рамках Change 1's замеров;
  экран/виджет -- нет); soak дольше 24 часов.

## Change

1. Baseline-замеры latency/памяти существующих путей + spike
   безопасности `mem`-suspend -> ADR с конкретными бюджетами.
2. Один реальный механизм deep idle (или задокументированный,
   обоснованный отказ), физически подтверждён -- засыпание, пробуждение

3. Комбинированный регрессионный проход S01-S10 + 24-часовой soak на

## Acceptance criteria

- latency/memory-бюджеты для холодной загрузки до `Сейчас`, launch/
  switch приложения и planner-цикла Intent -> Result зафиксированы
  как конкретные числа (не "быстро"/"приемлемо") и физически
  подтверждены минимум тремя независимыми прогонами каждый;
- если Change 2 реализован: реальное снижение энергопотребления в
  простое физически измерено (не предполагается по документации SoC) и
  устройство гарантированно просыпается по каждому из
  touch/power-button без ручного вмешательства (переподключение кабеля,
  холодная перезагрузка) в 10 из 10 циклов;
- если Change 1 покажет `mem`-suspend небезопасным на этом железе --
  явный, обоснованный отказ вместо форсированной реализации тоже
  считается выполненным Acceptance для Change 2;
- комбинированный регрессионный проход не находит ни одной регрессии
  против уже принятых ADR S01-S10 инвариантов;
- 24-часовой soak проходит без незапланированных рестартов процессов и
  без растущего тренда `mem_used_pct` в audit log.

## Threat / privacy impact

Главный новый риск этого спринта -- не конфиденциальность, а
**физическая доступность устройства**. Вход в `mem` (suspend-to-RAM) на
ранее никогда не использованном для этого ядре/железе рискует не
разбудить устройство (известный класс проблем для кастомных Android-
ядер с урезанным userspace -- заводские suspend/resume hooks
(`early_suspend`/genuine PM domains) настроены под сток Android
framework, которого здесь больше нет). Неразбуженное устройство
требует физического вмешательства (кнопка питания, при необходимости
-- переподключение в fastboot и заново через bootloader), не
исправимо программно с этой сессии. Поэтому: первая реальная попытка
`echo mem > /sys/power/state` -- только с явным согласием пользователя
непосредственно перед попыткой, не заранее одним общим разрешением на
весь спринт; при малейшей неопределённости -- не форсировать, перейти
к задокументированному отказу (см. Acceptance).

Данные `system.metrics`/audit log, используемые для soak-анализа, уже
физически подтверждены как не содержащие пользовательского контента
(S07's audit-без-содержимого инвариант) -- этот спринт не меняет их
состав, только частоту анализа.

## Rollback

Change 1 не меняет код устройства -- только замеры и документ. Change
2 (если реализован) -- локализованное изменение (новый вызов
`/sys/power/state` из уже существующей точки простоя, не
архитектурное); откат -- не вызывать `mem`, возврат к сегодняшнему
UI-only lock (`IDLE_TIMEOUT`), без переустановки `init_boot`, если
изменение не потребовало пересборки `native-init.c` (маловероятно --
sleep triggering естественнее всего добавить в `saai-shell`'s уже
существующий idle-check, не в PID 1). Если всё же потребовалась
пересборка `native-init.c` -- тот же rollback-путь, что ADR-035:
пересобрать предыдущий коммит, перепрошить.

## Evidence

**Change 1 закрыт (ADR-040), 2026-09-11.** Реальные замеры на том же
Pixel 7: холодная загрузка (PID1 -> "native userspace ready" по
`dmesg`-timestamp'ам, три независимых `reboot -f`) -- 7.078с / 7.094с
/ 7.104с. Запуск приложения (`appd.launch` IPC round-trip, три
независимых цикла) -- 50мс / 47мс / 43мс -- честно помечено как
spawn-latency, не визуальная готовность. Planner-цикл -- переиспользованы
уже физически снятые в S10 замеры (ADR-034/037/039): 31с / 10.9с / 5.3с
/ 4.1с, заметный разброс от локальной модели. Память сразу после
загрузки -- 258 708 KB used из 7 619 724 KB total.

`mem`-suspend физически проверен с явного согласия пользователя перед
попыткой: полный, чистый цикл `PM: suspend entry (deep)` ->
`PM: suspend exit` (~465мс по `dmesg`), но самопробуждение через ~227мс
из-за Wi-Fi-чипа (`bcmdhd4389`)'s собственного host-wake IRQ -- не
serial-активности хоста. USB-NCM и serial пережили цикл без единого
ручного вмешательства; все пять native-сервисов и память -- в норме
после. Вывод для Change 2: нужно явно усыплять/отключать Wi-Fi перед
входом в `mem`, иначе устройство не удержит простой.

**Change 2 реализован, частично подтверждён физически, НЕ закрыт
(ADR-041), 2026-09-11.** `check_deep_idle()` в `saai-shell`: после
`IDLE_TIMEOUT`-блокировки и дополнительных `deep_idle_timeout` (по
умолчанию 300с, `SAAIOS_DEEP_IDLE_SECS` для тестов) простоя --
`wlan0` вниз, `mem`-suspend, `wlan0` вверх, сброс таймера. 22
host-теста, fmt, clippy чисты. Физическая проверка вскрыла
методологическую ошибку тестирования (запущен дублирующий,
неучтённый экземпляр `saai-shell` для короткого тестового таймаута),
которая реально усыпила боевое устройство дважды подряд без
запланированного согласия на каждую попытку: первый цикл -- 82
реальных секунды (устройство разбудило себя само), второй -- 229
секунд (потребовалось физическое нажатие кнопки питания
пользователем). Оба цикла подтвердили главное -- реальный, устойчивый
(не мгновенно самопробуждающийся) простой действительно достигается
отключением Wi-Fi перед `mem`; все сервисы и память пережили оба
цикла без деградации. Но: `dmesg` показал оба пробуждения через один
и тот же `VGPIO2PMU_EINT`, хотя пользователь нажимал кнопку только
один раз -- источник второго пробуждения не идентифицирован, открытый
вопрос. Touch как wake-источник не тестировался (недоступность
устройства всё это время). Change 2 остаётся `In progress`: нужен
отдельный, чистый, по одному согласованный раунд 10 циклов для
полного Acceptance, а не текущий, случайно образовавшийся результат.
