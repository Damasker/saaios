# Идеи (черновик, не план)

Свободные мысли, возникшие по ходу работы -- ничего отсюда не входит
в roadmap автоматически, только после явного согласия, что сработает
и стоит того.

- Мастер-тумблер "Удалённый доступ" в v1 гасит только новые
  спаривания (pairing), но НЕ отзывает уже одобренные ключи и НЕ
  останавливает сам Dropbear (он просто продолжает слушать порт,
  как любой обычный sshd, без непройденной аутентификации толку
  всё равно ноль). Это сознательное упрощение ради скорости, не
  недосмотр -- см. ADR по этой фиче. Но честно: ADB прячет порт
  вовсе, когда "Отладка по USB" выключена. Можно дотянуть позже:
  native-init.c проверяет файл-флаг и держит/убивает процесс
  dropbear динамически.
- Как только `saai-shell` сам переедет на `/data` (следующий заход,
  ещё не сделано) -- обновления `saai-shell`/`saai-displayd` можно
  будет катить тем же SSH/scp, без единой перепрошивки вообще.
  Тогда единственная причина трогать `fastboot flash` останется --
  сам `native-init.c`/kernel-модули/дровер.
- Список доверенных клиентов сейчас читается прямо из
  `authorized_keys` (comment-поле = имя клиента) -- `saai-shell` не
  хранит отдельную копию списка. Это нарочно (один источник
  правды, тот же принцип, что ADR-030's "no cross-runtime
  dependency"), но если формат когда-то станет сложнее (даты
  последнего входа, IP и т.п.) -- потребуется отдельный JSON рядом.
- Fingerprint ключа в UI сейчас -- не настоящий SHA256, а просто
  обрезанный base64 (нет `sha2` в зависимостях `saai-shell`). Если
  захочется полноценный отпечаток -- добавить `sha2` (уже
  используется в `saai-displayd`, не новая зависимость для проекта
  в целом).
- Нет экрана "доверенные клиенты" со списком/отзывом -- `authorized_
  keys` растёт, но убрать оттуда запись можно сейчас только вручную
  (serial console / SSH). См. roadmap S26.
- Выключение тумблера "Удалённый доступ" не убивает уже запущенный
  Dropbear и не трогает уже одобренные ключи -- см. ADR-074's
  "Последствия". Чтобы дотянуть до полного поведения adb, нужно
  либо динамически стартовать/останавливать Dropbear по флагу
  (native-init.c должен бы следить за файлом-маркером в цикле, не
  только читать его при старте), либо явное действие "Забыть все".
- `saaios-console` выпал из образа при поиске места под Dropbear
  (ADR-074) -- баннер в консоли всё ещё его упоминает. Либо вернуть
  в образ, либо (лучше, по аналогии с `saaios-runtime`) переместить
  на `/data/saaios/system/` и поправить баннер.
- Dropbear сейчас без `sftp-server`/legacy scp -- `scp` с клиента
  не работает. `file-recv` уже закрывает "загрузить на устройство";
  если понадобится "скачать" -- либо это (S31), либо найти/собрать
  минимальный sftp-server.
- Найдено при отладке S28: `sandbox::apply()` безусловно прячет
  `/saaios` целиком от ЛЮБОГО стороннего приложения (`mask_if_
  present` по списку `/metadata`, `/proc`, `/sys`, `/saaios`) -- а
  именно там лежат системные шрифты (`/saaios/fonts/*.ttf`).
  Подтверждено вживую: `saai-mahjong` под песочницей рисует доску
  вообще без текста (только цветные прямоугольники) -- `Fonts::
  load()` тихо проваливается через `.ok()`/`if let Ok`, и код это
  прекрасно переживает, но результат для пользователя честно
  выглядит недоделанным. Это касается КАЖДОГО стороннего
  Wayland-приложения, не только маджонга -- ни одно из них никогда
  не сможет показать текст, пока `/saaios/fonts` не станет читаемым
  внутри песочницы (по аналогии с тем, как `wayland_socket`/
  `portal_socket` уже точечно "пробиваются" сквозь маску `/run`).
