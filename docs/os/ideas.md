# Идеи (черновик, не план)

Свободные мысли, возникшие по ходу работы -- ничего отсюда не входит
в roadmap автоматически, только после явного согласия, что сработает
и стоит того.

- Список доверенных клиентов сейчас читается прямо из
  `authorized_keys` (comment-поле = имя клиента) -- `saai-shell` не
  хранит отдельную копию списка. Это нарочно (один источник
  правды, тот же принцип, что ADR-030's "no cross-runtime
  dependency"), но если формат когда-то станет сложнее (даты
  последнего входа, IP и т.п.) -- потребуется отдельный JSON рядом.
- Выключение тумблера "Удалённый доступ" не трогает уже одобренные
  ключи -- см. `authorized_keys`, для этого есть отдельный экран
  "Доверенные клиенты" (ADR-084). Сам Dropbear теперь реально
  останавливается (ADR-085); "Забыть все" одним действием
  по-прежнему нет, только по одному через тот экран.
- HIA-01 (ADR-086): жизненный цикл пространства можно менять (тап
  по уже выбранной карточке), а связи (`saaios.space-relation`) --
  только читать. Создать связь между двумя пространствами сейчас
  нельзя нигде в UI вообще -- если понадобится, нужен отдельный
  экран/жест для этого.
- `saai-entity-store`'s `entity_type` не разрешает подчёркивания в
  dot-сегментах (только буквы/цифры/одиночный дефис,
  `is_slug()`) -- реально стоило времени на отладку один раз
  (ADR-086). Любой новый `entity_type` в будущем -- дефисы, не
  подчёркивания.
- HIA-02 (ADR-087): как и `saaios.space-relation`, у
  `saaios.space-signal` (связь Wi-Fi SSID <-> пространство) нет UI
  для создания -- сейчас без единой вручную созданной записи
  автопереключение по присутствию просто ничего не делает. Если
  когда-то понадобится реальным пользователям -- нужен отдельный
  экран (например "привязать эту сеть к пространству" прямо со
  списка Wi-Fi сетей, где SSID уже есть под рукой).
- HIA-02: Bluetooth как второй физический источник контекста не
  построен -- у него, в отличие от Wi-Fi/`wpa_supplicant`, нет
  фонового демона, `bt-scan` сам блокируется на ~8с, что не годится
  для тихого периодического опроса присутствия каждые несколько
  секунд. Понадобится либо держать `bt-scan` в режиме непрерывного
  discovery отдельным процессом, либо какой-то другой механизм.
- HIA-03: цвет пространства цикл через карточку "Цвет пространства"
  на "Я", а не прямо на карточке пространства на странице
  "Пространства" (та уже занята жестом жизненного цикла, HIA-01,
  плюс на ней нет места для второй кнопки). Из-за этого карточка
  "Цвет пространства" всегда действует на `selected_space_id` -- если
  открыть "Я" не с того пространства, сменится цвет не того, что
  ожидаешь. Не проверено, насколько это реально мешает.
- HIA-03: всего 6 цветов в фиксированном цикле (включая "Обычный"),
  без настоящего color picker'а -- ни один экран в этом проекте пока
  не даёт выбрать произвольный цвет/значение, только цикл по
  небольшому списку (яркость, громкость, контраст и т.п.). Если
  когда-то понадобится больше гибкости -- отдельная задача.
- HIA-07 (ADR-088): уведомление больше не скрывается прямым тапом
  по строке в "Входящие" -- теперь тап открывает Object View, "Скрыть"
  отдельное действие внутри него (один лишний тап ради единообразия
  с задачами). Не проверялось, насколько это раздражает в реальном
  ежедневном использовании -- если станет заметной проблемой, можно
  вернуть свайп/долгий тап как более быстрый путь для уведомлений
  отдельно.
- HIA-19 (ADR-089): `saai-shell` по-прежнему нигде не знает, доступен
  ли `saaios-runtime` (реальный ИИ, обычно живёт на подключённом по
  USB-NCM хосте, не на самом телефоне) ВООБЩЕ, до отправки
  намерения -- нет статус-индикатора вроде "AI недоступен" на экране
  ввода. (Отдельный пункт про исчезающие без следа провалившиеся
  задачи закрыт тем же ADR-089 -- `fail_task()`/`fail_confirmed_
  action()` теперь создают `saaios.notification`.)
- HIA-05: меню Orb различает "сопряжено ли вообще хоть одно
  Bluetooth-устройство" (`bluetooth_paired_count`, S20) -- не
  "подключено ли оно СЕЙЧАС". Настоящего понятия "живое состояние
  соединения" нигде в проекте нет. Если понадобится точнее -- нужен
  отдельный источник данных, не просто более частый опрос
  существующего.
- HIA-05: меню по-прежнему не читает открытый объект (Object View,
  HIA-07) -- только текущее пространство и Bluetooth. Документ-
  источник (раздел про Orb) предполагает и это тоже; не сделано,
  честный пробел.
- HIA-16: только форма (полая рамка при Attention) реализована из
  трёх альтернатив, что называл документ-источник -- haptic (нет
  доступа к вибромотору нигде в проекте) и подпись-по-запросу
  (текстовая метка состояния Orb) не сделаны. Приёмка требовала
  только одну, но если понадобится больше -- haptic начнётся с поиска
  реального устройства вибрации на Pixel 7 (ничего похожего в этом
  кодовой базе ещё не трогалось).
- HIA-20: экран "Диагностика" показывает только ТЕКУЩИЙ снимок --
  capability-гранты каждого приложения прямо сейчас, не историю
  решений во времени (в проекте вообще нет лога "кто когда что
  разрешил", только итоговое состояние в `apps_grants`). Если
  понадобится настоящий журнал policy-решений -- отдельная задача,
  не то же самое, что этот экран.
- HIA-20: строки экрана "Диагностика" не постраничные и не
  прокручиваемые (как и весь остальной UI -- в проекте нигде нет
  scroll/drag-распознавания). При большом числе установленных
  приложений список может не поместиться на экране -- не проверялось
  на реалистичном количестве приложений, только на 1-2.
- Голос (ADR-092): микрофон физически не захватывает аудио под этой
  ОС -- не аппаратное отсутствие, а незавершённая инициализация AoC
  DSP-прошивки (`FW Revision` остаётся `0x0` даже после ручного
  `force_reload`, хотя сама прошивка и автозагрузка на месте).
  Реальный следующий шаг для будущего возврата -- не дальнейшее
  тыканье в `tinymix` (уже упёрлось в потолок за этот спайк), а
  либо реверс-инжиниринг настоящей init-последовательности AoC из
  stock Android audio HAL для gs201/Tensor (вне этого репозитория),
  либо физическая проверка через полную перезагрузку с немедленным
  чтением `dmesg` в момент boot-time зонда драйвера `aoc`/`aoc_core`
  (не сделано в этом спайке -- буфер `dmesg` не достаёт до момента
  последней реальной загрузки устройства).
- AOD/self-refresh (ADR-093, РЕШЕНО): первый шаг реализован --
  `present_status_bar()` теперь сравнивает `StatusBarSnapshot` и
  пропускает рендер+commit, когда контент не изменился, а
  `apply_appd_message()` больше не считает рутинный раз-в-секунду
  `appd.list()`-ответ за "изменение" по умолчанию. Живой тест: 209
  коммитов статус-бара за 188 минут простоя (≈1/мин, совпадает с
  минутной точностью часов) вместо ~11000, `self_refresh_active=1`
  подтверждён. Уточнение диагноза по пути: заблокированный экран уже
  держал self-refresh и без этого фикса (`affects_scene`-фильтр в
  `saai-displayd` и так исключает коммиты статус-бара, пока
  заблокировано) -- реальный пробел был именно в окне "разблокировано,
  но бездействие" (до авто-блокировки), плюс отдельный источник
  безусловных flip'ов нашёлся не в статус-баре, а в `appd.list()`'s
  polling главного toplevel-окна. Полный AOD UI по-прежнему отдельные
  спринты, но с известным низким-уровневым фундаментом, не гипотезой.
- `saaios-console` выпал из образа при поиске места под Dropbear
  (ADR-074) -- баннер в консоли всё ещё его упоминает. Либо вернуть
  в образ, либо (лучше, по аналогии с `saaios-runtime`) переместить
  на `/data/saaios/system/` и поправить баннер.
- Dropbear сейчас без `sftp-server`/legacy scp -- `scp` с клиента
  по-прежнему не работает. `file-recv`'s `GET` (S31, ADR-080) закрыл
  практическую нужду "скачать файл с устройства" отдельным простым
  протоколом; настоящий scp/sftp остаётся отдельным, не сделанным
  пунктом, если он когда-то понадобится сам по себе (например ради
  совместимости со сторонними GUI SFTP-клиентами).
