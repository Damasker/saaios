# Идеи (черновик, не план)

Свободные мысли, возникшие по ходу работы -- ничего отсюда не входит
в roadmap автоматически, только после явного согласия, что сработает
и стоит того.

- Список доверенных клиентов сейчас читается прямо из
  `authorized_keys` (comment-поле = имя клиента) -- `saai-shell` не
  хранит отдельную копию списка. Это нарочно (один источник
  правды, тот же принцип, что ADR-030's "no cross-runtime
  dependency"), но если формат когда-то станет сложнее (даты
  последнего входа, IP и т.п.) -- потребуется отдельный JSON рядом.
- Выключение тумблера "Удалённый доступ" не трогает уже одобренные
  ключи -- см. `authorized_keys`, для этого есть отдельный экран
  "Доверенные клиенты" (ADR-084). Сам Dropbear теперь реально
  останавливается (ADR-085); "Забыть все" одним действием
  по-прежнему нет, только по одному через тот экран.
- HIA-01 (ADR-086): жизненный цикл пространства можно менять (тап
  по уже выбранной карточке), а связи (`saaios.space-relation`) --
  только читать. Создать связь между двумя пространствами сейчас
  нельзя нигде в UI вообще -- если понадобится, нужен отдельный
  экран/жест для этого.
- `saai-entity-store`'s `entity_type` не разрешает подчёркивания в
  dot-сегментах (только буквы/цифры/одиночный дефис,
  `is_slug()`) -- реально стоило времени на отладку один раз
  (ADR-086). Любой новый `entity_type` в будущем -- дефисы, не
  подчёркивания.
- HIA-02 (ADR-087): как и `saaios.space-relation`, у
  `saaios.space-signal` (связь Wi-Fi SSID <-> пространство) нет UI
  для создания -- сейчас без единой вручную созданной записи
  автопереключение по присутствию просто ничего не делает. Если
  когда-то понадобится реальным пользователям -- нужен отдельный
  экран (например "привязать эту сеть к пространству" прямо со
  списка Wi-Fi сетей, где SSID уже есть под рукой).
- HIA-02: Bluetooth как второй физический источник контекста не
  построен -- у него, в отличие от Wi-Fi/`wpa_supplicant`, нет
  фонового демона, `bt-scan` сам блокируется на ~8с, что не годится
  для тихого периодического опроса присутствия каждые несколько
  секунд. Понадобится либо держать `bt-scan` в режиме непрерывного
  discovery отдельным процессом, либо какой-то другой механизм.
- HIA-03: цвет пространства цикл через карточку "Цвет пространства"
  на "Я", а не прямо на карточке пространства на странице
  "Пространства" (та уже занята жестом жизненного цикла, HIA-01,
  плюс на ней нет места для второй кнопки). Из-за этого карточка
  "Цвет пространства" всегда действует на `selected_space_id` -- если
  открыть "Я" не с того пространства, сменится цвет не того, что
  ожидаешь. Не проверено, насколько это реально мешает.
- HIA-03: всего 6 цветов в фиксированном цикле (включая "Обычный"),
  без настоящего color picker'а -- ни один экран в этом проекте пока
  не даёт выбрать произвольный цвет/значение, только цикл по
  небольшому списку (яркость, громкость, контраст и т.п.). Если
  когда-то понадобится больше гибкости -- отдельная задача.
- HIA-07 (ADR-088): уведомление больше не скрывается прямым тапом
  по строке в "Входящие" -- теперь тап открывает Object View, "Скрыть"
  отдельное действие внутри него (один лишний тап ради единообразия
  с задачами). Не проверялось, насколько это раздражает в реальном
  ежедневном использовании -- если станет заметной проблемой, можно
  вернуть свайп/долгий тап как более быстрый путь для уведомлений
  отдельно.
- HIA-19 (ADR-089): `saai-shell` по-прежнему нигде не знает, доступен
  ли `saaios-runtime` (реальный ИИ, обычно живёт на подключённом по
  USB-NCM хосте, не на самом телефоне) ВООБЩЕ, до отправки
  намерения -- нет статус-индикатора вроде "AI недоступен" на экране
  ввода. (Отдельный пункт про исчезающие без следа провалившиеся
  задачи закрыт тем же ADR-089 -- `fail_task()`/`fail_confirmed_
  action()` теперь создают `saaios.notification`.)
- HIA-05: меню Orb различает "сопряжено ли вообще хоть одно
  Bluetooth-устройство" (`bluetooth_paired_count`, S20) -- не
  "подключено ли оно СЕЙЧАС". Настоящего понятия "живое состояние
  соединения" нигде в проекте нет. Если понадобится точнее -- нужен
  отдельный источник данных, не просто более частый опрос
  существующего.
- HIA-05: меню по-прежнему не читает открытый объект (Object View,
  HIA-07) -- только текущее пространство и Bluetooth. Документ-
  источник (раздел про Orb) предполагает и это тоже; не сделано,
  честный пробел.
- HIA-16: только форма (полая рамка при Attention) реализована из
  трёх альтернатив, что называл документ-источник -- haptic (нет
  доступа к вибромотору нигде в проекте) и подпись-по-запросу
  (текстовая метка состояния Orb) не сделаны. Приёмка требовала
  только одну, но если понадобится больше -- haptic начнётся с поиска
  реального устройства вибрации на Pixel 7 (ничего похожего в этом
  кодовой базе ещё не трогалось).
- HIA-20: экран "Диагностика" показывает только ТЕКУЩИЙ снимок --
  capability-гранты каждого приложения прямо сейчас, не историю
  решений во времени (в проекте вообще нет лога "кто когда что
  разрешил", только итоговое состояние в `apps_grants`). Если
  понадобится настоящий журнал policy-решений -- отдельная задача,
  не то же самое, что этот экран.
- HIA-20: строки экрана "Диагностика" не постраничные и не
  прокручиваемые (как и весь остальной UI -- в проекте нигде нет
  scroll/drag-распознавания). При большом числе установленных
  приложений список может не поместиться на экране -- не проверялось
  на реалистичном количестве приложений, только на 1-2.
- Голос (ADR-092, окончательный диагноз): микрофон физически не
  захватывает аудио под этой ОС -- корень найден точно, это не
  конфигурация. Запуск настоящего `aocd` (реальный Android-бинарник
  из `vendor.img`, запущен напрямую на устройстве через `linker64`+
  bionic-библиотеки, без chroot) показал в `dmesg`: прошивка AoC
  реально загружается и репортит версию ("14022723-polygon type
  release"), но `GSA: FW authentication failed: -16` -- secure
  element (тот же класс, что Titan M) отклоняет проверку подлинности
  подписанного образа. Это криптографическая граница доверия, не
  забытый шаг инициализации -- дальше означало бы обход
  аутентификации прошивки secure element'ом, вне объёма легитимной
  OS-разработки. HIA-06 остаётся закрыт по этой причине, не
  гипотетически.
- AOD/self-refresh (ADR-093, РЕШЕНО): первый шаг реализован --
  `present_status_bar()` теперь сравнивает `StatusBarSnapshot` и
  пропускает рендер+commit, когда контент не изменился, а
  `apply_appd_message()` больше не считает рутинный раз-в-секунду
  `appd.list()`-ответ за "изменение" по умолчанию. Живой тест: 209
  коммитов статус-бара за 188 минут простоя (≈1/мин, совпадает с
  минутной точностью часов) вместо ~11000, `self_refresh_active=1`
  подтверждён. Уточнение диагноза по пути: заблокированный экран уже
  держал self-refresh и без этого фикса (`affects_scene`-фильтр в
  `saai-displayd` и так исключает коммиты статус-бара, пока
  заблокировано) -- реальный пробел был именно в окне "разблокировано,
  но бездействие" (до авто-блокировки), плюс отдельный источник
  безусловных flip'ов нашёлся не в статус-баре, а в `appd.list()`'s
  polling главного toplevel-окна. Полный AOD UI по-прежнему отдельные
  спринты, но с известным низким-уровневым фундаментом, не гипотезой.
- `saaios-console` выпал из образа при поиске места под Dropbear
  (ADR-074) -- баннер в консоли всё ещё его упоминает. Либо вернуть
  в образ, либо (лучше, по аналогии с `saaios-runtime`) переместить
  на `/data/saaios/system/` и поправить баннер.
- Dropbear сейчас без `sftp-server`/legacy scp -- `scp` с клиента
  по-прежнему не работает. `file-recv`'s `GET` (S31, ADR-080) закрыл
  практическую нужду "скачать файл с устройства" отдельным простым
  протоколом; настоящий scp/sftp остаётся отдельным, не сделанным
  пунктом, если он когда-то понадобится сам по себе (например ради
  совместимости со сторонними GUI SFTP-клиентами).
- GPU/panthor и реальный kbase (ADR-024, дошло до очень точной
  локализации причины, не до включения GPU -- честно открытый
  вопрос): нашли публичный device-specific исходник
  (`kerneltoast/android_kernel_google_gs201`, не в официальном
  kernel/manifest) с реальным CAL (`cmucal_get_node`,
  `EXPORT_SYMBOL_GPL`) и открытым kbase-исходником для этого чипа
  (`borr_mali_kbase`/`mali_pixel`).

  Открытый бэкпорт panthor (мейнлайн-драйвер, полностью независимая от
  Google реализация CSF-протокола): написали `panthor_compat_
  get_gpu_clk()` (клок через `of_clk_get_from_provider()`), поправили
  IRQ-имена, скопировали реальный `mali_csffw-r54p3.bin` (формат
  прошивки общий с kbase, magic `0xc3f13a6e` совпал побайтово) --
  **GPU реально начал выполнять код** (page fault от собственного MMU
  при `MCU_CONTROL_AUTO` -- прямое доказательство исполнения).
  Регистровая трассировка (`trace_printk` в `gpu_write`/`gpu_read`,
  т.к. внешних средств трассировки на этой ОС нет) показала: AS0
  настраивается корректно, `MCU_CONTROL_AUTO` пишется, затем 5+ секунд
  полной тишины на шине регистров, затем `MCU_STATUS=fatal` без единого
  прерывания. Нашли и физически проверили привязку power domain
  `"top"`/`"cores"` (`dev_pm_domain_attach_by_name()` +
  `pm_runtime_get_sync()`, по образцу реального
  `pixel_gpu_power.c`) -- на чистой перезагрузке оба домена подтверждённо
  `on`/`active` в `pm_genpd_summary`, и MCU всё равно уходит в `fatal`
  ровно через 5.04с. Гипотеза отклонена экспериментально, несмотря на
  сильную теоретическую поддержку.

  Собрали НАСТОЯЩИЙ, открытый (GPL) `mali_kbase.ko`+`mali_pixel.ko` от
  Google для этого чипа из исходников (не проприетарные блобы под
  конкретную сборку) тем же тулчейном -- как диагностику, не как смену
  архитектуры. После ~десятка мелких реальных багов сборки (несогласованность
  `.c`/`.h` в этом конкретном срезе кода, недостающие `-I`, `MALI_
  KERNEL_TEST_API`, `__ANDROID_COMMON_KERNEL__`) оба модуля собрались и
  загрузились. Первая попытка тихо зависла в вечном `-EPROBE_DEFER`
  (`kbase_platform_device_probe()` требует non-NULL
  `google_retrieve_bcl_handle()` -- BCL-модуль не собираем, заглушка
  возвращала `NULL`; заменили на валидный ненулевой dummy-указатель,
  безопасно, т.к. нигде не разыменовывается). После этого реальный
  kbase дошёл ЗАМЕТНО дальше panthor и упал на чёткой причине:
  `pixel_gpu_power.c`'s `gpu_pm_init()` ищет домен `"cores"` ВТОРЫМ,
  отдельным, Samsung-специфичным способом --
  `exynos_pd_lookup_name("pd-embedded_g3d")` (не через стандартный Linux
  genpd, который уже работает). Модуль `exynos_pd.ko`,
  экспортирующий эту функцию, уже загружен штатной прошивкой Android
  (не нужно собирать) -- просто не хватало `-DCONFIG_EXYNOS_PMU_IF=1
  -DCONFIG_SOC_GS201=1` при компиляции kbase, чтобы вызов вообще
  генерировался. После этого вызов реально происходит -- и всё равно
  `NULL`.

  Написали read-only диагностический модуль
  (`gpu-probe-tools/pd-diag/`, вне git), который делает то же самое,
  что `exynos_pd_lookup_name()` по открытому исходнику (обход
  devicetree + `platform_get_drvdata()`), без хуков. Результат:
  **`pd->name` для `pd-embedded_g3d` побайтово совпадает** со строкой,
  которую ищет kbase -- домен зарегистрирован, доступен, привязан к
  драйверу, имя точное. По открытому исходнику `strcmp()` обязан был
  совпасть, но kbase всё равно рапортовал `NULL` -- на тот момент
  казалось, что настоящий `exynos_pd.ko` ведёт себя иначе, чем открытый
  исходник.

  **Этот вывод оказался неверным.** По совету пользователя поставили
  `kretprobe` (не дизассемблирование) прямо на реальный
  `exynos_pd_lookup_name()` -- пробник НЕ СРАБОТАЛ ВООБЩЕ, хотя тот же
  лог отказа появился. Значит функция не вызывалась вообще. Канарейки
  `pr_info()` внутри `#if IS_ENABLED(CONFIG_EXYNOS_PMU_IF)` показали,
  что ветка берётся, но сам вызов `exynos_pd_lookup_name()` заменялся
  компилятором на `static inline` заглушку "всегда NULL" из
  `exynos-pd.h` -- та гейтится ДРУГИМ конфигом, `CONFIG_EXYNOS_PD`, а
  не `CONFIG_EXYNOS_PMU_IF` (который гейтит только сам вызов в
  `pixel_gpu_power.c`). Добавили `-DCONFIG_EXYNOS_PD=1` -- kretprobe
  тут же сработал с реальным ненулевым возвратом. Тот же класс ошибки
  повторился ещё дважды (`CONFIG_CAL_IF`, `CONFIG_SOC_GOOGLE` -- оба
  нужны, чтобы реальные, уже загруженные на устройстве функции CAL
  (`cal_dfs_set_rate` и т.д. из `cmupmucal.ko`) вообще вызывались, а не
  заменялись заглушками/недостижимым кодом).

  **Итог: `mali 28000000.mali: Probed as mali0`.** Полный, чистый probe
  настоящего, официального, открытого kbase от Google на этом железе --
  ни одной ошибки инициализации, ни одного "Failed to boot MCU".
  `/dev/mali0` создан вручную (`mknod`, нет udev/mdev, ADR-011).
  `gpu_memory` показывает 0 байт -- похоже, эта версия kbase грузит
  CSF-прошивку (MCU) лениво, при первом реальном использовании GPU
  (создание контекста/queue group), а не сразу при probe, как panthor.
  Значит вопрос "реально ли исполняется прошивка MCU" под kbase ещё
  не проверен напрямую -- нужен отдельный минимальный userspace
  ioctl-инструмент (`KBASE_IOCTL_VERSION_CHECK` + создание контекста),
  не сделан в этой сессии. Урок методологии: `pd-diag`'s собственные
  находки были технически верны (домен существует, имя совпадает) --
  неверной была ИНТЕРПРЕТАЦИЯ ("раз лукап не сработал при верных
  условиях, дело в бинарнике"), пока `kretprobe` не показал, что лукап
  вообще не вызывался. Устройство стабильно весь эксперимент (десятки
  циклов insmod/reboot, 0 сбоев).

  **ФИНАЛ: MCU-прошивка реально загрузилась и запустилась.** Написали
  минимальный статически слинкованный userspace ioctl-инструмент
  (`gpu_probe_test.c`, кросс-`gcc -static`, независим от musl целевой
  ОС), открыли `/dev/mali0` (создан вручную через `mknod`, нет
  udev/mdev). Первая попытка провалилась содержательно: kbase лениво
  (при первом открытии, не при probe) попытался загрузить прошивку по
  ДРУГОМУ пути/имени, чем panthor (`mali_csffw-r51p0.bin` ->
  `mali_csffw.bin`, без подпути `arm/mali/arch10.8/`). Добавили
  симлинк на тот же самый, уже проверенный реальный блоб -- и:
  ```
  mali 28000000.mali: Firmware boot completed
  mali 28000000.mali: Firmware load successful
  ```
  Это именно та стена, в которую весь panthor-путь упирался всю
  сессию. Настоящий, официальный, полностью открытый (GPL) kbase от
  Google, собранный нашим тулчейном на нашем бэкпорте, физически
  поднял GPU Mali-G710 и запустил MCU-прошивку на этом устройстве под
  этой ОС -- ядерный уровень GPU bring-up решён. Рабочее дерево
  (ядро+тулчейн+`.ko`+device-specific исходники CAL/kbase/mali_pixel+
  все 5 файлов прошивки+диагностические модули+ioctl-тест) сохранено
  на R620 (`/home/mike/panthor-backport/`, вне git).

  **Дальше, тем же днём: userspace/Vulkan тоже заработал.** Настоящий
  Mali UMD (`vulkan.mali.so`/`libGLES_mali.so`) из официального
  factory-образа (`panther-cp2a.260705.006`, предоставлен
  пользователем после того, как реконструкция `vendor`-раздела
  напрямую на устройстве через liblp+`dm-linear` упёрлась в
  необъяснимое расхождение размеров ext4) запущен под bionic-кросс-
  компиляцией (`clang --target=aarch64-linux-android30 -nostdlib`, без
  NDK, линковка напрямую против извлечённого `apex_payload.img`).

  `libvulkan.so`'s собственный HAL discovery (`hw_get_module`/`HMI`)
  не работает без Android property-сервиса; обошли его, воспроизведя
  вручную ~10 строк реальной логики загрузчика AOSP
  (`dlopen`+`dlsym("HMI")`, найден транзитивно через `libGLES_mali.so`
  -- `vulkan.mali.so`'s собственный `.dynsym` символа `HMI` не
  содержит). `open("vk0")` сначала возвращал устройство с NULL
  `CreateInstance`/`GetInstanceProcAddr` -- написали собственный
  `ptrace`-трейсер (`strace` на этой ОС нет, ~160 строк glibc-статики,
  прозрачно трассирует bionic-процесс) и нашли, что не хватает
  bionic property area (`/dev/__properties__`). Вместо реконструкции
  бинарного формата `property_info` по памяти -- скачали настоящий
  исходник Google (`libpropertyinfoserializer`) и собрали его как
  хост-инструмент на x86_64, прогнали через реальные
  `plat_property_contexts`/`vendor_property_contexts` устройства.

  После этого properties реально заработали, но NULL callbacks
  остались -- трассировка показала, что Mali UMD вообще не читал
  `vendor.mali.*` в этом пути. Настоящая причина нашлась сверкой с
  реальным `hardware.h` из AOSP: `hw_device_t.reserved` на `__LP64__`
  -- это `uint64_t[12]`, а не `uint32_t[12]`, как было в нашей ручной
  реконструкции структуры; расхождение в 48 байт сдвигало чтение
  `CreateInstance`/`GetInstanceProcAddr` в середину настоящего
  (зануленного) паддинга. После исправления:
  ```
  vk-probe: CreateInstance result=0x0 (VK_SUCCESS)
  vk-probe: device[0] name=Mali-G710
  vk-probe: vkCreateDevice result=0x0 (VK_SUCCESS)
  ```
  Трассировка подтвердила: внутри `vkCreateDevice` UMD реально
  открывает `/dev/mali0` и выполняет десятки настоящих `ioctl()` к
  kbase, все -- успешно. Полная цепочка bionic-приложение -> настоящий
  Mali UMD -> `vkCreateInstance`/`vkEnumeratePhysicalDevices`
  (`Mali-G710`)/`vkCreateDevice` -> `/dev/mali0` -> `mali_kbase.ko` ->
  железо физически работает на этой ОС. Подробности, структуры и
  инструменты (`sysprobe`, `propsetup`, `mkpropinfo`) -- ADR-024.

  **Дальше, тем же днём: реальный submit команды дошёл до железа, но
  MCU-прошивка не квитирует CS-уровень.** `vkCmdFillBuffer`+`VkFence`
  (минимальная команда, без render pass) показала: `vkQueueSubmit`
  возвращает успех, `VkFence` никогда не сигнализируется. Первое
  зависание (`vkQueueWaitIdle`) списали было на свой самописный
  `_start` без bionic TLS-инициализации -- пересобрали с настоящими
  NDK crt-объектами (`crtbegin_dynamic.o`, NDK на сервере уже был) --
  зависание осталось идентичным, гипотеза отклонена.

  Встроили диагностику прямо в `mali_kbase.ko` (`csq_probe.c` в
  `Kbuild` самого драйвера, не отдельный модуль -- чтобы компилятор
  сам посчитал офсеты `struct kbase_queue`, без ручной реконструкции).
  `kretprobe` на `kbase_csf_process_queue_kick()` показал: `CS_INSERT`
  (курсор ring buffer, который пишет UMD) реально продвигается
  (`0x40`->`0x100`) -- команда не пустая. Но `CS_EXTRACT` (курсор,
  который должна продвигать firmware) не сдвигается ни на бит. Второй
  `kretprobe`, на сам doorbell (`kbase_csf_ring_cs_kernel_doorbell` +
  низкоуровневый `kbase_csf_ring_doorbell`), показал: хост корректно
  взводит `CSG_DB_REQ` (`0x7`->`0xf`->`0x1f`) и `CS_REQ` (`0x1501`),
  реальная MMIO-запись в доорбелл происходит (подтверждено), но
  `CSG_DB_ACK`/`CS_ACK` со стороны firmware остаются `0x0` всегда.
  Дизассемблирование собранного `.ko` подтвердило `dmb osh` на месте
  (не потерян компилятором); версия firmware-интерфейса (`0x01050000`)
  и топология (`group_num=8`) совпадают с реально загруженной
  прошивкой -- не version mismatch.

  Итог: вся хост-driver сторона проверена и чиста, группа (CSG)
  успешно стартует и уходит в `RUNNING`/`IDLE`, но CS-уровень
  (конкретный command stream внутри группы) MCU никогда не
  обрабатывает. Открытый вопрос на конец сессии -- дальше нужны либо
  исходники прошивки (недоступны), либо сравнение со stock Android.
  Инструменты (`vk_frame.c`, `vk_exec01.c`, `csq_probe.c`) -- ADR-024.
